# Agent guide

Svelte Native: the library and its native modules (`native/`) in `packages/svelte-native`, the QA app (the development lab), its QA-only Expo modules and the QA harness in `apps/qa`; the showcase app in `apps/example` (one readable route per feature). The layout and the install are in `README.md`; the library's own docs are `packages/svelte-native/README.md` and `REFERENCE.md`, the Android engine's spec is `packages/svelte-native/native/svelte-core/SPEC.md`.

## Checks

- `pnpm install --frozen-lockfile`, then `pnpm lint`, `pnpm typecheck`, `pnpm test` from the root.
- Package only: `cd packages/svelte-native && pnpm test` (`bun test --timeout 60000`, then the HTML differential test in a Bun process of its own: `bun test ./tests/html-differential.own-process.ts`, the file says why; a bare `bun test` leaves it out), `pnpm lint`, `pnpm typecheck`.
- Async mode (`router.prepare` needs it; `tests/async-mode-setup.ts`, preloaded by `packages/svelte-native/bunfig.toml`): `SVELTE_NATIVE_TEST_ASYNC=1|microtask|frames bun test` (any other value, `0` included, is the default run) compiles every file with Svelte's async mode through a mock of the compiler and stands a frame in for `requestAnimationFrame`. `1`: a 16 ms timer; four files hang for ever (`app-tree`, `navigation`, `responder` and `router-link`: Bun's fake timers stop every timer, so async mode's `tick()` never resolves), so run a file at a time under `timeout`; `list.test.ts` fails seven tests (the four of `frames`, and the three of `microtask`); `svelte-async-mode.test.ts` fails "the Metro transformer compiles components and modules without Svelte's async mode, unless the app asks for it" (by design: it compiles without the option). `microtask`: the frame is a microtask, nothing hangs; fails that one test and `list.test.ts`'s "a list that fills mounts the rows that show first and the overscan a few frames later", "a list that waits for its overscan lets go of the wait when it empties" and "the overscan wait counts from the fill: a list that grows during it does not start it again, one that empties and refills does" (they count the frames they stub, and `tick()` asks for one). `frames`: the frame alone, async mode off; fails `list.test.ts`'s "a virtual list mounts a window of rows, moves it on scroll and keeps keyed rows", "horizontal lists window on x and scroll by x", "initialScrollIndex mounts and scrolls to that row on first layout" and "a list that says its height mounts the rows that fill it first, the overscan after its layout" (a `requestAnimationFrame` that exists takes the list's other path). Tests whose control needs async mode off are skipped in `1` and `microtask`. The HTML differential test is outside a bare `bun test`: run `bun test ./tests/html-differential.own-process.ts` with the same variable.
- After changing Node-side code (what `scripts/build-node.ts` bundles: `cli.ts`, `build.ts`, `compile-options.ts`, `metro.ts`, `transformer.ts`, `expo.ts`, `vite.ts`, `lower.ts`, `doctor/`, `init-app.ts`, `remote/{transform,plugin,host}.ts`, `svelte-build.ts`, `package-root.ts`, `route-tree.ts`, `variant.ts`): `pnpm --dir packages/svelte-native build` and commit `packages/svelte-native/dist/node/`. Node cannot load the package's TypeScript from an app's `node_modules`, so those entries ship as JavaScript; `tests/package/dist.test.ts` fails on a stale `dist/node/`.
- After changing a type an entry exports (or anything its declaration reaches): the same build also writes `packages/svelte-native/dist/types/`, the declarations an app's type checker reads (the `types` condition of each entry); commit it. `tests/types.test.ts` fails on a stale one and `tests/type-budget.test.ts` on a declaration that makes an app's checker load more (REFERENCE "Type checking an app"). The repository's own tsconfigs set `customConditions: ["svelte-native-source"]` so they check against `src/` and need no rebuild.
- Harness only: `cd apps/qa && bun test --timeout 120000 qa`, `pnpm native-qa:typecheck`, `pnpm lint`.
- CI (`.github/workflows/`, README "CI"): `ci.yml` runs the checks above on every push to main and every pull request with `CI=1` (the Kotlin and C++ host checks fail instead of skipping when kotlinc, a JDK or a jar is missing); `consumer.yml` is `scripts/consumer-check.sh` (its `starter` mode follows the guide: `sv create`, `pnpm add`, `svelte-native init`; after editing the script run `bash -n` and `shellcheck -x -S warning scripts/*.sh`); `native-qa.yml` is the emulator lane and stays off until the owner registers the runner and sets `QA_EMULATOR_RUNNER` (`apps/qa/qa/ci/RUNBOOK.md`); `release.yml` publishes a tag `v<version>` (README "Release"). After editing a workflow run `actionlint` (its config is `.github/actionlint.yaml`). Dispatching a workflow, setting a secret or variable, registering a runner and pushing a tag are the owner's, not an agent's.
- Heavy runs (full test suites, builds) on a shared machine: cap them, for example `systemd-run --user --scope -p CPUQuota=600% nice -n 19 ionice -c3 <command>`.

## QA harness

`node qa/native-qa.ts <command>` from `apps/qa` (commands and flags: `apps/qa/qa/README.md`; the pass/fail numbers are in `qa/gates.json`). Everything that needs a device takes `--device <serial>`; nothing defaults to a phone or a Mac.

## Devices

- The Samsung phone is shared. Install with `adb install -r` only; never clear an app's data, uninstall other apps or change settings. Touch only the QA apps (`io.rasheed.svelteqa*`).
- The harness holds a lock per emulator and per EAS channel (README "Devices and locks"); do not bypass it.
- Do not start device runs, builds or pushes unless asked.

## Rules

- Do not rewrite history or add a remote without the owner's OK.
- Keep the library generic: no product code, secrets or proprietary SDKs. The smoke app has no Samsung Pay module (`expo-samsung-pay` and its SDK jar are not part of this repository and are not added); `apps/qa/libs/` stays ignored so a proprietary jar put there is never committed.
- The library's native code is one module, `packages/svelte-native/native/svelte-core`: one Gradle project (`:svelte-core`, the engine's Kotlin and C++, the update store, the blur view, fetch and Blob, the clipboard, each in its own Kotlin package) and one pod (`SvelteCore`, a folder per area under `ios/`, the Objective-C++ screens among them), linked by the package's one `expo-module.config.json`. New native code goes into that module (a new Expo module class is an entry in its `modules` lists), not into a module or config of its own: autolinking reads only the package root's. `apps/qa/modules/` holds QA-only modules (they are excluded from the product).
- The QA app and the showcase consume the library through its workspace dependency, as an app outside the repository does: no relative path into `packages/svelte-native` in its runtime or build code (tests may). What a dependent receives is what `files` in the package's `package.json` packs (`pnpm pack --dry-run`); `tests/package/packaging.test.ts` pins it.
- Components are compiled in runes mode unless a file opts out (`<svelte:options runes={false} />`), outside `node_modules` and in the library's own sources (`src/compile-options.ts`, README "Coming from Svelte on the web"). A test that compiles a `.svelte` fixture takes its options from `componentOptions`, as the transformer does, and does not write its own.
- `svelte` is a peer dependency naming the custom-renderer build; the repository installs `vendor/svelte-5.56.7-216f258.tgz` as a development dependency. Do not put a `file:`, `workspace:` or `catalog:` specifier in the package's `dependencies` (a dependent cannot resolve it).
