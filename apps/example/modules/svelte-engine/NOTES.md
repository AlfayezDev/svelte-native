3. `FJ/FabricUIManagerBinding.cpp:721-748`:

4. `FJ/FabricMountingManager.cpp:1062-1080` `maybePreallocateShadowNode`: returns unless `shadowNode.getTraits().check(ShadowNodeTraits::Trait::FormsView)` (line 1064); returns when the calling thread is the main thread (`static thread_local bool onMainThread = isOnMainThread();` line 1068, comment "View preallocation is not beneficial when rendering on the main thread"); otherwise pushes a `ShadowView` copy onto `preallocatedViewsQueue_` (mutex `preallocateMutex_`). 5. ### Flags and defaults

| Flag | Declared | Default C++ | Default Kotlin | Effect |
|---|---|---|---|---|
| `disableViewPreallocationAndroid` | `ReactCommon/react/featureflags/ReactNativeFeatureFlags.h:90` | `ReactNativeFeatureFlagsDefaults.h:66` false | `RJ/internal/featureflags/ReactNativeFeatureFlagsDefaults.kt:44` false | Both the C++ early return (Binding.cpp:725) and the Java drain (FabricUIManager.java:1613) honour it. This is THE switch. |
| `disableImageViewPreallocationAndroid` | `ReactNativeFeatureFlags.h:70` | `Defaults.h:50` false | `Defaults.kt:36` false | Only skips `Image`. Not needed when the one above is true. |
| `enableDifferentiatorMutationVectorPreallocation` | `ReactNativeFeatureFlags.h:130` | false | false | Unrelated: it reserves capacity in the Differentiator's mutation vector. |

C++ reads the flags through `JReactNativeFeatureFlagsCxxInterop.cpp:96-98`, which calls the Java provider's `disableViewPreallocationAndroid()`, and caches the value in the C++ accessor. So one `dangerouslyForceOverride` before the first read switches both sides.

### Expo plugin

`packages/svelte-native/src/expo.ts:34-51` (`applyFeatureFlags`) emits `override fun <name>(): Boolean = true` inside `object : ReactNativeNewArchitectureFeatureFlagsDefaults() {...}` after `loadReactNative(this)`. `disableViewPreallocationAndroid` is a plain Boolean method of `ReactNativeFeatureFlagsDefaults` (open, `Defaults.kt:44`), so the plugin can switch it with zero generator changes: add the name `"disableViewPreallocationAndroid"` to the array passed to `applyFeatureFlags` (today only `recyclingOverrides(...)` feeds it, `expo.ts:70`). It needs a new option (or a spike-specific default) because `overrides.length === 0` makes the plugin strip the block. All current overrides are `= true`; a Double flag such as `preparedTextCacheSize` would need the generator extended.

### Alternative (not recommended)

Registering shadow nodes under a component name the Java registry does not know does NOT work: with preallocation on, `SurfaceMountingManager.createViewUnsafe` (line 610) does `viewManagerRegistry?.get(componentName) as ViewManager`, and `ViewManagerRegistry.kt:72-78` throws `IllegalViewOperationException("Can't find ViewManager ...")`. On that path the exception is thrown inside a `PreAllocateViewMountItem` executed by `executeOrEnqueue(preMountItem)` (`MountItemDispatcher.kt`, pre-mount loop, no try/catch), so it would most likely crash the UI thread (the pre-mount loop in `MountItemDispatcher.kt` has no try/catch of its own). Do not rely on this.

Note on what preallocation costs even when "off for our surface": since the flag is global, the entire app loses preallocation (acceptable for the spike; the whole point is that we do not use Java views for this surface).

## 2. Mounting override delegate

### Slot semantics: it is a LIST, not a single slot (SPEC.md is wrong here)

`RC/mounting/MountingCoordinator.h:133` `mutable std::vector<std::weak_ptr<const MountingOverrideDelegate>> mountingOverrideDelegates_;` and `MountingCoordinator.cpp:210-215`:
```cpp
void MountingCoordinator::setMountingOverrideDelegate(std::weak_ptr<const MountingOverrideDelegate> delegate) const {
  std::scoped_lock lock(mutex_);
  mountingOverrideDelegates_.insert(mountingOverrideDelegates_.end(), std::move(delegate));
}
```
- Append only, no dedupe, no removal (dead weak_ptrs stay but are skipped: `delegate.lock()` null -> `shouldOverridePullTransaction` false).
- It stores a `weak_ptr`: we must keep a `shared_ptr` alive (hold it in `SvelteEngineNative`).
- `pullTransaction` (`MountingCoordinator.cpp:71-190`) chains them in insertion order (loop at line 100): each delegate whose `shouldOverridePullTransaction()` is true receives `transaction->getMutations()` of the previous result (line 117-124: `mutations = transaction->getMutations(); ... transaction = mountingOverrideDelegate->pullTransaction(surfaceId_, number_, telemetry, std::move(mutations));`). If there is no diff pending (`lastRevision_` empty) the delegate is still called with an empty list and `number_` is incremented (lines 112-122). The last delegate's return value is what the platform mounts.
- All of it runs under `std::scoped_lock lock(mutex_)` (`mutex_` is a plain `std::mutex`, `MountingCoordinator.h:127`). Do NOT call back into the coordinator (`getBaseRevision`, `hasPendingTransactions`, `pullTransaction`) or `Scheduler::reportMount` (which calls `getBaseRevision`, `UIManager.cpp:683-705`) from inside `pullTransaction`: instant self-deadlock. Copy what you need and do the work after returning (or post it).

### When and on which thread `pullTransaction` runs

1. A commit finishes in `ShadowTree::commit` -> `ShadowTree::mount` (`RC/mounting/ShadowTree.cpp:476-481`): `mountingCoordinator_->push(revision)` then `delegate_.shadowTreeDidFinishTransaction(coordinator, mountSynchronously)` -> `UIManager.cpp:658-667` -> `Scheduler::uiManagerDidFinishTransaction` (`Scheduler.cpp:303-337`).
2. `delegate_->schedulerDidFinishTransaction(coordinator)` -> `FJ/FabricUIManagerBinding.cpp:622-652`. With `enableAccumulatedUpdatesInRawPropsAndroid` false (default, `Defaults.h:74`, `Defaults.kt:48`) it calls `mountingCoordinator->pullTransaction(/*willPerformAsynchronously*/ true)` right there (line 631), on the committing thread (JS thread for React/Svelte commits; the UI thread for synchronous/state commits; Reanimated commits come from the UI runtime thread). The resulting transaction is merged into `pendingTransactions_` (`MountingTransaction::mergeWith`, `RC/mounting/MountingTransaction.cpp:44-55`, appends mutation vectors).
3. Then `runtimeScheduler_->scheduleRenderingUpdate(surfaceId, ...)` (or inline when `mountSynchronously`) runs `schedulerShouldRenderTransactions` (`Binding.cpp:654-702`), which only drains `pendingTransactions_` and calls `FabricMountingManager::executeMount` (line 699). With the flag on, the pull happens in step 3 instead (line 675).
So our delegate can run concurrently on several threads (different surfaces or Reanimated commits), but never concurrently for the same surface (coordinator mutex). Make it thread-safe; keep per-surface state under its own lock.

### Empty mutation list on the Java side

`FabricMountingManager::executeMount` (`FJ/FabricMountingManager.cpp:570-...`): with zero mutations all vectors are empty, `computeBufferSizes` gives 0, and at lines 835-851:
```cpp
if (batchMountItemIntsSize == 0) { ... scheduleMountItem(javaUIManager_, nullptr, telemetry...); return; }
```
So NO `IntBufferBatchMountItem` is created (the `createIntBufferBatchContainer` call at 988 is after the early return). Java `FabricUIManager.scheduleMountItem` (`RJ/fabric/FabricUIManager.java:909-960`): `isBatchMountItem = mountItem instanceof BatchMountItem` is false for null, `shouldSchedule = mountItem != null` is false, so nothing is queued, `didScheduleMountItems` listeners are still notified (line 935), no `FABRIC_*` markers are logged for non-batch.
Consequences:
- `SurfaceMountingManager`, `ReactSurfaceView`: the surface stays "started" with only its root `ViewState` (`FabricMountingManager::onSurfaceStart` registers `{surfaceId}` as allocated, `FabricMountingManager.cpp:44-48`). `ReactSurfaceView.onMeasure` still feeds Yoga constraints through `updateLayoutSpecs` -> `binding.setConstraints`; keep that view attached, measured and not `GONE`.
- `onLayout`: emitted by C++ in `ShadowTree::emitLayoutEvents` (`ShadowTree.cpp:455`, 564-580), only for nodes with `viewProps->onLayout`, at commit time, independent of mounting. Works as is.
- Mounted flag/event emitters: `updateMountedFlag(...)` (`ShadowTree.cpp:427`) calls `ShadowNode::setMounted(true)` (`RC/core/ShadowNode.cpp:322-330`), which enables `EventEmitter`/`EventTarget` (`RC/core/EventEmitter.cpp:209-228`). This is done at commit, not by Java. Emitters work without Java ever mounting.
- `UIManagerMountHook::shadowTreeDidMount` (and everything built on `Scheduler::reportMount`) is triggered ONLY from Java: `FabricUIManager.java:1502` `binding.reportMount(surfaceId)` after real mount items ran. With empty batches it never fires. That also leaves `MountingCoordinator::hasPendingTransactionsOverride_` true (reset by `didPerformAsyncTransactions`, called from `FabricUIManagerBinding::reportMount`, `Binding.cpp:76-113`); no non-test code reads `hasPendingTransactions()`, so harmless. If something needs mount hooks (Reanimated's `ReanimatedMountHook`, JS `IntersectionObserver`/performance mount marks), call `scheduler->reportMount(surfaceId)` ourselves after our UI-thread apply, outside the coordinator lock.
- `SurfaceMountingManager.updateLayout` on the root: never called (root `Update` mutation is dropped with the rest).

### Does React Native install its own delegate?

Yes, conditionally: `FJ/FabricUIManagerBinding.cpp:151`, `211`, `385`: `if (ReactNativeFeatureFlags::enableLayoutAnimationsOnAndroid()) { surfaceHandler.getMountingCoordinator()->setMountingOverrideDelegate(animationDriver_); }` (`animationDriver_` = `LayoutAnimationDriver`, created unconditionally at line 591, passed to the `Scheduler` as animation delegate at 594). Default `false` in 0.86.3: `ReactNativeFeatureFlagsDefaults.h:166-168`, `RJ/internal/featureflags/ReactNativeFeatureFlagsDefaults.kt:94`. Keep it false (it is not in `ReactNativeNewArchitectureFeatureFlagsDefaults`). If true, it is registered at surface start, before ours, and would rewrite mutations for RN `LayoutAnimation`.

### Reanimated 4.5.1

`node_modules/react-native-reanimated/Common/cpp/reanimated/Fabric/ReanimatedCommitHook.cpp:24-50` (the only `setMountingOverrideDelegate` call under `Common/` and `android/src/main/cpp`, line 46):
- It is installed lazily per surface, from inside `shadowTreeWillCommit` (`maybeInitializeLayoutAnimations(surfaceId)` at line 58): on the first commit it sees a surface id greater than `currentMaxSurfaceId_`, it enumerates the registry and adds `layoutAnimationsProxy_` to every unseen surface.
- The hook itself exists only once `ReanimatedModuleProxy` has been created (`ReanimatedModuleProxy.cpp:1210` `commitHook_ = std::make_shared<ReanimatedCommitHook>(...)`, `initializeLayoutAnimationsProxy()` at 1191/1213), i.e. when the Reanimated native module/worklets runtime is initialised (importing `react-native-reanimated` JS).
- Its delegate returns `shouldOverridePullTransaction() == true` ALWAYS (`LayoutAnimationsProxy_Legacy.cpp:607`, `LayoutAnimationsProxy_Experimental.cpp:110`: "we need to listen to every possible mutation"), whether or not any layout animation is configured. It forwards/modifies mutations and may return a different list.
- It does not read `enableLayoutAnimationsOnAndroid`; it uses its own `setAnimationDelegate` for the legacy proxy (`ReanimatedModuleProxy.cpp:1253`).

### Conflict and ordering that makes ours win

Both chain in registration order and the LAST delegate's output is what React Native Java mounts. Ours must return an empty list and be the last effective stage, or any later stage must be fed an empty list so it cannot re-introduce mutations.
- Install-time registration (our `install()` runs before the first Svelte commit; the RN root already exists): we go in BEFORE Reanimated's (Reanimated registers at its first commit seen for a new surface id, unless a React-rendered root already committed before). Order = [ours, Reanimated]. Reanimated then receives our empty list (its light tree is empty, layout animations are a no-op, nothing reaches Java). Safe for the spike; Reanimated never sees the real mutations.
- If Reanimated registered earlier (it saw the surface first): order = [Reanimated, ours]. We receive the full, possibly rewritten list and return empty. Better for Phase 3 (animations see everything).
- Either order yields "Java mounts nothing". The integrator should log the registration order (`mountingOverrideDelegates_` is private; log from each `pullTransaction` entry with surface id and mutation count) and not assume. If we ever need to force "last", register lazily from our own `UIManagerCommitHook::shadowTreeWillCommit` created after Reanimated's hook (hooks run in registration order, `UIManager.cpp` commitHooks_ vector), with the same enumerate-based pattern.
- Never `setMountingOverrideDelegate` twice with the same object per surface: there is no dedupe, the delegate would run twice per pull (and the second would receive our empty list).

## 3. Shadow tree registry and surfaces

- Reach the UIManager: `JFabricUIManager::getBinding()` (public, `react/fabric/JFabricUIManager.h:20`, exported `T facebook::react::JFabricUIManager::getBinding()` in libreactnative.so) -> `FabricUIManagerBinding::getScheduler()` (public, `FabricUIManagerBinding.h:48`, returns `std::shared_ptr<Scheduler>`, exported) -> `Scheduler::getUIManager()` (`RC/scheduler/Scheduler.h:111`) -> `UIManager::getShadowTreeRegistry()` (`UIManager.h:211`). This is exactly what Reanimated does: `node_modules/react-native-reanimated/android/src/main/cpp/reanimated/android/NativeProxy.cpp:47`.
- `ShadowTreeRegistry` (`RC/mounting/ShadowTreeRegistry.h`): `void enumerate(const std::function<void(const ShadowTree&, bool& stop)>&) const` and `bool visit(SurfaceId, const std::function<void(const ShadowTree&)>&) const`; both callable from any thread, take a shared lock on the registry mutex (`add`/`remove` take the unique lock). There is NO listener API on the registry.
- From a `const ShadowTree&`: `getSurfaceId()`, `getMountingCoordinator()` (-> `std::shared_ptr<const MountingCoordinator>`), `getCurrentRevision()` (`RC/mounting/ShadowTree.h`, header present in prefab).
- Surface id / root tag: `RC/mounting/ShadowTree.cpp:238` creates the root with `{.tag = surfaceId, .surfaceId = surfaceId, ...}`, so root tag == surfaceId. `Differentiator.cpp:1687-1692` runs the child diff with `parentTag = oldRootShadowNode.getTag()` (= surfaceId), so mutations of the root's direct (non-flattened) children carry `parentTag == surfaceId`. `FabricMountingManager::onSurfaceStart` registers `{surfaceId}` as the root's allocated tag (line 46). Also, the differ emits an Update mutation for the root itself when its `ShadowView` changed (`Differentiator.cpp:1659-1663`: `UpdateMutation(oldRootShadowView, newRootShadowView, {})`): its `parentTag` is 0 and `newChildShadowView.tag == surfaceId`. Our encoder must skip (or treat as root layout) Update mutations whose tag equals the surface id, never create a view for them.
- Flattening: only `FormsView` nodes appear in mutations (see `RC/components/view/ViewShadowNode.cpp:38-80`: backgroundColor, border, non-collapsable, events, opacity, transform, overflow != visible, pointerEvents none/box-only, testId, `accessible`, `nativeId`, zIndex with non-static position, display none, ... make a node form a view). Flattened parents are skipped and `ShadowView.layoutMetrics.frame` of children already includes the flattened offset (`Differentiator` passes `layoutOffset`). Android also marks "virtual" nodes (`RCTRawText`, `RCTVirtualText`) with `layoutMetrics == EmptyLayoutMetrics`: `ShadowViewMutation::mutatedViewIsVirtual()` (`RC/mounting/ShadowViewMutation.cpp:73-85`, Android only: both old and new layout metrics equal `EmptyLayoutMetrics`). `FabricMountingManager.cpp:623` skips Remove/Insert/Update for virtual views, but still emits Create/Delete and the event emitter update for them. Mirror this: no view for virtual nodes, but keep their emitters in the tag registry.
- How React Native itself encodes the same list (reference for our encoder, `FJ/FabricMountingManager.cpp:616-800`): Create (skipped if already allocated); Insert carries full state: UpdateProps (only if the view was not already created/allocated by preallocation), UpdateState, UpdatePadding (if `contentInsets != ZERO`), UpdateLayout, UpdateOverflowInset, then UpdateEventEmitter ALWAYS; Update compares old/new for props/state/padding/layout/overflowInset/eventEmitter separately; Delete decrements. Our delegate should do the same diffing (props pointer equality `old.props != new.props`, `state`, `layoutMetrics`, `eventEmitter`) so Update mutations only re-send what changed. Layout in Insert/Update uses `parentTag` of the mutation.
- Catching surfaces started after install: there is no registry hook. Options: (a) `UIManager::registerCommitHook(UIManagerCommitHook&)` (`UIManager.h:101`, exported): `shadowTreeWillCommit(const ShadowTree&, oldRoot, newRoot, commitOptions)` fires before every commit (`ShadowTree.cpp:393`), including the first commit of a surface, so enumerate/visit-and-register there (Reanimated's pattern, `ReanimatedCommitHook.cpp:30-50`). It runs inside the commit; the hook is called while the registry shared lock may already be held by `visit`, so keep it to a short `enumerate` guarded by a "known surface ids" set, as Reanimated does. The coordinator is reachable directly from the `const ShadowTree&` argument (`shadowTree.getMountingCoordinator()`), so enumerate is not even required. Registering inside the first commit is early enough: `pullTransaction` for that commit runs after the hook returns. (b) `UIManagerMountHook::shadowTreeDidMount` (`RC/uimanager/UIManagerMountHook.h`): fires only after Java reports a mount (see section 2), so it is useless for us. (c) Kotlin side: `FabricUIManager`'s own `startSurface` (Java `FabricUIManager.java:338-390`) is where `ReactHost` starts surfaces; no listener, but a `UIManagerListener`/`ReactSurface` callback could call our native `install`.
- Surface stop: `UIManager::stopSurface` (`UIManager.cpp:274-289`) removes the tree via `getShadowTreeRegistry().remove(surfaceId)`; the coordinator dies with it, so our weak_ptr entry disappears too. There is no stop callback for us (`UIManagerMountHook::shadowTreeDidUnmount` is also fed through Java `reportMount`), so drop our per-surface state when `visit(surfaceId, ...)` returns false or when the Kotlin side learns the surface stopped.

## 4. Text

### What `ParagraphState` carries on Android

`RC/components/text/platform/android/react/renderer/components/text/ParagraphState.h:35-88`:

(`RC/textlayoutmanager/TextLayoutManagerExtended.h:117-121`; `PreparedTextLayout = SafeReleaseJniRef<jni::global_ref<JPreparedLayout>>`, `RC/textlayoutmanager/platform/android/.../TextLayoutManager.h:32`; `JPreparedLayout` = `Lcom/facebook/react/views/text/PreparedLayout;`.) The Java `PreparedLayout` (`RJ/views/text/PreparedLayout.kt:15-23`, `internal class`, `@DoNotStrip`) holds `layout: android.text.Layout`, `maximumNumberOfLines`, `verticalOffset: Float` (textAlignVertical offset in px), `reactTags: IntArray`, `textBreakStrategy`, `justificationMode`.

### Prepared text layout flag

- `enablePreparedTextLayout`: `ReactNativeFeatureFlags.h:255` ("Enables caching text layout artifacts for later reuse"), default FALSE (`Defaults.h:198-200`, `Defaults.kt:110`). Related: `preparedTextCacheSize` (`ReactNativeFeatureFlags.h` ~378, default 200.0, `Defaults.kt:160`).
- With it false: `measuredLayout.preparedTextLayout` is a default-constructed (null) `SafeReleaseJniRef` and the state only has `attributedString` + `paragraphAttributes`. Java measures through the MapBuffer path (`measureText`) and RN's `ReactTextView` builds its own layout in the view.
- With it true (`RC/components/text/ParagraphShadowNode.cpp:241-262`): during Yoga measure `TextLayoutManagerExtended::prepareLayout` + `measurePreparedLayout` run (JNI `FabricUIManager.prepareTextLayout` / `measurePreparedLayout`, `TextLayoutManager.cpp:294-373`, 375-434), the results are kept in `measuredLayouts_`, and `ParagraphShadowNode::layout` (lines 300-343) re-selects the one matching the final frame (`findUsableLayout()`) or re-measures, then `updateStateIfNeeded<ParagraphState>(content, *measuredLayout)`. So the final `ParagraphState` of a mounted paragraph carries the exact Java `PreparedLayout` that was measured: RN's Android text view then draws exactly this (`PreparedLayoutTextView`, `onDraw` translates by `paddingLeft`, `paddingTop + preparedLayout.verticalOffset` and calls `layout.draw`, `RJ/views/text/PreparedLayoutTextView.kt:100-136`; `MainReactPackage.kt:155` swaps the text manager when the flag is on).
- Getting the object from C++: from a `ShadowView` (mutation) do `auto state = std::static_pointer_cast<const ConcreteState<ParagraphState>>(shadowView.state)` (needs `<react/renderer/core/ConcreteState.h>` and the Android `ParagraphState.h`; `shadowView.componentName == "Paragraph"`), then `state->getData().measuredLayout.preparedTextLayout` is the `SafeReleaseJniRef<global_ref<JPreparedLayout>>`; `.get()` (see `ParagraphState::getJNIReference`, `ParagraphState.cpp:27-29`: `jni::make_local(measuredLayout.preparedTextLayout.get())`) is a `jobject`; test `if (ref)` first. Pass a local/global ref to Kotlin through the `objects` array. The global ref lives as long as the state (and the `preparedTextCache_`); Kotlin must not hold it past the shadow view's lifetime without its own reference (a JNI `NewGlobalRef` from the jobject is automatic when stored in a Kotlin field).
- Kotlin access: `PreparedLayout` and its members are `internal` to React Native's Kotlin module, so our module cannot reference it from Kotlin source. Either use a tiny Java class in our module (Java sees it as public: `com.facebook.react.views.text.PreparedLayout#getLayout()`, `getVerticalOffset()`) or reflection once. `getLayout()` returns the `android.text.Layout`.
- Caveat: `needsNewReactTags` path (`TextLayoutManager.cpp:340-368`) clones the layout with `reusePreparedLayoutWithNewReactTags` when the same text is rendered by different fragments.
- Recommendation: add `enablePreparedTextLayout` to the spike flag set. It removes the need to rebuild spans in Kotlin and guarantees draw == measure. Keep the fragments fallback (`record 21`) for when it is false. Cost: Java layout creation moves into the Yoga measure (it already happens there, via `measureText`, so no extra cost; the layout object is just kept instead of discarded).

## 5. Touch

### Java behaviour to mirror (`RJ/uimanager/JSTouchDispatcher.kt`)

- `handleTouchEvent` (lines 90-221) is driven by the root `ReactSurfaceView`. ACTION_DOWN (line 98-124): `gestureStartTime = ev.eventTime`, `targetTag = findTargetTagAndSetCoordinates(ev)` (line 236: `TouchTargetHelper.findTargetTagAndCoordinatesForTouch(ev.x, ev.y, viewGroup, targetCoordinates, null)`), then dispatches `TouchEvent.obtain(surfaceId, targetTag, START, ...)`. The target tag is fixed at DOWN and used for ALL later events of the gesture (MOVE/UP/CANCEL use `targetTag`). For MOVE/UP the hit test is re-run only to refresh `targetCoordinates`: its returned tag is discarded, and the coordinates are relative to whatever view is under the finger now, so `locationX/Y` can be relative to a different view than `target` once the finger leaves it. A simpler engine may keep the local offset relative to the DOWN target.
- MOVE (line 180): `MotionEvent.ACTION_MOVE`; POINTER_DOWN -> START with the same target; POINTER_UP -> END; CANCEL -> `dispatchCancelEvent` if `touchEventCoalescingKeyHelper.hasCoalescingKey(downTime)`, `targetTag = -1`.
- `TouchTargetHelper` (`RJ/uimanager/TouchTargetHelper.kt`): `findTargetTagAndCoordinatesForTouch` (75-97) = DFS over native children in REVERSE order (`findTouchTargetView`, children from `childCount-1` down to 0), coordinates mapped child-wise with scroll offset and inverse transform (`getChildPoint` 292-320: `x + parent.scrollX - child.left`, then `child.matrix.invert` for non-identity transforms; non-invertible children are skipped); a point must satisfy `0 <= x < width && 0 <= y < height` (plus `hitSlop` for `ReactHitSlopView`); `clipChildren`/`overflow hidden|scroll` parents reject points outside their bounds (unless inside the overflow inset); `pointerEvents` in `findTouchTargetViewWithPointerEvents` (322+): `NONE` -> view and subtree excluded; `BOX_ONLY` -> only the view itself; `BOX_NONE` -> only descendants; `AUTO` -> children first (reverse order), then self; disabled views downgrade AUTO->BOX_NONE, BOX_ONLY->NONE. `ReactCompoundView` (text spans) and `ReactCompoundViewGroup.interceptsTouchEvent` can return a virtual child tag; irrelevant for us (our text has no touchable spans in the spike).

## 9. Commands and measure

- `nativeFabricUIManager.dispatchCommand(node, name, args)` -> `UIManagerBinding.cpp:542` -> `UIManager::dispatchCommand` -> `Scheduler::uiManagerDidDispatchCommand` (`Scheduler.cpp:345-368`, scheduled on the runtime scheduler's rendering queue) -> `FabricUIManagerBinding::schedulerDidDispatchCommand` (`FJ/FabricUIManagerBinding.cpp:753-762`) -> `FabricMountingManager::dispatchCommand` (`FJ/FabricMountingManager.cpp:1144-1162`) -> Java `FabricUIManager.dispatchCommand(surfaceId, reactTag, String commandId, ReadableArray)` (`FabricUIManager.java:1295-1311`) -> `MountItemDispatcher.addViewCommandMountItem` (UI thread queue) -> `DispatchStringCommandMountItem.execute` -> `SurfaceMountingManager.receiveCommand(reactTag, commandId, args)` (`SurfaceMountingManager.kt:740-767`): no `ViewState` for the tag -> `throw RetryableMountingLayerException("Unable to find viewState for tag ...")`. That exception is caught in `dispatchViewCommand` (`MountItemDispatcher.kt:155-186`): `getRetries() == 0` -> retried ONCE in the next batch, then `ReactSoftExceptionLogger.logSoftException(..., ReactNoCrashSoftException("Caught exception executing ViewCommand"))` (soft, no crash; in debug builds soft exceptions may log loudly). Confirmed: a soft exception, no crash. Commands to our views (scrollTo, focus, blur) therefore do nothing today: the engine needs its own command path (`schedulerDidDispatchCommand` is not interceptable through `MountingOverrideDelegate`; options: a `UIManagerCommitHook` cannot see commands either; Phase 2 should wrap `nativeFabricUIManager.dispatchCommand` in JS and call our module directly, keeping RN's path for real RN views).
- `nativeFabricUIManager.measure/measureInWindow/measureLayout` (`UIManagerBinding.cpp:642`, 682, 591): pure C++ over the current shadow tree revision (`dom::measure(currentRevision, *shadowNode)` -> `LayoutableShadowNode::computeRelativeLayoutMetrics`), returning `x, y, width, height, pageX, pageY` in points; no Java involved, so it keeps working. It honours `ScrollViewState.contentOffset` (section 6) and applies transforms (`getRelativeLayoutMetrics` with `includeTransform`). `measureInWindow` adds the root's viewport offset set by `FabricUIManagerBinding::setConstraints(offsetX, offsetY)`.
- Other Java-bound scheduler callbacks that break with no Java views:
  - `schedulerDidSetIsJSResponder` -> `FabricMountingManager::setIsJSResponder` (`FJ/FabricMountingManager.cpp:1176-1202`) -> `FabricUIManager.setJSResponder(surfaceId, reactTag, initialReactTag, blockNativeResponder)` (`FabricUIManager.java:1350-1380`) queues a normal `MountItem` that calls `SurfaceMountingManager.setJSResponder` (`SurfaceMountingManager.kt:998-1033`): with `blockNativeResponder == true` it does `getViewState(reactTag)` which throws `RetryableMountingLayerException` ("Unable to find viewState for tag ..."). ## Risks and recommended switches

### Feature-flag overrides for the spike build (Expo plugin)

All are `Boolean` overrides, i.e. compatible with the current `applyFeatureFlags` generator (`expo.ts:34-51`, only needs an option that feeds extra names into the array passed at `expo.ts:70`):
1. `disableViewPreallocationAndroid` = true. REQUIRED (section 1).
2. `enablePreparedTextLayout` = true. RECOMMENDED: `ParagraphState.measuredLayout.preparedTextLayout` then carries the exact `android.text.Layout` that Yoga measured (section 4); the fragments path stays as fallback. Side effects: RN's own text view manager becomes `PreparedLayoutTextViewManager` (irrelevant for us), `TextLayoutManager::measure` skips its C++ cache.
3. Keep default (do not override): `enableLayoutAnimationsOnAndroid` (false), `enableAccumulatedUpdatesInRawPropsAndroid` (false), `enableViewCulling` (false), `enableViewRecycling*` (not needed: our views are not RN views; leave the existing `androidViewRecycling` option off for the engine spike so we do not pay for a recycling pool we never use).
4. Optional: `disableMountItemReorderingAndroid` is irrelevant for us (no Java mounting).
`preparedTextCacheSize` (Double, default 200.0) cannot be set with the current generator.

### What the evidence contradicts in SPEC.md

1. "single slot (last set wins)" / install "hooks the surface": `MountingCoordinator` keeps a VECTOR of weak delegates run in order; ours does not replace RN's/Reanimated's, it chains with them (section 2). Keep a `shared_ptr` (weak storage).
2. Step 3 "enumerate at install time; hook later surfaces if the registry offers it": the registry offers nothing; use a `UIManagerCommitHook` (`shadowTreeWillCommit` sees every new surface before its first mount); `UIManagerMountHook` is useless because Java never reports mounts for empty batches (section 3).
3. `parentTag == surfaceId` is true for root children, but the differ also emits an Update for the root itself (tag == surfaceId, parentTag 0): must be skipped (section 3). Virtual nodes (`RCTRawText`/`RCTVirtualText`) are identified by `layoutMetrics == EmptyLayoutMetrics`.
4. "All lengths in pixels (C++ multiplies Yoga points by `pointScaleFactor`)": correct for layout (round x/y/w/h independently, floor padding, as RN does), WRONG for text metrics: Java computes `fontSize = ceil(sp->px)` with font scale, `lineHeight` via sp, `letterSpacing = spPx / fontSizePx` in em; send raw dp/sp from C++ and convert in Kotlin the same way, or measurement will diverge from Yoga's (section 4). The same applies to `maxFontSizeMultiplier`/`allowFontScaling`.
5. Prop 3 corner order (TL, TR, BR, BL) vs `RectangleCorners` (TL, TR, BL, BR), prop 20 ellipsize order (tail, head, middle, clip) vs `EllipsizeMode` (Clip=0, Head=1, Tail=2, Middle=3), prop 20 textAlign (0 auto, 1 left?, ...) vs `TextAlignment` (Natural=0, Left=1, Center=2, Right=3, Justified=4). SPEC's numbers are an encoding of its own; the C++ must map, not cast. `ParagraphAttributes.includeFontPadding` (default true), `textBreakStrategy` (default HighQuality), `android_hyphenationFrequency` are needed for exact measurement but have no record in the SPEC table (add them to record 20). `alignment` comes from fragment 0's `TextAttributes`, not `ParagraphAttributes`.
6. Border colour: SPEC record 5 is one colour; `BorderColors` is per edge (`isUniform()` check); border widths record 4 is fine (`borderWidths.left/top/right/bottom`).
7. "Touches: EngineRoot ... like React Native's `NativeGestureUtil.notifyNativeGestureStarted`": that helper is a no-op for our overlay (it climbs to a `RootView` and the overlay is outside `ReactSurfaceView`), so EngineRoot must emit the cancel itself. Also return true for all touches to avoid `ReactSurfaceView` sending root-target touches to JS (section 5).
8. "`onLayout` needs nothing": true, but only for nodes with the `onLayout` prop (`ShadowTree.cpp:564-580`). `UIManager.measure` also works untouched. Missing and NOT in SPEC: `setIsJSResponder(…, true, true)`/accessibility events/commands on engine tags either crash or soft-fail (section 9); `UIManagerMountHook`/Reanimated mount hook never fire unless we call `scheduler->reportMount(surfaceId)` ourselves after applying a batch.
9. "`ScrollViewEventEmitter` ... all values in points": yes; `ScrollEvent.timestamp` is in SECONDS (JS gets `*1000`), velocity points/s, `contentInset` all zeros.
10. Prefab: ParagraphState and all scrollview headers are not on the default include path (section 8); the SPEC's CMake file list must add `ReactCommon` and the `text/platform/android` include dirs.

### Other risks

- Thread-safety: our delegate is called on whichever thread commits, under the coordinator mutex; JNI calls from there need an attached env (fbjni `ThreadScope`), and the `Post to UI thread` hand-off must copy everything (the `ShadowViewMutation` list and the `jobject` prepared layouts are only valid inside the call unless you create global refs).
- Prepared-layout lifetime: `SafeReleaseJniRef` releases on destruction on any thread; our Kotlin side must not keep using the `Layout` after the state it came from is replaced (we hold our own reference once copied into the Kotlin object array).
- A second JS-visible effect of returning empty transactions: `MountingTransaction` telemetry/`FABRIC_*` markers and "time to mount" metrics in RN disappear; Perfetto traces for mounting must come from our own `Trace.beginSection`.
- Unmount of surface: Java `SurfaceMountingManager.stopSurface` runs without any views; our overlay must be torn down from `ReactSurface` stop or on `onDetachedFromWindow`.
