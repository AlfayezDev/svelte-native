# native-qa

The Svelte Native QA harness. It builds the QA app, runs the lab (28 functional checks plus the stress scenarios) and the boot runner on a device, merges what it measured into `report.json`, and judges that report against the production bar in `gates.json`. `gates` exits non-zero on any miss.

```
pnpm native-qa build  [--abi x86_64|arm64-v8a] [--prebuild] [--variant qa|smoke|production] [--updates-channel qa]
pnpm native-qa lab    --device <serial> [--apk <path> | --no-install] [--dexopt profile|none] [--repeat <n>] [--run checks,quick] [--timeout <s>]
pnpm native-qa boot   --device <serial> [--apk <path> | --no-install] [--dexopt profile|none] [--warm <n>] [--cold <n>] [--idle <s>]
pnpm native-qa soak   --device <serial> [--apk <path> | --no-install] [--minutes 10] [--interval <s>] [--parts <names>]
pnpm native-qa crashes --device <serial> [--apk <path> | --no-install] [--starts 1000] [--suites 100] [--idle <s>] [--map <file>] [--symbols <dir>]
pnpm native-qa symbolicate [--input <logcat file>] [--map <file>] [--symbols <dir>] [--abi x86_64] [--all]
pnpm native-qa parity     --device <serial> [--apk <path> | --no-install] [--update | --missing] [--quick] [--filter <screen>]
pnpm native-qa a11y       --device <serial> [--apk <path> | --no-install] [--quick] [--filter <screen>]
pnpm native-qa resilience --device <serial> [--apk <path> | --no-install] [--rotations <n>] [--cycles <n>] [--rounds <n>]
pnpm native-qa resilience --platform ios --device <devicectl id> --mac <user@host> [--udid <hardware UDID>] [--team <id>] [--rebuild] [--build-only] [--rotations <n>] [--cycles <n>] [--rounds <n>] [--timeout <s>] [--assume-system-kill]
pnpm native-qa smoke      --device <serial> [--apk <path> | --no-install] [--timeout <s>]   # the smoke app; build --variant smoke first
pnpm native-qa product    --device <serial> [--apk <path> | --no-install] [--dexopt profile|none]   # the product boot check, lab emulator only; build --variant production first
pnpm native-qa gestures   --device <serial> [--apk <path> | --no-install] [--input adb|qa|both] [--run box,row,...] [--repeat <n>] [--timeout <s>]
pnpm native-qa gestures   --platform ios --device <devicectl id> --mac <user@host> [--udid <hardware UDID>] [--team <id>] [--rebuild] [--run ...] [--repeat <n>] [--timeout <s>]
pnpm native-qa updates --device <serial> [--apk <channel build>] [--baseline-apk <path> | --no-baseline] [--channel qa] [--warm <n>] [--max-launches <n>] [--settle <n>] [--faults boot,mount,effect] [--eas "<command>"] [--environment <eas environment>] [--reset app|data] [--dexopt profile|none] [--package <id>]
pnpm native-qa report
pnpm native-qa gates  [--platform android|ios] [--all] [--smoke] [--runs lab,parity,...] [--except lab.runs,...] [--markdown <file>]
pnpm native-qa hold   --device <serial> [--wait <seconds>] -- <command...>   # the emulator lock held across several commands
pnpm native-qa leakcheck [--staged] [--all]    # the QA account's address in what is about to be committed, the run files and the manifests (see "Signed-in phase")
pnpm native-qa:emulator     # build, lab x10, boot 30 warm + 30 cold, report, gates (android) on localhost:5555
pnpm native-qa:smoke        # build the smoke app, run the native module smoke test on localhost:5555, report, gates --smoke
pnpm native-qa:suites       # parity, a11y and resilience on localhost:5555, then report (see "Parity, accessibility, resilience")
pnpm native-qa:test         # bun test qa
pnpm native-qa:typecheck    # tsc -p qa
```

Node 25 runs the TypeScript directly (`node qa/native-qa.ts`). Bun is only needed for the tests. Prerequisites for `build` are the Android SDK, JDK 17 and the repo's `pnpm install`; `build --variant smoke` also needs `apps/platform/libs/samsungpay.jar` (the Samsung Pay SDK the smoke app's `expo-samsung-pay` needs: proprietary, copied from the production app's `libs/`, ignored by git; `build` says so when it is missing); `lab` and `boot` need `adb` and `flock` (a machine that reaches the emulator through a tunnel also needs `ssh` to the host).

## Devices and locks

`--device` is required for `lab` and `boot`; nothing defaults to a phone or a Mac. Serials that reach the shared OVH emulator (`localhost:<port>`, `127.0.0.1:<port>`, `emulator-<n>`) make the command re-run itself under the emulator lock, so it waits while another agent or job holds the emulator. `build` always runs under `flock /tmp/svelte-qa-gradle.lock`. `updates` also takes the channel's lock for every device (it keeps two runs from publishing to one channel at once, and is taken after the emulator lock): a lock of the OVH host like the emulator's, `/run/svelte-qa/channel-<channel>.lock`, so a CI `updates` run on the host and a run from this PC on the same channel exclude each other (below). If the tunnel is down: `ssh -f -N -L 5555:127.0.0.1:5555 ovh-root && adb connect localhost:5555`.

**One lock for every machine that uses the OVH emulator.** The emulator is one device that this PC reaches through the tunnel and the OVH host's own CI runner reaches directly (`localhost:5555` on both), so a lock file on each machine would not exclude anyone. The lock file lives on the OVH host, `/run/svelte-qa/emulator.lock` (its own directory: `/tmp` is sticky and `fs.protected_regular` refuses a second user a file the first one created). On the host a command takes it with `flock`. On any other machine it takes the same file over `ssh <host> flock ...`: a held `ssh` session, one per command, that keeps the lock for as long as the command runs and that the host lets go of when the session ends or goes silent for 5 minutes (a heartbeat line every 30 s). If that session ends while the command runs, the lock is lost and the command is stopped (exit 1). Which host:

| Where | Setting | Lock |
| ----- | ------- | ---- |
| a machine with `ssh -L 5555:127.0.0.1:... <host>` listening on the port of the serial | nothing: found from `ss` and the ssh command line | `<host>:/run/svelte-qa/emulator.lock` |
| the OVH host (the directory `/run/svelte-qa` exists) | nothing | `/run/svelte-qa/emulator.lock` |
| any other machine with an emulator of its own | nothing | `/tmp/svelte-qa-emulator.lock` |
| anywhere, explicitly | `NATIVE_QA_LOCK_HOST=<ssh destination>` / `=local`, `NATIVE_QA_LOCK_FILE=<path>`, `NATIVE_QA_LOCK_WAIT=<seconds, default: until free>` | as set |

**One lock per EAS channel, on the same host.** A channel is one thing for every machine (two runs publishing to it would each find the other's updates at its head), so `updates` takes `/run/svelte-qa/channel-<channel>.lock` (`qa`, or `qa-<suffix>`) with the same machinery as the emulator lock, whichever device it runs on: a `flock` on the host, and over a held `ssh` session with a heartbeat from every other machine. If that session ends while the run goes, the lock is lost and the run is stopped. Which host, for the channel: `NATIVE_QA_LOCK_HOST=<ssh destination>` or `=local` as above; else the host of the `ssh -L 5555:...` tunnel to the emulator when one is up; else this machine when it is the OVH host (it has `/run/svelte-qa`); else `QA_EMULATOR_HOST`, `ovh-root` by default. A machine that cannot `ssh` to the host therefore stops at the lock with the destination it tried; `NATIVE_QA_LOCK_HOST=local` takes a lock on that machine instead (no exclusion of anyone else). Distinct channels do not exclude each other, which is what a run of its own channel (`--channel qa-<suffix>`) is for.

Worktrees that predate this change still take `/tmp/svelte-qa-emulator.lock` on the PC, and so does the PC-side `emu_watchdog.sh`: nothing makes them wait for a run that took the host's lock. Rebase them, and move the watchdog to the host (`qa/ci/RUNBOOK.md`, step 6).

`native-qa hold --device localhost:5555 [--wait <s>] -- <command...>` holds the lock across several harness calls (they see it as held and do not take it again): the CI lane runs under it, and so can an agent's own sequence of runs. `ssh ovh-root fuser -v /run/svelte-qa/emulator.lock` shows who holds it. The host's watchdog and the CI jobs take the same file ("CI", below).

## Dexopt

`adb install` leaves an app at dexopt `verify`: everything runs in ART's interpreter until the JIT warms it up, which is not what a store install ships. After every install the harness does what the store does — installs the APK's baseline profile (`am broadcast -a androidx.profileinstaller.action.INSTALL_PROFILE -n <package>/androidx.profileinstaller.ProfileInstallReceiver`) and compiles against it (`cmd package compile -m speed-profile -f`), printing the broadcast result (1 installed, 2 already there) and the resulting dexopt status. `--dexopt none` skips it to measure the verify-only state; `--no-install` never touches it. The profile itself comes from the svelte-native Expo plugin (`baseline-prof.txt`: the engine and the updates module).

## Commands

**build** builds the QA app `io.rasheed.svelteqa`, the app every command but `smoke` measures; `--variant smoke` builds the smoke app `io.rasheed.svelteqa.smoke` instead (below, "Native module smoke test"). `--variant production` builds the product `io.rasheed.app` for the product boot check (below, "product"); it is not an app any gate measures. It runs `svelte-native sync`, runs `expo prebuild --platform android --no-install` when `apps/platform/android` is missing or older than `app.config.ts`, `package.json`, the svelte-native Expo plugin or a module's `expo-module.config.json` (or with `--prebuild`), then `./gradlew :app:assembleRelease -PreactNativeArchitectures=<abi>` with the memory settings from the build recipe. The APK is copied to `qa/out/app-<abi>.apk` (the smoke app: `app-smoke-<abi>.apk`) and described in `qa/out/build-<abi>.json` (`build-smoke-<abi>.json`) (size, sha256, commit, whether the tree was dirty). Gradle output goes to `qa/out/build-<abi>.log` (`build-smoke-<abi>.log`). `APP_VARIANT` is set by the command, whatever the shell has. `android/` holds one variant at a time, and only a finished project counts: `android/.native-qa-variant` is written when a prebuild ends (a project without it is of unknown origin, never read as the QA app), `android.prebuilding` is there while one runs (a failed prebuild removes the half project, a killed one leaves the file and the next build removes it). Building the other variant renames `android/` to `android-<variant>/` and brings the other back, so the two keep their Gradle outputs and a failed prebuild of one never costs the other. The project is made again when any prebuild input is newer (`app.config.ts`, `package.json`, `react-native.config.js`, `qa/smoke-modules.json`, `qa/smoke-packages.cjs`, the fake Firebase file, the Svelte native plugin, the local modules). On the Mac, `build --platform ios` prebuilds with `--clean` when the variant differs from the one in `ios/.native-qa-variant` (or there is none). `EXPO_PUBLIC_API_URL` defaults to `https://dev.qarnos.com`. `UPDATES_CHANNEL` is always set for the build, empty by default, so a plain QA build has `checkAutomatically: NEVER` and measures the app without update checks whatever the calling shell exports. `--updates-channel qa` builds the QA app for the EAS Update channel `qa` (`checkAutomatically: ON_LOAD`, request header `expo-channel-name: qa`): the APK, its record, its log, its source map and its symbols go to `qa/out/channel-qa/`, so the plain build is never replaced; `android/` is regenerated when the channel it was generated for (recorded in `android/.native-qa-updates-channel`, inside the project, so it is parked with it) differs from the build's. Only `qa` and `qa-<suffix>` are accepted: the harness never builds for or publishes to `preview` or `production`. A channel build is always the QA app: `--updates-channel` with `--variant smoke` is refused. After Gradle the build reads the release `AndroidManifest.xml` Gradle merged (`lib/manifest.ts`) and fails unless the update settings it carries are the ones asked for, in both directions (a plain build must not check for updates, a channel build must check on that channel).

**lab** installs the APK (`--apk`, else `qa/out/app-<abi>.apk` for the device's ABI if present, else the app already installed is measured as it is; `--no-install` never installs), then repeats `--repeat` times: force-stop, clear logcat, open `rasheed-svelte:///__dev?run=checks,quick`, follow logcat until the lab logs `[Svelte stress] complete` (or `--timeout` seconds pass), force-stop. The full logcat of each run is kept in `qa/runs/lab-<device>-<stamp>-<n>.log`; the parsed run goes to `qa/runs/lab-<device>-<stamp>.json`. A lab that hangs or crashes is recorded as incomplete, not as an error of the tool. So is a lab another app interrupted: once the package has started, the first `ActivityTaskManager: START ... cmp=<other package>/<class>`, `WindowManagerShell: Transition requested ... type = OPEN` naming another package's component, or `Displayed <other package>/<class>` line (an emergency cell-broadcast alert, a permission dialog, a call) is recorded as `interrupted: { at, by }` on the run (`at` is the device clock as logcat prints it, `by` the component) and the run stays `complete: false` even if the lab's last line came; `report` counts it in `lab.interruptedRuns` and names it under the lab line. `--run` also takes single scenarios (`list-300-virtual`, `churn-animated`, ...). The lab file records the `--run` it was started with (`run`), and `gates.json` pins the scenarios the full `checks,quick` run produces (`scenarios`, per platform): `report` computes `lab.scenarios.missing`, the pinned scenarios some run of the file lacks, and the gate on it is `<= 0`, so `lab --run checks,list-300-virtual --repeat 10` reads as the partial run it is. The frame gates see every pinned scenario too (a missing one is `not measured`), and `report` lists the missing names under the device's lab line. Two scenarios outside `quick` are for work on the windowed list: `list-mount-loop` mounts the 300-row `List` 40 times in one run (median, minimum and first mounts in its summary; the loop for a CPU profile of the mount) and `list-300-virtual-profile` is the gate's scenario with the host timing every flush (`detail.flushes`: start, duration, nodes created, payload, `createNode`, `appendChild` and `completeRoot` milliseconds).

**boot** installs the same way and then measures `--warm` warm and `--cold` cold launches (30 each by default, the production sample size). Per launch it clears logcat, runs `am start -W -n <package>/.MainActivity`, waits for `Displayed` and the `[Svelte boot]` line, and parses logcat. A launch whose `Start proc` to `Displayed` pair is missing from logcat while the app process is alive (`pidof`) and the log shows no crash is launched once more at once, in the same slot: the second launch replaces it and carries `attempts: 2` (`boot.<kind>.retried` counts them, and `report` prints it); a second miss is the failure it always was (`error`, counted in `boot.<kind>.failed`), and a launch that crashed or whose process is gone is never retried. Results go to `qa/runs/boot-<device>-<stamp>.json` and a filtered log (`Start proc`, `Displayed`, `Running "main"`, `[Svelte boot]`, engine lines, faults) to `qa/runs/boot-<device>-<stamp>.log`.

**smoke** is the native module smoke test (SPEC.md, "Native modules (smoke test)"). It runs in the smoke app, which links the production app's native libraries; the QA app does not, so every gate keeps measuring an app with the product's native modules. `smoke` installs `qa/out/app-smoke-<abi>.apk` like `lab` installs the QA one, force-stops `io.rasheed.svelteqa.smoke`, clears logcat, opens `rasheed-svelte-smoke:///__dev?run=smoke`, follows logcat until the lab logs `[Svelte stress] complete` (or `--timeout` seconds, default 180, pass), force-stops the app, and keeps the log in `qa/runs/smoke-<device>-<stamp>.log`. The parsed run goes to `qa/runs/smoke-<device>-<stamp>.json`, a run kind of its own: one entry per `[Svelte smoke] <module> ok|fail|skip path=… ms=… <detail>` line (the last line of a module wins), the `[Svelte smoke] complete` counts, crashes and JavaScript errors, and whether the run completed (the lab's last line and the app's own came, nothing crashed or took the screen). It prints every failure, skip and missing module. `--platform ios` launches the same URL with a token and reads `Documents/smoke-results.json` through the Mac, like `lab` (the iOS smoke build, `build --platform ios --variant smoke`, needs its own Terminal script on the Mac, `--build-script`). Nothing prompts and nothing touches the network; the scenario is not part of `checks,quick`, so the pinned lab scenarios are unchanged.

**product** (Android) is the product boot check. The product (`io.rasheed.app`, `APP_VARIANT=production`) has no development lab: Metro resolves everything in `src/lib/native/dev/` and `src/routes/__dev/` to a stub that throws on any property read and on a call, so a use of the lab in shared code that is not behind `nativeLabEnabled` passes every gate of the QA app (which has the lab) and crashes the product's root layout. Nothing else starts the product, so this does. `build --variant production --abi x86_64` makes it (`qa/out/app-production-<abi>.apk`, `build-production-<abi>.json`; the Maps key a product takes from the environment is a placeholder, `android/` is parked and brought back like the smoke app's; `--updates-channel` is refused, and so is `--platform ios`: what ships is built by EAS). `product --device localhost:5555` installs it, clears its data (so it starts signed out), starts it cold and, for 15 s from the start, polls the accessibility tree of its window for the login screen (the button `auth.continueWithEmail`, in either language) while logcat collects what the app does. It passes when the screen came within the 15 s and logcat shows no JavaScript fatal (`handleHostException`, `FATAL EXCEPTION`) and no native crash (a fatal signal, an ANR, a debuggerd report) of the app and its process was still there at the end (a process that was gone is a fatal). The window is held to its end even when the screen came early. It writes `qa/runs/product-<device>-<stamp>.json` (the run kind `product`; the logcat beside it as `.log`) and exits 1 when it fails. Gates `product.boot.fatals` (at most 0) and `product.boot.firstScreen` (at least 1, within 15 s whatever window the run had); the OVH emulator provides the run, no phone does, so both are informational for the phones. `js errors` (`E ReactNativeJS` lines) are recorded and not judged. **It refuses any phone-role device**: by its serial, from `gates.json`, before the first adb command (the Samsung phone is not even asked for its properties), and again by what the device reports about itself (it must say it is an emulator and `gates.json` must list it as the lab), so `io.rasheed.app` is never installed, started or cleared on a phone (`lib/reset.ts`, `refusePhone` and `assertProductDevice`). It takes the emulator lock like every command on that serial. The CI lane runs it on every push and dispatch, after the stages of the QA app ("CI"): `lane.sh build` makes the product too (`build --abi x86_64 --variant production`), and a product that does not boot fails the lane.

**updates** (Android) runs the over-the-air update scenario against the `qa` channel with the build from `build --updates-channel qa` (`--apk`, else `qa/out/channel-qa/app-<abi>.apk`, whose record must say the build is for that channel). The scenario, its evidence rules and the reset are described in `modules/svelte-engine/SPEC.md`, "End to end on a QA channel"; in short:

0. *Preflight.* The device is identified from its own properties; `eas whoami` and `eas channel:view qa --json` must pass (the channel must map to exactly one branch, named `qa`); the run takes the channel's lock (`/run/svelte-qa/channel-qa.lock` on the OVH host, over ssh from any other machine; every device, "Devices and locks") as well as the emulator lock. eas-cli is `npx -y eas-cli@27.2.0` (`eas.json` asks for 24.14 or newer, which the `eas` of some machines is not; `--eas` or `NATIVE_QA_EAS` replaces the command), runs in `apps/platform` as the logged-in EAS user (or `EXPO_TOKEN`) with a short list of environment variables, and everything it prints is redacted before it reaches the log or the run file, which records only the program's name and version. `--environment` (default `development`, an EAS environment with no variables) is the one SDK 55 and later `eas update` requires.
1. Installs the plain QA build (`--baseline-apk`, else `qa/out/app-<abi>.apk`; `--no-baseline` skips it) and measures `--warm` (30) warm launches.
2. Installs the channel build (`adb install -r`), resets its update state, publishes a known-good starting update (so a stale or bad head left by an earlier run is not what the run measures), cold-starts it (the embedded bundle must run and the probe must say the build checks on a channel) and starts again until the starting update runs with its marker.
3. Publishes a marked update and cold-starts (force-stop, start, read that launch's logcat until its check ended) until the app reports that update id with the marker of the published bundle, counting the launches.
4. For each fault `boot`, `mount`, `effect` (`--faults`): publishes an update that fails that way and cold-starts until it runs, starts once more (the failed id must be reported, the app must boot and run the previous update or the embedded bundle), then `--settle` (at least 1, default 3) more times (none may run or download the bad update, and every one of those launches must be read to its end and show the client refusing it).
5. Publishes a good clean-up update right after the last bad one and starts until it runs, so the channel ends healthy, also when an earlier step failed (every publish is an attempt, parsed or not; SIGINT and SIGTERM publish it too).
6. Measures `--warm` warm launches of the channel build on the healthy channel and compares them with step 1.
7. Restores the device: removes the reset setting if it is still there and installs the plain QA build over the channel build (`deviceState.finalBuild`; without a plain build to put back, the run says so loudly and the report notes it).

The reset (`--reset`) is by default the app's own: the harness puts a token in the global setting `svelte_qa_reset_updates` (`adb shell settings put global`) and the first start of the QA app that sees a token it has not honoured deletes its updates directory and failed list before it picks a bundle (`QaReset.kt`, `UpdateStore.reset`; honoured only in `io.rasheed.svelteqa`, and read only when the store holds something to forget; logged as `QA reset (<token>): forgot N update(s)`). The harness deletes the setting as soon as the first launch has run, not at the end of the run. `--reset data` runs `pm clear` instead. **A device is cleared or uninstalled only if it positively says it is an emulator (`ro.kernel.qemu` or `ro.boot.qemu` is 1) and `gates.json` lists it as the lab; a `phone` is never cleared**, whichever serial adb reaches it by (`ro.serialno` is looked up in `gates.json` as well): `lib/reset.ts` is the only code that can emit `pm clear`, and `test/reset.test.ts` fails if any other source of the harness mentions `pm clear` or an uninstall. A phone takes `adb install -r` and the app-level reset only.

A launch is read until the check the client logs after the first commit has ended (a download included), or a moment after a bundle logged a fatal and its host died before the check, or 90 s. `--max-launches` (4) bounds the starts any step may take, and must be at least 2: one start downloads an update, the next runs it. Each publish takes about a minute (`expo export` plus the upload), so a run takes about 20 to 30 minutes with 30 warm launches per series. Results go to `qa/runs/updates-<device>-<stamp>.json` and the filtered logcat of every launch, with the redacted `eas` output, to `qa/runs/updates-<device>-<stamp>.log`. The scenario is in `lib/updates.ts` over a driver, which `commands/updates.ts` implements with adb and eas-cli and `test/updates-scenario.test.ts` implements as a model of the client's policy.

**report** takes the newest lab run and the newest boot run of each device, computes the flat metrics, evaluates every gate and writes `qa/report.json`. It prints a per-device summary and the gate table. It warns when the runs of a device (lab, boot, soak, crashes, parity, a11y, resilience) measured different builds (the updates run is left out of that comparison: it installs the channel build, a different APK by design), or when one cannot say which build it measured. The warning is about the artifact, not the commit: runs of one device must share the installed identity, and runs of one artifact started at different source commits (harness-only commits land between the runs of one campaign) are a `note:` that names each run's commit, not a warning. A build is identified by the sha256 of the installed `base.apk` on Android and by what the app itself reported on iOS (the digests of `main.jsbundle` and of the executable, "iOS" below); a run with no identity is a warning (`build identity not reported`), not a skip. For each device that has an accessibility run it prints one line per screen: the reach percentage (reachable of the interactive elements), `clipped`, the elements modelled from UIKit's state on iOS, and `tree not settled` for an Android dump that was not stable.

**gates** evaluates `gates.json` against the metrics in `report.json` (so editing a bar needs no new measurement) in one of two lanes: without `--smoke` every gate but `smoke.*` (the QA app), with `--smoke` only `smoke.failed` and `smoke.missing` (the smoke app, which no other gate sees). It prints the table (wildcard gates collapsed to their worst value; `--all` prints every row) and exits 1 unless every row passed. `--platform android` judges only the Android bars, which is what the emulator lane does. A gate nobody measured is `not measured`, and `not measured` fails. `gates` also fails, with the reason printed first (`FAIL: ...`, before the table), when the report is not the current picture: a run file of a device of the judged platform under `qa/runs` (in the smoke lane, a smoke run file) was written after the report's `generatedAt` (run `report` again), or the report carries warnings for the judged platform (runs of different builds, runs that did not identify their build; the smoke run is another app, so it is not compared with them). It prints the report's `generatedAt` and its age. Without `--platform` every device and every warning counts. A lane that ran only some run kinds judges those: `--runs lab,parity,a11y,gestures` limits the kinds every device provides to the listed ones, so the gates of the others (the soak, the crash volume, ...) are `informational` instead of `not measured`; `--except lab.runs` leaves the named gates out the same way, for a gate whose bar is a sample size the lane ran smaller (the CI push lane's 3 lab repeats against the production 10); a gate id that does not exist is an error. `--markdown <file>` also writes the table as GitHub Markdown (failures first, passes and informational rows folded), which the CI job summary shows.

**gestures** runs the lab's `gestures-*` stress scenarios with touches injected into them and judges the counters the recognisers report, see "Gestures" below. It writes `qa/runs/gestures-<device>-<stamp>.json` (one launch of the lab per way of driving and repeat, with its logcat in `gestures-<device>-<stamp>-<input>-<n>.log`), which `report` merges and the `gestures.*` gates judge.

## Boot definitions

Both are processes started from nothing: `am force-stop` kills the app first, so `Start proc` is always in the log. The distance of each from a real first launch after install or reboot is stated, not hidden.

- **warm**: `am force-stop`, a 1.5 s pause, `am start`. The previous launch ran seconds earlier, so the page cache and the dex and oat files are hot.
- **cold**: Settings is brought to the front, the app is killed with `am force-stop`, the device idles `--idle` seconds (default 20), then the app is launched. Nothing is cleared (a `pm clear` would also delete the session and make every launch a first-run launch), and a stock emulator or phone cannot drop the page cache, so this is a process-cold, idle-gap launch, not a power-cycle launch. It captures what a user sees after the app has been out of the foreground and swapped out for a while.

The number gated is `Displayed` minus `Start proc`, both timestamps from the activity manager's lines in `logcat -v threadtime`, so it contains the zygote fork, the native host and the JavaScript. `am start -W` `TotalTime`, the system's own `Displayed ... +NNNms`, `Start proc` to `Running "main"` and the `[Svelte boot]` JavaScript total are recorded next to it (`boot.<kind>.totalTime.p90`, `.runningMain.p90`, `.jsTotal.p90`). p90 is nearest rank: with 30 samples it is the 27th smallest.

On a phone with a little/big core split (the Samsung A16: two big cores) the launch is sensitive to which cores the start-up threads get: `am start -W` runs a JVM that holds a big core for 200 to 460 ms of the launch, and `system_server`'s garbage collector takes the other one in about one launch in four. The app pins its start-up threads to the big cores until the first mount (`BootBoost`, SPEC "Boot on the phone"), so a collector run costs a few milliseconds instead of doubling the JavaScript time. `cmd activity start-activity -W` has no JVM; 30 interleaved pairs against `am start -W` showed the same distribution, so the harness keeps `am`.

`gates.json` is the production bar of `packages/svelte-native/PLAN.md`:

```json
{
	"id": "boot.warm.p90",
	"title": "Warm boot p90, Start proc to Displayed",
	"unit": "ms",
	"metric": "boot.warm.p90",
	"bar": { "android": { "max": 350 }, "ios": { "max": 250 } }
}
```

`bar` maps a platform to `max`, `min` or both, or to `equals` (a text: the gate on `crashes.run` is `== "checks,quick"`, and a metric that is a text only meets an `equals` bar), with an optional `round` (decimals the measured value is rounded to before comparing; `droppedPct` uses 1, so 0.04 % reads as the lab prints it, 0.0 %). A gate is judged for every device of each platform it names (and, with `roles`, of the roles it lists: see "Device roles"). A platform with no device in the report and a metric a device never produced are `not measured`, which fails. `*` in `metric` matches one name segment and yields one row per match (`frames.*.droppedPct` is one row per scenario).

**Device roles.** `gates.json` also maps each serial to a role and a name (`devices`: `R58Y90KNGRP` is the phone "Samsung A16", the iPhone `E74A5608-...` the phone "iPhone SE 3", `localhost:5555` the lab "OVH emulator, software GL"). A `phone` is real hardware: its frame, boot and list timings are the production numbers. A `lab` is a device that exists for the engine checks, crash volume, soak, parity pixels, accessibility and resilience; the OVH emulator renders under software GL (`swiftshader_indirect`), so its animated scenarios drop 10 to 30 % of their frames and its boot takes 700 to 900 ms whatever the build does, and those timings say nothing about production. A gate may carry `roles` (`["phone"]`); without it the gate judges every role. For a device whose role a gate leaves out the gate is still evaluated and printed, with the verdict `informational`: the value shows, and the row is not a pass, a failure or `not measured`, so no summary line counts it (`gates` prints `N informational, not counted`, and one line per device with its own counts). A serial the table does not list has no role and gets every gate: nothing is exempted by omission. `report.json` records each device's `role` and `name`; `gates` reads the roles from `gates.json` as it is now, so changing one needs no new measurement. A role that is not `phone` or `lab`, or an empty `roles` list, is an error when the file is read.

| Gate | Roles | Run kind | Why |
| ---- | ----- | -------- | --- |
| `frames.droppedPct`, `frames.maxPeriodRatio`, `frames.maxMs` | phone | lab | frame times of animated scenarios depend on the GPU; software GL is slower than any phone |
| `boot.{warm,cold}.p90`, `boot.warm.jsTotal.p90`, `boot.{warm,cold}.{samples,failed}`, `boot.js.samples` | phone | boot | a launch on the emulator is a different zygote, CPU and disk; the production boot is the phone's |
| `list.virtual300.mountMs` | phone | lab | a mount-to-layout time is CPU and GL bound |
| `lab.scenarios.failed` | phone | lab | the lab marks a scenario failed on its own frame and time limits, which the emulator's software GL breaks |
| `checks.*`, `lab.runs`, `lab.incomplete`, `lab.scenarios.missing` | phone and lab | lab | counts and bugs, not speed |
| `log.*` | phone and lab | lab or boot | fatals and engine warnings are as true on the emulator as on a phone |
| `memory.*`, `soak.*` | phone and lab | soak | heap growth, leaked views and dead-tag writes are measured honestly on the emulator; a device that runs no soak shows them informational |
| `crashes.*` | phone and lab | crashes | crash volume runs on the emulator |
| `parity.*`, `a11y.*`, `resilience.*` | phone and lab | parity, a11y, resilience | pixels, accessibility and resilience do not depend on speed |
| `smoke.complete`, `smoke.fatals`, `smoke.failed`, `smoke.missing`, `smoke.unexpectedSkips`, `smoke.ok` | phone and lab | smoke | a native library either answers its call or it does not, and a run that crashed or never finished answers nothing; judged by `gates --smoke` only |
| `gestures.frames.{droppedPct,maxPeriodRatio,maxMs}` | phone | gestures | frame times of a gesture-driven animation depend on the GPU (the bars are `frames.*`'s) |
| `gestures.checks`, `gestures.churn.leaked`, `gestures.agreement`, `gestures.{launches,incomplete,scenarios.missing,fatals,engineWarnings,harnessErrors}` | phone and lab | gestures | counters, rests, scroll offsets, leaks and agreement are bugs, not speed |

**Run kinds.** A device is also judged only on the run kinds it is meant to provide: `devices[serial].runs` lists them (`lab`, `boot`, `soak`, `crashes`, `parity`, `a11y`, `resilience`, `smoke`, `gestures`, `updates`, `product`). The Samsung A16 provides `["lab", "boot", "smoke", "gestures"]` (no `updates` run yet: it has not been run on the phone), the iPhone SE 3 `["lab", "boot", "parity", "a11y", "resilience", "smoke", "gestures"]` (its `log.crashReports` is summed from the lab, boot, parity, a11y, resilience and gestures pulls, so it is judged; until its first `resilience --platform ios` run the three `resilience.*` gates read `not measured`), the OVH emulator `["lab", "soak", "crashes", "parity", "a11y", "resilience", "smoke", "gestures", "updates", "product"]` (its boot and frame gates are informational through its role; no phone provides `product`). A gate belongs to the kind its metric prefix names: `lab.*`, `checks.*`, `frames.*`, `list.*` to `lab`; `boot.*` to `boot`; `log.*` to `lab` and `boot` (judged when the device provides either); `memory.*` and `soak.*` to `soak`; `crashes.*`, `parity.*`, `a11y.*`, `resilience.*`, `smoke.*`, `gestures.*`, `updates.*`, `product.*` to their own kind (the `updates.*` gates name Android only: `applied`, `rolledBack` and `channelHealthy` at least 1, `badRetried` and `unexpectedFaults` at most 0; the OVH emulator provides the run, and a device that should be judged on it gets `updates` in its `runs`); any other metric to every kind. A gate of a kind the device does not provide is `informational`, exactly like a role mismatch: the value (or `-`) shows and nothing counts. A gate of a kind the device does provide that has no measurement is still `not measured`, which fails: the list says what must be run, not what may be skipped. A serial `gates.json` does not list provides every kind. An unknown kind or an empty `runs` list is an error when the file is read; `report.json` records each device's `runs`.

## Native module smoke test

Three apps come out of `app.config.ts`: the product (`io.rasheed.app`), the QA app (`io.rasheed.svelteqa`) and the smoke app (`APP_VARIANT=smoke`, `io.rasheed.svelteqa.smoke`, "Svelte smoke", scheme `rasheed-svelte-smoke`). The first two link the same native modules (a test compares their autolinker output, package for package, and SPEC.md compares the generated `PackageList.java` and `ExpoModulesPackageList.kt` with those of `c75c31491`); only the smoke app adds the 31 libraries of the smoke test, their config plugins, the fake Firebase files and the Huawei repository, and only it needs `libs/samsungpay.jar`. A fresh checkout or CI builds and measures the QA app without any of that.

`gates.json` pins the modules a smoke run must report (`smoke.modules`, per platform; today the same 36) and the skips that are expected (`smoke.skips`: Android `hms` and `web-browser`; iOS `web-browser`, `hms`, `samsung-pay`), and gates, for every role and in their own lane (`gates --smoke`; `gates` leaves them out, and `report` prints them apart once a smoke run exists, with the smoke run's own warnings): `smoke.complete >= 1`, `smoke.fatals <= 0`, `smoke.failed <= 0`, `smoke.missing <= 0`, `smoke.unexpectedSkips <= 0` and `smoke.ok >= 34` (Android) or `33` (iOS), the pinned modules less the expected skips. A module that logged `fail` counts as failed; a pinned module no line reported (the app crashed before it, a call never returned and the next ones did not run, or the list names a module the app does not know) counts as missing, so a run that dies half-way fails by its missing modules; a run that crashed, was interrupted or logged no completion line is not complete, whatever it reported before. A `skip` is a report and passes only where the platform lists it: Huawei's library on a Samsung (on a Huawei or Honor device it is `ok`), `web-browser` where no browser has Custom Tabs, an Android-only library on the iPhone. `native-qa smoke` itself exits 1, naming the gate, when one of these fails. `qa/test/smoke.test.ts` pins the list against the checks in `smoke-checks.ts`, the module table and the dependencies, and runs both autolinkers for the three variants; `qa/test/bundle.test.ts` bundles the JavaScript of the three, and of the combinations the lab tests need (nine bundles, about a minute), and checks that the product's and the QA app's carry none of the libraries, so the JavaScript boot gate measures what it measured before the smoke test. It also lists each bundle's modules and checks that the product has no development lab (no `/__dev` route, no module of `src/lib/native/dev` or `src/routes/__dev`), that the QA app is the product plus the lab, and that the product is smaller by the lab's size; `qa/test` is the QA app's own: the lab is its whole point. After `report`, the device's line reads `smoke 35 ok, 0 failed, 1 skipped, 0 missing of 36 pinned`, and the module that failed is named.

The smoke run is an explicit step (`pnpm native-qa:smoke` builds the smoke app, runs it, reports and runs `gates --smoke`); `native-qa:emulator` does not run it, because it would mean installing a second app on every pass. The two apps can be installed side by side.


## Signed-in phase (parity and a11y)

`parity` and `a11y` have a second phase for the product's signed-in screens (the cases with `signedIn: true` in `lib/screens.ts`, ids `app-*`). The run does the signed-out cases first (the login needs a signed-out device), then signs in **once**, visits every signed-in case in every variant, and signs out. `parity --filter app-` or `a11y --filter app-` runs this phase alone; `--device` is the only thing that changes between the emulator and a phone (a reference set is kept per device kind, like the others).

**What is covered** (the account must have a profile, because the sign-in must not land on the onboarding screen, and at least one workspace, whose first entry the cases open): the list of workspaces (`app-workspaces`), the create form (`app-workspace-create`, never submitted), the workspace's home (`app-workspace-home`) and settings list (`app-workspace-settings`), the five sections of the account settings as pages of the workspace settings (`app-settings-profile|preferences|devices|workspaces|danger`) and as sections of the account modal (`app-account-*`), and the change-email modal (`app-account-change-email`, never sent). The cases press the product's own buttons from the list of workspaces, like a user, so each screen has the back button and the stack it has in use. Parity takes the eight variants (theme x direction x text size), the accessibility run the four layouts, as for the other cases. `/onboarding/profile` is not reachable for an account that has a profile and is listed in `notCovered` with that reason; the delete-account code, the confirmation of a deletion and the sign-out of other devices are never pressed. The phase only reads: it signs in (which makes this device a session of the account, and the app renews it like it always does), sets nothing, and signs out. The cases' anchors, declared controls and titles are written from the screens' source (`src/routes`, `AccountSettings.svelte`) and the message catalog (`lib/copy.ts` takes the words from it, so a copy change reaches them); the first run against a database that signs in is where they are checked against the device, and a case that names a control the tree does not show fails by name.

**How it signs in.** `lib/signin.ts` types the address into the login screen with `adb shell input text`, presses enter, types the code, presses enter and waits for the list of workspaces; nothing in the app takes the address, so the product bundle (and the QA app) carry no sign-in hook. The session is the device token the app keeps in its SecureStore, so it survives the `am force-stop` every case starts with; the phase ends with the "Sign out" button, so the signed-out cases of the next run find the login again (a session an earlier, killed run left is signed out first). The code is `RASHEED_QA_CODE` (six digits), and `000000` (the development database's) only when none is set. A database that is not in development mode emails its codes, which no harness can read, so such a database signs the QA account in with a fixed code instead: the module has two environment variables, `QA_SIGNIN_EMAIL` (one address) and `QA_SIGNIN_CODE` (six digits), set only at publish (`apps/database/module/src/identity.rs`, `plan_code`). When both are set, a sign-in code requested for that address is `QA_SIGNIN_CODE` and nothing is emailed; every other address, and every other purpose for that address (change of email, deletion of the account), is issued a random emailed code exactly as before, and the limits on codes (three tries, the 30 s cooldown, five live codes) apply to the fixed code too. A half-set or malformed pair is no pair. Use a dedicated QA address and a code that is not guessable: the fixed code is a credential of that account for as long as the variables stay published.

To turn it on, publish the module with the pair (the address and code are placeholders; they come from the shell or the ignored `.env.local`, never from a committed file), then give the harness the same two values:

```
# the module: setup.mjs builds it, passes the pair to `spacetime publish`, and unsets it when either is missing (one of the two alone is an error)
SPACETIME_URL=<dev SpacetimeDB url> APP_URL=<dev platform url> SERVICE_IDENTITY=<the deployed service identity> SERVICE_TOKEN=<the deployed service token> \
  QA_SIGNIN_EMAIL=<qa address> QA_SIGNIN_CODE=<six digits> node apps/database/setup.mjs
# without setup.mjs, the CLI as the database's owner (publishing keeps the environment values it is not given)
QA_SIGNIN_EMAIL=<qa address> QA_SIGNIN_CODE=<six digits> spacetime publish rasheed --server <dev SpacetimeDB url> --bin-path apps/database/module/target/wasm32-unknown-unknown/release/rasheed_database.wasm
# the harness (the environment, or the ignored .env.local at the repository root)
RASHEED_QA_EMAIL=<qa address>  RASHEED_QA_CODE=<six digits>
```

`setup.mjs` mints a new service identity when `SERVICE_TOKEN` is not set, which on a deployed database replaces the one the platform runs with: give it the deployed values. Publishing again without the pair removes it. The harness types `RASHEED_QA_CODE` and never prints it (the code is redacted like the address, and a file that contains it as a whole number is refused). A database that rejects the code ("Invalid login code") says in the run file whether `RASHEED_QA_CODE` is set; the signed-in cases are then recorded as skipped (parity) or not dumped (a11y), which the `*.signedIn.missing` gates fail as `not measured`. Every sign-in request on a database that emails its codes sends a real email, so a run does it once.

**How the account is supplied, and never printed.** The address is `RASHEED_QA_EMAIL` in the environment, else that one key read from `.env.local` at the repository root (gitignored, mode 600; no other key of the file is read, and the value is kept in the harness's memory, not in `process.env`). It is a secret of the machine: it is never printed, logged, written to a run file or report, put in a file name or a reference, or passed in a URL or an intent (the one place it goes is the argument of `input text`, and any error that could quote that command is redacted). What stands behind that:

- the screens that show it (the list of workspaces, the profile) mask it with the `account: "email"` selector, which matches the node whose text is the address; a mask that matches nothing refuses the reference, and so does a screen that shows the address outside the case's masks (`exposedAccount`);
- the pixels under a signed-in screen's masks (the address, the photo from the network, the account's devices) are painted over in one flat grey before the reference is written (`paintOver`), and in the `actual.png` a failure keeps, so no reference carries them; the comparison ignores them anyway;
- what the accessibility run keeps of a signed-in screen (focus stops, findings) is redacted (`redactDeep`), and every run file and the references' manifest pass `assertClean` when written, which refuses a file that contains the address;
- `pnpm native-qa leakcheck` looks for it in the staged diff, the unstaged diff and untracked files, the run files, the report and the manifests (`--staged` only the first, `--all` every tracked file) and prints file names, never the address or its line. Run it before committing anything of the harness.

**Stable data.** The phase has no timestamps or counts of its own to mask: it masks the address, the photo of the profile (`masksWhenShown`, the network's image) and the screens' dynamic lists (the account's devices). A reference is deterministic across runs only while the account's data is: its profile, its first workspace and its devices as they were when the references were taken. The `maskedPct` gate (25 %) applies to these cases like the others.

**The interface language.** The QA app (`io.rasheed.svelteqa`) does not apply the signed-in account's language to the interface (`languageFollowsAccount` in `state.svelte.ts`; every other app, the product included, does): the harness runs each screen in English and in Arabic under one account, so the language there is the device's per-app language, which the harness sets with the layout direction, and neither the account's language nor the stored language is touched.

**Gates and the pins.** `gates.json` `signedIn.android` pins the ids of the signed-in cases; `parity.signedIn.missing` and `a11y.signedIn.missing` count the pinned cases (in every variant) that a run did not compare or dump, and are gated at 0, so a case removed from the matrix, or a phase that did not run, fails by name. The existing parity and a11y gates see the new cases through the matrix as they do the others. The iPhone's lab cannot sign in yet and runs the signed-out screens only (`iosNotCovered` says so); its pins are absent. The accessibility oracle also counts controls under 48 dp (`a11y.smallTargets`, a `target` finding), which no gate judges.

## Gestures

`native-qa gestures` drives the gesture lab (SPEC.md, "Gestures (react-native-gesture-handler)"): the page `/__dev/gestures?mode=<mode>` and the stress scenarios `gestures-<mode>` (`apps/platform/src/lib/native/dev/gestures-lab.ts` describes them all: what to inject, when a step is over, what must have been counted). They are outside `quick`; any lab run can name them (`--run gestures-box,gestures-row`) and `native-qa gestures` is the command that injects the touches.

| Scenario | What it measures | Input | Driven by |
| -------- | ---------------- | ----- | --------- |
| `gestures-box`, `-box-busy`, `-box-js`, `-box-js-busy` | one Pan on a box, UI thread, a spring on release: begin, start, end(success), finalize once, 10 updates or more, the drag reached (the Pan's peak translation within 90 % of the 160 x 96 dp commanded with the injector, 80 % with `adb`: a Pan counts from where it activated and `input swipe` ends its path early), the box back at 0. `-busy` blocks the JavaScript thread 40 ms of every 50 and must give the same counters and smooth frames (the UI-thread proof); `-box-js` is `runOnJS(true)`; `-box-js-busy` is recorded, not judged. Frames judged for `box` and `box-busy` | one drag, 400 ms, 160 x 96 dp | adb, qa, xctest |
| `gestures-pinch-rotate` | `Simultaneous(Pinch, Rotation)`: both active together, final scale and rotation against what the injector delivered (RNGH counts from where each handler activates: the pinch two touch slops plus one after the second finger went down and the rotation at 5 degrees, each resetting to zero there, so a 3x spread through 40 degrees reads 2.21 and 34, which `expectedTwoFinger` replays from the injector's event times), frames judged | two pointers, 80 to 240 dp apart, 40 degrees, 600 ms | qa, xctest (a pinch, then a rotation: both-active is not judged there) |
| `gestures-row` | 20 swipe-to-delete rows in a ScrollView: row 3 swiped left is removed and the list stays; row 5 dragged up fails its pan (`finalize(false)`, never started) and the list scrolls | a swipe of 220 dp, a drag of 200 dp | adb, qa, xctest |
| `gestures-carousel` | a horizontal Pan pager in a vertical ScrollView: horizontal and 30 degree (600 ms: `shouldFail` runs before `shouldActivate`, so an event must land between the active and the fail offsets) swipes turn the page and do not scroll, a vertical one scrolls and does not turn it, the pager's pan counts 3 begins, 2 successes, 3 finalizes | three swipes | adb, qa, xctest |
| `gestures-pushed-edge` | a pushed screen with a full-width Pan: a swipe from x = 8 dp pops the screen and the pan never starts; from 100 dp the pan starts and the screen stays (two rounds, two pushes) | two swipes | adb, qa, xctest |

| `gestures-longpress-tap` | `Exclusive` and `Race` of `LongPress(500 ms)` and `Tap` with a `Pressable` inside, per box a tap (tap fires once, long press fails), a 700 ms hold (long press once, tap cancelled, the press cancelled) and a hold that drifts 16 dp (both fail) | six inputs | adb, qa, xctest |
| `gestures-scroll-native` | a Pan with `simultaneousWithExternalGesture(Gesture.Native())` around a ScrollView: both active, the list moves | a drag of 250 dp | adb, qa, xctest |
| `gestures-churn` | 200 mounts and unmounts of a view with three gestures, half on the UI thread; `fabricStats().gestures` (records, native handlers, UI registrations) back to 0 and the engine's live views back to the baseline | none | any |

**The handshake.** A page opens a `Session` for its scenario round and logs `[Svelte gesture] ready` (`'[Svelte gesture] ready', '{json}'` in logcat) when it waits for input: `scenario`, `round`, `step` of `steps`, `drive` (`none`, `adb`, `qa`, `xctest`), `density`, `screen` (the engine overlay), `rects` (every view a step aims at, in window pixels: `measureInWindow` times the density; inside a sheet the page adds the sheet's current native translation, which layout does not know) and `input` (what to inject, in dp relative to a named rectangle: `tap`, `drag`, `hold` with an optional drift, `twoFinger` with a distance and an angle going from one value to another). When the step's effects were reported (`Step.done`) and its settle time (a spring, a fling) has passed, the page logs `[Svelte gesture] step`, then the next `ready`; at the end `[Svelte gesture] result`. The stress scenario returns the usual `[Svelte stress]` line: counters, frames and a verdict, with `detail.checks` (`[name, 1 | 0, value]`), `detail.counters` (`[begin, start, update, end, endOk, finalize, finalizeOk]` per handler), `detail.marks` and `detail.observed.frames`. `parseGestureLine` (`gestures-lab.ts`) reads the handshake lines and refuses a cut one. The stress run is `--run <names>,drive:<adb|qa|xctest>`: the `drive:` entry says who injects (none: a person, or a page opened by hand, which starts itself after 1.2 s).

**Android.** `--input adb` opens the lab with `drive:adb` and, for each `ready` line, runs `adb shell input tap | swipe` with exact pixel coordinates from the rectangles (a zero length swipe of 700 ms is a long press): one pointer through the real input pipeline; `input swipe` moves as fast as the shell can, so it proves counters, not latency. The harness checks the overlay is at the window's origin and the input stays on screen (`aimProblems`) and records it. `--input qa` opens the lab with `drive:qa`: the page itself calls `SvelteQaTouch.run(plan)` (`modules/svelte-qa-android` (`QaTouch.kt`), its own Expo module, listed in `expo-module.config.json`), which dispatches one `MotionEvent` per `Choreographer` frame to `EngineRoot` with the frame time as `eventTime`, two pointers included, and reports the event times and the touch slop the lab uses to say what a pinch should have read. It moves a finger the way the pipeline delivers one: each MOVE holds history samples every 4.17 ms (a 240 Hz panel) and a frame that came late (software GL misses frames) is preceded by the moves of the frames it missed, one per nominal period, so no event carries more than a period of travel and what is judged is the arbitration, not the emulator's frame jitter (`lateFrames` in its result says how often). It is compiled into every build and refuses to run unless the app is the QA variant (`io.rasheed.svelteqa`). `both` (the default) does one launch of each and `gestures.agreement.mismatches` counts where the two disagree. `sendevent` on the emulator's touch device would be the end-to-end path for a pinch and is not built. `--run` takes short names (`box,row`); a scenario `adb` cannot drive (`pinch-rotate`) is left out of that launch.

**iOS.** Touches cannot be synthesized from inside the app without private API, so `--platform ios` uses an XCUITest bundle, `qa/ios-ui-tests/` (`make-project.rb` generates `GesturesUITests.xcodeproj` with the `xcodeproj` gem CocoaPods brings; `GesturesUITests/GesturesUITests.swift` is the test). The test opens the lab's link itself (`XCUIApplication.open`, iOS 16.4+: an app that `devicectl` launched is not one XCUITest observes), reads the `ready` JSON from the label of the element `gestures.status`, finds the view by its identifier `gesture.<name>` (the page's `testID`, so no pixel handshake) and performs the input with `press(forDuration:thenDragTo:withVelocity:thenHoldForDuration:)` (a drag goes 10 pt past the commanded distance: a Pan counts from where it activated), `pinch(withScale:velocity:)` and `rotate(_:withVelocity:)`, printing `GESTURES-ACTION {json}` for each. The harness reads the verdicts the lab writes to `Documents/lab-results.json`, as `lab` does, and the phone's crash log (two name-filtered pulls: the crash log also holds sysdiagnose archives that take minutes to copy). Run it with `pnpm native-qa gestures --platform ios --device <devicectl id> --mac <user@host> --team <development team id>`: it copies `qa/ios-ui-tests/` to `/tmp/native-qa-ios/gestures-ui-tests` on the Mac, builds the runner with `xcodebuild build-for-testing` in the GUI Terminal (signing needs the logged-in user's keychain, the way `build --platform ios` does; again only when the sources changed or with `--rebuild`; `--build-only` stops there), then runs `xcodebuild test-without-building` over `ssh`. The phone is asked nothing while the test runs (`devicectl` calls hang then); the results and the trace are read once it has ended. The phone must be on USB (checked), unlocked and awake, with Settings > Developer > Enable UI Automation on: otherwise the runner fails 60 s after `Running tests...` with `Timed out while enabling automation mode`, and the phone writes a sysdiagnose into its crash log. `--trace` has the app record every gesture recognizer per frame, where each touch landed and what UIKit hit-tested, and UIKit's pop and sheet state (`Documents/gesture-trace.json`, kept beside the log as `.trace.json`, summarised per action in the output). The pushed-edge swipe starts 2 pt from the edge on iOS (UIKit's edge zone; `--edge-x` overrides; Android 8 dp). XCUITest cannot move two fingers on both axes at once: `pinch-rotate` is a pinch and then a rotation there. Its accessibility snapshots load the app (3 to 15 % of the frames dropped), so the frame gates cannot be judged with it on iOS. What ran and what did not: SPEC.md, "iOS status (lane G5)".

**Gates.** `gestures.checks` (no failed check anywhere, a timeout counting as one), `gestures.frames.*` (the `frames.*` bars, phone only, for `box`, `box-busy` and `pinch-rotate`), `gestures.churn.leaked`, `gestures.agreement` (Android), no missing scenario, no incomplete launch, no fatal, no engine warning, no harness error; `gestures.launches` needs 2 on Android (adb and qa) and 1 on iOS. Every device lists `gestures` among its run kinds, so a device nobody has run the command on reads `not measured`, which fails. The long run (`gestures --repeat 10`, about an hour with both ways of driving) is not part of any script.

## Resilience on the iPhone

`native-qa resilience --platform ios` is the Android resilience run (rotation, text size, language, 100 trips to the background, the process ended and the app returned to; `lib/resilience.ts`) as far as an iPhone allows, with the same checks (the process is alive, the screens are on screen, nothing crashed) and the same gates (`resilience.failures`, `resilience.stepsMissing`, `resilience.skipped`, `resilience.gateBypassed`, all at 0 but the 2 skipped steps of the appearance pair). The plan and the reading of the output are `lib/iphone/resilience.ts` (host-tested); an XCUITest, `ios-ui-tests/GesturesUITests/ResilienceUITests.swift`, carries the plan out in one go and prints `RESILIENCE-STEP {json}` per step, because nothing else can ask the phone anything while it runs (a `devicectl` call made then hangs, as in "Gestures"). The runner is built and started the way the gesture runner is (`--team`, `--rebuild`, `--build-only`; one `xcodebuild` project holds both tests; the phone must be on USB, unlocked, with Settings > Developer > Enable UI Automation on). `qa/runs/resilience-<device>-<stamp>.json` is the run file (the same kind as Android's, with the phone's crash log and `navigation`: what the app's navigation module did at its last start, read from `Library/Application Support/svelte-navigation/last.json`), the XCUITest's output and that line are kept in `.log`.

```
pnpm native-qa resilience --platform ios --device <devicectl id> --mac <user@host> --team <id> [--udid <hardware UDID>]   # the full plan: 126 steps (an estimate of 10 to 20 minutes: it has not been run)
pnpm native-qa resilience --platform ios ... --rotations 1 --cycles 10 --rounds 1                                          # a short plan, to work on the loop
```

What the run does (126 steps; the lab page opens first, with `run=resilience&token=...`, which only writes `Documents/resilience.json` with the build the app reports, so the run is checked against `qa/out/ios-build.json` like the other suites; the menu is opened over it and "Push eight screens with headers" is tapped, so the loop screen is the header screen, three screens deep):

| Group | Steps | What each does, and what it checks |
| ----- | ----- | ---------------------------------- |
| `rotation` | 12 | launch and open the menu; push the header screen; landscape and portrait 5 times (`XCUIDevice.orientation`). The header's navigation bar, its first row and its back button are on screen |
| `fontScale` | 4 | for the default size asked for by name (`UICTContentSizeCategoryL`, the reference whose first-row height is recorded), the largest (`UICTContentSizeCategoryAccessibilityXXXL`), the smallest (`...XS`) and the default again: Home, end the process, launch with `-UIPreferredContentSizeCategoryName <category>`. The screens come back (the restore) and the row is at least 1.5 times as high as the reference (largest), at most 0.97 (smallest), within 5 % (default again) |
| `locale` | 2 | the same restart with `-AppleLanguages (ar) -AppleLocale ar_SA`, then without |
| `appearance` | 2 | dark, then light, while running (`XCUIDevice.appearance`, looked up at run time: where the runner's SDK has none, both steps are `skipped` and the gate allows 2) |
| `background` | 100 | Home, 0.3 s, activate; the app is in the foreground, and every tenth time (and the last) the header screen is on screen |
| `lowMemory` | 6 | twice: Home, 1.5 s, end the process (`notRunning`), launch without a link, the header screen is back with its stack; then a link opened after the process was ended (the menu) wins over the restored screens (the header row is gone); and a process ended in the foreground, with no trip to the background, restores nothing |

What an iPhone cannot be put through, and what stands in for it:

- **A live change of the text size, the language or the layout direction.** They are settings of the phone that only the Settings app changes, and XCUITest has no call for them. The launch arguments above override them for one launch, so each of those steps ends the process and starts it again: what they prove is the restore of the navigation under that size and language (what Android's recreation proves for its font scale and locale), and the larger text itself, by the pixels of the first row. `UICTContentSizeCategoryAccessibilityXXXL` is the largest size the system offers. Parity and accessibility still run at the standard size only (`iosNotCovered`): a launch argument per run would change that, and is not done.
- **Memory pressure.** There is no `am send-trim-memory`. The system ending a backgrounded app is stood in for by ending it from outside after the Home button (`XCUIApplication.terminate()`), which the system may or may not count as its own: see "The system's say" below.
- **The user's swipe-away from the app switcher.** XCUITest cannot reach it on a phone with a Home button. The rule that it restores nothing is the system's (the state of its own that the module relies on is deleted when the user force-quits), not exercised here.

**The system's say.** The app restores its screens only when UIKit offers its own restoration state at the launch (`application(_:shouldRestoreSecureApplicationState:)`, wired by the Expo plugin's AppDelegate patch), because the system deletes that state when the user swipes the app away, which is how the app tells a process the system ended from one the user ended (SPEC.md, "Navigation state across recreation and process death"). Whether iOS offers it after the harness's kill is the one thing the run cannot know in advance, so the run prints what the module did at the app's last start (`navigation module, the last start: restored | dropped (reason) | none`; `none` when it found no file): a restart step that fails with `dropped (the system kept no state of its own ...)` is the system declining, and one that fails with `restored` is a fault of the restore. `--assume-system-kill` launches the QA app with `-SvelteNavigationAssumeSystemKill YES`, which makes the module hand its state over without the system's offer, to tell the two apart; the run file carries `assumeSystemKill`, and `resilience.gateBypassed` fails it, so a diagnostic cannot be taken for the product's evidence. The runner also launches every app with `-ApplePersistenceIgnoreState NO`: XCUITest starts an app with it `YES`, which switches UIKit's restoration off.

The restart steps need the platform configuration (`https://dev.qarnos.com/api/configuration`) to load before the screens show, as any launch without a lab link does; a phone that cannot reach it fails those steps on the loading screen, not on the restore.

## CI

`.github/workflows/native-qa.yml` runs the harness on every push and on demand. The unit job runs on a GitHub-hosted runner; the Android emulator lane runs on a self-hosted runner on the OVH host (label `svelte-qa-emulator`), next to the emulator. Setting that runner up, and registering it, is `qa/ci/RUNBOOK.md`; nothing runs until it is registered.

| Job | Runs on | When | What | Time |
| --- | ------- | ---- | ---- | ---- |
| `unit` | GitHub-hosted (`QA_UNIT_RUNS_ON` moves it to the OVH runner) | every push, dispatch | eslint of the platform app and of `packages/svelte-native`; `svelte-check` of both and `tsc -p qa`; the engine's Kotlin and C++ host checks (`modules/svelte-engine/android/src/test/run.sh`: animated wire, foreign views, capture, gesture rules; about 20 s); `bun test --timeout 60000` of `packages/svelte-native` (route discovery, Metro stubs, gestures, svg, the app-tree mounts with the product's stubs, the updates client, launch and store tests, the Kotlin host checks of the modal, navigation records, big cores and the updates store) and `bun test --timeout 120000 qa/test` (the harness, including the updates scenario, log and EAS tests and the bundle test, which bundles the QA, smoke and product apps with Metro) | 15 to 25 min |
| `emulator` | OVH runner, after `unit` | every push (the quick lane), dispatch (the full lane) | the stages below, under the emulator lock | push 45 to 60 min, dispatch 2 to 3 h |
| `crashes` | OVH runner | dispatch with `crashes: true` | 1,000 cold starts and 100 suites in chunks of 100, resumed up to 5 times after an outage | 8 to 15 h |

A push that only changes Markdown, `docs/`, `deploy/` or `LICENSE` runs nothing. A weekly crash volume is a commented `schedule:` in the workflow; it holds the emulator for most of a day, so it is off.

**The emulator lane** (`qa/ci/lane.sh`, one step per phase in the workflow, one log group per stage). The build comes first and without the lock, so it overlaps whatever else is using the emulator: the QA app and the product (`io.rasheed.app`, no development lab, for the product boot check), each for x86_64 only. The two builds are separate Gradle builds on the runner's Gradle caches (`GRADLE_USER_HOME`) and the same Gradle daemon; each keeps its generated project and Gradle outputs beside the other (`android/`, `android-qa/`, `android-production/`: "build"), so a build after the first is incremental (25 to 75 s each on a 16-core PC; the first one on a new runner has a prebuild and the C++ of the engine to compile, 15 to 30 min). Then `native-qa hold` takes the shared emulator lock ("Devices and locks") for the whole lane and runs:

| Stage | Push | Dispatch |
| ----- | ---- | -------- |
| `emulator-restart` | a fresh emulator instance, so frame measurements and the first stage do not inherit the leak of everything before | same |
| `lab` (`checks,quick`) | `--repeat 3` | `--repeat` input, default 10 |
| `boot` | | `--warm 30 --cold 30` (inputs) |
| `parity` | `--quick`: the base, dark, right-to-left and large-text sets, 102 of the 200 cases, about 17 min | the full matrix, about 33 min |
| `a11y` | `--quick`: the first two layout variants, 52 of the 100 screens, about 11 min | the full matrix, about 21 min |
| `resilience` | | rotations, cycles, rounds |
| `gestures` | `--input both` (adb and the in-app injector) | same |
| `smoke` | | the smoke app, built after the QA app (`smoke` input, needs `libs/samsungpay.jar` on the runner) |
| `updates` | | the over-the-air update scenario against the EAS channel (`updates` and `updates_channel` inputs, off by default; `native-qa updates --channel <channel> --warm <n>`, last of the stages that measure the QA app). It **publishes** to EAS, so a push never runs it, and it needs the `EXPO_TOKEN` repository secret (only this step gets it). The channel build (`build --updates-channel`) is made after the smoke app, in the build step |
| `product` | `native-qa product --device localhost:5555`: the product started cold with its data cleared, watched for 15 s for the login screen and for a fatal; after all the stages of the QA app, which have the lab the product does not | same, after `smoke` and `updates` |
| `report`, `gates` | `gates --platform android --runs lab,parity,a11y,gestures,product --except lab.runs,parity.signedIn.missing,a11y.signedIn.missing` | `--runs lab,boot,parity,a11y,resilience,gestures` (plus `updates` when that stage ran, then `product`), with `--except parity.signedIn.missing,a11y.signedIn.missing` only when the lane has no QA account; then `gates --smoke --runs smoke` |

Between stages, `guard-<stage>` restarts the emulator if qemu's resident set is at 11 GB or more or adb has gone away. **Leak and watchdog, decided:** gfxstream leaks a host thread per app launch of the guest, so the emulator is restarted three ways. The lane restarts it first (a fresh instance) and between stages (`guard`, which holds the lock, so nobody is hurt); the host runs `svelte-qa-emulator-watchdog.service`, the PC-side watchdog moved to the host, which restarts at once when adb has been gone for two checks or qemu passes 18 GB, and at 11 GB as soon as the lock is free; and `svelte-qa-emulator.service` restarts the emulator if it dies. The one gap is a single stage that outgrows 18 GB on its own (the full parity matrix has come closest): the watchdog restarts the emulator under it, that stage fails and the next ones recover. The lane does not run a watchdog of its own, because a job cannot outlive its runner and the host needs one when no job runs. The crash volume runs in chunks that each take the lock, so the host watchdog restarts the emulator between them.

**The gates.** The emulator is the `lab` device of `gates.json`, so the gates that decide a push are the ones that are bugs, not speed: `checks.passed`, `checks.failed`, `lab.incomplete`, `lab.scenarios.missing`, `log.fatals`, `log.engineWarnings`, the three `parity.*`, the seven `a11y.*`, every `gestures.*` that is not a frame time, and `product.boot.fatals` and `product.boot.firstScreen` (a crash of the product alone, such as a read of the lab where the product has its stub, which no stage of the QA app sees). Informational on the emulator, whatever they read: the frame, boot and list-mount timings and `lab.scenarios.failed` (phone gates; software GL is slower than any phone) and, on a push, `lab.runs` (3 repeats against the production 10, left out with `--except`) and, on a push, `parity.signedIn.missing` and `a11y.signedIn.missing` (the quick lane compares the pinned signed-in screens in fewer variants than the pin lists, and a push does not sign in; on a dispatch they are judged when the repository secrets `RASHEED_QA_EMAIL` and `RASHEED_QA_CODE` are set, and the lane says `no QA account` when they are not). The soak, memory, crash, resilience and boot gates are informational on a push because it did not run them (`--runs`). A gate that belongs to a stage which ran and was not measured fails.

**What blocks a push.** Nothing stops a push itself: the workflow reports on the commit. A red `unit` job (a lint, type or test failure) skips the emulator lane. A red `emulator` job means a stage failed or a gate above failed or was not measured; the job is the check to require in the branch protection of the branches that should not merge red, together with `unit` (a repository setting, not set by the workflow). A run that a newer push replaced before it started shows as cancelled: GitHub keeps one running and the newest pending run per concurrency group, so nothing ran and nothing failed.

**Reading a failure.**

1. The run's summary page has the stage table (result, time, qemu GB after each stage), the gate table with the failed and not-measured gates first and the passing and informational ones folded, and the last 30 lines of every failed stage.
2. The `emulator` job has one step per phase (`Build`, `Emulator lane`) and one log group per stage inside the lane; each failed stage is an annotation (`::error title=parity failed`). A stage prints the harness's own words: a lab run that never completed, a parity case with its pixel count, an a11y finding with the screen and the node.
3. The artifact `native-qa-emulator-<run>-<attempt>` (14 days) has `qa/runs/` (the run files and their logcat, the parity and a11y evidence of the failed cases), `qa/out/lane-<stage>.log`, `qa/out/build-*.log`, `qa/report.json` and `qa/out/gates*.md`. Open the run file the failed gate names.
4. `no emulator` / `no boot within 300 s` at `emulator-restart`: the host could not start the emulator (`journalctl -u svelte-qa-emulator`). `gave up waiting for ... after 5400 s` (10800 s on a dispatch): something else held the emulator that long (`fuser -v /run/svelte-qa/emulator.lock` on the host). `the session that holds ... ended`: an ssh lock was lost; only a machine that reaches the host over ssh sees this.
5. A `parity` failure after an intended visual change means the references moved: take them again on the emulator with `parity --update` (the references of the emulator are `qa/screenshots/android-api36-emulator-1080x2400-420dpi/`) and commit them.

**Re-running.** *Re-run failed jobs* on the run page repeats the lane for the same commit. A full run: *Run workflow* with the branch and inputs, or `gh workflow run native-qa.yml --ref <branch> -f repeat=10 -f warm=30 -f cold=30 -f smoke=true -f updates=false -f updates_channel=qa -f crashes=false` (a workflow can be dispatched once its file is on the default branch). The lane also runs from a terminal against the emulator, through the tunnel, under the same lock (`QA_ONLY=<kinds>`, for example `QA_ONLY=product`, builds, runs and judges only those stages):

```
export QA_DEVICE=localhost:5555 QA_MODE=push QA_REPEAT=3
bash qa/ci/lane.sh reset && bash qa/ci/lane.sh build
node qa/native-qa.ts hold --device "$QA_DEVICE" -- bash qa/ci/lane.sh emulator   # restarts the emulator through emulator.sh: on the host
bash qa/ci/lane.sh summary
```

(`emulator.sh` controls the systemd service on the host; from the PC run the lane with `QA_EMULATOR_SH=qa/ci/emulator-remote.sh`, which forwards to it over ssh.)

**Cost and time per push.** `unit` is 6 to 8 billable minutes of a GitHub-hosted Linux runner (none for a public repository, none with `QA_UNIT_RUNS_ON` on the OVH runner, where it then queues behind the lane of the push before). The lane is free in Actions minutes and costs the OVH host: the emulator (4 cores, 3 GB guest, qemu resident set 5 to 18 GB) and the build (8 cores, a 3 GB Gradle heap) for 45 to 60 minutes, with a first build on a new runner of 15 to 30 minutes (cold Gradle and NDK) and later builds of 2 to 6 minutes (two of them now, the QA app's and the product's: on a 16-core PC an incremental build of either took 25 to 30 s and one that switched `android/` to the other app 60 to 90 s; the OVH host has half the cores). The product boot check itself is about 30 s (install, a cold start, the 15 s window). Estimates from the run files of this emulator: lab 2.4 min a repeat, quick parity 17 min, quick a11y 11 min, gestures `both` 2 to 4 min, boot 30 + 30 16.5 min, full parity 33 min, full a11y 21 min, resilience 5 to 15 min. A push to green is about 55 to 70 minutes with `unit` in front; pushes queue on the one runner, so a burst of pushes costs one lane at a time and only the newest pending one is kept. Disk: the workspace (kept between runs so builds are incremental), Gradle's caches and the AVD take 20 to 30 GB of the host; an artifact is 20 to 100 MB. Cleanup is in `qa/ci/RUNBOOK.md`.

**Kotlin and C++ host checks in `unit`.** `run.sh` and the package tests that compile `tests/native/*Host.kt` need g++, a JDK and kotlinc, and the updates store's also an Android SDK `android.jar` and the `org.json` jar; without a tool they skip themselves, which is right on a laptop and wrong in CI. The job sets up Java 17 (`actions/setup-java`) and runs `qa/ci/host-tools.sh`, which downloads kotlinc 2.1.20 (the Kotlin the Android build compiles with) and the `org.json` 20250517 jar, each against a pinned sha256, into `~/.cache/native-qa-host-tools` (kept on a runner whose home survives, so downloaded once there), and puts kotlinc on `PATH` and the jar in `ORG_JSON_JAR`; `eval "$(bash qa/ci/host-tools.sh)"` does the same in a terminal. g++ and `android.jar` (`ANDROID_HOME`) come with the hosted image and, for `QA_UNIT_RUNS_ON` on the OVH runner, with `setup-runner.sh`. `packages/svelte-native/tests/native-tools.test.ts` fails under `CI=1` when any of them is missing, so a runner without kotlinc is a red job and not a green one that ran nothing.

**Files.** `qa/ci/lane.sh` (the stages), `qa/ci/host-tools.sh` (the unit job's kotlinc and jar), `qa/ci/emulator.sh` (restart, guard, watchdog, on the host) and `qa/ci/emulator-remote.sh` (the same over ssh), `qa/ci/setup-runner.sh` (installs everything on the host; `--dry-run`), `qa/ci/RUNBOOK.md`, `.github/actionlint.yaml` (the runner label, for `actionlint`). The lock is `qa/lib/lock.ts`; `gates --runs/--except/--markdown` are `qa/commands/gates.ts`.
