# native-qa

The Expo Svelte QA harness. It builds the QA app, runs the lab (49 functional checks plus the stress scenarios) and the boot runner on a device, merges what it measured into `report.json`, and judges that report against the production bar in `gates.json`. `gates` exits non-zero on any miss.

```
pnpm native-qa build  [--abi x86_64|arm64-v8a] [--prebuild] [--variant qa|smoke|production] [--updates-channel qa]
pnpm native-qa lab    --device <serial> [--apk <path> | --no-install] [--dexopt profile|none] [--repeat <n>] [--run checks,quick] [--timeout <s>]
pnpm native-qa boot   --device <serial> [--apk <path> | --no-install] [--dexopt profile|none] [--warm <n>] [--cold <n>] [--idle <s>]

pnpm native-qa symbolicate [--input <logcat file>] [--map <file>] [--symbols <dir>] [--abi x86_64] [--all]
```

Node 25 runs the TypeScript directly (`node qa/native-qa.ts`). Bun is only needed for the tests. Prerequisites for `build` are the Android SDK, JDK 17 and the repo's `pnpm install`; `lab` and `boot` need `adb` and `flock` (a machine that reaches the emulator through a tunnel also needs `ssh` to the host).

## Devices and locks

`--device` is required for `lab` and `boot`; nothing defaults to a phone or a Mac. Serials that reach the shared OVH emulator (`localhost:<port>`, `127.0.0.1:<port>`, `emulator-<n>`) make the command re-run itself under the emulator lock, so it waits while another agent or job holds the emulator. `build` always runs under `flock /tmp/svelte-qa-gradle.lock`. `updates` also takes the channel's lock for every device (it keeps two runs from publishing to one channel at once, and is taken after the emulator lock): a lock of the OVH host like the emulator's, `/run/svelte-qa/channel-<channel>.lock`, so a CI `updates` run on the host and a run from this PC on the same channel exclude each other (below). If the tunnel is down: `ssh -f -N -L 5555:127.0.0.1:5555 ovh-root && adb connect localhost:5555`.

**One lock for every machine that uses the OVH emulator.** The emulator is one device that this PC reaches through the tunnel and the OVH host's own CI runner reaches directly (`localhost:5555` on both), so a lock file on each machine would not exclude anyone. The lock file lives on the OVH host, `/run/svelte-qa/emulator.lock` (its own directory: `/tmp` is sticky and `fs.protected_regular` refuses a second user a file the first one created). On the host a command takes it with `flock`. On any other machine it takes the same file over `ssh <host> flock ...`: a held `ssh` session, one per command, that keeps the lock for as long as the command runs and that the host lets go of when the session ends or goes silent for 5 minutes (a heartbeat line every 30 s). If that session ends while the command runs, the lock is lost and the command is stopped (exit 1). Which host:

| Where | Setting | Lock |
| ----- | ------- | ---- |
| a machine with `ssh -L 5555:127.0.0.1:... <host>` listening on the port of the serial | nothing: found from `ss` and the ssh command line | `<host>:/run/svelte-qa/emulator.lock` |
| the OVH host (the directory `/run/svelte-qa` exists) | nothing | `/run/svelte-qa/emulator.lock` |
| any other machine with an emulator of its own | nothing | `/tmp/svelte-qa-emulator.lock` |
| anywhere, explicitly | `NATIVE_QA_LOCK_HOST=<ssh destination>` / `=local`, `NATIVE_QA_LOCK_FILE=<path>`, `NATIVE_QA_LOCK_WAIT=<seconds, default: until free>` | as set |

**One lock per EAS channel, on the same host.** A channel is one thing for every machine (two runs publishing to it would each find the other's updates at its head), so `updates` takes `/run/svelte-qa/channel-<channel>.lock` (`qa`, or `qa-<suffix>`) with the same machinery as the emulator lock, whichever device it runs on: a `flock` on the host, and over a held `ssh` session with a heartbeat from every other machine. If that session ends while the run goes, the lock is lost and the run is stopped. Which host, for the channel: `NATIVE_QA_LOCK_HOST=<ssh destination>` or `=local` as above; else the host of the `ssh -L 5555:...` tunnel to the emulator when one is up; else this machine when it is the OVH host (it has `/run/svelte-qa`); else `QA_EMULATOR_HOST`, `ovh-root` by default. A machine that cannot `ssh` to the host therefore stops at the lock with the destination it tried; `NATIVE_QA_LOCK_HOST=local` takes a lock on that machine instead (no exclusion of anyone else). Distinct channels do not exclude each other, which is what a run of its own channel (`--channel qa-<suffix>`) is for.

Worktrees that predate this change still take `/tmp/svelte-qa-emulator.lock` on the PC, and so does the PC-side `emu_watchdog.sh`: nothing makes them wait for a run that took the host's lock. Rebase them, and move the watchdog to the host (`qa/ci/RUNBOOK.md`, step 6).

`native-qa hold --device localhost:5555 [--wait <s>] -- <command...>` holds the lock across several harness calls (they see it as held and do not take it again): the CI lane runs under it, and so can an agent's own sequence of runs. `ssh ovh-root fuser -v /run/svelte-qa/emulator.lock` shows who holds it. The host's watchdog and the CI jobs take the same file ("CI", below).

## Dexopt

`adb install` leaves an app at dexopt `verify`: everything runs in ART's interpreter until the JIT warms it up, which is not what a store install ships. After every install the harness does what the store does — installs the APK's baseline profile (`am broadcast -a androidx.profileinstaller.action.INSTALL_PROFILE -n <package>/androidx.profileinstaller.ProfileInstallReceiver`) and compiles against it (`cmd package compile -m speed-profile -f`), printing the broadcast result (1 installed, 2 already there) and the resulting dexopt status. `--dexopt none` skips it to measure the verify-only state; `--no-install` never touches it. The profile itself comes from the expo-svelte Expo plugin (`baseline-prof.txt`: the engine and the updates module).

## Commands

**build** builds the QA app `io.example.svelteqa`, the app every command but `smoke` measures; `--variant smoke` builds the smoke app `io.example.svelteqa.smoke` instead (below, "Native module smoke test"). `--variant production` builds the product `io.example.sveltenative.qaproduct` for the product boot check (below, "product"); it is not an app any gate measures. It runs `expo-svelte sync`, runs `expo prebuild --platform android --no-install` when `apps/qa/android` is missing or older than `app.config.ts`, `package.json`, the expo-svelte Expo plugin or a module's `expo-module.config.json` (or with `--prebuild`), then `./gradlew :app:assembleRelease -PreactNativeArchitectures=<abi>` with the memory settings from the build recipe. The APK is copied to `qa/out/app-<abi>.apk` (the smoke app: `app-smoke-<abi>.apk`) and described in `qa/out/build-<abi>.json` (`build-smoke-<abi>.json`) (size, sha256, commit, whether the tree was dirty). Gradle output goes to `qa/out/build-<abi>.log` (`build-smoke-<abi>.log`). `APP_VARIANT` is set by the command, whatever the shell has. `android/` holds one variant at a time, and only a finished project counts: `android/.native-qa-variant` is written when a prebuild ends (a project without it is of unknown origin, never read as the QA app), `android.prebuilding` is there while one runs (a failed prebuild removes the half project, a killed one leaves the file and the next build removes it). Building the other variant renames `android/` to `android-<variant>/` and brings the other back, so the two keep their Gradle outputs and a failed prebuild of one never costs the other. The project is made again when any prebuild input is newer (`app.config.ts`, `package.json`, `react-native.config.js`, `qa/smoke-modules.json`, `qa/smoke-packages.cjs`, the fake Firebase file, the Svelte native plugin, the library's `expo-module.config.json` and the app's local modules). On the Mac, `build --platform ios` prebuilds with `--clean` when the variant differs from the one in `ios/.native-qa-variant` (or there is none). `UPDATES_CHANNEL` is always set for the build, empty by default, so a plain QA build has `checkAutomatically: NEVER` and measures the app without update checks whatever the calling shell exports. `--updates-channel qa` builds the QA app for the EAS Update channel `qa` (`checkAutomatically: ON_LOAD`, request header `expo-channel-name: qa`): the APK, its record, its log, its source map and its symbols go to `qa/out/channel-qa/`, so the plain build is never replaced; `android/` is regenerated when the channel it was generated for (recorded in `android/.native-qa-updates-channel`, inside the project, so it is parked with it) differs from the build's. Only `qa` and `qa-<suffix>` are accepted: the harness never builds for or publishes to `preview` or `production`. A channel build is always the QA app: `--updates-channel` with `--variant smoke` is refused. After Gradle the build reads the release `AndroidManifest.xml` Gradle merged (`lib/manifest.ts`) and fails unless the update settings it carries are the ones asked for, in both directions (a plain build must not check for updates, a channel build must check on that channel).

**lab** installs the APK (`--apk`, else `qa/out/app-<abi>.apk` for the device's ABI if present, else the app already installed is measured as it is; `--no-install` never installs), then repeats `--repeat` times: force-stop, clear logcat, open `example-svelte:///__dev?run=checks,quick`, follow logcat until the lab logs `[Svelte stress] complete` (or `--timeout` seconds pass), force-stop. The full logcat of each run is kept in `qa/runs/lab-<device>-<stamp>-<n>.log`; the parsed run goes to `qa/runs/lab-<device>-<stamp>.json`. A lab that hangs or crashes is recorded as incomplete, not as an error of the tool. So is a lab another app interrupted: once the package has started, the first `ActivityTaskManager: START ... cmp=<other package>/<class>`, `WindowManagerShell: Transition requested ... type = OPEN` naming another package's component, or `Displayed <other package>/<class>` line (an emergency cell-broadcast alert, a permission dialog, a call) is recorded as `interrupted: { at, by }` on the run (`at` is the device clock as logcat prints it, `by` the component) and the run stays `complete: false` even if the lab's last line came; `report` counts it in `lab.interruptedRuns` and names it under the lab line. `--run` also takes single scenarios (`list-300-virtual`, `churn-animated`, ...). The lab file records the `--run` it was started with (`run`), and `gates.json` pins the scenarios the full `checks,quick` run produces (`scenarios`, per platform): `report` computes `lab.scenarios.missing`, the pinned scenarios some run of the file lacks, and the gate on it is `<= 0`, so `lab --run checks,list-300-virtual --repeat 10` reads as the partial run it is. The frame gates see every pinned scenario too (a missing one is `not measured`), and `report` lists the missing names under the device's lab line. Two scenarios outside `quick` are for work on the windowed list: `list-mount-loop` mounts the 300-row `List` 40 times in one run (median, minimum and first mounts in its summary; the loop for a CPU profile of the mount) and `list-300-virtual-profile` is the gate's scenario with the host timing every flush (`detail.flushes`: start, duration, nodes created, payload, `createNode`, `appendChild` and `completeRoot` milliseconds).

**boot** installs the same way and then measures `--warm` warm and `--cold` cold launches (30 each by default, the production sample size). Per launch it clears logcat, runs `am start -W -n <package>/.MainActivity`, waits for `Displayed` and the `[Svelte boot]` line, and parses logcat. A launch whose `Start proc` to `Displayed` pair is missing from logcat while the app process is alive (`pidof`) and the log shows no crash is launched once more at once, in the same slot: the second launch replaces it and carries `attempts: 2` (`boot.<kind>.retried` counts them, and `report` prints it); a second miss is the failure it always was (`error`, counted in `boot.<kind>.failed`), and a launch that crashed or whose process is gone is never retried. Results go to `qa/runs/boot-<device>-<stamp>.json` and a filtered log (`Start proc`, `Displayed`, `Running "main"`, `[Svelte boot]`, engine lines, faults) to `qa/runs/boot-<device>-<stamp>.log`.

**smoke** is the native module smoke test (SPEC.md, "Native modules (smoke test)"). It runs in the smoke app, which links the production app's native libraries; the QA app does not, so every gate keeps measuring an app with the product's native modules. The four packages `expo-svelte` itself carries (vendored: react-native-quick-crypto and react-native-quick-base64, which the device's `crypto` is made of, and react-native-mmkv and react-native-nitro-modules, which `localStorage` is made of) are not among "the libraries" in this sense: they are `shared` in `qa/smoke-modules.json`, so every app links and bundles the real ones, and the smoke test still checks them. The vendored four are no app's dependency, the smoke app's included (it does not install them as stand-ins: `packages` is empty for their modules in `qa/smoke-modules.json`, and the smoke checks `require` the library's copies by name, which Metro resolves to them); the production app's quick-crypto plugin with `sodiumEnabled: true` is the library plugin's `sodiumEnabled` option, on in the smoke variant. `smoke` installs `qa/out/app-smoke-<abi>.apk` like `lab` installs the QA one, force-stops `io.example.svelteqa.smoke`, clears logcat, opens `example-svelte-smoke:///__dev?run=smoke`, follows logcat until the lab logs `[Svelte stress] complete` (or `--timeout` seconds, default 180, pass), force-stops the app, and keeps the log in `qa/runs/smoke-<device>-<stamp>.log`. The parsed run goes to `qa/runs/smoke-<device>-<stamp>.json`, a run kind of its own: one entry per `[Svelte smoke] <module> ok|fail|skip path=… ms=… <detail>` line (the last line of a module wins), the `[Svelte smoke] complete` counts, crashes and JavaScript errors, and whether the run completed (the lab's last line and the app's own came, nothing crashed or took the screen). It prints every failure, skip and missing module. `--platform ios` launches the same URL with a token and reads `Documents/smoke-results.json` through the Mac, like `lab` (the iOS smoke build, `build --platform ios --variant smoke`, needs its own Terminal script on the Mac, `--build-script`). Nothing prompts and nothing touches the network; the scenario is not part of `checks,quick`, so the pinned lab scenarios are unchanged.

**product** (Android) is the product boot check. The example's production variant (`io.example.sveltenative.qaproduct`, `APP_VARIANT=production`) has no development lab: Metro resolves everything in `src/lib/native/dev/` and `src/routes/__dev/` to a stub that throws on any property read and on a call, so a use of the lab in shared code that is not behind `nativeLabEnabled` passes every gate of the QA app (which has the lab) and crashes the production variant's root layout. Nothing else starts the production variant, so this does. `build --variant production --abi x86_64` makes it (`qa/out/app-production-<abi>.apk`, `build-production-<abi>.json`; the Maps key a product takes from the environment is a placeholder, `android/` is parked and brought back like the smoke app's; `--updates-channel` is refused, and so is `--platform ios`: what ships is built by EAS). `product --device localhost:5555` installs it, clears its data (so it starts with no stored state), starts it cold and, for 15 s from the start, polls the accessibility tree of its window for the home screen (its title or its description, `home.title` and `home.description` of `src/lib/native/messages.ts`, in either language) while logcat collects what the app does. It passes when the screen came within the 15 s and logcat shows no JavaScript fatal (`handleHostException`, `FATAL EXCEPTION`) and no native crash (a fatal signal, an ANR, a debuggerd report) of the app and its process was still there at the end (a process that was gone is a fatal). The window is held to its end even when the screen came early. It writes `qa/runs/product-<device>-<stamp>.json` (the run kind `product`; the logcat beside it as `.log`) and exits 1 when it fails. Gates `product.boot.fatals` (at most 0) and `product.boot.firstScreen` (at least 1, within 15 s whatever window the run had); the OVH emulator provides the run, no phone does, so both are informational for the phones. `js errors` (`E ReactNativeJS` lines) are recorded and not judged. **It refuses any phone-role device**: by its serial, from `gates.json`, before the first adb command (the Samsung phone is not even asked for its properties), and again by what the device reports about itself (it must say it is an emulator and `gates.json` must list it as the lab), so `io.example.sveltenative.qaproduct` is never installed, started or cleared on a phone (`lib/reset.ts`, `refusePhone` and `assertProductDevice`). It takes the emulator lock like every command on that serial. The CI lane runs it on every push and dispatch, after the stages of the QA app ("CI"): `lane.sh build` makes the product too (`build --abi x86_64 --variant production`), and a product that does not boot fails the lane.

**updates** (Android) runs the over-the-air update scenario against the `qa` channel with the build from `build --updates-channel qa` (`--apk`, else `qa/out/channel-qa/app-<abi>.apk`, whose record must say the build is for that channel). The scenario, its evidence rules and the reset are described in `packages/expo-svelte/native/svelte-core/SPEC.md`, "End to end on a QA channel"; in short:

0. *Preflight.* The device is identified from its own properties; `eas whoami` and `eas channel:view qa --json` must pass (the channel must map to exactly one branch, named `qa`); the run takes the channel's lock (`/run/svelte-qa/channel-qa.lock` on the OVH host, over ssh from any other machine; every device, "Devices and locks") as well as the emulator lock. eas-cli is `npx -y eas-cli@27.2.0` (`eas.json` asks for 24.14 or newer, which the `eas` of some machines is not; `--eas` or `NATIVE_QA_EAS` replaces the command), runs in `apps/qa` as the logged-in EAS user (or `EXPO_TOKEN`) with a short list of environment variables, and everything it prints is redacted before it reaches the log or the run file, which records only the program's name and version. `--environment` (default `development`, an EAS environment with no variables) is the one SDK 55 and later `eas update` requires.
1. Installs the plain QA build (`--baseline-apk`, else `qa/out/app-<abi>.apk`; `--no-baseline` skips it) and measures `--warm` (30) warm launches.
2. Installs the channel build (`adb install -r`), resets its update state, publishes a known-good starting update (so a stale or bad head left by an earlier run is not what the run measures), cold-starts it (the embedded bundle must run and the probe must say the build checks on a channel) and starts again until the starting update runs with its marker.
3. Publishes a marked update and cold-starts (force-stop, start, read that launch's logcat until its check ended) until the app reports that update id with the marker of the published bundle, counting the launches.
4. For each fault `boot`, `mount`, `effect` (`--faults`): publishes an update that fails that way and cold-starts until it runs, starts once more (the failed id must be reported, the app must boot and run the previous update or the embedded bundle), then `--settle` (at least 1, default 3) more times (none may run or download the bad update, and every one of those launches must be read to its end and show the client refusing it).
5. Publishes a good clean-up update right after the last bad one and starts until it runs, so the channel ends healthy, also when an earlier step failed (every publish is an attempt, parsed or not; SIGINT and SIGTERM publish it too).
6. Measures `--warm` warm launches of the channel build on the healthy channel and compares them with step 1.
7. Restores the device: removes the reset setting if it is still there and installs the plain QA build over the channel build (`deviceState.finalBuild`; without a plain build to put back, the run says so loudly and the report notes it).

The reset (`--reset`) is by default the app's own: the harness puts a token in the global setting `svelte_qa_reset_updates` (`adb shell settings put global`) and the first start of the QA app that sees a token it has not honoured deletes its updates directory and failed list before it picks a bundle (`QaReset.kt`, `UpdateStore.reset`; honoured only in `io.example.svelteqa`, and read only when the store holds something to forget; logged as `QA reset (<token>): forgot N update(s)`). The harness deletes the setting as soon as the first launch has run, not at the end of the run. `--reset data` runs `pm clear` instead. **A device is cleared or uninstalled only if it positively says it is an emulator (`ro.kernel.qemu` or `ro.boot.qemu` is 1) and `gates.json` lists it as the lab; a `phone` is never cleared**, whichever serial adb reaches it by (`ro.serialno` is looked up in `gates.json` as well): `lib/reset.ts` is the only code that can emit `pm clear`, and `test/reset.test.ts` fails if any other source of the harness mentions `pm clear` or an uninstall. A phone takes `adb install -r` and the app-level reset only.

A launch is read until the check the client logs after the first commit has ended (a download included), or a moment after a bundle logged a fatal and its host died before the check, or 90 s. `--max-launches` (4) bounds the starts any step may take, and must be at least 2: one start downloads an update, the next runs it. Each publish takes about a minute (`expo export` plus the upload), so a run takes about 20 to 30 minutes with 30 warm launches per series. The run records the device's boot id after the install and compares it before every launch and at the end: a restart under the run (the emulator's watchdog, a host crash) cuts off a download in flight and can leave files written moments before with no data, so the run file lists it in `scenario.errors` (`the device restarted before launch N`) and the launches after it are not to be read as the updates' own result (2 November: the watchdog killed the emulator two seconds after the starting update was downloaded, and the run's every later check failed on an asset of 0 bytes; the store now syncs a download before naming it and downloads again a file in place that does not hash to the manifest's). Results go to `qa/runs/updates-<device>-<stamp>.json` and the filtered logcat of every launch, with the redacted `eas` output, to `qa/runs/updates-<device>-<stamp>.log`. The scenario is in `lib/updates.ts` over a driver, which `commands/updates.ts` implements with adb and eas-cli and `test/updates-scenario.test.ts` implements as a model of the client's policy.

**report** takes the newest lab run and the newest boot run of each device, computes the flat metrics, evaluates every gate and writes `qa/report.json`. It prints a per-device summary and the gate table. It warns when the runs of a device (lab, boot, soak, crashes, parity, a11y, resilience) measured different builds (the updates run is left out of that comparison: it installs the channel build, a different APK by design), or when one cannot say which build it measured. The warning is about the artifact, not the commit: runs of one device must share the installed identity, and runs of one artifact started at different source commits (harness-only commits land between the runs of one campaign) are a `note:` that names each run's commit, not a warning. A build is identified by the sha256 of the installed `base.apk` on Android and by what the app itself reported on iOS (the digests of `main.jsbundle` and of the executable, "iOS" below); a run with no identity is a warning (`build identity not reported`), not a skip. A run that `carried` in `gates.json` names, with the build it measured, is left out of that comparison and listed instead ("Carried runs" below). For each device that has an accessibility run it prints one line per screen: the reach percentage (reachable of the interactive elements), `clipped`, the elements modelled from UIKit's state on iOS, and `tree not settled` for an Android dump that was not stable.

**gates** evaluates `gates.json` against the metrics in `report.json` (so editing a bar needs no new measurement) in one of two lanes: without `--smoke` every gate but `smoke.*` (the QA app), with `--smoke` only `smoke.failed` and `smoke.missing` (the smoke app, which no other gate sees). It prints the table (wildcard gates collapsed to their worst value; `--all` prints every row), then the documented exceptions it holds ("Documented exceptions" below) and the summary `N gates pass, N exception, N fail, N not measured`, and exits 1 unless every row passed or is a documented exception: only a failure or a gate nobody measured sets a non-zero status. `--platform android` judges only the Android bars, which is what the emulator lane does. A gate nobody measured is `not measured`, and `not measured` fails. `gates` also fails, with the reason printed first (`FAIL: ...`, before the table), when the report is not the current picture: a run file of a device of the judged platform under `qa/runs` (in the smoke lane, a smoke run file) was written after the report's `generatedAt` (run `report` again), or the report carries warnings for the judged platform (runs of different builds, runs that did not identify their build; the smoke run is another app, so it is not compared with them). It prints the report's `generatedAt` and its age. Without `--platform` every device and every warning counts. A lane that ran only some run kinds judges those: `--runs lab,parity,a11y,gestures` limits the kinds every device provides to the listed ones, so the gates of the others (the soak, the crash volume, ...) are `informational` instead of `not measured`; `--except lab.runs` leaves the named gates out the same way, for a gate whose bar is a sample size the lane ran smaller (the CI push lane's 3 lab repeats against the production 10); a gate id that does not exist is an error. `--markdown <file>` also writes the table as GitHub Markdown (failures first, passes and informational rows folded), which the CI job summary shows.

**gestures** runs the lab's `gestures-*` stress scenarios with touches injected into them and judges the counters the recognisers report, see "Gestures" below. It writes `qa/runs/gestures-<device>-<stamp>.json` (one launch of the lab per way of driving and repeat, with its logcat in `gestures-<device>-<stamp>-<input>-<n>.log`), which `report` merges and the `gestures.*` gates judge.

## Boot definitions

Both are processes started from nothing: `am force-stop` kills the app first, so `Start proc` is always in the log. The distance of each from a real first launch after install or reboot is stated, not hidden.

- **warm**: `am force-stop`, a 1.5 s pause, `am start`. The previous launch ran seconds earlier, so the page cache and the dex and oat files are hot.
- **cold**: Settings is brought to the front, the app is killed with `am force-stop`, the device idles `--idle` seconds (default 20), then the app is launched. Nothing is cleared (a `pm clear` would also delete the session and make every launch a first-run launch), and a stock emulator or phone cannot drop the page cache, so this is a process-cold, idle-gap launch, not a power-cycle launch. It captures what a user sees after the app has been out of the foreground and swapped out for a while.

The number gated is `Displayed` minus `Start proc`, both timestamps from the activity manager's lines in `logcat -v threadtime`, so it contains the zygote fork, the native host and the JavaScript. `am start -W` `TotalTime`, the system's own `Displayed ... +NNNms`, `Start proc` to `Running "main"` and the `[Svelte boot]` JavaScript total are recorded next to it (`boot.<kind>.totalTime.p90`, `.runningMain.p90`, `.jsTotal.p90`). p90 is nearest rank: with 30 samples it is the 27th smallest.

On a phone with a little/big core split (the Samsung A16: two big cores) the launch is sensitive to which cores the start-up threads get: `am start -W` runs a JVM that holds a big core for 200 to 460 ms of the launch, and `system_server`'s garbage collector takes the other one in about one launch in four. The app pins its start-up threads to the big cores until the first mount (`BootBoost`, SPEC "Boot on the phone"), so a collector run costs a few milliseconds instead of doubling the JavaScript time. `cmd activity start-activity -W` has no JVM; 30 interleaved pairs against `am start -W` showed the same distribution, so the harness keeps `am`.

`gates.json` is the production bar of `packages/expo-svelte/PLAN.md`:

```json
{
	"id": "boot.warm.p90",
	"title": "Warm boot p90, Start proc to Displayed",
	"unit": "ms",
	"metric": "boot.warm.p90",
	"bar": { "android": { "max": 350 }, "ios": { "max": 250 } }
}
```

`bar` maps a platform to `max`, `min` or both, or to `equals` (a text: the gate on `crashes.run` is `== "checks,quick"`, and a metric that is a text only meets an `equals` bar), with an optional `round` (decimals the measured value is rounded to before comparing; a percentage gate would use 1, so 0.04 % reads as the lab prints it, 0.0 %; the frame gates now count late intervals instead, see "The frames rule"). A gate is judged for every device of each platform it names (and, with `roles`, of the roles it lists: see "Device roles"). A platform with no device in the report and a metric a device never produced are `not measured`, which fails. `*` in `metric` matches one name segment and yields one row per match (`frames.*.lateIntervals` is one row per scenario).

**The frames rule (D9, 3 Nov 2026).** On the phones a scenario passes `frames.droppedPct` and `frames.maxPeriodRatio` when every run has at most one late interval, an interval longer than 1.5 frame periods (the lab's own `dropped`: single OS-side stalls, the A16 drops one interval in idle in 9 runs of 10), instead of a strict 0.0 %; it still passes `frames.maxMs` only when no frame is over 33 ms. Both gates read `frames.<scenario>.lateIntervals` with the bar `max: 1`, so the period gate is judged the way the dropped-frame gate is (the longest frame over the period is shown beside it, and a frame over 33 ms is `frames.maxMs`'s). The gestures gates (`gestures.frames.*`) take the same rule per launch. The lab role keeps its rules: the frame gates are `phone` only, so the OVH emulator's rows stay `informational`. The count comes from the run record, not from a rounded percentage: a lab scenario line holds `count` (every interval of the window) and `droppedPct`, which the lab writes as `100 * dropped / count` in full double precision and the run file keeps unrounded, so `lateIntervals` is `droppedPct * count / 100` rounded to the whole number it must be (`lateIntervals()` in `parse/logcat.ts`). A record whose percentage no whole count reproduces (a figure rounded to a tenth, an empty window) gives `null`, which is `not measured` and fails: a count is never guessed. The worst run (launch) is what the metric holds, as for every frame metric; D10 below changes which run the lab's frame gates judge. The row reads `3 (churn-animated), 3.7 %`: the late intervals of the worst scenario and, beside it, the gate's `also` figure (`"also": {"metric": "frames.*.droppedPct", "unit": "%"}`, the same scenario's dropped share), which is shown and never judged.

**All but one run of ten (D10, 3 Nov 2026).** The lab frame gates (`frames.droppedPct`, `frames.maxPeriodRatio`, `frames.maxMs`) are judged on the phones with an allowance: a scenario passes when all but one of its runs meet the D9 rule, so the one worst run is set aside and the gate is judged on the worst of the other nine, and a second bad run fails the scenario. A bad run has more late intervals than `frames.droppedPct`'s bar allows or a longer frame than `frames.maxMs`'s (the bars of `gates.json`, not constants of the code); the run set aside is the one that overshoots most (late intervals and time over the bar together). The allowance is `allowance` on the three gates (`runs`: `frames.*.runs`, `min`: 10, `late` and `long`: the gates whose bars define a bad run). A lab with fewer than 10 runs, or one whose run list is missing or has a run without an exact late count, gets no allowance and the worst run is judged. The set-aside run is never hidden: the grouped table prints `worst run: 20 late, 38 ms, run 2` beside the judged value, the row's `worstRun` is in `report.json`, and the console and the Markdown summary list every set-aside run with what the other runs gave (the list is not a pass or a failure of its own). The dropped share and the ratio shown beside a judged value are those of the judged run. Exceptions and their caps apply to the judged value: `churn-animated` and `header-8` (D1) are judged on their other runs and are exceptions there; a capped entry covers the judged value only up to its cap. `lab.scenarios.failed` stays consistent: a scenario that passes the frame gates is not counted in the one run D10 set aside (nor, as for exceptions, in any run when it has an exception row), and every other failure counts. The allowance is for the lab frame gates only: `gestures.frames.*` (3 launches) keep the D9 rule per launch, strictly, and the OVH emulator's frame rows stay informational.

**Documented exceptions.** `exceptions` in `gates.json` lists the misses a decision accepts. An entry is `{ gate, device, scenarios?, maxLateIntervals?, maxMs?, decision, reason, evidence }`: the gate id; the device it is for (a key of `devices`, so the scope is "Samsung A16", "iPhone SE 3" or the lab by name); for a gate with a row per scenario (`*` in its metric) the scenarios it covers (a gate without scenarios is its own scenario: `boot.warm.p90`, `list.virtual300.mountMs`); the decision (`D1`: a platform floor, `D9`: the round-2 evidence of 3 Nov, `D11`: the Samsung's `list-300-raw` and two lists, `D18`: the Samsung's `churn-static` and `input-120` on the final build, `1 Nov first touch`); a one-line reason; and where the evidence is (a `SPEC.md` section or a run file). A row that misses its bar and is covered by an entry (same gate, same device, same scenario) is judged `exception`, not `pass` and not `fail`; the table shows its measured value and the decision (`exception (D1)`), `gates` lists each covered row with value, bar, decision, reason and evidence, and the Markdown summary has a table of them. Summaries count pass, exception, fail and not measured apart (`70 gates pass, 5 exception, 3 fail, 0 not measured`; a gate line with a failing scenario and an excused one reads `fail 9/17 (+3 exception)`). Only a miss is excepted: a gate that passes stays `pass`, one that was not measured stays `not measured`, and nothing is excused outside the named device and scenarios, so the same scenario on another device, another scenario of the same device, and every gate of the lab's role still fail or stay `informational`. A malformed entry is an error when the file is read, not a wider exemption: an unknown decision, gate or device, a device the gate does not judge, a per-scenario gate without its scenarios (or a plain gate with them), an empty reason or evidence pointer, and two entries for one row. `report.json` records the entry on each row it covers. Today: D1 for the iPhone's `header-8` and the Samsung's `churn-animated` (the three frame gates each: UIKit's bar re-layout, Reanimated's worklet runtime on the UI thread); D9 for the Samsung's `list.virtual300.mountMs`, `boot.warm.p90`, `boot.cold.p90` and the dropped-frame and period gates of `animation-48`, `animation-48-square` and `animation-48-translate` (the first interval, capped at 2 late intervals; its 19 to 27 ms is inside the 33 ms bar, so `frames.maxMs` has no exception there); D11 for the Samsung's `list-300-raw` (capped at 4 late intervals; `churn-static` was here until 11 November) and, since 9 November, `list-300` and `list-300-clipped` (capped at 2), all with a 23 ms frame cap (repeated short late intervals on its 90 Hz display; the evidence is SPEC.md, "The Samsung's frame spread under D10 and D11"), on the dropped-frame and period gates; D18 (11 Nov 2026) for the Samsung's `churn-static` (capped at 6 late intervals) and `input-120` (capped at 2), 23 ms, on the same two gates: noise late in a long session on the final build, which an interleaved A/B of `churn-static` against 0.3.0 showed was not the build's (GOAL.md D18); `1 Nov first touch` for the Samsung's `box` gesture frames (RNGH's first worklet run and class initialisation). **Caps.** An entry may be capped to what its decision observed: `maxLateIntervals` (for a gate that reads `*.lateIntervals`) and `maxMs` (for one that reads `*.maxMs`) are the largest worst-run value it covers, inclusive. A row above the cap, or without a value, is not covered and fails; the lists show the cap (`D9 (up to 2 late intervals)`). The D9 entries of the `animation-48` family carry `maxLateIntervals: 2`, the first interval plus the one late interval every scenario is allowed, so a window with 20 late intervals is a failure. The D1 floors (UIKit's bar, Reanimated's runtime) and the first touch carry no cap. `maxMs` has two uses: on a gate that reads `*.maxMs` it caps that gate's value, and on a gate that reads `*.lateIntervals` it is a condition, the scenario's longest frame (as the row is judged, so after D10 sets its run aside) must be known and within it too; the D11 entries use it, so a 4-late-interval window with a 21 ms frame is not covered. A cap under the gate's own bar would cover nothing, which is why `frames.maxMs` has no entry for `animation-48`, `churn-static` or `list-300-raw` (their frames are inside the 33 ms bar, and the 20 ms limit is on the late-interval entries). All caps are judged values: D10's set-aside run is not held to them, the next worst run is.

**Carried runs (D14, 8 Nov 2026).** After a fix only the suites its diff can affect run again on the new build; the others carry their result from the build that measured them. `carried` in `gates.json` lists them: an entry is `{ device, runs, build, commit, decision, reason }`, the device (a key of `devices`), the runs carried (the labels of the report's build comparison: `lab`, `boot`, `soak`, `crash`, `parity`, `accessibility`, `resilience`, `gestures`, `foreign`), the build they measured as the report prints its key (`sha256 <12 hex>` for an APK, `main.jsbundle <12 hex>, CDHash <12 hex>` for an iOS app), the commit it was built from, `D14`, and why the result stands for the final source (what the diff from that commit changes, and why those runs cannot see it or which runs on the final build measured it instead). A run an entry names is carried only while it measured that build: it is left out of the one-build check and the report notes it with its build, commit and reason. A run of another build is compared as usual, with a note that the entry no longer describes it, so an entry cannot hide a run. The runs that are not carried must still agree on one build. `report.json` records `measuredBuilds` per device (each run's build key, commit and carry), `gates` prints a `carried (D14): ...` line per carried run, and `gates --markdown` ends with a "Builds measured" table per device. A malformed entry is an error when the file is read: another decision, an unknown device or run label, a run carried twice, a build that is not a build key, a commit that is not a hash, an empty reason. The check is made by `report`, so `report.json` records the entries it applied, and `gates` fails when gates.json's `carried` differ from them (run `report` again); the carried groups name the commit an entry declares, not the harness commit a run was taken at.

**`lab.scenarios.failed`** counts the scenarios the lab itself marked `fail`, and leaves out the ones whose frame misses are all covered by exceptions on that device: its `excusing` entry names the three frame gates and `lab.scenarios.failedRuns`. A scenario is left out when the lab's own frame criterion failed it (`smooth` false), at least one of its rows on those gates is an `exception`, and none is a failure or a gap. The rest counts as before (the worst run's failures that are not frame failures plus its frame failures that are not covered), the raw count shows beside it when they differ (`0, 2 before exceptions`), and a run list the report cannot give leaves the raw count.

**Device roles.** `gates.json` also maps each serial to a role and a name (`devices`: `R58Y90KNGRP` is the phone "Samsung A16", the iPhone `E74A5608-...` the phone "iPhone SE 3", `localhost:5555` the lab "OVH emulator, software GL"). A `phone` is real hardware: its frame, boot and list timings are the production numbers. A `lab` is a device that exists for the engine checks, crash volume, soak, parity pixels, accessibility and resilience; the OVH emulator renders under software GL (`swiftshader_indirect`), so its animated scenarios drop 10 to 30 % of their frames and its boot takes 700 to 900 ms whatever the build does, and those timings say nothing about production. A gate may carry `roles` (`["phone"]`); without it the gate judges every role. For a device whose role a gate leaves out the gate is still evaluated and printed, with the verdict `informational`: the value shows, and the row is not a pass, a failure or `not measured`, so no summary line counts it (`gates` prints `N informational, not counted`, and one line per device with its own counts). A serial the table does not list has no role and gets every gate: nothing is exempted by omission. `report.json` records each device's `role` and `name`; `gates` reads the roles from `gates.json` as it is now, so changing one needs no new measurement. A role that is not `phone` or `lab`, or an empty `roles` list, is an error when the file is read.

| `list.virtual300.mountMs` | phone | lab | a mount-to-layout time is CPU and GL bound |
| `lab.scenarios.failed` | phone | lab | the lab marks a scenario failed on its own frame and time limits, which the emulator's software GL breaks |
| `checks.*`, `lab.runs`, `lab.incomplete`, `lab.scenarios.missing` | phone and lab | lab | counts and bugs, not speed |
| `log.*` | phone and lab | lab or boot | fatals and engine warnings are as true on the emulator as on a phone |
| `memory.*`, `soak.*` | phone and lab | soak | heap growth, leaked views and dead-tag writes are measured honestly on the emulator; a device that runs no soak shows them informational |
| `crashes.*` | phone and lab | crashes | crash volume runs on the emulator |
| `parity.*`, `a11y.*`, `resilience.*` | phone and lab | parity, a11y, resilience | pixels, accessibility and resilience do not depend on speed |
| `smoke.complete`, `smoke.fatals`, `smoke.failed`, `smoke.missing`, `smoke.unexpectedSkips`, `smoke.ok` | phone and lab | smoke | a native library either answers its call or it does not, and a run that crashed or never finished answers nothing; judged by `gates --smoke` only |
| `gestures.frames.{droppedPct,maxPeriodRatio,maxMs}` | phone | gestures | frame times of a gesture-driven animation depend on the GPU (the bars are `frames.*`'s: at most one late interval per launch, no frame over 33 ms) |
| `gestures.checks`, `gestures.churn.leaked`, `gestures.agreement`, `gestures.{launches,incomplete,scenarios.missing,fatals,engineWarnings,harnessErrors}` | phone and lab | gestures | counters, rests, scroll offsets, leaks and agreement are bugs, not speed |
| `foreign.<library>.{failedChecks,checks,skipped}`, `foreign.{libraries.missing,unparsedLines,leftovers,launches,incomplete,fatals,engineWarnings}` | phone and lab | foreign | a native view either mounts, updates, answers and draws what a prop says or it does not, and every check of it ran (a minimum count, none skipped, no log line unreadable); both platforms, with the iPhone's own counts (`bar.ios`, and `foreign.ios` in `gates.json` says why each differs from Android) |

**Run kinds.** A device is also judged only on the run kinds it is meant to provide: `devices[serial].runs` lists them (`lab`, `boot`, `soak`, `crashes`, `parity`, `a11y`, `resilience`, `smoke`, `gestures`, `foreign`, `updates`, `product`). The Samsung A16 provides `["lab", "boot", "smoke", "gestures", "foreign"]` (no `updates` run yet: it has not been run on the phone), the iPhone SE 3 `["lab", "boot", "parity", "a11y", "resilience", "smoke", "gestures", "foreign"]` (its `log.crashReports` is summed from the lab, boot, parity, a11y, resilience, gestures and foreign pulls, so it is judged; until its first `resilience --platform ios` run the three `resilience.*` gates read `not measured`), the OVH emulator `["lab", "soak", "crashes", "parity", "a11y", "resilience", "smoke", "gestures", "foreign", "updates", "product"]` (its boot and frame gates are informational through its role; no phone provides `product`). A gate belongs to the kind its metric prefix names: `lab.*`, `checks.*`, `frames.*`, `list.*` to `lab`; `boot.*` to `boot`; `log.*` to `lab` and `boot` (judged when the device provides either); `memory.*` and `soak.*` to `soak`; `crashes.*`, `parity.*`, `a11y.*`, `resilience.*`, `smoke.*`, `gestures.*`, `foreign.*`, `updates.*`, `product.*` to their own kind (the `updates.*` gates name Android only: `applied`, `rolledBack` and `channelHealthy` at least 1, `badRetried` and `unexpectedFaults` at most 0; the OVH emulator provides the run, and a device that should be judged on it gets `updates` in its `runs`); any other metric to every kind. A gate of a kind the device does not provide is `informational`, exactly like a role mismatch: the value (or `-`) shows and nothing counts. A gate of a kind the device does provide that has no measurement is still `not measured`, which fails: the list says what must be run, not what may be skipped. A serial `gates.json` does not list provides every kind. An unknown kind or an empty `runs` list is an error when the file is read; `report.json` records each device's `runs`.

## Soak and crashes

PLAN.md step 8: the heap, the views and the crash count over time. Three commands, one run-file kind each, merged by `report` like the lab and the boot run (the newest `soak-*.json` and `crashes-*.json` of each device).

```
pnpm native-qa soak    --device localhost:5555 --apk qa/out/app-x86_64.apk [--minutes 10] [--interval 5] [--parts churn,nav]
pnpm native-qa crashes --device localhost:5555 --apk qa/out/app-x86_64.apk [--starts 1000] [--suites 100] [--idle 2] [--chunk 100] [--resume] [--inject-crash --suites 0]
pnpm native-qa symbolicate --input qa/runs/crashes-localhost_5555-<stamp>.log [--all]
```

Both runners take the same lock as `lab` and `boot` for their whole run, install the APK the same way (`--apk`, `--no-install`, `--dexopt`) and accept `--package`.

### soak

`native-qa soak` opens the lab as `example-svelte:///__dev?run=soak-mix-<seconds>s`. Its `soak-mix` scenario (`src/lib/native/dev/Stress.svelte`) repeats one cycle until the requested time is up (the first two cycles are the warm-up and count in it):

1. 6 s of animated churn (32 Reanimated tiles replaced every 250 ms, the cleanup check of `churn-60s`),
2. two push/pop of a 60-row screen,
3. two modal open/close,
4. one sheet open/close,
5. two native-header screens pushed and popped,
6. a 300-row windowed list mounted, scrolled to the end and back, unmounted,
7. three tab switches.

About 28 s per cycle on the emulator. After the second cycle and after the last one everything is unmounted and the app idles for about 8 s: that is the **baseline** and the **final** window, three samples each. Before every sample of a window the lab collects all three heaps that can hold garbage: this runtime (`gc()`; this Hermes build exposes it, and without it the lab records `collected: null` and no JS growth is derived), the Java heap (`SvelteEngine.collectJava()`: a dead view, text layout or render node holds native memory until its Java object is collected, so a window should not depend on when ART last ran; with the 26 October leak present the same build measured +3.1 % and +3.6 % without it and +8.4 %, +8.4 %, +6.1 % with it) and the worklet (UI) runtime's own Hermes heap (`gc()` on the UI thread). In between, every 5 s, a `[Svelte soak]` line carries the same numbers without a collection, and every two minutes of soak time (after a cycle) the lab takes a **checkpoint**: the same idle window as the baseline, three samples. The floors of the windows over time say whether a growth keeps rising (a leak) or levels off (allocator, caches): `memory.native.slopeKbPerMin`.

Three sources are read:

| Source | What | Where it comes from |
| --- | --- | --- |
| lab, JS heap | `allocated`, `heapSize`, `malloc`, `va`, `gcs` of this runtime (`heap`) and of the worklet runtime (`ui`: `allocated` after its collection, `uiBefore`: without) | `HermesInternal.getInstrumentedStats()`, logged by the lab as `[Svelte soak]` |
| lab, engine | `alive` (engine views mounted under a React tag), `pooled`, `held`, `created`, `deleted`, the animated-write classes `lateWrites`, `staleWrites`, `replayedWrites`, `expiredWrites`, `overflowWrites`, `earlyPending`, and the sizes of the C++ delegate's tables `emitters` and `scrollStates` | `SvelteEngine.stats()` (`MountingManager.stats()`, SPEC "Stats for the soak runner") |
| host, process | Native Heap Pss / Heap Alloc / Heap Size, Dalvik Heap Pss / Alloc, total Pss, `Views`, `ViewRootImpl`, `Activities`, `AppContexts` | `adb shell dumpsys meminfo <package>`, every `--interval` seconds and once per window sample the lab announces (`parseMeminfo`) |

`--parts churn,static,spans,nav,modal,sheet,header,list,tabs` runs only the named parts of the cycle (`static` is plain view churn and `spans` is churn of pressable nested Texts, whose event emitters the engine keeps with no view: both off by default), to find where a growth comes from; such a run is written as `partsoak-<device>-<stamp>.json`, which `report` never reads, so a bisect cannot stand in for the full soak.

`qa/runs/soak-<device>-<stamp>.json` keeps the raw series (`js`, `memory`), the faults seen, and the `metrics` derived from them (`report` derives them again from the series, so editing the derivation needs no new run); the full logcat is `soak-<device>-<stamp>.log`.

| Metric | Definition |
| --- | --- |
| `memory.heapGrowthPct` | the worst of `memory.js.growthPct` (Hermes `allocated`), `memory.ui.growthPct` (the worklet runtime's, when the build logs it) and `memory.native.growthPct` (`Native Heap` Heap Alloc, the live malloc bytes: a leak raises it, arena slack does not), final window over baseline window, medians of three. Not derived (null, so `not measured`) when either window is missing, a JS sample was not collected, or the build logs the worklet runtime's heap and one of its two windows was not collected (the growth left out would be the worst one) |
| `memory.native.pssGrowthPct`, `memory.java.growthPct` | the same for `Native Heap` Pss and for Dalvik Heap Alloc; reported, not gated |
| `memory.native.slopeKbPerMin` | least-squares slope of `Native Heap` Heap Alloc over the idle floors (baseline, every checkpoint, final; the median of each window at the median of its time); reported, not gated. A leak is a slope that stays positive from the first checkpoint on; a cache or an allocator arena fills and then goes flat |
| `memory.leakedViews` | engine views alive in the last final sample minus the last baseline sample (everything unmounted in both), never below 0 |
| `memory.leakedEmitters` | nodes the C++ delegate holds an event emitter for in the last final sample minus the last baseline sample, never below 0 (a node Fabric deleted must leave the table); null for builds that do not log it |
| `memory.deadTagWrites` | `staleWrites + expiredWrites + overflowWrites` between the start sample and the last final sample: animated writes for a tag deleted more than 1 s ago (an animation that outlives its node), never claimed by a view within 1 s, or dropped because the table of early writes was full |
| `memory.lateTagWrites` | `lateWrites` over the same span: writes for a tag deleted a moment ago. Expected by design (SPEC "View recycling"): Reanimated drops a removed node a frame or two after the batch that deleted it. Reported, not gated |
| `memory.androidViews.growth`, `memory.viewRootImpls`, `memory.activities` | `Views` growth between the windows, and `ViewRootImpl` and `Activities` at the end |
| `soak.minutes` | from the lab's `start` sample to its last `final` sample, warm-up and idle windows included |
| `soak.crashes` | crash, native signal and ANR lines of the package during the run, plus one if the process died without any |
| `soak.complete` | 1 when the lab announced its end and the final window exists |

### Where a native growth comes from

When `memory.native.slopeKbPerMin` stays positive after the first checkpoints, the growth is a leak, and the next question is which allocation site. `heapprofd` cannot unwind this app's JavaScript thread; `malloc_debug` can:

```
flock /tmp/svelte-qa-emulator.lock qa/soak/malloc-debug-soak.sh localhost:5555 qa/out/app-x86_64.apk /tmp/dumps 420
python3 qa/soak/heapdiff.py /tmp/dumps qa/out/app-x86_64.apk qa/out/app-x86_64.symbols --frames 6
```

The script starts the app under `malloc_debug` with 14-frame backtraces (`wrap.<package>` on a userdebug image, `su`), runs the lab's soak and writes `am dumpheap -n` dumps at the baseline window, the first checkpoint and the final window (the process is several times slower, so the soak's cycle count is lower than in a normal run). `heapdiff.py` symbolizes the frames (the app's own libraries from `app-<abi>.symbols`, React Native's and Hermes's by their exported symbols, system libraries when pulled into `<dir>/syslibs`) and prints the call sites by growth, with their live allocation counts: a site whose count rises with the cycles and never falls back is a leak, one that rises once and stays flat is a cache. The 26 October growth was found this way: 1,300 `UpdatesRegistry` entries and the shadow nodes they hold (SPEC "Android wave 4").

### crashes

`native-qa crashes` runs `--starts` cold starts and then `--suites` full lab suites on the same install, and writes `crashes-<device>-<stamp>.json` (rewritten every 25 starts and after every suite, and on Ctrl-C, so a run of hours is never lost) with `crashes-<device>-<stamp>.log` (the tail of the log of every failed start) and `...-suite-<n>.log` (the full logcat of each suite).

A **cold start** is the boot runner's launch loop without its timing: wake, `am force-stop`, `--idle` s (default 2), `logcat -c`, `am start -W`, follow logcat (main, system, crash) until `[Svelte boot]` plus 1.5 s, then `pidof`. It **crashed** when the log has a `FATAL EXCEPTION` or a native `Fatal signal` of the package, or a JavaScript fatal (in this release build React Native logs `handleHostException` with the JS stack, destroys the React host and leaves the process alive and blank: there is no `FATAL EXCEPTION`, and only the log shows it), an **ANR** with `ANR in <package>`, and it **died** when no process is left after the boot line. A start that did none of that but printed no `[Svelte boot]` within 20 s is a start without boot. A **suite** is `lab --run checks,quick` (`labOnce`): it crashed with any crash or ANR line of the package, and is incomplete when the lab never logged its last line or its log could not be parsed (the error is stored in the suite).

| Metric | Definition |
| --- | --- |
| `crashes.run` | the lab `--run` the suites ran (a text; gated `== "checks,quick"`; `not measured` for a file that never recorded it) |
| `crashes.coldStarts`, `crashes.suites` | runs made (the bar is 1000 and 100) |
| `crashes.coldStartCrashes` | starts that crashed or died |
| `crashes.coldStartsNoBoot` | starts that hung without booting and without crashing |
| `crashes.suiteCrashes`, `crashes.suitesIncomplete` | suites with a crash; suites that did not complete and did not crash |
| `crashes.anrs` | ANRs over starts and suites |
| `crashes.signatures` | distinct failures kept (at most 20) |

The file records what it was started with: `run` (the lab `--run` of the suites), `idleSeconds` and `packageName`, next to the installed build. `--resume` continues the device's newest `crashes-*.json` after an emulator outage, a Ctrl-C or between the chunks of `--chunk`: the runs already measured are kept and the counts go on from there. It refuses, naming each difference, when `--run`, `--idle`, `--package` or the installed build differ from the file's, when the file predates these fields, and when the installed build could not be identified on either side (a null on both sides is not a match). `report` computes `crashes.run` from the file and the gate on it is `== "checks,quick"`, so a crashes file whose suites ran a partial lab does not count. A device that goes offline ends the run with an error instead of counting as a crash, and what was measured is written first.

`--inject-crash --suites 0` is a self-test: after every launch the runner sends `am crash <package>` (a real Java crash of the app process) and writes `crashtest-<device>-<stamp>.json`, which `report` never reads. It proves that a crash is seen, classified, deduplicated into one signature with a count and symbolicated.

The file holds the first 20 distinct failures as `signatures`: kind (`java`, `native`, `anr`, `death`, `no-boot`, `suite-incomplete`), title, frames, a count (the same failure again is one signature with a higher count; the key ignores pids, fault addresses, install paths and build ids) and where it was first seen.

### Symbolication

The release bundle is Hermes bytecode and the native libraries are stripped, so `native-qa build` keeps what is needed next to the APK (`qa/out/build-<abi>.json` records them):

- `app-<abi>.bundle.map`: the composed source map React Native's Gradle plugin writes at `android/app/build/generated/sourcemaps/react/release/index.android.bundle.map` (Metro's map composed with Hermes's; one generated line, columns are bytecode offsets). No Gradle change was needed, the plugin already runs `hermesc -output-source-map` for release.
- `app-<abi>.symbols/`: the unstripped `libsvelteengine.so` and `libreanimated.so` (our engine and Reanimated with the engine's sink) from `merged_native_libs`, before Gradle's strip step.

`soak/symbolicate.ts` (also `native-qa symbolicate`) reads a logcat capture on stdin or `--input` and prints each crash of the package with its frames resolved: JavaScript frames (Hermes `at name (address at index.android.bundle:1:OFFSET)` and React Native's fatal-exception `name@1:OFFSET`) through the map with `@jridgewell/trace-mapping`, native frames through `ndk-stack -sym app-<abi>.symbols` (found from `ANDROID_NDK_HOME`, `ANDROID_HOME/ndk/<newest>` or the path). `--all` prints the whole capture with every JavaScript frame rewritten instead. The crash runner symbolicates every signature it stores the same way and warns when `qa/out/build-<abi>.json` describes another APK than the installed one; `--map` and `--symbols` point it at the files of the build that was installed. The offset convention is React Native's own (`parseHermesStack`: line 1, 0-based virtual offset).

### Durations and the full run

On the OVH emulator (60 Hz, software GL) a cold start takes about 5 s with its idle gap and liveness check, a suite 2.4 to 3 minutes, and a soak takes its requested time plus about 40 s (the last cycle finishes, two idle windows) and the install. The full production run is therefore

```
pnpm native-qa build --abi x86_64
pnpm native-qa soak    --device localhost:5555 --minutes 10                  # about 13 min
pnpm native-qa crashes --device localhost:5555 --starts 1000 --suites 100 --chunk 100   # about 1.5 h for the starts, about 4-5 h for the suites
pnpm native-qa report && pnpm native-qa gates --platform android
```

`--chunk 100` runs the series as several commands (cold starts in steps of 100, suites in steps of 10, 20 s apart, each chunk continuing the same file with `--resume`, so the counts add up), each taking and releasing the emulator lock on its own: the OVH emulator's graphics stack (`-gpu swiftshader_indirect`) leaks host memory with every app launch (about 13 MB in October; about 0.12 GB of qemu's resident set per cold start on 9 Nov 2026, so a chunk of 100 starts peaks near 15 GB on the 22 GB host; on 10 Nov 2026 a chunk of 300 was killed for memory at 235 starts, one of 150 peaked at 19.9 GB with 2 GB left, and chunks of 100 at 13.4 GB), so on the shared emulator every chunk restarts it once it holds the lock (`--fresh`, which a single run takes too), the first chunk included because it may follow a suite that left the instance large, and the other agents get the device between chunks. The run does not depend on a host watchdog: on 8 Nov 2026, with none running, the OVH host (22 GB) killed the emulator for memory 225 cold starts into a volume that followed a foreign run (qemu at 22.9 GB). A chunk that fails stops the run with the command to continue it; continued with `--resume`, the run skips the chunks the file already covers (each would restart the emulator for nothing). Without `--chunk` the command holds the lock for the whole series; run that only when nothing else needs the device. `report` takes the newest file of each kind, so a short run made afterwards replaces a full one: the count gates (`crashes.coldStarts` 1000, `crashes.suites` 100, `soak.minutes` 10) fail for what was not run.

The native heap is the one number that misses its bar, and the series shows a leak, not noise: with the JS heap, the Java heap, the engine's views, the pool and the Android view count all flat, the floor of `Native Heap` Heap Alloc rises by about 2 MB per minute (minimum per minute of the series: 68.5, 69.1, 70.1, 74.1, 76.2, 79.3, 81.1, 84.8, 84.7 MB), 16.4 MB over 31,000 views created and destroyed, about 520 bytes per view. It is native (C++) memory that `gc()` does not return: Fabric shadow nodes held past their unmount, the engine's C++ side, or Reanimated's native registries are the candidates. Splitting the soak into its parts (`--parts`, three minutes each) points at the animated tiles: `--parts churn` alone grew `Native Heap` Heap Alloc by 16.7 % (63.5 → 74.1 MB over 11,104 tiles created and destroyed, about 980 bytes per animated tile, with the JS heap -0.8 %, 0 leaked views and 0 dead-tag writes), about the per-tile cost the full soak implies. `--parts static` (19,600 plain views created and destroyed, no animation) stayed flat: +0.3 MB, +0.65 %. The third split (`--parts nav,modal,sheet,header,list,tabs`) was cut short when the emulator went offline during it (about 14:54, `adb logcat exited with 255`, which the runner reports as an error, not as a crash); the full soak's per-view cost (520 bytes over all views, 980 over the animated tiles that make up about two thirds of them) says the other parts add little, but that is not measured. The leak is therefore tied to animated views: roughly 1 KB of native memory per Reanimated tile that `gc()` and the unmount do not return, in Reanimated's native registries (CSS animation and keyframe registrations, shared-value and mapper bookkeeping) or in the engine's animated write path.

**Resolved on 27 October** (SPEC "Android wave 4"): the leak was Reanimated's `UpdatesRegistry` re-adding entries for removed tiles whose update was still pending (found with `malloc_debug` dumps, `qa/soak/heapdiff.py`), and `detachAnimation` now marks a removed node removable a second time 400 ms later. On the fixed build the 10-minute soak measures `memory.heapGrowthPct` 0.08 (native -4.68 %, the floors 59.4, 57.1, 55.7, 56.0, 56.2, 56.6 MB) and the 30-minute soak 0.14 (native -4.08 %, 14 idle windows between 56.1 and 57.1 MB, +18 KB/min), with 0 leaked views and emitters. The numbers above stay as the record of the build before the fix.

The 200 cold starts ran as 100 and 100: the emulator host went down after start 100 (about 13:00), the runner stopped on `adb shell pidof ... device offline` instead of counting a death, and `--resume` continued from the file it had written. The cold-start loop takes about 4.8 s per start (idle gap, `am start -W`, boot line, settle, `pidof`): 1000 starts are about 80 minutes. A suite takes 141 to 142 s: 100 are about 4 hours, so the full run is about 5.5 hours of device time.

Faults found on the way, both visible only through this runner. A JavaScript fatal in this release build is not a crash to Android: React Native logs `handleHostException`, destroys the React host, and the process stays alive with a blank activity (no `FATAL EXCEPTION`, no tombstone, `pidof` still finds it); `findFaults` now counts it, so lab, boot and the runners see it. And the symbolicator was checked on a real stack of such a fatal (the lab's `crash-js` scenario, `anonymous@1:3185559`): it resolves to `apps/qa/src/lib/native/dev/Stress.svelte:375:41`, the `throw` of the scenario. Native symbolication was checked with ndk-stack on a tombstone written around two real addresses of `libsvelteengine.so` (they resolve to `encodeProps` and `encodeState` in `PropsEncoder.cpp`); no native crash of the app has been seen to date.

## Parity, accessibility, resilience

Production step 7. Three suites drive the QA app on a device through adb, each writes one run file, and `report` merges the newest of each per device into the metrics `gates.json` judges.

```
pnpm native-qa parity     --device <serial> [--apk <path> | --no-install] [--update | --missing] [--quick] [--filter <screen>] [--chunk <n> | --limit <n>] [--resume] [--fresh]
pnpm native-qa a11y       --device <serial> [--apk <path> | --no-install] [--quick] [--filter <screen>] [--chunk <n> | --limit <n>] [--resume] [--fresh]
pnpm native-qa resilience --device <serial> [--apk <path> | --no-install] [--rotations 5] [--cycles 100] [--rounds 2] [--font-cycles 1] [--only <groups>]
pnpm native-qa:suites     # all three on localhost:5555 (parity compares, it never updates), then report
```

None of them exits non-zero for a failed check; `gates` judges, as for `lab` and `boot`. They take the device flags and the emulator lock of `lab` and `boot` (`--device`, `--apk`, `--no-install`, `--dexopt`, `--package`; `flock /tmp/svelte-qa-emulator.lock` for the shared emulator, so install the build you mean with `--apk qa/out/<your copy>.apk` when other agents overwrite `qa/out/app-<abi>.apk`). `--quick` runs four variants (parity) or two (a11y), `--filter` selects the screens whose id contains the text, `--rotations`, `--cycles` and `--rounds` shorten the resilience plan, `--font-cycles 6` runs the text sizes six times over (each change recreates the Activity: the way to exercise that path often) and `--only rotation,fontScale` (groups: rotation, fontScale, locale, background, lowMemory) runs those groups only, after the plan's first step, which opens the loop screen; a partial run leaves the rest of the matrix counted as missing, so it cannot pass a gate.

**Long matrices in chunks** (Android; `lib/chunks.ts`, the design of `crashes --chunk`). The OVH emulator's graphics stack leaks host memory with every app launch, so the full parity matrix (224 cases, about 37 minutes) and a11y matrix (112 screens, about 24 minutes) can outgrow one emulator instance: the host's watchdog restarts it under the run at 18 GB and the cases it was in are lost. `--chunk 50` runs the matrix as several commands of `--limit 50`, one after the other: each takes the emulator lock on its own and releases it at its end (the other agents get the device between chunks), every chunk after the first first restarts the emulator (`--fresh`, with the lock held) and continues the run file of the one before (`--resume`: the cases the file holds are done, the others are taken in the order of the matrix, and the file keeps its name and its start time), and does not install the build again (`--no-install`: the emulator keeps its userdata, and a file is only continued by the build it measured). The same file comes out, with the same fields; the settings, the signed-in phase and the device restarts of each chunk are recorded as for any run. `--limit n` alone is one chunk: it takes at most `n` cases that the file lacks, writes the file and ends with status 3 when cases are left (status 0 when the matrix is done, 1 when the device went away or a setting could not be restored, which stops `--chunk` with the command to continue). `--resume` alone continues the device's newest file of the kind (a run the device interrupted, a Ctrl-C); a file of another `--filter`, `--quick` or mode (`--update`), or of another installed build, is refused. `--fresh` alone restarts the emulator once the lock is held, before the run. The restart is `bash $QA_EMULATOR_SH restart <reason>`, the contract of `ci/emulator.sh`: `qa/ci/emulator-remote.sh` for an emulator behind an ssh tunnel, `qa/ci/emulator.sh` on the host; `QA_EMULATOR_SH` names another script (a host that runs its emulator by hand has its own). A phone has nothing to restart: `--fresh` on it is an error. A chunk that stops before its cases are done leaves the run file with what it measured, and the cases it did not reach count as missing like any other.

### What the suites drive

`lib/screens.ts` holds the screens: one route in one state each, reachable without a signed-in session.

**How a case is reached.** The router makes the link the app is launched with the base of its stack (no back arrow), and the Android suites launch every case by a deep link, so a screen the lab normally pushes would open without the back button it declares (`Navigate up`). A screen that is pushed is therefore reached the way a user reaches it: the link is the screen below it (the lab's own screen `/__dev` for the menu, the menu `/__dev/screens` for the screens it pushes) and the case's steps push it, by a tap on the menu's button where it has one (`screens-header`, `screens-translucent`; the buttons ask for `presentation: "push"`, since every screen of the lab is the menu's own page with another `?mode=`, and a `goto` to the page the user is on with another query changes it in place) and, where the menu has none (`screens-toolbar`, `screens-toolbar-center`, which the menu leaves out so that its rows stay what the references show), by a tap that pushes screen 1 and a second link opened onto it (an `open` step: `am start` without stopping the app, which the router goes to as a plain `goto`). That link is screen 1's own page with another query, so it changes screen 1 into the toolbar screen in place, with the menu still below it. Screens that are bases (`/__dev`, the `dev-*` cases, `tree-*`, the slots and tabs pages) keep their deep link, and the sheets and the modal were already tapped from the menu: `tree-detail` too, because a launch link opened with `reset` selects the pane and resets its stack to the pane's index page plus the target (`plan` in `packages/expo-svelte/src/route-tree.ts`), which gives the target its back arrow.

**How the app starts, and what that means for the suites.** The root layout (`src/routes/+layout.mobile.svelte`) waits for nothing but the fonts (local) and, in a build that has the lab, for the launch link: a launch by a lab link (`example-svelte:///__dev...`, which the `dev-*`, `lab-screen`, `screens-*` and `tree-*` cases and every command that runs the lab by a link use: `lab`, `gestures`, `smoke`, `soak`, the iPhone lab and probe runs) opens the link into the router before anything is rendered, so the lab starts on its own screen and never shows the home screen first; a launch without a link (`boot`, the `product` check) renders the home screen (`src/routes/+mobile.svelte`) once the fonts are in. There is no request and no session: nothing a backend does changes how the app starts. A start that fails (the launch link read or the fonts) shows a notice with a Retry button and is tried again by itself after 1 s, 2 s, 4 s and 8 s and then every 15 s while the app is in the foreground (an app that is not active, in the background or on iOS `inactive`, tries nothing and tries at once when it is active again, without logging a new error; the Retry button tries at once and starts the schedule over); the first failure of a streak is the only `console.error` (`[native startup]`), the later ones are warnings (`src/lib/native/startup.ts`, `qa/test/startup.test.ts`). A build without the lab sends a link to a lab path to the home screen (`src/lib/native/lab-guard.ts`).

A case can make the app's network hang or refuse (`network: "hang" | "refuse"`, with `state: "loading" | "error"`): the app's HTTP is then routed (`settings put global http_proxy localhost:<port>` and `adb reverse`) to a socket on the machine running the suite that accepts and never answers (a client's own timeout is the loading state) or one that refuses (the error state), and the proxy is removed afterwards. The example has no such case today (it makes no request); the iPhone leaves such cases out, as it cannot be pointed at a proxy. Routes with a `+mobile.svelte` page that no case reaches are listed in `notCovered` with the reason; `test/screens.test.ts` fails when a page is neither covered nor listed, so a new route cannot slip by.

Every screen runs in the **variants** theme (light, dark: `cmd uimode night yes|no`) x direction (LTR, RTL: `cmd locale set-app-locales io.example.svelteqa --locales en-US|ar-SA`, which gives the app Arabic strings and a `ldrtl` configuration for the native chrome) x text size (1.0 and 2.0, `settings put system font_scale`, the largest Android 14+ offers), eight in all (`light-ltr-normal` ... `dark-rtl-large`). Rotation is locked to portrait. Everything the suites change is recorded before the first change in `qa/out/device-state-<serial>.json` and put back in a `finally` (and on SIGINT/SIGTERM); if a run was killed outright, the next run restores from that file first.

**Leftovers.** A run whose adb link dropped cannot restore anything, and the device keeps the proxy and the text size of its last case. A session therefore never takes those for the device's own: when it opens, a `http_proxy` of the form `localhost:<port>` or `127.0.0.1:<port>` (a hole port of this harness; no device is set up with a proxy on its own loopback), a `font_scale` of 2.0 (1.0 is the default and cannot be told apart), a per-app locale of `en-US` or `ar-SA` for the app under test, or a `user_rotation` of 1, 2 or 3 is logged as a warning that names it, cleared on the device, and recorded as cleared in the original (`original.proxy` is `null`, so `close` does not put the dead proxy back). The theme and auto-rotate are not judged: a dark device or a rotation lock is as likely the device's own choice, and every variant sets the theme anyway. The cleared settings are written to the run file as `leftovers: string[]`, and `report` prints them as a `note:` (not a warning: the run measured a clean device) so a report shows that the previous run did not restore.

**The network mode is read back.** After `networkMode` has set the proxy (and also when the mode is the one already set, which catches a proxy changed behind the session's back) the session reads `http_proxy` and throws `the proxy on <serial> is "<value>" after switching to <mode>` when it is not the mode's. This happens before the app is launched, so a case never opens in the wrong mode; it is a `DeviceStateError`, which ends the run like a lost device.

**A missing anchor is checked against the device.** When a case on the normal network does not show its anchor (`no node ... on screen`), parity and a11y read the device's `http_proxy` and `font_scale` once, before they retry (a genuine slow screen still gets its one retry). If either is not what the case needs (no proxy, the variant's text size) the whole run stops with the cause, `the device is not in the state the case needs: http_proxy localhost:33699 (expected none)`, after the session has restored the device; the message is the run file's `aborted` and is printed, instead of 60 screens each recording `no node ... on screen after 15000 ms`. Cases on the failing proxies are not checked: their proxy is meant to be one.

**A case whose screen does not show up is retried once and photographed.** A launch whose wait or dump failed (`isWaitFailure`: the anchor never comes, `no node ... on screen after 15000 ms`; a dump that holds less than the screen's own controls; a dump that cannot be read, `produced no tree`) is run once more by `parity` and by `a11y` (`lib/evidence.ts`, `attemptCase`; before this `parity` had no retry, only `a11y` did). Any other failure of a parity case (a reference whose image is not there) is one run and an `error` at once, with no second launch and no evidence; `a11y` retries every failure that does not end the run, as it always did. Before the retry launches the case again, while the screen is still the one that failed, the harness keeps what the device shows, once per failed try and never for a case that passed its first: a screenshot (`screencap -p`), the raw `uiautomator dump` the wait last read (a dump taken after the failure when it read none), the window manager's `mCurrentFocus`, `mFocusedApp` and window list (`dumpsys window windows`, else `dumpsys window` when that answers nothing: an empty answer is a missing part, not an empty file), the top and resumed activity, and logcat: the last 400 lines of the app's process (the lines that name the package when the process is gone, narrowed to the try) followed by the crash buffer (`logcat -b crash`, 100 lines), which is always read so that a crash followed by the relaunch of the retry is not lost. The lines that can come from an earlier case or try (the crash buffer, and the lines of an app with no process) are narrowed to the try: those at or after its start, read off the device's own clock (`date`, less the time the try has run on this host's, less a second), so an earlier case's crash is not filed under it; a device whose clock cannot be read gives the whole buffer and says so. The files are next to the run file, in the directory named like it (`qa/runs/parity-<device>-<stamp>/<case>.attempt<n>.png | .uidump.xml | .windows.txt | .activity.txt | .logcat.txt`, and `qa/runs/a11y-<device>-<stamp>/`); each part is size-capped (the dump 600 KB, a text 256 KB, a screenshot 8 MB) and one **process** keeps at most 40 sets and 64 MB: with `--chunk`, `--resume` or `--limit` every chunk is a process of its own and has a budget of its own. The case's record says what it holds: `failures` (one entry per failed try: the error, how long the wait ran and over how many dumps, the top-level window of the last dump (package, class, bounds, node count and first texts: a sheet, a system dialog, the launcher or the app's own loading page each read differently), the paths, and `missing`, the parts that could not be kept and why), and the runs of the case: an `a11y` screen records `attempts`, a `parity` case `tries`, and a `parity` `error` also puts the tries in `attempts` (which is the screenshots taken for every other verdict). They count every run of the case, so they are 2 for a retry, 1 otherwise, and more only when the emulator restarted under the case and `DeviceSession.guarded` ran it again. A case that failed once and passed its retry carries its first try's evidence, the console line says `(2 tries)`, the final line counts the retried cases, and the metrics `parity.casesRetried` and `a11y.screensRetried` (informational gates) count them in the report.

**What is kept of the account in the evidence.** When a QA account is configured ("Signed-in phase"), its address is redacted from every text, before the size cap cuts it (a cut through the address would leave a piece no redaction recognises), and from `missing`. The screenshot is painted over the way a failed comparison is (`liveRedactions`): every node of every dump that shows the address (the wait's own dump, a plain dump and, for a screen over another, the compressed dump a service walks, the last two taken after the failure, the plain one with up to 3 attempts and the compressed one with up to 2 so that a busy screen's `could not get idle state` does not cost the picture; the plain one lists the screen a sheet or modal covers, the compressed one leaves it out; the screenshot is taken between the two) and the screen's masks (the devices' text, the photo). A signed-in screen's picture is only kept when every one of those dumps is a window of the app: under a dialog or the launcher the dump walks that window and the app's frame with the address, dimmed, is still in the picture. `native-qa leakcheck` reads the dumps, logs and run files again; the screenshots are only as clean as the rectangles painted over them.

**A device lost at the end.** When `close` cannot restore because adb reports the device missing (or a setting did not take), the run file records `restoreFailures` (the failures `restoreState` returned, the adb error that kept the settings from being read back, or the settings that differ), the command prints it and exits with 1, and `report` warns `<serial>: the device was left in a changed state by the <run> run (...)`. That is an integrity warning like the cross-build ones: `gates` fails on it until the suite has been run again on the repaired device. The saved state stays in `qa/out`, so the next run repairs the device first.

**A device that restarts under a run.** The emulator can die or be restarted by a watchdog during a long run; its userdata persists, but a fresh boot has the system defaults (night mode off, text size 1.0, no proxy, no per-app language) and the `adb reverse` ports of the holes are gone, while the session still believes what it applied is in place. The session therefore records the device's boot identity when it opens (`cat /proc/sys/kernel/random/boot_id`, a new UUID at every boot; `getprop ro.boottime.init` when that cannot be read; the check is off when neither can) and compares it before every case (`launchCase` and `openCase`, and the whole case in parity and a11y), after a case failed (waiting up to 90 s for a device that dropped off to come back), and in `close`. When it changed the session prints `the device restarted at <time> (boot id ...): re-applying its settings`, waits for `sys.boot_completed`, re-applies every setting it manages (theme, text size, app language, rotation, the reverse ports of the holes and the proxy that points at them), reads them back (a setting that reads differently is a `DeviceStateError`, as everywhere else), appends `{ at, bootId }` to `deviceRestarts` in the run file, and retries the case that was in flight once. In `close` a restart is only recorded: the restore that follows puts the original settings back. `report` prints each restart as a `note:` (a run that survived one is still a measured run; a restart that broke a case is that case's own error).

### Parity

```
screenshots/<device kind>/<screen>--<variant>.png    one reference per case
screenshots/<device kind>/manifest.json              checksum, size, masks, what it is a reference of
```

The references are about 130 KB each. The device kind is `<platform>-api<sdk>-<emulator | model>-<width>x<height>-<dpi>dpi` (today `android-api36-emulator-1080x2400-420dpi`): pixels depend on all of them, so a different device kind has its own references (and its first run is `--update`). A reference is a full-display screenshot (status and navigation bar included) written as PNG by the harness's own encoder (`lib/png.ts`, no dependency).

- **Check** (the default): launch the screen from a fresh process, run its steps, take screenshots until one equals the reference, for up to 12 s (25 s for a screen that needs a backend). The bar is **0 differing pixels outside the masks**: all four channels, no tolerance, no anti-aliasing allowance. If the window closes without a match, one more screenshot decides between `unstable` (two in a row disagree outside the masks) and `fail`; a failure keeps what the device drew and a red-on-grey diff in `qa/runs/parity-<device>-<stamp>/<name>.actual.png` and `.diff.png`, and the run file records the count and the bounding box.
- **Masks** are frozen in the manifest beside the image: the status bar band (its inset frame from the window manager, 0 to 128 px on the emulator: the clock, battery and notification icons vary) and, per case, the bounds of nodes that move on their own (the startup spinner, the Reanimated test square). A mask whose node is not in the tree when the reference is taken is an error, not an unmasked reference, except for nodes the largest text pushes off screen. `parity.maskedPct`, the share of the screen the masks cover in the worst case, is gated at 25 %, and every parity line prints the case's own share (`masked 20.7 %`). `--update` refuses to freeze a reference whose masks cover more than 25 % (`lib/parity.ts`, `maxMaskedPct`, the gate's bar): the case is recorded as an error that names the kinds of mask (status bar and moving nodes on Android; moving, glass and sheet views on iOS) with their counts and shares, so the one to cut is visible. **The status bar band is read only once the bars have settled** (`statusBarRect`): after a boot the window manager lays the status bar out in steps (63 px with no camera cutout known, the 128 px cutout known while the bar is still 63, then 128, within 5 to 9 s of the system saying it has booted), and a reference frozen from the first answer masks half of the band the clock is drawn in (2 November: the eight `screens-tabs` references, 63 of 128 px, so every later check saw another time and another app's notification icon). The harness waits until the device has been up 60 s and returns a band that reaches the display cutout's inset and that two answers a second apart agree on, else an error. A check also refuses (`error`, "retake it with --update") a reference whose frozen status bar mask is not the device's band. The chrome rule (`maskedChrome`) does not count a control that is inside a masked node (a node above it lies wholly within a mask): the Animated touch target is the whole surface of the Reanimated test square the `dev-animation` case masks, and moves with it.
- **Update** (`--update`): the same launch, but the anchor of the screen must be in the accessibility tree and two screenshots in a row must agree outside the masks before one is frozen, so a reference is never taken mid-animation. Each updated case says `new`, `unchanged` or `changed` against the previous reference. The manifest is rewritten after every case; `--missing` updates only the cases that have no reference yet, which resumes an interrupted update. If the device goes away mid-run (adb offline) the suites stop with that error instead of recording every remaining case as failed. An update run verifies nothing: `report` ignores its metrics, so a gate stays "not measured" until a check run follows. Review the changed PNGs in the diff like any other change.

### Box styles

The Android engine draws box shadows, dashed and dotted borders, a colour for each border side and the transform origin with React Native's own drawables (`packages/expo-svelte/native/svelte-core/SPEC.md`, "Box styles"). `/__dev/styles` is their lab: `?mode=shadow`, `?mode=border` and `?mode=origin`, one screen each, 32 tiles in all (`src/lib/native/dev/styles-cases.ts`: plain style objects; the animated tiles of `origin` are turned by Reanimated to a fixed value and stay there). The grid has the `testID` `styles.grid`; in `shadow` an input below it (`styles.focus`) takes a focus ring when pressed and loses it when pressed again, so the ring comes and goes at run time. `?rows=300&border=0|1&cycles=6` is not a mode of tiles: it mounts and removes 300 rows (a fill, a radius, with `border=1` a 1 dp border) six times, for the mount cost of bordered views, which is read from the engine's own `SvelteEngine: ... apply=` log line of each mounting transaction. `?reuse=<from>-<to>` (indices of `reuseStyles` in `styles-cases.ts`) mounts ten boxes in one style, removes them and mounts ten in another from the views the engine recycled; its screenshot must equal the one of `?reuse=-<to>`, which has no recycled view (a recycled view keeps React Native's drawables and rewrites them, so what it had must not show). The three modes are the parity cases `lab-styles-shadow`, `lab-styles-border` and `lab-styles-origin` (24 references: the engine's own frozen output, as for every case).

**The comparison with React Native's pixels.** The parity references are the engine's, so they say the drawing did not change, not that it is React Native's. `qa/styles-reference` is the other half: `entry.js` is a plain React Native app that draws the same tile objects with React Native's own views, and `build.sh` puts it into the QA app's APK in place of the Svelte bundle (the Svelte host never runs, so the engine is never installed and `ReactViewGroup` and the drawables of `BackgroundStyleApplicator` draw every view; the APK keeps the QA app's debug signature and installs over it and back). Open the same link on both (`example-svelte:///__dev/styles?mode=border`; the reference also takes `&top=<dp>`, the space above its grid, so the two grids start on the same pixel) and cut each screenshot into tiles by the bounds of `styles.grid` from `uiautomator dump`: a tile is 168 by 112 dp, `441 x 294` px at 420 dpi, two to a row in the order of the tile list. The run of 24 November 2026 on the OVH emulator, with the differences per tile, is in SPEC.md, "Box styles on the emulator".

### Accessibility

`a11y` opens each screen in four layouts (LTR and RTL at text size 1.0 and 2.0; theme changes no node) and checks the accessibility tree. The oracle is `uiautomator dump --compressed`: the node info the engine publishes (`A11y.kt`, `EngineText`, `EngineHeader`, `EngineTabs`) for what a service walks. The run file says so (`oracle`). TalkBack (`com.google.android.marvin.talkback`) is on the AVD, but its gestures cannot be driven reliably by injected input, so the suite does not run it; a session with TalkBack and a probe service that logs what a service receives (SPEC "Android wave 4") settled the one question the dump could not answer, and the TalkBack and VoiceOver passes are manual ([A11Y-MANUAL.md](A11Y-MANUAL.md)).

There are two dumps. The plain one (`uiautomator dump`) sets `flagIncludeNotImportantViews`: it lists every view, the views the engine marks `importantForAccessibility=no` (a sheet's or modal's scrim, whichever of the large and the inline title does not show) and everything under a `noHideDescendants` view (a screen under a sheet or modal, which the engine hides from services). A service does not ask for them, TalkBack included. The compressed one (`--compressed`) leaves them out and is the tree a service walks. **Every check reads the compressed dump**: interactive elements, reach, labels, actions, order, title first and the focus trap. Read from the plain dump, a sheet's full-screen scrim is an unlabeled stop and a button of the screen underneath breaks the order and puts content before the sheet's title, none of which a service meets. The plain dump has no check of its own; it only drives the app (`openCase` waits for the screen's anchor and finds the nodes its steps tap in it; the parity suite takes its masks from it), where every view counts. A node a check needs that only the plain dump lists is not in the tree a service walks, which is the finding.

The compressed dump is settled the way the screen needs: taken again until two in a row are identical (`settledTree`), and, while a sheet or modal covers a screen (`hidden`), first taken again, up to three times, until it contains the screen's own declared controls (its title when it declares none), because one taken while the screen is still drawing would be judged half built. Without them after three dumps the case is launched once more; without them again the screen is recorded as an error (`a11y.incomplete`). A screen that covers nothing is judged on what it shows: a declared control missing from its dump is an unreachable finding, not a retry. Each screen result records `stable`, whether `settledTree` found two dumps in a row identical.

| check       | passes when                                                                                                                                                                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| reachable   | the element is in the tree with non-zero bounds inside the display, is enabled, and a service can focus it (focusable, actionable or labeled); a control the screen's source declares (`controls` in `lib/screens.ts`, by label) that is not in the tree at all is unreachable; `scrolled` lists controls the largest text pushes below the fold, which are checked when the tree has them and never reported missing |
| labeled     | text, content description or hint on the node or a descendant                                                                                                                                                                                                                  |
| actionable  | clickable, long-clickable, checkable, or a text field: a node exposed as a button (`android.widget.Button`) that advertises no action fails; a lab control whose node info (below) offers a custom action or a slider's increment and decrement counts too                                                                                                                                    |
| order       | the focus stops, in tree order, run top to bottom and, within a row, start to end (right to left in RTL); stacked stops (a button and the text inside it) are not compared                                                                                                     |
| title first | the screen's title is a focus stop and the first one after the bar's back button and left slot: what comes before it is above its row or at its start side, never content (`judgeReadingOrder`, one definition for both platforms); a header reads back, left slot, title (or center slot), right slot, search, start to end, and its large title (the bar's second row) is the one step of the order that goes up |
| focus trap  | while a sheet or modal is up, the labels of the screen underneath (`hidden`) are not in the tree a screen reader walks (`uiautomator dump --compressed`); a sheet titled like the button that opened it ("Form sheet") does not count its own title                                |

**State, value, hint and actions (the accessibility lab).** The engine publishes `accessibilityState`, `accessibilityValue`, `accessibilityHint`, `accessibilityActions`, the live region, `importantForAccessibility` and `role` the way React Native's Android views do (SPEC "Accessibility props"), and `/__dev/a11y` has a control of each kind with a `testID` (`a11y.<name>`): `?mode=states` (a checkbox and a mixed one, a radio group, tabs, a disabled, a busy and an expandable button, a hidden element) and `?mode=actions` (a slider with a value, a button with a hint, a swipe row with custom actions, a live-region counter). Two cases of the suite, `lab-a11y-states` and `lab-a11y-actions` (Android only: `androidOnly`, left out of the iPhone's matrix), open them with `probe=nodes` and `probe=actions` and add a seventh check, `state` (`stateMismatches`, gate `a11y.stateMismatches` at 0, finding kind `state`), from two readers, because neither sees it all (`lib/a11y-state.ts`):

- **The dump** (`NodeExpectation`, `expect` on the case, by `testID`, which is the dump's `resource-id`) carries class, `checkable`, `checked`, `selected`, `enabled`, `clickable`, `focusable`, text, content description and `hint`. It shows the role (a `CheckBox`, a `RadioButton`, a `SeekBar`), a checked checkbox or radio, a selected tab, a disabled button, the label with the words React Native appends ("Select all, mixed", "Saving, busy", the value's text: in Arabic layouts they are React Native's Arabic strings, which the engine uses too), the hint attribute being empty (React Native writes no hint text), and a `no-hide-descendants` view and what is under it being absent. At the normal text size every expected node must be in the tree; at 2.0 the ones below the fold are not judged and the ones present are.
- **The app's own node info** (`InfoExpectation`, `info` on the case): the link's `probe=` makes the lab log, once the screen is up, one `[Svelte a11y] node {...}` line per `testID` node (`SvelteEngine.accessibilityNodes()`, `A11yDump.kt`: the `AccessibilityNodeInfo` the node's delegate fills, which is what a service receives) and `[Svelte a11y] done N`; the suite clears logcat before it opens the screen and reads those lines. It carries what the dump cannot show: the tooltip text (React Native's hint), the range (min, max, current), the role description ("Tab", "Radio Group"), heading, the live region, `importantForAccessibility`, and the list of actions with ids and labels (the standard ones by id, custom ones counted from `0x3f000000` per name, matched by label). `probe=actions` also performs `archive` on the row and `increment` on the slider through their nodes (`SvelteEngine.performAccessibilityAction`, which calls `performAccessibilityAction` on the view as a service does), so that the event path from the node to JavaScript shows in the dump as "Last action: archive" and the slider's new value.

What neither reader can see: **how TalkBack speaks any of it** (the manual checklist), whether a service is told of a change while it has focus (the selected and click events, the live region's content-change event), and the node info of a control that is not in the lab. The node info is the app's word for what it publishes, read from inside the process.

An interactive element is a node that is clickable, long-clickable, checkable, a text field, or of a control class. Disabled controls are counted (`disabled`) but not checked. An element outside the display, or one uiautomator reports with a negative extent (a row scrolled out of its container), is `clipped` and skipped only when it sits inside a scroll container (a `scrollable` ancestor or a scroll, list or pager class) and the screen declares it below the fold (`scrolled` in `lib/screens.ts`); any other element out of the display is unreachable (`outside the display`, or `negative extent ... not declared below the fold`). A zero-size element (no visible width or height: uiautomator clips the bounds to the visible area, so a text field on the bottom edge of its scroll view reports `886x0`) defers to the same rule: it is `clipped` when it is inside a scroll container and declared below the fold, exactly like one off the screen, and stays unreachable (`zero-size bounds`) anywhere else. The report prints `clipped` and the reach percentage per screen. The heading flag and `accessibilityTraversalBefore/After` are not in the dump: the title is identified by its text, and a header's own traversal chain is not observable here.

### Resilience

`resilience` runs one screen (`screens-menu`: a large header over a scroll view) through the plan, then the low-memory rounds on `screens-header`. After every step it asks, in one adb call, whether the process is alive (`pidof`) and what the filtered log shows (`AndroidRuntime:E ActivityManager:E SvelteEngine:W libc:F DEBUG:F ReactNativeJS:E`, then cleared): a fatal, an ANR, a native signal, a JavaScript error or an engine warning fails the step. Steps with anchors also dump the tree and need the header and a content node on screen. Failures keep their log lines in `qa/runs/resilience-<device>-<stamp>.log`. After a failed step the app is started again on the loop screen (`recovered: true` in the step), so one hang does not fail every step after it; the low-memory rounds are left as they fall, because they depend on the process state.

| group      | steps                                                                                                                                                                                   |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| rotation   | launch, then landscape and portrait x 5 (`user_rotation`, auto-rotate off)                                                                                                              |
| font scale | 2.0, 0.85, 1.0                                                                                                                                                                          |
| locale     | Arabic while running, Arabic after a restart, English while running, English after a restart                                                                                            |
| background | `HOME` then `am start -n .../.MainActivity` x 100 (the process and log every cycle, the tree every tenth and the last)                                                                  |
| low memory | x 2: `am send-trim-memory RUNNING_CRITICAL` in the foreground, `HOME` and `COMPLETE`, `am kill` (the process must be gone), return to the app (the route of the deep link must be back) |

The full plan has 126 steps.

### Not covered, and why

- `/__dev` async panel, pending and error-boundary states, at 200 % text (`notCoveredStates`, 8 cases left out of the matrix): the button that sets the state is below the first screen of a `Page`, and the `Page`'s scroll view reports `scrollable=false` and does not move under a swipe (the same on `/__dev/screen` with its 60 rows), so neither a user nor the harness can reach it.
- Routes behind a sign-in would be the second phase of both suites ("Signed-in phase"; the example has none); the pages no case reaches are listed in the run file's `notCovered` and in `lib/screens.ts`.
- `/__dev/foreign` (WebView, map, video): third-party content that varies between runs.
- Empty states of search results and the keyboard: the soft keyboard is not part of the app and its rendering varies; the one list with an empty state (header search in `screens-slots`) needs typed text.
- VoiceOver and TalkBack themselves: a person checks them with [A11Y-MANUAL.md](A11Y-MANUAL.md); the suites read the accessibility tree and never run a screen reader.
- A screen that needs a backend (`needsBackend`; the example has none) is skipped, not failed, when `QA_BACKEND_URL` is unset or does not answer from the machine running the suite (`parity.casesSkipped`; the gate on `casesIncomplete` still fails).

## iOS

The same commands run on the iPhone with `--platform ios`: `build`, `lab`, `boot`, `parity`, `a11y`. They write the same run files (`device.platform` is `ios`), so `report` and `gates` read the iPhone like any device and judge the `ios` bars of `gates.json`.

```
pnpm native-qa build  --platform ios --mac <user@host> --mac-checkout <dir on the Mac> [--build-script <path on the Mac>]
pnpm native-qa lab    --platform ios --device <devicectl id> --mac <user@host> [--app <.app on the Mac> | --no-install] [--run checks,quick] [--repeat <n>] [--timeout <s>]
pnpm native-qa boot   --platform ios --device <devicectl id> --mac <user@host> [--warm <n>] [--cold <n>] [--idle <s>]
pnpm native-qa parity --platform ios --device <devicectl id> --mac <user@host> [--update | --missing] [--quick] [--filter <screen>]
pnpm native-qa a11y   --platform ios --device <devicectl id> --mac <user@host> [--quick] [--filter <screen>]
pnpm native-qa probe  --platform ios --device <devicectl id> --mac <user@host> [--probes <names>] [--direction ltr|rtl]
```

`--mac` (or `NATIVE_QA_MAC`) names the Mac the iPhone is paired with; `--device` is the id `xcrun devicectl list devices` prints. Every command also takes `--udid <hardware UDID>` (default `00008110-001E10593410401E`, the lab phone's: what `idevice_id -l` prints on the Mac), by which the phone's crash log is read ("Crash reports" below). Commands run on the Mac over `ssh` (one shared connection, `BatchMode`) and files come back over `scp`; nothing runs on the Mac but `xcrun devicectl`, `rsync`'s target, `pnpm`, `expo prebuild`, `pod install` and the build script. A run takes `flock /tmp/svelte-qa-iphone.lock`, so two runs never fight over the app. The commands never pair, re-pair or change a setting of the phone or the Mac.

**build** copies this checkout to the Mac checkout (`--mac-checkout` or `NATIVE_QA_MAC_CHECKOUT`: the directory the recipe fixes, `rsync` with the Android and iOS project directories left alone), installs the dependencies, runs `expo prebuild --platform ios` and `pod install`, and then opens the build script with `open -a Terminal` and waits for its `.exit` file. Signing needs the login keychain, so the build runs only in the GUI Terminal (default script `/tmp/example-ios-lab-20261025.command`, which writes `.log` and `.exit` next to it). The Mac-side preparation runs under `set -o pipefail`, so a failing `pnpm install` stops the build instead of being hidden by the `tail` it is piped to. The result is `qa/out/ios-build.json`: the signed `.app` on the Mac, the commit and whether the tree was dirty, the SHA-256 of its `main.jsbundle` (`bundleSha256`, also written as `jsbundleSha256`) and of its executable (`cdHash`: `shasum -a 256` of the file `CFBundleExecutable` names in the app's `Info.plist`, read with `PlistBuddy` on the Mac). `lab`, `boot`, `parity` and `a11y` install that app first (`devicectl device install app`) unless `--no-install` is given.

**Build identity.** The app reports `build: { jsbundleSha256, cdHash }` (the SHA-256 of `main.jsbundle` and the executable's code directory hash, read from its signature; `codesign -dvvv` prints the same `CDHash`) at the top level of `Documents/lab-results.json`, `Documents/boot-report.json` and `Documents/capture/index.json` (the parity and a11y captures; the probe index carries none). Every iOS command compares what the app reported with `ios-build.json`, install or `--no-install` alike, and ends the run with the mismatch printed, writing no run file, when they differ (`probe` too; an `--app` other than the recorded one has no record to compare with). The record's executable digest is compared when it has one. Every iOS run file records `app.installed` (what the app reported, or `null` when it reported none: an older app, in which case the command warns `build identity not reported`) and `app.build` (`commit`, `dirty`, `jsbundleSha256`, `cdHash` of the record it was compared with); `app.installedSha256` is the reported executable digest, null with `installed`. `source` stays the checkout's HEAD when the command ran, which says nothing about the build. `report` identifies an iOS run by `installed` and warns for every run that has none, so `gates` fails on it.

**lab** starts the lab by its URL (`example-svelte:///__dev?run=checks,quick&token=<random>`) and reads `Documents/lab-results.json` from the app's data container every 10 s until the file carries the launch's token and says `stressDone` (or `phase: done` for a checks-only run); every 30 s it asks `devicectl` whether the process is still there, and a lab whose app died is recorded as incomplete with that as its fault. The app is ended afterwards; a lab whose app then aborts is found by the crash log ("Crash reports" below), and its run is marked incomplete. The file's scenarios are the `[Svelte stress]` objects Android logs, so `labMetrics` reads them unchanged. iOS has no log stream the harness can follow: the app counts its own `console.error` calls and reports them as `jsErrors` (top level of `lab-results.json` and `boot-report.json`), which the run files keep (`jsErrorCount`, `jsErrors`, null when the app reports none) and `log.fatals` adds to a dead app. The engine's warnings do not exist on iOS (no engine), so `log.engineWarnings` is 0 by absence.

**boot** is measured inside the app by the QA module (`apps/qa/modules/svelte-qa-ios`, a Swift Expo module that refuses to run outside `io.example.svelteqa`). The process start is the kernel's (`sysctl` `p_starttime`); the first frame is the display link tick after React Native mounted the first content (`RCTContentDidAppearNotification`), taken at its `targetTimestamp`, the vsync the frame is shown at (a resolution of one frame, 16.7 ms). `Documents/boot-report.json` carries both, `didFinishLaunching` and the `[Svelte boot]` line. `displayMs` (the number gated) is process start to that first content frame; `runningMainMs` is process start to the content being mounted and `totalTimeMs` process start to `application(_:didFinishLaunchingWithOptions:)`, the nearest iOS counterparts of Android's `Running "main"` and `am start` time. Warm is: end the app, wait 1.5 s, launch; cold is: end the app, idle `--idle` seconds (20), launch. Every launch ends a running instance first (`--terminate-existing`), and a report counts as that launch's only when it names the launched process and its `processStartMs` is later than the moment the harness started the launch command (both are recorded in the sample, `commandStartedAtMs` and `processStartMs`): a report the previous launch left behind is refused and the sample counts as failed. The two times are on the phone's clock and this machine's, which must agree to within the few seconds a launch takes. A copy of the report caught half written is read again on the next poll. iOS cannot be made to drop its page cache, so both are process-cold launches, as on Android, and the first frame is the first content frame: the system's launch screen and Expo's splash overlay are drawn before it.

**parity** and **a11y** cannot be driven from outside, because nothing outside the process can take an iOS app's screenshot or read its accessibility tree and `devicectl` has no input. So the lab drives itself: `run=capture:<ids>&themes=light.dark&token=<random>` (`lib/native/dev/capture.ts`) visits each screen of the matrix in turn (`router.goto`, presenting sheets and modals over the menu), takes screenshots of its own window until two in a row have the same SHA-256, dumps the accessibility tree, and writes `Documents/capture/index.json`, `<screen>--<theme>.png` and `<screen>--<theme>.a11y.json`. The harness polls the index until it says `done` and copies the directory. The theme is `overrideUserInterfaceStyle` on the app's windows (the native bars and sheets follow it); the direction is the launch language: right-to-left runs launch with `-AppleLanguages (ar) -AppleLocale ar_SA`, which gives the process an Arabic locale and UIKit's right-to-left layout, and the window reports the direction it got (a run that asked for one and got the other is an error, not a pass).

- Parity: `screenshots/<ios release>-<model>-<w>x<h>-<scale>x/` (today `ios26-iPhone-SE-3rd-generation-750x1334-2x`), one reference per screen x theme x direction (4 variants, standard text size). The screenshot is the app's own window: no status bar, so no status bar mask; the masks are the frames of the views that move on their own (every `UIActivityIndicatorView` and views with a `qa-mask` test id, which the lab sets on the Reanimated square) and the edges of the system's glass capsules (the bar items and the tab bar of iOS 26: `_UI...Glass`/`...Platter` views, masked at their round ends (half their height and 6 pt more) and along their top and bottom edge, 6 pt; a capsule less than 1.5 times as wide as it is tall is masked whole), because the system draws their rim a level differently on a few pixels from one launch to the next and the rim of a presented sheet's card (its corners, 64 pt squares, and a strip along each side, 6 pt inside the frame of the presented view and 8 pt outside it (32 pt above, where the card of a sheet that fits its content starts): the system's corner mask, border and shadow) for the same reason (before the masks 3 of 72 cases failed by 31 to 73 pixels on the glass edges, and the `auto` sheet by 48 to 235 on its rim, in one launch out of three); what is inside a capsule or a sheet, the app's icons, labels, badges and content, is compared. The bar is the Android one: 0 differing pixels outside the masks, all four channels, no tolerance, and the masks together may cover at most 25 % of the screen (`parity.maskedPct`; the widest today is the `screens-sheet` case at 20.7 %): the parity output prints each case's share, and `--update` refuses a reference over the limit, naming the moving, glass and sheet views with their shares.
- Accessibility: the dump is what the app's accessibility elements report (`SvelteQAAccessibility.swift`: the traversal the system does for VoiceOver, with hidden views, `accessibilityElementsHidden`, explicit `accessibilityElements`, containers and `accessibilityViewIsModal` applied as the system applies them). `lib/iphone/a11y.ts` runs the six checks of the Android suite (reachable, labeled, actionable, order, title first, focus trap) on it, reading traits instead of Android's classes and actions: actionable is the button, link, adjustable or search field trait (or a text input), the title must carry the header trait, and VoiceOver's default order, a sort by position, is applied to the elements no container orders. VoiceOver itself was not run.
  - An element outside the screen is `clipped` (counted, not checked) only when the dump puts it in a scroll view (`RCTScrollView`, `UIScrollView`, table and collection views among its `parents`) and the screen declares it below the fold: `scrolled` in `lib/screens.ts`, plus `iosBelowTheFold` in `lib/iphone/screens.ts` for what the 667 pt iPhone SE leaves below the fold of the Android matrix's screens. Every other element outside the screen is unreachable, with the finding `outside the screen`. The report prints `clipped` and the reach percentage per screen.
  - **iOS chrome order and labels are modelled from UIKit's state, not read from an accessibility client.** UIKit's bars are not accessibility elements until a client runs, so the dump has no navigation bar title, back button, search field or tab bar item. The harness builds them from `uikitState` (the real titles, `hidesBackButton`, tab titles, accessibility labels, badges and enabled flags; guessed frames), marks them `synthesized`, keeps them in the order model (back button, then the title) and leaves them out of `interactive`, `reachable`, `labeled`, `actionable` and the other counts: a label the harness wrote proves nothing. `chromeModelled` counts them per screen. A declared control that only a modelled element carries is present, not counted; one the model lacks is unreachable. Every shown controller stack is modelled, the ones under a presented sheet or modal marked `covered`: they join the focus-trap check only when the dump shows no modal view hiding what lies under the sheet (`ignoredSiblings` 0), the way the covered screen's own content does.

**probe** is the device check of the native screens that no gate can express (SPEC.md, "Native screens, iOS", "Verified on the device"): `run=probe:<names>` (`lib/native/dev/probe.ts`) puts a screen in a state, does through `SvelteQA` what a user would (scroll the first scroll view, type into the search field, move a sheet to a detent, press the system's escape on it, focus a text field) and writes what UIKit reports (`uikitState`: navigation bars and their items, sheet detents, tab items, the keyboard's frame against the field's) and the accessibility tree to `qa/runs/probe-<device>-<stamp>-<direction>/<name>.json` with a screenshot beside it. Probes: `large-title`, `translucent`, `search`, `sheet`, `dismissal`, `reset-form`, `reset-modal`, `reset-sheet`, `back-form`, `back-modal`, `back-sheet`, `tabs`, `keyboard`, `keyboard-sheet`. It cannot press a screen the way a finger does, so the system's own gestures (the sheet's drag, the swipe-down dismissal, the edge swipe) are exercised only through the equivalent API calls and the escape action.

**Crash reports.** An app that aborts after it wrote its results (at the end of the last scenario, or while the harness ends it) leaves nothing in `lab-results.json` or `boot-report.json`: the run read "complete". Only the system's crash report says so (on 27 October the lab phone held 38 of the QA app, all `SIGABRT`s with the same stack: an `NSRangeException` thrown in `-[SvelteTabView unmountChildComponentView:index:]`). Every iOS command (lab, boot, parity, a11y, probe) therefore reads the phone's crash log twice through the Mac (`lib/iphone/crash-reports.ts`): once when it starts, after the install, and once at the end, after the app is ended and 5 s have passed (the system writes the report a moment after the process dies).

- *The pull* has two doors, both through the Mac. `devicectl` (CoreDevice) lists the log (`xcrun devicectl device info files --domain-type systemCrashLogs`, about 1 s) and copies the new reports one by one (`device copy from`). The second is the phone's own crash-report service over USB: `idevicecrashreport -k -u <udid> -f <name> <scratch directory>` on the Mac (Homebrew's `/opt/homebrew/bin` and `/usr/local/bin` are added to the PATH), once for the app's process name and once for `JetsamEvent`, which copies the files whose names contain the filter (about 50 files, 1.4 s on the lab phone, retired ones included) and never a sysdiagnose archive. `-k` keeps the reports on the phone: without it the tool deletes them there, so it is never run without. A USB copy counts only when the tool exits 0 and prints `Done.`; the new reports are told apart by file name exactly as with the listing, and only they come back over `scp`. A Mac without the tool, or a phone `usbmuxd` does not list (the cable, a locked phone), is an error with the tool's own words, never an empty list. The order is `devicectl` first and USB when it fails, except after a UI test (`gestures`, `resilience`): CoreDevice stays wedged after an XCUITest run until the phone is plugged in again, and every `devicectl` call then costs its whole limit, so those commands read USB first and `devicectl` second. The start of a command tries the same two doors, so a CoreDevice that does not answer at the start does not leave the run without a baseline. The record says which door read the log at the end (`crashLogRead`: `devicectl` or `usb`); a run where neither answered is `crashReportsError` naming both.
- *Each report* is `{ file, capturedAt, processStartedAt, pid, exceptionType, signal, reason, framesOf, topFrames }`. `reason` is the exception's message (`exceptionReason`, with its name), else the abort's own words (`asi`), else the termination's, at most 300 characters. `topFrames` are 12 frames (image, offset, symbol): `lastExceptionBacktrace`'s, where an exception was thrown (the faulting thread's first frames of an Objective-C exception are the runtime's abort code, and the app's frame comes after the twelfth), or the faulting thread's when the report has none (`framesOf` says which). A jetsam event counts only when the system killed the app (an entry named `ExampleSvelteQA` with a `reason`; the lab phone has none for the app yet, so that shape is read from the entries of the processes it did kill); a report of the app that cannot be read is a report with `exceptionType: null`, never dropped.
- *New since the run started* is decided by file name: the reports whose files were not on the phone at the first pull. No clock is involved, so the phone's and this machine's may differ by anything. (A moment on the phone's clock would also need the first pull, and would miss a report written late for a crash before it.) A report the system wrote late for a crash of the previous command's app is new to this command and is listed `unattributed`.
- *Attribution* (lab and boot) is by process: the report names a `pid`, each lab run and boot launch records the pid `devicectl` launched, and a report belongs to the run whose pid it names and whose process started before the report was captured (the harness's start of the run for a lab, the kernel's `processStartMs` for a boot launch). That is the one place the two clocks meet; it has 60 s of slack, so a pid the phone reuses long after a run is not that run's. A report no run owns is `unattributed` and counts all the same. A lab run whose app aborted is `complete: false` with `crashes` saying "the app aborted after it wrote its results: <reason> (<signal>, <file>)" (when the harness had already found the app gone it is the same crash, explained, not a second one), so `lab.incompleteRuns`, `lab.runs` and `log.fatals` count it; a boot launch keeps its display time (it was measured before the abort) and its `crashes` becomes 1 (`boot.fatals`). Parity, a11y and the probe launch the app several times for one result and attribute nothing: their reports are listed.
- *The record*: `crashReports` (the new reports, each with `attributedTo`: `lab 3`, `warm 7`, `cold 2` or `unattributed`; empty when there are none) or `crashReportsError` (why they could not be read: before the run, after it) in the run file, printed at the end of the command, and the `.ips` files in `qa/runs/<run file name>-crashes/`. The probe writes `crash-reports.json` in its directory and also lists the reports when it fails because the app died. `report` prints the reports of each run file under the device.
- *The gate* `log.crashReports` (iOS, `<= 0`) counts them over the newest lab, boot, parity, a11y, resilience and gestures files. A file whose pull failed or that has no record (a run from before the pull) is `not measured`, which fails, never 0.
- *The clock*: the times in a report (`capturedAt`, `processStartedAt`) are the phone's own, as an instant (the report names the phone's UTC offset). They are compared with this machine's clock only in the attribution check above.

Which `ios` bars have a measurement: `lab.*`, `checks.*`, `frames.*`, `list.virtual300.mountMs` (the lab), `boot.*` (boot), `log.fatals` and `log.engineWarnings` (sums over the lab and boot runs: a dead app, the crash reports of the phone and the JavaScript errors the app reports are fatals, an app that reports none leaves `log.fatals` not measured; the Android engine's warnings do not exist on iOS, so that sum is 0 by absence), `log.crashReports` (iOS only: the reports the crash log gained during the runs), `parity.*` and `a11y.*`. The sample-size bars are the production ones (`lab.runs` 10, `boot.*.samples` 30), so a short run reads as a miss until the full series is run: `lab --repeat 10` is about 35 minutes of device time, `boot --warm 30 --cold 30` about 25.

Not covered on iOS, and why (the run files list them): the startup screen's loading and error states, which need the app's HTTP held or refused (a system proxy setting of the phone); every text size but the standard one (Dynamic Type is a setting only the Settings app changes); resilience, soak and crash runs (the Android runners are `adb`/logcat/`dumpsys` based and have no iOS counterpart yet), so `resilience.*`, `soak.*`, `memory.*` and `crashes.*` read "not measured" for the iPhone (the phone's crash log is read by every command, "Crash reports" above).

## Profiling a lab scenario on the iPhone

`xctrace` on the Mac records the lab phone without the harness: `xcrun xctrace record --template 'Time Profiler' --instrument 'dyld Activity' --device <hardware UDID> --time-limit 65s --output X.trace --launch -- io.example.svelteqa`, and 14 s later `xcrun devicectl device process launch --device <devicectl id> --payload-url 'example-svelte:///__dev?run=navigation-8&token=t' io.example.svelteqa` (no `--terminate-existing`: the lab opens in the process the recorder started; `--attach` by name fails on this phone, and `Blank` is not a template). Run it over `ssh` in the background and wait for `Output file saved`: saving takes as long as the recording. `dyld Activity` is what gives the trace the images' load addresses, so the app's own frames come symbolicated (without it only the system's do; adding more instruments, `Core Animation Commits` among them, made the recorder fail with a modeler error, and the `Logging` template with `Runloops` gives the run loop's busy turns without sampling). Export with `xcrun xctrace export --input X.trace --xpath '/trace-toc/run[@number="1"]/data/table[@schema="time-profile"]'` (the elements are deduplicated by `id`/`ref`; the stack column is a `tagged-backtrace` holding a `backtrace` of `frame` elements) and `runloop-intervals` (a `Busy` interval is one turn of the main run loop). A lab that the recorder launched writes `Documents/lab-results.json` only up to the scenario before the last one it finished: read the numbers from a harness run, and the cause from the trace. The frame monitor ticks on the main thread (Reanimated's display link), so an interval over 25 ms is a main-thread turn of about 8 ms or more that started within a frame of the last tick: look for turns that long, and for what UIKit does in them.

## iPhone crash log

`lib/iphone/crash-reports.ts` (the "Crash reports" the gate table above refers to). Every iOS command lists the phone's crash log when it starts (`xcrun devicectl device info files --domain-type systemCrashLogs` on the Mac: names, sizes and dates, about 1 s on the lab phone) and again 5 s after its app was ended. The reports that were not in the first listing and are the app's (`<process>-<date>.ips`, where the process is `ExampleSvelteQA` or `Sveltesmoke`) or a jetsam event (`JetsamEvent-*.ips`) are copied one by one (`devicectl device copy from`, about 1 s each), read, and attributed to the run whose process they name. Nothing else is copied.

The log is not small: it holds a sysdiagnose archive of about 270 MB for every UI-testing start that timed out (seven of them, 1.6 GB, on 1 Nov 2026), and the first pull (`idevicecrashreport` without a filter, which copies the whole log through the phone's crash-report mover) took minutes, past the 180 s the harness allowed, while its script went on orphaned on the Mac and the next pull queued behind it. A listing costs nothing whatever the phone holds, and a report shows in it a few seconds after the crash with no mover (measured with a deliberate SIGABRT: 4.5 s). Each call to the phone runs under an `alarm` on the Mac (40 s, a listing twice), so a call that hangs ends there and does not go on holding the phone. The USB door asks `idevicecrashreport` for the two name filters only (`-f <process>`, `-f JetsamEvent`), so the archives are never copied either. A listing or copy that fails through both doors is `crashReportsError`, which leaves `log.crashReports` `not measured`. The harness never deletes anything on the phone: the archives stay until the owner says to remove them (Settings > Privacy & Security > Analytics & Improvements > Analytics Data, or Xcode's Devices window).

After a UI test the commands print which UI-testing processes are still on the Mac (`xcodebuild`, `xctest`, `XCTRunner`, `testmanagerd`, `CoreDeviceService`; nothing is ended but the test the command started), so that a CoreDevice that stays wedged can be traced to one of them.

## Native module smoke test

Three apps come out of `app.config.ts`: the product (`io.example.sveltenative.qaproduct`), the QA app (`io.example.svelteqa`) and the smoke app (`APP_VARIANT=smoke`, `io.example.svelteqa.smoke`, "Svelte smoke", scheme `example-svelte-smoke`). The first two link the same native modules (a test compares their autolinker output, package for package, and SPEC.md compares the generated `PackageList.java` and `ExpoModulesPackageList.kt` with those of `c75c31491`); only the smoke app adds the libraries of the smoke test that are neither the product's nor the four the library carries (the vendored react-native-quick-crypto, react-native-quick-base64, react-native-mmkv and react-native-nitro-modules, which every app links), their config plugins, the fake Firebase files and the Huawei repository. A fresh checkout or CI builds and measures the QA app without any of that.

`gates.json` pins the modules a smoke run must report (`smoke.modules`, per platform; today the same 35) and the skips that are expected (`smoke.skips`: Android and iOS `hms` and `web-browser`), and gates, for every role and in their own lane (`gates --smoke`; `gates` leaves them out, and `report` prints them apart once a smoke run exists, with the smoke run's own warnings): `smoke.complete >= 1`, `smoke.fatals <= 0`, `smoke.failed <= 0`, `smoke.missing <= 0`, `smoke.unexpectedSkips <= 0` and `smoke.ok >= 33` (Android and iOS), the pinned modules less the expected skips. A module that logged `fail` counts as failed; a pinned module no line reported (the app crashed before it, a call never returned and the next ones did not run, or the list names a module the app does not know) counts as missing, so a run that dies half-way fails by its missing modules; a run that crashed, was interrupted or logged no completion line is not complete, whatever it reported before. A `skip` is a report and passes only where the platform lists it: Huawei's library on a Samsung (on a Huawei or Honor device it is `ok`), `web-browser` where no browser has Custom Tabs, an Android-only library on the iPhone. `native-qa smoke` itself exits 1, naming the gate, when one of these fails. `qa/test/smoke.test.ts` pins the list against the checks in `smoke-checks.ts`, the module table and the dependencies, and runs both autolinkers for the three variants; `qa/test/bundle.test.ts` bundles the JavaScript of the three, and of the combinations the lab tests need (nine bundles, about a minute), and checks that the product's and the QA app's carry none of the smoke-only libraries (and all four packages the library requires or carries, the real ones), so the JavaScript boot gate measures what it measured before the smoke test plus what the library itself needs. It also lists each bundle's modules and checks that the product has no development lab (no `/__dev` route, no module of `src/lib/native/dev` or `src/routes/__dev`), that the QA app is the product plus the lab, and that the product is smaller by the lab's size; `qa/test` is the QA app's own: the lab is its whole point. After `report`, the device's line reads `smoke 33 ok, 0 failed, 2 skipped, 0 missing of 35 pinned`, and the module that failed is named.

The smoke run is an explicit step (`pnpm native-qa:smoke` builds the smoke app, runs it, reports and runs `gates --smoke`); `native-qa:emulator` does not run it, because it would mean installing a second app on every pass. The two apps can be installed side by side.


## Foreign: the native-view libraries

`native-qa foreign` checks the fourteen native-view libraries (expo-image, expo-blur, the library's own `BlurView`, expo-linear-gradient, react-native-video, datetimepicker, lottie-react-native, react-native-pdf, react-native-view-shot, rive-react-native, expo-conic-gradient, react-native-fast-shadow, react-native-animateable-text, react-native-svg: SPEC.md, "Foreign views", "Device verification of the libraries") on a device. It opens the lab twice, `run=foreign-libraries,drive:adb` (each library mounted inline, in a row of the windowed List and in a native sheet, and checked there) and then `run=foreign-leftovers` (the capture files the first launch's dead process left in the cache directory are gone), reads the release bundle's source map for the libraries' own JavaScript (`React stays out`), and writes `qa/runs/foreign-<device>-<stamp>.json`.

Every check is a line of its own in logcat (`[Svelte foreign library] {"library","where","name","passed","detail"}`), so a failure names what was read and what was expected. A check reads the platform where it can: the class Android built for the view and its size (`SvelteEngine.inspect`), the colours of a capture of the section against what a prop says they are (`captureRef`, then `SvelteQaPixels.sample`), an event the library raised, a command's own answer, the string the native text holds, and the pressed date dialog's answer (the harness taps its buttons with `adb input` when the lab asks, `drive:adb`). A check the platform cannot make is `skipped` and reported, never passed: on Android every check can be made, so `foreign.<library>.skipped` is gated `<= 0` (a skip would otherwise hide a check that stopped running behind a green gate), and `foreign.<library>.checks` is gated `>=` the count a clean run makes (all three places), so a check that quietly stops running fails too. The count moves when a check is added or removed on purpose: re-pin it in `gates.json` in the same commit. Hermes writes a string to logcat with `'` as `\'` and `\` as `\\`; the parser undoes that, and a tagged line that still is not a check (cut, not JSON, an unknown place) is counted in `foreign.unparsedLines` (gated `<= 0`) and printed, never dropped.

*Android below 12.* `RenderEffect` starts at API 31; before it the view draws a stronger tint and blurs nothing (`BlurRules`: a tint of 0.30 to 0.75). `Ctx.canBlur` is false there (the lab reads `Platform.Version`), and the checks that tell a blur from a tint read the opposite: at 100 the edge stays hard (the near pair as far apart as the far pair, at least 20) and the red stripe's green is lifted towards white (above 140), and the contrast (`near`) falls as the intensity grows, 1 over 50 over 100. The other pixel checks hold unchanged. The branch is the API level and not what the capture shows, so a blur that never draws on Android 12 and up fails the three checks above and the fallback does not hide it (`qa/test/foreign-blur.test.ts`).

*Software GL, and the capture's own fallback.* The emulator draws with SwiftShader: the render effect is the same and slower, and a capture may show a prop a frame or two after it was set. A capture whose GPU frame does not arrive in 3 s (`GPU_FRAME_MS` in `Capture.kt`) fails or is drawn again in software, where the view can only tint. Every reading therefore waits for what it asks (`lookUntil`: the capture again every 400 ms, and a capture that failed is taken again like any other that is not wanted, for 14 s, 24 in a row: room for a timed-out frame, the one after it and the settle) and only then judges; a prop change is followed by 400 ms before the first capture. `qa/test/foreign-blur.test.ts` runs the checks against a model of the capture (a Gaussian blur, a tint, a band, a chip; Android 12 and up, iOS, the tint-only fallback and the ways of being broken: a tint instead of a blur, a blur a third too weak, a radius that ignores the intensity, a picture off by 6 dp or more, a tint that ignores its prop, a floor lowered; with a native view that lags its props, a tint that comes on slowly, captures that fail and a software first capture).

*The list row on the Samsung.* The first Samsung run (main at `f46221b`) had the blur gradual inline and in a sheet and not in the windowed list's row, where the picture and the tint were right and the ratio was 1.00 at every intensity (the three checks that need a blur failed and the other six of the nine pixel checks passed, which a tint over the live stripes passes too). The next run, on the PC's emulator (12 Nov), named it: the row's view was ready since its intensity-70 picture, the lab's intensity 0 is a frame in which the view draws nothing, the renderer dropped the display list of the node that holds the picture (`RenderNode.hasDisplayList()` answered false), and at 100 the picture equalled the one on show, so it was not recorded again and the node drew nothing (a blurred tint over sharp stripes: every number of the Samsung's log). Inline's and the sheet's view are attached again by the engine after their first frames, which is why they passed by accident. `Backdrop` now asks the node and records again when it is empty (`BlurRules.nodeLost`), and the same session fixed a view that stayed a tint on a quiet pushed screen (it asks again after 100 ms without a frame under a layer, `BlurRules.afterQuietWait`); the log says each (`the node had lost its display list ... recorded again`, `... with no frame for 100 ms: asks for one`). The quiet case has no place in the lab (every page of it has something else that invalidates the screen): it was checked by hand on a pushed screen that held a plain `View`, five stripes and a `BlurView`, nothing else, with `adb shell am start -a android.intent.action.VIEW -d <example-svelte:///...>` and a screenshot. iOS has no recorded view tree for it yet: `qa/test/ios-foreign-pins.test.ts` lists `svelteblur` as not recorded and fails the day its tree is added to `samples/ios-foreign-trees.json` without taking it off the list. `--only image,video` narrows the libraries: the others' `failedChecks`, `checks` and `skipped` gates then read `not measured`, and `libraries.missing` counts only the asked ones (a narrowed run is a bisect, not a verdict on the rest). `--attempts <n>` (default 3) launches a scenario again when another app took the screen from it (the shared emulator also runs other agents' apps); the launch records how many attempts it took. The lab alone: `lab --run foreign-libraries,only:image.video` (a scenario of the lab, outside `quick`). Both platforms are judged (`bar` names `android` and `ios`): the iPhone has its own counts, below.

**On the iPhone** (`foreign --platform ios`, `commands/ios-foreign.ts`): the same two launches (`run=foreign-libraries`, then `run=foreign-leftovers`, the app ended after each) opened by URL with a token through `devicectl`, as `lab --platform ios` does, and the same run file (`foreign-<device>-<stamp>.json`) and gates. The phone has no log to follow, so the lab puts every check and every skip of the scenario into the `detail` of its entry in `Documents/lab-results.json` (iOS only; Android's scenario detail is unchanged and its checks stay one logcat line each: `foreign-records.ts`, pinned by a test), and after every place into `Documents/foreign-progress.json`, which the harness reads when a launch ends without finishing (the app died, the time ran out) so that the run file says how far it got. Nothing is driven from the harness (`drive:adb` is Android's date dialog and XCUITest does not run on this phone): a check that needs a finger is a skip with its reason.

Three kinds of difference from Android, kept apart so that a hole cannot hide in a number:
- *Android-only checks* read an Android fact that iOS does not have (the date and time dialogs of `openDatePicker`, the video's `SurfaceView` and the capture option that draws it, react-native-fast-shadow's native view and the engine's canvas clip, the engine's frame and node counters). The lab reports each on iOS as `androidOnly` with the reason; they are counted in `foreign.<library>.androidOnly` and are neither checks nor skips.
- *Checks that read the same thing from another place*: the class of the view (`SvelteQA.inspect` gives UIKit's; `src/lib/native/dev/foreign-pins.ts` pins each library's own view from its iOS source and from the trees the phone printed, in the two spellings iOS uses: the section's own view by `NSStringFromClass`, module-qualified for a Swift class (`ExpoImage.ImageView`), and every view below it by Swift's `String(describing:)`, which has no module, shows `ContainerView` for the class lottie exports to Objective-C as `LottieContainerView`, and spells a generic class with its arguments (`HostingView<ConicGradientProps, ConicGradientView>`, the SwiftUI view of expo-conic-gradient); `qa/test/ios-foreign-pins.test.ts` holds every pin against the first iPhone run's trees and fails each pin when the library's view is absent; two pins are only as strong as a plain React Native view: `capture` mounts no library view at all and `shadow`'s card is a plain `View`, since react-native-fast-shadow has no iOS code, so their mount check holds the lab's layout rather than a library class), the text of the animated text (the paragraph view's `attributedText`), the capture's shadow (layer shadow props on iOS, `elevation` on Android), the picker (a view with props and events on iOS, a dialog on Android: the QA module gives the `UIDatePicker` what a finger gives it, and the library's own path from the control event to `onValueChange` and `onDismiss` is what is checked).
- *Skips*: a check iOS could make with a finger that the lab has not (a press on a shadowed child or on an `Svg`). `foreign.<library>.skipped` is gated at the count a clean iPhone run has, never more.

`gates.json` pins the iPhone's counts per library (`bar.ios`: `failedChecks` at most 0, `checks` at least the count a clean iPhone run makes, `skipped` at most the skips a finger would avoid), `foreign` is one of the iPhone's run kinds, and its `foreign.ios` table says, for each library, why its counts differ from Android's. `checkGatesFile` refuses a pinned library whose foreign gates lack an iPhone bar (`evaluate` walks the bars, so a gate without one is never judged there), a count that is not Android's with no reason, and a reason for a count that is Android's. The counts are those of the first iPhone run's structure (3 Nov: 393 checks, 78 Android-only checks, 6 skips for a finger), whichever of its checks passed (the built-in `BlurView`, added on 11 Nov, has no iPhone run yet: its bar of 39 is the structure its checks make); a check added or removed on purpose re-pins its bar and rewrites its reason in the same commit. The build's JavaScript modules for "React stays out" come from Metro's source map of the same tree, which `build --platform ios` makes on the PC (`qa/out/ios-bundle.map`, `lib/ios-bundle.ts`): the Xcode build keeps none. The run's `bundle.matchesBuild` is true only when the app's reported build is the recorded one.

## Classes (the `css` option)

The QA app uses `class` (the library's own CSS compiler, docs "Styling", "Classes"): `apps/qa/src/global.css` is `@import "tailwindcss";` (Tailwind 4.3.5, a development dependency, exact) and one class of the lab's own, `.qa-card`, in the `components` layer with a dark override; `metro.config.cjs` gives it to `withExpoSvelte` as `css`. The product variant (`APP_VARIANT=production`) gets no table: it has no lab and no class of its own, and Tailwind reads every word of `src/` as a candidate (`flex`, `border`, `container`, ... are classes), so the table would be bytes the product never reads.

The lab's page (`/__dev`, "Run all checks") adds **10 functional checks** to the 28 of its own runner after the animation check, which is why `checks.passed` is gated `>= 38` on both platforms (`qa/test/class-checks.test.ts` counts the page's own `check(...)` calls, holds `28 + the class checks` against `gates.json` and keeps the result line under logcat's 4 KB cut: the Android harness counts the entries of that one line, and the 28-check line was 2,224 characters). They run on views of `ClassProbe.svelte`, which the page mounts for the length of the run only (the screens the parity suite freezes do not show it); each is a `<View>` imported from the package, so the page lowers it to a host tag, and `{@attach}` hands the check the renderer's own node (`bind:this` is refused by the custom renderer). The check reads what the host sends for that mounted node on the device: `mergeHostProps(node.peekProps())` (`native-props.ts`, which the host itself calls and the library's `./renderer` entry exports for this), whose `style` is `nativeClass` (what the resolver made of `class`, on Hermes, from the table in the bundle) under `nativeStyle` (the element's own style). The check does not merge the two itself, so a host that put the class over the inline style fails the inline check (`qa/test/class-probe.test.ts` runs the real merge with its order swapped and the check fails).

| Check | Reads |
| --- | --- |
| `p-4` | 16 on the four sides |
| `p-4` reaches the layout | the one check that reads the native side: `measureInWindow` of the padded view and of its child, which sits 16 dp in from each side |
| `bg-sky-500/50` | `rgba(0, 166, 244, 0.5)`, sky-500 at half opacity |
| `md:` and `max-md:` | `p-2 md:p-10` is 8 on a phone-width window (`md:` absent) and `p-2 max-md:p-10` is 40 (`max-md:` applies); at 768 dp and over the check expects 40 and 8: the expected values follow the window's width. `class-probe.test.ts` runs a resolver that applies `md:` everywhere and one that never applies `max-md:`, and the check fails on both |
| `dark:` | `bg-white dark:bg-zinc-900` is white, then zinc-900 after the app's appearance is set to the scheme the device is not in (`Appearance.setColorScheme`, the library's documented override), and the override is taken off (`"unspecified"`) and waited for |

The `dark:` check is the only one that changes the system's view of the app: it picks the opposite of the device's scheme, so it is a real change on a phone in either mode, and a platform that never announces the change fails it with the colours it read. `qa/test/class-checks.test.ts` holds every expectation against the table that `expo-svelte css` makes of `src/global.css` and `qa/test/class-probe.test.ts` runs the whole page flow on the host with the real table, resolver, renderer, probe and runner and a stand-in platform (the scheme, the window, a layout). Measured on 11 Nov 2026 (`expo export:embed`, release, not minified, as `qa/test/bundle.test.ts` makes it): the QA bundle went from 5,767,609 to 5,808,942 bytes, 6,292 of them the class table, 11,635 the built-in BlurView's section and checks and 23,406 the class probe, checks and runner; the product variant stayed at 4,108,744. The QA bundle's 1 % over the reference commit's size is exceeded by that, and moving the baseline is the owner's.

The lab has a screen written with HTML elements and classes alone (`/__dev/html`, `src/lib/native/dev/HtmlScreen.svelte`; the app's own files are lowered, so no component of the library is imported): a card whose `text-lg text-sky-900` is inherited by the text inside it, with `h1` to `h3` and a `p`; a flex row of two spans (`justify-between`); a block `div` with text, spans and an `<a>`; a form (a text input, a password input, a checkbox, a submit button and a `type="button"` one); an `<hr>` and a `<pre>`. It is a parity and accessibility case, `html-elements` (light and dark, on Android and the iPhone, the standard and the largest text on Android; the capture mode of the iPhone's lab knows it, `capture.ts`), static until something is pressed, so a reference is stable. `qa/native-qa.ts parity --device <serial> --missing` takes the references; none are in the repository yet.

The lab's checks (`/__dev`, "Run all checks") mount the same screen after the class checks and run **6 functional checks** on it (`html-lab.ts`, expectations in `html-checks.ts`), which is why `checks.passed` is gated `>= 49` (28 + 10 class checks + 6 + the 5 of "Transitions", `qa/test/class-checks.test.ts` holds the arithmetic and the length of the result line). They read the mounted host tree: `{@attach}` keeps the renderer's node of each element, a node's props are read through `mergeHostProps`, its children through `getSnapshot().children`, and what the host built for it through `hostState` (`viewName`, `flex` and the props it gave the native view, with the inherited text style and the element's default style in them: the host's own record, which its own tests read through a fake Fabric). `hostState` is internal to the host, so a change of its fields fails the checks, which is what they are for.

| Check | Reads |
| --- | --- |
| text inherits colour and size | the card's own style (`text-lg`: 18, `text-sky-900`: `#024a70`), and the style the host gave a `p` of the card and a span of its flex row, which sits in a view between them |
| a flex row has 2 items | the row was laid out as items (`flex`), its two elements each a text of their own (`RCTText`), not spans of one line |

`qa/test/html-probe.test.ts` runs the whole flow against the real pieces (the class table, the lowering, the renderer, the Fabric host and the lab's runner, with a fake Fabric binding) and breaks the library's source as the bundle reads it, one thing at a time: the host stops inheriting text style (the inheritance and the heading checks fail), `isFlexContainer` answers no (the row), the inline elements stop being one line (the block), `h1` loses its factor of 2 (the heading), the submit event's `preventDefault` does nothing, the submission never reaches the form or a button that is not a submit button submits (the submit check), `type="password"` stops being secure (the password check): each fails exactly the check named for it and the real host passes all six. `qa/test/html-checks.test.ts` holds the expectations against readings that are wrong, the values they name against the class table, and the reading of a tree.

**The span press** (`gestures-span`, "Gestures"): a `<p>` of two lines with an `<a>` that begins the second, three taps by the same injectors as the other scenarios (`adb input tap` on Android; an XCUITest tap on the iPhone, which takes the same rectangles): the link (the link presses, the paragraph does not), the first line, and beside the link on its line (the paragraph presses, the link does not). The step is over when a `Tap` around the paragraph has counted the tap, so a tap that presses nothing still ends it. ## Transitions

The lab has a screen of Svelte's transitions on HTML elements (`/__dev/transitions`, `src/lib/native/dev/TransitionsScreen.svelte`, written with HTML and classes alone): a card with `in:fade` and `out:fly` that a button shows and hides, a keyed `<ul>` whose items `animate:flip` when a button shuffles it, and a panel with `transition:slide` that a button opens and closes. The host plays them on the UI thread with Reanimated (`fabric/transitions.ts`). The route opens the screen settled (the card shown, the panel open: a block that is there when its screen opens plays nothing), so it is a parity and accessibility case, `transitions` (light and dark, on Android and the iPhone, the standard and the largest text on Android; `capture.ts` knows it) with no animation running when it is photographed. `qa/native-qa.ts parity --device <serial> --missing` takes the references; none are in the repository yet.

The lab's checks (`/__dev`, "Run all checks") mount the same screen after the HTML checks, last because they take about eight seconds of real time (the screen's durations are in `transition-checks.ts`: 400, 600, 500 and 1,200 ms), and run **5 functional checks** on it (`transition-lab.ts`, expectations in `transition-checks.ts`). `{@attach}` keeps the renderer's node of each element; nothing in the lab plays an animation or works out a frame, each check reads what the host and Reanimated left. The reads: `getAnimations()` of the node and the `currentTime` of its animation (which is the value of the animation's shared value, a read that asks the UI runtime), the animation state the host keeps on the node (`dom.animation`: the animations that draw it, the values it is still writing back, its worklet), the props the host built the view with (`hostState`: its style, and `collapsable: false` for a view an animation draws), and the box React Native reports for the view from the committed tree (`nativeFabricUIManager.getBoundingClientRect(node, includeTransform)`), with and without the committed transform, which has Reanimated's last values over it.

| Check | Reads |
| --- | --- |
| intro ends: the node's own props | after `in:fade` has ended (`introend` once): no animation on the node, nothing drawing it, no values waiting to be written back, no worklet or `collapsable: false`, `opacity` 1 or unset, no transform, and the committed box with the committed transform is the box without it |
| outro keeps the node until its end | `out:fly` (600 ms): the node is still in the tree at half of it, `outroend` comes once, and the node leaves after its duration (within 100 ms before it and 1.5 s after) |
| flip ends in identity, new order | after a shuffle: an item was drawn off its layout box while the flip ran, and when it is over every item has no animation, its committed box is its layout box (the committed transform is identity), and the items sorted by their committed `y` are in the order Svelte was given |
| reversed intro removes the node | `transition:slide` closed when it was a sixth of the way open: the intro was running at the reversal, `outroend` comes once, the node leaves the tree, and the values the host writes back have all been written (`restore` is empty) |
| animation runs while JS is blocked | the progress of the slide (read before and after the JavaScript thread is blocked for 300 ms with a busy loop) advances by at least 60 % of the time it was blocked and the animation has not run out: the progress is the UI runtime's, and the JavaScript thread's timers did not move it |

The signal of the last check is the host's own: `Playback.currentTime` of a running animation is its shared value, which the UI runtime moves and a read from JavaScript asks it for; the lab's older check of the runtime (`verifyAnimation`, "Reanimated UI runtime continues while JS is busy") is the same measure with a shared value of its own, and this one is the shared value of a real transition.

`qa/test/transition-probe.test.ts` runs the whole flow against the real pieces (the class table, the lowering, Svelte's own transitions, the renderer, the Fabric host and the host's animation layer, with the lab's runner) and breaks the library's source as the bundle reads it, one thing at a time. The platform is a stand-in: a fake Fabric binding (a layout of the committed tree, with Reanimated's props registry over the props of every commit, as its commit hook does) and a Reanimated whose UI thread is a virtual clock: an animated shared value is a function of the clock, the mappers run each frame, the animation's callback is called when its time is up, and the JavaScript thread's timers run only when the test lets the clock go on, so the lab's busy loop (a few hundred reads of the clock) stands still for JavaScript while the UI side moves. Each of these fails exactly the check named for it, and the real animation layer passes all five: the node's worklet and `collapsable: false` never taken off after the animations end (the intro check), an outro that ends at once instead of after its duration (the outro check), the values written back when a flip ends being the animation's first frame instead of the node's own, so that Reanimated's last values leave the item displaced (the flip check), the values to write back never given up for a node that has already left the tree (the reversal check), and progress that a JavaScript timer moves instead of the shared value (the check of the UI thread). `qa/test/transition-checks.test.ts` holds the expectations against readings that are wrong and the screen against the durations the checks wait for.

**The flash of a flip is not checked on a device from the app.** The failure a flip can have that these checks do not see is the one the engine's `holdMounts` exists for: a frame drawn between the two commits shows the new order with no inverse transform, for one or two frames. A detector that captures frames during a shuffle and fails when one shows an item at its new place without its transform would have to see every frame, and the app cannot: the capture the lab has (`SvelteQaPixels.sample`, the engine's `Capture.kt`) is one view's pixels per call, a round trip to the main thread and a copy of a GPU frame (which can take seconds when it falls back to software), so a burst of them during a 500 ms flip gives a few frames at best, and a flash of one or two frames would pass unseen: a check that can only fail when it happened to look is not a gate. The evidence stays what it was: `adb shell screenrecord` of the shuffle at the device's frame rate, flagged frame by frame on the host ("Transaction order" in the engine's `SPEC.md`).

## Signed-in phase (parity and a11y)

`parity` and `a11y` have a second phase for the screens of an app with an account (the cases with `signedIn: true` in `lib/screens.ts`). **This repository's example app has no account, so it has no such case**: `signedInCases` is empty, `gates.json` `signedIn.android` is an empty list, the phase never starts, and what follows is the machinery for a project that has one (D15: the signed-in screens of the app this code came out of stay with that app). With cases, the run does the signed-out cases first (a sign-in screen needs a signed-out device), then signs in **once**, visits every signed-in case in every variant, and signs out. `parity --filter <id prefix>` or `a11y --filter <id prefix>` runs this phase alone; `--device` is the only thing that changes between the emulator and a phone (a reference set is kept per device kind, like the others). A signed-in case sets `needsBackend: true` too, and the suites ask the backend at `QA_BACKEND_URL` (a page that answers 2xx while it is up) before they run one; with the variable unset the answer is "no backend is configured", and such a case is skipped (parity) or not dumped (a11y) with that reason.

**How it signs in.** `lib/signin.ts` types the address into the sign-in screen with `adb shell input text`, presses enter, types the code, presses enter and waits for the first screen of the signed-in app; nothing in the app takes the address, so the production bundle (and the QA app) carries nothing for it. The labels it looks for are one table at the top of that file, written for the sign-in the phase was first used with (an email address, a one-time code, a list of workspaces); a project with another sign-in changes that table and `signIn` together. The session lives in the app's SecureStore, so it survives the `am force-stop` every case starts with; the phase ends with the app's own sign-out button, so the signed-out cases of the next run find the sign-in screen again (a session an earlier, killed run left is signed out first). The code is the development backend's public one (`000000`) unless the backend was configured with a fixed code for one dedicated QA address, which is then `QA_ACCOUNT_CODE`: that code is a credential of the account like the address is, read the same way and kept out of every message and file. A backend that rejects the code says in the run file whether `QA_ACCOUNT_CODE` is set.

**How the account is supplied, and never printed.** The address is `QA_ACCOUNT_EMAIL` in the environment, else that one key read from `.env.local` at the repository root (gitignored, mode 600; no other key of the file is read, and the value is kept in the harness's memory, not in `process.env`). With none configured, nothing here is needed: every function of `lib/qa-account.ts` answers "none" or does nothing, and only starting the signed-in phase asks for it (`requireAccount`). It is a secret of the machine: it is never printed, logged, written to a run file or report, put in a file name or a reference, or passed in a URL or an intent (the one place it goes is the argument of `input text`, and any error that could quote that command is redacted). What stands behind that:

- the screens that show it mask it with the `account: "email"` selector, which matches the node whose text is the address; a mask that matches nothing refuses the reference, and so does a screen that shows the address outside the case's masks (`exposedAccount`);
- the pixels under a signed-in screen's masks (the address, a photo from the network, the account's devices) are painted over in one flat grey before the reference is written (`paintOver`), and in the `actual.png` a failure keeps, so no reference carries them; the comparison ignores them anyway;
- what the accessibility run keeps of a signed-in screen (focus stops, findings) is redacted (`redactDeep`), and every run file and the references' manifest pass `assertClean` when written, which refuses a file that contains the address;
- `pnpm native-qa leakcheck` looks for it in the files a CI would upload (the run files and the evidence of failed tries under `qa/runs`: `.json`, `.log`, `.txt` and the `.xml` of the raw dumps; `qa/out/*.log`, `build-*.json`, `lane-stages.tsv` and `gates*.md`; the report), then in the staged diff, the unstaged diff and untracked files and the manifests (`--staged` only the staged diff, `--all` every tracked file) and prints file names, never the address or its line. The uploaded files are read first, before anything needs git, and a git that fails is reported without stopping the rest. `--purge` deletes every uploaded file that holds the address (the lane logs, copies of console output, included; never a tracked file or a manifest); a file that holds only the fixed sign-in code is reported and kept, because six digits can be a pixel count. `--artifacts` reads the uploaded files and nothing else (no git) and passes when no account is configured. **This repository's workflow does not run it** (no account, so nothing to look for); a project with an account adds `node qa/native-qa.ts leakcheck --artifacts --purge` as a step that always runs before its artifact upload, and it cannot read a screenshot: the screenshots of a failed try are only as clean as the rectangles painted over them ("What is kept of the account in the evidence").

**D13 (3 Nov 2026): iOS gesture frames through XCUITest are a documented exception.** iOS injects touches only through XCUITest, and its synthetic touches get no touch boost while its runner loads the phone: the same `gestures-box` read 7.3 to 8.8 % dropped and 53 to 67 ms through XCUITest, 1.5 % with the JavaScript thread kept busy, and 0.3 % (one late interval of 301), 33 ms worst, driven by a finger (`lab --platform ios --run gestures-box` with no `drive:`; the person drags after the round is announced, about 2 s after the box shows). `gates.json` `exceptions` hold `gestures.frames.*` for the iPhone's `box`, `box-busy` and `pinch-rotate` under D13; the gesture checks stay judged.

**Gates and the pins.** `gates.json` `signedIn.android` pins the ids of the signed-in cases (an empty list here); `parity.signedIn.missing` and `a11y.signedIn.missing` count the pinned cases (in every variant) that a run did not compare or dump, and read nothing without a pin. **D12 (3 Nov 2026): the signed-in phase covers an app's account screens, not the library, so it does not block.** The two gates are `informational` (`"informational": "D12, D15: ..."` in `gates.json`: the value shows, nothing counts, with or without a device or a measurement), and `parity.incomplete` / `a11y.incomplete` leave out the signed-in cases the run recorded as skipped because its signed-in phase never started (`signedInPhase.signedIn` false: no QA account, no backend, or the sign-in was refused); `parity.signedIn.skipped` and `a11y.signedIn.skipped` count them. Every signed-out case that is incomplete still counts, a signed-in case the run never recorded still counts, and a phase that did sign in is held to all its cases; a project that wants its signed-in screens to block removes the `informational` entry of the two gates. The pin is what one full run captures and no more: every pinned screen in all eight variants (theme x direction x text size), less the states a case leaves out at the largest text (`largestText: false`, listed in `notCoveredStates`). `qa/test/signed-in.test.ts` holds the arithmetic against the matrix, with fixtures standing for such cases (`qa/test/fixture-cases.ts`: this repository has none of its own). A reference taken with a mask over the screen's own chrome (the title, a control, a modal's tab strip) is refused at capture and reported as an error by a check that would otherwise pass (`maskedChrome`), and its manifest entry is removed so that `--missing` retakes it. The iPhone's lab cannot sign in and runs the signed-out screens only (`iosNotCovered` says so). The accessibility oracle also counts controls under 48 dp (`a11y.smallTargets`, a `target` finding), which no gate judges.

## Gestures

`native-qa gestures` drives the gesture lab (SPEC.md, "Gestures (react-native-gesture-handler)"): the page `/__dev/gestures?mode=<mode>` and the stress scenarios `gestures-<mode>` (`apps/qa/src/lib/native/dev/gestures-lab.ts` describes them all: what to inject, when a step is over, what must have been counted). They are outside `quick`; any lab run can name them (`--run gestures-box,gestures-row`) and `native-qa gestures` is the command that injects the touches.

**The handshake.** A page opens a `Session` for its scenario round and logs `[Svelte gesture] ready` (`'[Svelte gesture] ready', '{json}'` in logcat) when it waits for input: `scenario`, `round`, `step` of `steps`, `drive` (`none`, `adb`, `qa`, `xctest`), `density`, `screen` (the engine overlay), `rects` (every view a step aims at, in window pixels: `measureInWindow` times the density; inside a sheet the page adds the sheet's current native translation, which layout does not know) and `input` (what to inject, in dp relative to a named rectangle: `tap`, `drag`, `hold` with an optional drift, `twoFinger` with a distance and an angle going from one value to another). When the step's effects were reported (`Step.done`) and its settle time (a spring, a fling) has passed, the page logs `[Svelte gesture] step`, then the next `ready`; at the end `[Svelte gesture] result`. The stress scenario returns the usual `[Svelte stress]` line: counters, frames and a verdict, with `detail.checks` (`[name, 1 | 0, value]`), `detail.counters` (`[begin, start, update, end, endOk, finalize, finalizeOk]` per handler), `detail.marks` and `detail.observed.frames`. `parseGestureLine` (`gestures-lab.ts`) reads the handshake lines and refuses a cut one. The stress run is `--run <names>,drive:<adb|qa|xctest>`: the `drive:` entry says who injects (none: a person, or a page opened by hand, which starts itself after 1.2 s).

**Android.** `--input adb` opens the lab with `drive:adb` and, for each `ready` line, runs `adb shell input tap | swipe` with exact pixel coordinates from the rectangles (a zero length swipe of 700 ms is a long press): one pointer through the real input pipeline; `input swipe` moves as fast as the shell can, so it proves counters, not latency. The harness checks the overlay is at the window's origin and the input stays on screen (`aimProblems`) and records it. `--input qa` opens the lab with `drive:qa`: the page itself calls `SvelteQaTouch.run(plan)` (`apps/qa/modules/svelte-qa-android` (`QaTouch.kt`), its own Expo module, listed in `expo-module.config.json`), which dispatches one `MotionEvent` per `Choreographer` frame to `EngineRoot` with the frame time as `eventTime`, two pointers included, and reports the event times and the touch slop the lab uses to say what a pinch should have read. It moves a finger the way the pipeline delivers one: each MOVE holds history samples every 4.17 ms (a 240 Hz panel) and a frame that came late (software GL misses frames) is preceded by the moves of the frames it missed, one per nominal period, so no event carries more than a period of travel and what is judged is the arbitration, not the emulator's frame jitter (`lateFrames` in its result says how often). It is compiled into every build and refuses to run unless the app is the QA variant (`io.example.svelteqa`). `both` (the default) does one launch of each and `gestures.agreement.mismatches` counts where the two disagree. `sendevent` on the emulator's touch device would be the end-to-end path for a pinch and is not built. `--run` takes short names (`box,row`); a scenario `adb` cannot drive (`pinch-rotate`) is left out of that launch.

**iOS.** Touches cannot be synthesized from inside the app without private API, so `--platform ios` uses an XCUITest bundle, `qa/ios-ui-tests/` (`make-project.rb` generates `GesturesUITests.xcodeproj` with the `xcodeproj` gem CocoaPods brings; `GesturesUITests/GesturesUITests.swift` is the test). The test opens the lab's link itself (`XCUIApplication.open`, iOS 16.4+: an app that `devicectl` launched is not one XCUITest observes), reads the `ready` JSON from the label of the element `gestures.status`, finds the view by its identifier `gesture.<name>` (the page's `testID`, so no pixel handshake) and performs the input with `press(forDuration:thenDragTo:withVelocity:thenHoldForDuration:)` (a drag goes 10 pt past the commanded distance: a Pan counts from where it activated), `pinch(withScale:velocity:)` and `rotate(_:withVelocity:)`, printing `GESTURES-ACTION {json}` for each. The first round's pushed-edge swipe (the one from 2 pt; the swipe from 100 pt and every other drag keep XCUITest's) is the exception: `SvelteQAEvents` (Objective-C, the bridging header of the Swift test) builds it from XCTest's own event record (`XCPointerEventPath`, `XCSynthesizedEventRecord`, private to XCTest and looked up by name), a 50 ms press and then one speed to the end, where the finger lifts while still moving. XCUITest's drag slows the finger over its last frames, and UIKit decides an interactive pop on the finger's motion as it lifts: when the last move of the eased drag fell short (4.5 pt of a 16.7 ms frame instead of 10) UIKit cancelled the pop at 68 to 71 % (2 runs in 8 on 16 Nov 2026), which failed `edge swipe popped the screen` with the arbitration right. `--edge-release` chooses how that swipe ends: `moving` (the default), `eased` (XCUITest's drag), `rest` (held still for 0.4 s at the end) or `fling` (no press first); any other value is refused. The harness reads the verdicts the lab writes to `Documents/lab-results.json`, as `lab` does, and the phone's crash log (listed, and only the reports that appeared are copied: the crash log also holds sysdiagnose archives of 270 MB each, "Crash reports" below). Run it with `pnpm native-qa gestures --platform ios --device <devicectl id> --mac <user@host> --team <development team id>`: it copies `qa/ios-ui-tests/` to `/tmp/native-qa-ios/gestures-ui-tests` on the Mac, builds the runner with `xcodebuild build-for-testing` in the GUI Terminal (signing needs the logged-in user's keychain, the way `build --platform ios` does; again only when the sources changed, when the built runner's provisioning profile has expired (a Personal Team's lasts 7 days, and the phone then refuses the runner with `This provisioning profile has expired`), or with `--rebuild`; `--build-only` stops there), then runs `xcodebuild test-without-building` over `ssh`. The phone is asked nothing while the test runs (`devicectl` calls hang then); the results and the trace are read once it has ended. The phone must be on USB (checked), unlocked and awake, with Settings > Developer > Enable UI Automation on: otherwise the runner fails 60 s after `Running tests...` with `Timed out while enabling automation mode`, and the phone writes a sysdiagnose into its crash log. `--trace` has the app record every gesture recognizer per frame, where each touch landed and what UIKit hit-tested, and UIKit's pop and sheet state (`Documents/gesture-trace.json`, kept beside the log as `.trace.json`, summarised per action in the output). The pushed-edge swipe starts 2 pt from the edge on iOS (UIKit's edge zone; `--edge-x` overrides; Android 8 dp). XCUITest cannot move two fingers on both axes at once: `pinch-rotate` is a pinch and then a rotation there. Its accessibility snapshots load the app (3 to 15 % of the frames dropped), so the frame gates cannot be judged with it on iOS. What ran and what did not: SPEC.md, "iOS status (lane G5, 28 Oct to 1 Nov 2026)".

**Ties and the spacing of `adb input` samples.** A scenario that decides a tie (a pan with `activeOffsetY([-4, 4])` against a sheet's 8 dp drag; the carousel's diagonal; the edge swipe) is decided by which sample the finger gives, so its drag must be slow enough that a sample lands in the window that is meant to win. `input swipe` delivers a sample every 12 to 18 ms on the emulator (the injection and the 60 Hz frame batching decide how many land in a frame), and 120 dp in 400 ms moves 5.4 dp between two of them: the sheet's `[-4, 4]` pan, whose window is 4 to 8 dp, was skipped in 2 of 8 rounds on a fresh emulator (`SvelteGesture` trace: `ACTION_MOVE t=12 ms dy=-3.6 dp`, then `t=30 ms dy=-9.0 dp history=0`, `EngineSheet claims the gesture at sample 0 of 0`) while the injector, which gives a sample every 4 ms, passed every time; the other agreement counters differed because that one launch did. The lab now drags it for 1200 ms (`TIE_MS` in `gestures-lab.ts`, as `DIAGONAL_MS` does for the carousel): 12 of 12 rounds pass. To see why a tie went the other way, `adb shell setprop log.tag.SvelteGesture VERBOSE` and read the run's log (`SvelteGesture:` lines: every DOWN and MOVE with its history size, every claim and probe).

**Gates.** `gestures.checks` (no failed check anywhere, a timeout counting as one), `gestures.frames.*` (the `frames.*` bars, phone only, for `box`, `box-busy` and `pinch-rotate`: at most one late interval per launch and no frame over 33 ms, "The frames rule"; the Samsung's `box` frames carry the `1 Nov first touch` exception), `gestures.churn.leaked`, `gestures.agreement` (Android), no missing scenario, no incomplete launch, no fatal, no engine warning, no harness error; `gestures.launches` needs 2 on Android (adb and qa) and 1 on iOS. Every device lists `gestures` among its run kinds, so a device nobody has run the command on reads `not measured`, which fails. The long run (`gestures --repeat 10`, about an hour with both ways of driving) is not part of any script.

## Resilience on the iPhone

`native-qa resilience --platform ios` is the Android resilience run (rotation, text size, language, 100 trips to the background, the process ended and the app returned to; `lib/resilience.ts`) as far as an iPhone allows, with the same checks (the process is alive, the screens are on screen, nothing crashed) and the same gates (`resilience.failures`, `resilience.stepsMissing`, `resilience.skipped`, `resilience.gateBypassed`, all at 0 but the 2 skipped steps of the appearance pair). The plan and the reading of the output are `lib/iphone/resilience.ts` (host-tested); an XCUITest, `ios-ui-tests/GesturesUITests/ResilienceUITests.swift`, carries the plan out in one go and prints `RESILIENCE-STEP {json}` per step, because nothing else can ask the phone anything while it runs (a `devicectl` call made then hangs, as in "Gestures"). The runner is built and started the way the gesture runner is (`--team`, `--rebuild`, `--build-only`; one `xcodebuild` project holds both tests; the phone must be on USB, unlocked, with Settings > Developer > Enable UI Automation on). `qa/runs/resilience-<device>-<stamp>.json` is the run file (the same kind as Android's, with the phone's crash log and `navigation`: what the app's navigation module did at its last start, read from `Library/Application Support/svelte-navigation/last.json`), the XCUITest's output and that line are kept in `.log`.

```
pnpm native-qa resilience --platform ios --device <devicectl id> --mac <user@host> --team <id> [--udid <hardware UDID>]   # the full plan: 126 steps (an estimate of 10 to 20 minutes: it has not been run)
pnpm native-qa resilience --platform ios ... --rotations 1 --cycles 10 --rounds 1                                          # a short plan, to work on the loop
```

What the run does (126 steps; the lab page opens first, with `run=resilience&token=...`, which only writes `Documents/resilience.json` with the build the app reports, so the run is checked against `qa/out/ios-build.json` like the other suites; the menu is opened over it and "Push eight screens with headers" is tapped, so the loop screen is the header screen, three screens deep):

| Group | Steps | What each does, and what it checks |
| ----- | ----- | ---------------------------------- |
| `rotation` | 12 | launch and open the menu; push the header screen; landscape and portrait 5 times (`XCUIDevice.orientation`). The header's navigation bar, its first row and its back button are on screen |
| `fontScale` | 4 | for the default size asked for by name (`UICTContentSizeCategoryL`, the reference whose first-row height is recorded), the largest (`UICTContentSizeCategoryAccessibilityXXXL`), the smallest (`...XS`) and the default again: Home, end the process, launch with `-UIPreferredContentSizeCategoryName <category>`. The screens come back (the restore) and the row is at least 1.5 times as high as the reference (largest), at most 0.97 (smallest), within 5 % (default again) |
| `locale` | 2 | the same restart with `-AppleLanguages (ar) -AppleLocale ar_SA`, then without |
| `appearance` | 2 | dark, then light, while running (`XCUIDevice.appearance`, looked up at run time: where the runner's SDK has none, both steps are `skipped` and the gate allows 2) |
| `background` | 100 | Home, 0.3 s, activate; the app is in the foreground, and every tenth time (and the last) the header screen is on screen |
| `lowMemory` | 6 | twice: Home, 1.5 s, end the process (`notRunning`), launch without a link, the header screen is back with its stack; then a link opened after the process was ended (the menu) wins over the restored screens (the header row is gone); and a process ended in the foreground, with no trip to the background, restores nothing |

What an iPhone cannot be put through, and what stands in for it:

- **A live change of the text size, the language or the layout direction.** They are settings of the phone that only the Settings app changes, and XCUITest has no call for them. The launch arguments above override them for one launch, so each of those steps ends the process and starts it again: what they prove is the restore of the navigation under that size and language (what Android's recreation proves for its font scale and locale), and the larger text itself, by the pixels of the first row. `UICTContentSizeCategoryAccessibilityXXXL` is the largest size the system offers. Parity and accessibility still run at the standard size only (`iosNotCovered`): a launch argument per run would change that, and is not done.
- **Memory pressure.** There is no `am send-trim-memory`. The system ending a backgrounded app is stood in for by ending it from outside after the Home button (`XCUIApplication.terminate()`), which the system may or may not count as its own: see "The system's say" below.
- **The user's swipe-away from the app switcher.** XCUITest cannot reach it on a phone with a Home button. The rule that it restores nothing is the system's (the state of its own that the module relies on is deleted when the user force-quits), not exercised here.

**The system's say.** The app restores its screens only when UIKit offers its own restoration state at the launch (`application(_:shouldRestoreSecureApplicationState:)`, wired by the Expo plugin's AppDelegate patch), because the system deletes that state when the user swipes the app away, which is how the app tells a process the system ended from one the user ended (SPEC.md, "Navigation state across recreation and process death"). Whether iOS offers it after the harness's kill is the one thing the run cannot know in advance, so the run prints what the module did at the app's last start (`navigation module, the last start: restored | dropped (reason) | none`; `none` when it found no file): a restart step that fails with `dropped (the system kept no state of its own ...)` is the system declining, and one that fails with `restored` is a fault of the restore. `--assume-system-kill` launches the QA app with `-SvelteNavigationAssumeSystemKill YES`, which makes the module hand its state over without the system's offer, to tell the two apart; the run file carries `assumeSystemKill`, and `resilience.gateBypassed` fails it, so a diagnostic cannot be taken for the product's evidence. The runner also launches every app with `-ApplePersistenceIgnoreState NO`: XCUITest starts an app with it `YES`, which switches UIKit's restoration off.

**First run (1 Nov 2026, iPhone SE 3, iOS 26.6, the short plan: 26 steps).** 26 passed, 0 failed, 0 skipped, without `--assume-system-kill`: after Home and `XCUIApplication.terminate()` the app came back on the header screen with its stack (the system offered its state), a link after the end replaced the restored screens, and a process ended in the foreground restored nothing; `-UIPreferredContentSizeCategoryName` changed the first row's height as asked (largest, smallest, default) and `XCUIDevice.appearance` exists on this SDK (the two appearance steps ran). Afterwards CoreDevice stayed wedged for 10+ minutes (every device-specific `devicectl` call, `info lockState` included, hung until the Mac's alarm; `devicectl list devices` and `ideviceinfo` answered), as it does after the gesture runner. The run therefore reads the build the app reported and `last.json` through house_arrest (`afcclient --container`, `readAppFileAfc`) and asks `devicectl` only to end a leftover process, after a few bounded probes (`waitForPhone`); the crash log used to be listed through `devicectl` only and read `not measured` while it was wedged; it is now read over USB first (`idevicecrashreport -k -f`, which does not need CoreDevice; the first run after a replug confirms it on a wedged phone).

The restart steps start the lab from the restored screens (see "How the app starts" above); the app waits for nothing over the network, so a phone with no connection restores the same screens.

## CI

Two workflows are about the harness. `.github/workflows/ci.yml` runs the static checks on GitHub-hosted runners on every push and pull request (lint, types, the package, showcase and harness unit tests, the engine's Kotlin and C++ host checks: below, "Kotlin and C++ host checks"; the repository `README.md`, "CI", lists them). `.github/workflows/native-qa.yml` runs the Android emulator lane on every push and on demand, on a self-hosted runner on the OVH host (label `svelte-qa-emulator`) next to the emulator. Setting that runner up, registering it and switching the lane on (the repository variable `QA_EMULATOR_RUNNER`) is `qa/ci/RUNBOOK.md`; until then no job of `native-qa.yml` runs.

| Job | Runs on | When | What | Time |
| --- | ------- | ---- | ---- | ---- |
| `emulator` | OVH runner | every push (the quick lane), dispatch (the full lane) | the stages below, under the emulator lock | push 45 to 60 min, dispatch 2 to 3 h |
| `crashes` | OVH runner | dispatch with `crashes: true` | 1,000 cold starts and 100 suites in chunks of 100, resumed up to 5 times after an outage | 8 to 15 h |

A push that only changes Markdown, `docs/`, `deploy/` or `LICENSE` runs nothing of `native-qa.yml`; a pushed tag runs none of it either (`release.yml` builds tags). Both jobs carry `if: vars.QA_EMULATOR_RUNNER == 'true'`, so while that variable is not set, a push shows the workflow as skipped and nothing queues for a runner that does not exist; a dispatch then fails at once with "No emulator runner". A weekly crash volume is a commented `schedule:` in the workflow; it holds the emulator for most of a day, so it is off.

**The emulator lane** (`qa/ci/lane.sh`, one step per phase in the workflow, one log group per stage). The build comes first and without the lock, so it overlaps whatever else is using the emulator: the QA app and the product (`io.example.sveltenative.qaproduct`, no development lab, for the product boot check), each for x86_64 only. The two builds are separate Gradle builds on the runner's Gradle caches (`GRADLE_USER_HOME`) and the same Gradle daemon; each keeps its generated project and Gradle outputs beside the other (`android/`, `android-qa/`, `android-production/`: "build"), so a build after the first is incremental (25 to 75 s each on a 16-core PC; the first one on a new runner has a prebuild and the C++ of the engine to compile, 15 to 30 min). Then `native-qa hold` takes the shared emulator lock ("Devices and locks") for the whole lane and runs:

| Stage | Push | Dispatch |
| ----- | ---- | -------- |
| `emulator-restart` | a fresh emulator instance, so frame measurements and the first stage do not inherit the leak of everything before | same |
| `lab` (`checks,quick`) | `--repeat 3` | `--repeat` input, default 10 |
| `boot` | | `--warm 30 --cold 30` (inputs) |
| `parity` | `--quick`: the base, dark, right-to-left and large-text sets, 114 of the 224 cases, about 19 min | the full matrix, about 33 min |
| `a11y` | `--quick`: the first two layout variants, 52 of the 100 screens, about 11 min | the full matrix, about 21 min |
| `resilience` | | rotations, cycles, rounds |
| `gestures` | `--input both` (adb and the in-app injector) | same |
| `smoke` | | the smoke app, built after the QA app (`smoke` input) |
| `updates` | | the over-the-air update scenario against the EAS channel (`updates` and `updates_channel` inputs, off by default; `native-qa updates --channel <channel> --warm <n>`, last of the stages that measure the QA app). It **publishes** to EAS, so a push never runs it, and it needs the `EXPO_TOKEN` repository secret (only this step gets it). The channel build (`build --updates-channel`) is made after the smoke app, in the build step |
| `product` | `native-qa product --device localhost:5555`: the production variant started cold with its data cleared, watched for 15 s for the home screen and for a fatal; after all the stages of the QA app, which have the lab the production variant does not | same, after `smoke` and `updates` |
| `report`, `gates` | `gates --platform android --runs lab,parity,a11y,gestures,product --except lab.runs,parity.incomplete,a11y.incomplete` | `--runs lab,boot,parity,a11y,resilience,gestures` (plus `updates` when that stage ran, then `product`), with no `--except`; then `gates --smoke --runs smoke` |

Between stages, `guard-<stage>` restarts the emulator if qemu's resident set is at 11 GB or more or adb has gone away. **Leak and watchdog, decided:** gfxstream leaks a host thread per app launch of the guest, so the emulator is restarted three ways. The lane restarts it first (a fresh instance) and between stages (`guard`, which holds the lock, so nobody is hurt); the host runs `svelte-qa-emulator-watchdog.service`, the PC-side watchdog moved to the host, which restarts at once when adb has been gone for two checks or qemu passes 18 GB, and at 11 GB as soon as the lock is free; and `svelte-qa-emulator.service` restarts the emulator if it dies. The one gap is a single stage that outgrows 18 GB on its own (the full parity matrix has come closest): the watchdog restarts the emulator under it, that stage fails and the next ones recover. The lane does not run a watchdog of its own, because a job cannot outlive its runner and the host needs one when no job runs. The crash volume runs in chunks that each take the lock, so the host watchdog restarts the emulator between them.

**The gates.** The emulator is the `lab` device of `gates.json`, so the gates that decide a push are the ones that are bugs, not speed: `checks.passed`, `checks.failed`, `lab.incomplete`, `lab.scenarios.missing`, `log.fatals`, `log.engineWarnings`, the three `parity.*`, the seven `a11y.*`, every `gestures.*` that is not a frame time, and `product.boot.fatals` and `product.boot.firstScreen` (a crash of the product alone, such as a read of the lab where the product has its stub, which no stage of the QA app sees). Informational on the emulator, whatever they read: the frame, boot and list-mount timings and `lab.scenarios.failed` (phone gates; software GL is slower than any phone) and, on a push, `lab.runs` (3 repeats against the production 10), `parity.incomplete` and `a11y.incomplete` (the quick matrices are counted against the full ones, so a quick run never passes for a full one: 10 Nov 2026 the first push lane read 94 and 46), all three left out with `--except`; a quick case that is missing, unstable or errored still fails its stage. `parity.signedIn.missing` and `a11y.signedIn.missing` are informational everywhere (D12, D15) and count nothing here: the example pins no signed-in screen. The soak, memory, crash, resilience and boot gates are informational on a push because it did not run them (`--runs`). A gate that belongs to a stage which ran and was not measured fails.

**What blocks a push.** Nothing stops a push itself: the workflow reports on the commit. A red `CI` in `ci.yml` (a lint, type or test failure) no longer skips the emulator lane: the two workflows run side by side, and the lane takes the one runner in its turn. A red `emulator` job means a stage failed or a gate above failed or was not measured; the job is the check to require in the branch protection of the branches that should not merge red, together with `CI` (a repository setting, not set by the workflow). A run that a newer push replaced before it started shows as cancelled: GitHub keeps one running and the newest pending run per concurrency group, so nothing ran and nothing failed.

**Reading a failure.**

1. The run's summary page has the stage table (result, time, qemu GB after each stage), the gate table with the failed and not-measured gates first and the passing and informational ones folded, and the last 30 lines of every failed stage.
2. The `emulator` job has one step per phase (`Build`, `Emulator lane`) and one log group per stage inside the lane; each failed stage is an annotation (`::error title=parity failed`). A stage prints the harness's own words: a lab run that never completed, a parity case with its pixel count, an a11y finding with the screen and the node.
3. The artifact `native-qa-emulator-<run>-<attempt>` (14 days) has `qa/runs/` (the run files and their logcat, the parity and a11y evidence of the failed cases), `qa/out/lane-<stage>.log`, `qa/out/build-*.log`, `qa/report.json` and `qa/out/gates*.md`. Open the run file the failed gate names.
4. `no emulator` / `no boot within 300 s` at `emulator-restart`: the host could not start the emulator (`journalctl -u svelte-qa-emulator`). `gave up waiting for ... after 5400 s` (10800 s on a dispatch): something else held the emulator that long (`fuser -v /run/svelte-qa/emulator.lock` on the host). `the session that holds ... ended`: an ssh lock was lost; only a machine that reaches the host over ssh sees this.
5. A `parity` failure after an intended visual change means the references moved: take them again on the emulator with `parity --update` (the references of the emulator are `qa/screenshots/android-api36-emulator-1080x2400-420dpi/`) and commit them.

**Re-running.** *Re-run failed jobs* on the run page repeats the lane for the same commit. A full run: *Run workflow* with the branch and inputs, or `gh workflow run native-qa.yml --ref <branch> -f repeat=10 -f warm=30 -f cold=30 -f smoke=true -f updates=false -f updates_channel=qa -f crashes=false` (a workflow can be dispatched once its file is on the default branch). The lane also runs from a terminal against the emulator, through the tunnel, under the same lock (`QA_ONLY=<kinds>`, for example `QA_ONLY=product`, builds, runs and judges only those stages):

```
export QA_DEVICE=localhost:5555 QA_MODE=push QA_REPEAT=3
bash qa/ci/lane.sh reset && bash qa/ci/lane.sh build
node qa/native-qa.ts hold --device "$QA_DEVICE" -- bash qa/ci/lane.sh emulator   # restarts the emulator through emulator.sh: on the host
bash qa/ci/lane.sh summary
```

(`emulator.sh` controls the systemd service on the host; from the PC run the lane with `QA_EMULATOR_SH=qa/ci/emulator-remote.sh`, which forwards to it over ssh.)

**Cost and time per push.** `ci.yml` is the four-job static run on GitHub-hosted Linux runners (billable minutes on a private repository, none on a public one). The lane is free in Actions minutes and costs the OVH host: the emulator (4 cores, 3 GB guest, qemu resident set 5 to 18 GB) and the build (8 cores, a 3 GB Gradle heap) for 45 to 60 minutes, with a first build on a new runner of 15 to 30 minutes (cold Gradle and NDK) and later builds of 2 to 6 minutes (two of them now, the QA app's and the product's: on a 16-core PC an incremental build of either took 25 to 30 s and one that switched `android/` to the other app 60 to 90 s; the OVH host has half the cores). The product boot check itself is about 30 s (install, a cold start, the 15 s window). Estimates from the run files of this emulator: lab 2.4 min a repeat, quick parity 17 min, quick a11y 11 min, gestures `both` 2 to 4 min, boot 30 + 30 16.5 min, full parity 33 min, full a11y 21 min, resilience 5 to 15 min. A push to green is about 55 to 70 minutes for the lane; pushes queue on the one runner, so a burst of pushes costs one lane at a time and only the newest pending one is kept. Disk: the workspace (kept between runs so builds are incremental), Gradle's caches and the AVD take 20 to 30 GB of the host; an artifact is 20 to 100 MB. Cleanup is in `qa/ci/RUNBOOK.md`.

**Kotlin and C++ host checks in `ci.yml`** (the jobs `library` and `engine-host`). `run.sh` and the package tests that compile `tests/native-host/fixtures/*Host.kt` need g++, a JDK and kotlinc, and the updates store's also an Android SDK `android.jar` and the `org.json` jar; without a tool they skip themselves, which is right on a laptop and wrong in CI. The jobs set up Java 17 (`actions/setup-java`) and run `qa/ci/host-tools.sh` (both through the composite action `.github/actions/setup` with `host-tools: "true"`), which downloads kotlinc 2.1.20 (the Kotlin the Android build compiles with) and the `org.json` 20250517 jar, each against a pinned sha256, into `~/.cache/native-qa-host-tools` (kept on a runner whose home survives, so downloaded once there), and puts kotlinc on `PATH` and the jar in `ORG_JSON_JAR`; `eval "$(bash qa/ci/host-tools.sh)"` does the same in a terminal. g++ and `android.jar` (`ANDROID_HOME`) come with the hosted image. `packages/expo-svelte/tests/native-host/native-tools.test.ts` fails under `CI=1` when any of them is missing, so a runner without kotlinc is a red job and not a green one that ran nothing.

**Files.** `qa/ci/lane.sh` (the stages), `qa/ci/host-tools.sh` (the kotlinc and jar of the host checks in `ci.yml`), `qa/ci/emulator.sh` (restart, guard, watchdog, on the host) and `qa/ci/emulator-remote.sh` (the same over ssh), `qa/ci/setup-runner.sh` (installs everything on the host; `--dry-run`), `qa/ci/RUNBOOK.md`, `.github/actionlint.yaml` (the runner label, for `actionlint`), `.github/workflows/ci.yml`, `consumer.yml` and `release.yml` and `.github/actions/setup/action.yml` (the hosted workflows: the repository `README.md`, "CI" and "Release"). The lock is `qa/lib/lock.ts`; `gates --runs/--except/--markdown` are `qa/commands/gates.ts`.
