# Changelog

Notable changes to `expo-svelte` (named `@alfayez/svelte-native` up to 0.4.0-rc.9, and `@example/svelte-native` up to 0.4.0-rc.4), newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions are `0.x`, with Svelte and SvelteKit pinned to one version each, so a minor version may break. Each line is what an app that uses the package gets.

## Unreleased

## 0.4.0-rc.12 - 2026-11-26

### Added

- **Views that follow the keyboard frame by frame, on Android.** The engine hears each frame of the keyboard's animation (the window insets animation callback, on the main thread, in the frame the window moves in) and writes what moves with it there, with no JavaScript in between, so a busy JavaScript thread does not hold them back:
  - `KeyboardStickyView`: a view that rides the keyboard (`offset: { closed, opened }`, `enabled`), as react-native-keyboard-controller's: its translation is the keyboard's height plus the offset for how far it has opened. It is added to the view's own transform, which a commit or an `animatedStyle` does not take away. A view in a `Modal` is left to the modal, which makes room for the keyboard itself.
  - `KeyboardChatScrollView`: a `ScrollView` for a chat thread whose content lifts with the keyboard (`keyboardLiftBehavior`: `'always'`, `'whenAtEnd'`, `'never'`; `offset`), keeps the room the keyboard takes at its bottom while it is up, and tells `onEndVisible` when the end of the thread comes into view or leaves it. The lift's numbers are kb-controller's (`whenAtEnd` is within 20 points of the end). `scrollToEnd` goes to the end of the room the keyboard makes, so a message sent with the keyboard up ends above the composer; a keyboard that changes height while it is up lifts the thread by the difference, not by the whole new height again.
  - `KeyboardAwareScrollView`: a `ScrollView` that scrolls the focused input above the keyboard as the keyboard rises, and back as it closes (`bottomOffset`, `extraKeyboardSpace`, `disableScrollOnKeyboardHide`, `enabled`), and to the next input when the focus moves with the keyboard up.
  - `KeyboardAvoidingView` with `behavior="position"` moves with the keyboard; `'padding'` and `'height'` still change once, when the keyboard starts to move.
  - `createKeyboardMotion()` gives the keyboard's `height`, `progress` and `state` as shared values written on the UI thread with each frame, for your own `animatedStyle`. `insets.keyboardState` (`'closed'`, `'opening'`, `'open'`, `'closing'`) is the same fact as reactive state, once for each move; `KeyboardController.setFocusTo('next' | 'prev' | 'current')` from `expo-svelte/platform` moves the focus between inputs (Android). On iOS the components move once, when the keyboard starts to move, as before. Reanimated's own `useAnimatedKeyboard` is given what it always was (its states and whole dp); `createKeyboardMotion()` has its own frames.
  - The library's copy of Reanimated gets a fourth patch: `subscribeForKeyboardEvents` takes the keyboard's events from the engine, not from a window insets listener of its own (which replaces the decor view's and reports whole dips). It needs a new native build.
- On Android, `boxShadow` is drawn, as React Native draws it. It takes a CSS string or an array of objects, any number of shadows, outside or `inset`, with an offset, `blurRadius`, `spreadDistance` (negative too) and a colour. A shadow follows the view's corner radii, is drawn behind the background and the border (an inset one over them, inside the border), and an outside shadow stays visible when the view has `overflow: 'hidden'`, whose clip is to the inside of the border. Changing it at run time works, and so does taking it away (`'0 0 0 0 transparent'`, or no `boxShadow`): a focus ring that comes and goes on an input is one style change. The drawing is React Native's own (`BackgroundStyleApplicator`), so it is the same pixels as a React Native view with the same style. It was ignored.
- On Android, `transformOrigin` is read, in every form React Native takes: keywords (`'top left'`), percentages (`'25% 75%'`), lengths (`'10px 20px'`) and the array (`['100%', 0, 0]`), with two or three values. A transform turns about it, a static one and one that Reanimated (or the engine's animated write path) writes every frame, which now turns about the origin of the committed style instead of the view's centre. An origin given in percent follows the view when its size changes. It was ignored: every transform pivoted on the centre.
- On Android, `borderStyle: 'dashed'` and `'dotted'` are drawn, as React Native draws them, with rounded corners too. Before, a dashed or dotted border was a solid line.
- On Android, the border can have a colour for each side: `borderTopColor`, `borderRightColor`, `borderBottomColor`, `borderLeftColor`, `borderStartColor`, `borderEndColor`, over `borderColor`. Where two sides meet, the corner is split as React Native splits it, with a radius or without. Before, every side took the colour of the first side that had one.

### Changed

- On Android, the box of a view is drawn by one of three drawables, whichever draws it as a React Native view is drawn (a 1 dp border is no longer a crisp 3 px stroke: its edge pixels are half covered, as React Native's are). A fill with one radius for every corner and no border is a `GradientDrawable`, as before. The engine's own drawable (`BoxDrawable`) draws a solid border of one width and one colour with any radii, a border of square corners whose sides have widths or colours of their own (a divider is `borderBottomWidth` alone; dashes and dots when the sides that have a width share one opaque colour), and a fill whose corners have different radii (a `GradientDrawable` scaled radii that overflow all together, React Native scales each corner). React Native's own drawables draw a box shadow, dashes and dots with round corners (or square ones with colours that differ), and sides of different widths or colours with round corners. Mounting 300 recycled rows is within the noise of unbordered rows with the engine's drawable (a round border, a divider, four colours, dashes), and several milliseconds slower for the rows and much slower for the first mount with React Native's drawables (a shadow, round dashes, round sides), on the OVH emulator (a recycled view keeps its drawables and rewrites what differs). `overflow: hidden` clips to the padding box without allocating for each draw.
- On Android, a border with a width and no colour is black, as in React Native and on iOS. It was transparent, so `borderWidth: 1` alone drew nothing. `borderColor: 'transparent'` is still transparent, and a `boxShadow` layer written without a colour is black.

### Fixed

- On Android, `insets` and the window's `frame` reach JavaScript at whole precision (the pixels divided by the density as a float, as `react-native-safe-area-context` serializes them), not rounded to two decimals. A top inset of 128 px at 2.625 was 48.76 dp, 0.005 px short of 48.761906, which moved every view below a safe area by that much (the header, toolbar and tab bar reported their size and inset the same way, so a header screen laid out with the whole-precision estimate and then again with the rounded measure); a bordered box, a card and an indicator whose edge landed on a half pixel ended a pixel away from React Native's. (part of #143)
- On Android, a `TextInput` that allows font scaling (the default) is drawn at the size the system's font scale gives it, as in React Native, and its line height and letter spacing with it. Its text was drawn at the unscaled size inside a box that Yoga had sized with the scaled one, so a field at font scale 1.3 had small text in a tall box. A field with `allowFontScaling={false}` keeps its size, and `maxFontSizeMultiplier` caps the scale. (#144)
- On Android, a view with an elevation is drawn in the order its siblings are in, as in React Native, and no longer over the siblings that come after it. Platform Z ordering put an elevated sibling (the plate that carries a menu's shadow) over a later one (the card with the menu's rows), so the rows were hidden once the plate was opaque. A touch is hit in the same order (`zIndex`, then insertion order); an elevation no longer ranks a view over the ones after it.
- On Android, a `Text` that ends in an ellipsis (`numberOfLines`) lays out under the paint of React Native's `ReactTextView`, a `TextView` with the platform's default typeface, as it does there. The platform measures the "…" with the layout's own paint, and the engine's was the text's font: a title or a preview ended a letter earlier than React Native's ("lin…" there, "li…" here).
- On Android, the text of a `TextInput` is laid out as React Native's is: the font size is rounded up to a whole pixel, a field with a font family has subpixel and linear text on (a line of typed text was a pixel narrower for every few characters, and a letter-spaced code a pixel narrower per digit), the line height is a span on the text rather than the platform's line spacing (the typed text sat a pixel high), and the hint keeps the font's padding unless `includeFontPadding={false}` says otherwise (it sat a few pixels off in a field taller than its text). A `fontWeight` or `fontStyle` alone, `'400'` and `'normal'` included, turns on the exact advances as it does in React Native.
- Expo no longer warns on every build that the config plugin for "expo-svelte" was loaded from "app.plugin.js" but the package's `exports` does not include "./app.plugin.js". Expo finds the plugin by the package's name (the `app.plugin.js` at its root), then asks Node for the file under its own name, which `exports` did not list; it lists it now, next to `./app.plugin`, which resolves to the same file as before. `expo-svelte/app.plugin.js` is also a name `plugins` may hold: `init`, `doctor` and the Metro config know it next to `expo-svelte` and `expo-svelte/app.plugin`, so a hand-written entry of it keeps `init` from adding a second `expo-svelte` and the doctor can read its options (`expo-svelte` is still the one to write).
- A Svelte compile error now reaches Metro's output with its message, the file, the line and the column, and a code frame, where it printed a bare `SyntaxError`. A `{@const}` directly in a `<View>` is one (the lowering makes the `<View>` a plain native element, where `{@const}` is invalid): the transformer threw the message, but Svelte clears the stack of its compile errors, Metro made a `SyntaxError` of the error with that empty stack, and Expo's reporter prints the stack of a `SyntaxError` that has no code frame in place of its message. The transformer hands Metro the error as Babel's are, with a `loc` and a `codeFrame`, so it prints `CompileError in <file>: <message>` and the frame. The position is the file's own, the line, the column and the frame: the lowering moves the columns of a line that has a lowered tag (`<View>`, `<Text>`, an HTML element) or a `class` (a `nativeClass={...}` call takes its place), and Svelte reports where it saw the error, so the position goes back through the lowering's edits and the frame shows the line as written (not `<native-view nativeClass={...}>`). The position of an error in a `.svelte.ts` module is that of the TypeScript as written, and its frame is made of that TypeScript. The error keeps Svelte's `code` (`const_tag_invalid_placement`) and its name, `CompileError`.
- On Android, the build no longer stops with `Error: no such option /…/expo-svelte@…_patch_hash` (`CXX1429`, in the `:app:` C++ build of react-native-mmkv and react-native-reanimated) for an app whose pnpm names the library's folder with an "=". With `init`'s SvelteKit patch declared, the folder is `expo-svelte@<version>_@sveltejs+kit@3.4.0_patch_hash=<hash>_<hash>`; pnpm keeps a name no longer than `virtualStoreDirMaxLength` and with no uppercase letter as it is and cuts a longer one, or one with an uppercase letter (unless it starts with `file+`), to its first `limit - 33` characters and a hash (`depPathToFilename` of `@pnpm/dependency-path`), so at the default, 120, the 87 characters that stay hold the `=` of `patch_hash=`, and at 60 the 27 that stay do not. Android's prefab tool reads a package path with an "=" in it as an option. `expo-svelte init` writes `virtualStoreDirMaxLength: 60` into `pnpm-workspace.yaml` (lowering a larger one, keeping the comment on its line, said in its summary; `examples/minimal` has it), and installs again with `--config.confirmModulesPurge=false` when it has no terminal (pnpm asks to remove `node_modules` for the changed setting, and without a terminal and without CI it stopped with `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`); the entries of a `pnpm-workspace.yaml` block written in flow style are listed for the person as before, and the rest is written (it was dropped with them). `expo-svelte doctor` fails on a library folder with an "=" in it and says so, an "=" elsewhere in the path (the project's own, or the folder of a virtual store that is not `node_modules/.pnpm`) is reported as unknown with both ways out, the last `.pnpm` of the path is the library's folder, and an app whose `app.json` `platforms` has no android is told nothing. At 60 the declared patches (`name@version` of 19 and 24 characters) are cut before the `=`; a package of your own patches whose `name@version` is up to 15 characters keeps it (the limit would have to be its length plus 44 or less).
- Reversing or restarting a running `animate:flip` under a scaled parent (`style="scale: 2"`, or a `transform` with a `scale`) no longer makes the item jump: the new move starts where the item is drawn. The box a node reports counted its own animated offset as if the parent's scale did not apply to it, so a flip stopped half way through a 100 dp move under a parent scaled by 2 read 12.5 dp of the 25 dp the item still had to travel on the screen, and the reversed flip began 6.25 dp off. A px `transformOrigin` of a node under a scaled parent was off the same way. An item under no scale was already exact (#122).
- On Android, a tap on an `Svg` (react-native-svg), or on another view built on React Native's `ReactViewGroup` or Expo's `ExpoView` that takes no touch itself, presses the `Pressable` or the `View` with `onPress` around it, as in React Native. A `Pressable` that holds an `Svg` (an icon-only button) could be pressed beside its icon but not on it: the engine hit-tested into the foreign view, which has no tag of its own, and claimed the touch without telling JavaScript. A foreign view is now passed on only when it is a view of React Native's `ReactViewGroup` or Expo's `ExpoView` (react-native-svg's `SvgView` is one; so are the Expo views that declare none) with no `onTouchEvent`, `dispatchTouchEvent` or `onInterceptTouchEvent` declared below that class, nothing in it that is clickable or declares one, and nothing that made it clickable or gave it a click or touch listener: its frame is then the target of the touch, so JavaScript hears it and the responders above it press, and the view still gets the touch from the platform. It is an allow-list because a search for what takes touches cannot be complete: react-native-maps' `MapView` takes touches through `dispatchTouchEvent` only (the gms `MapView` under it declares no `onTouchEvent`), and a pan on a map inside a `Pressable` card must not press the card. Every other view (a WebView, a map, a video's surface, a PDF view, a Lottie animation, any class of a library that is not built on those two bases) keeps its touches, as before; so does a view whose touch listener cannot be read (the platform's hidden-API rules may deny the field). A shape's own `onPress` inside an `Svg` still does not run on Android: React Native finds the shape under the finger with `reactTagForTouch`, the engine's target is the `Svg`, and a `Pressable` around it presses.
- On Android, a sheet whose window is resized while it settles ends at the detent it reports. The settle wrote the place the detent had when it began, so a split-screen window that went from 800 to 600 px half way through the 220 ms left a sheet released towards the half detent at 400 px of its 600 px box, showing 200 px, while it reported the half detent at 300 px, and the next layout moved it 100 px. The settle now reads the detent's place at each frame and ends there (#118).
- On Android, a sheet's drag follows the finger from where it crossed the touch slop, whether the move that crossed it arrived alone or in a batch with the ones after it. A batched move started the drag from the batch's last position, so the finger's travel between the two was lost: positions 10, 40 and 60 px moved the sheet 20 px in a batch and 50 px one by one, and a drag paused at 220 px settled at the full detent in one case and the half detent in the other (#119).
- On Android, an app that loads Reanimated before its first animated view (a `Gesture` builder or the `animation` module used first) no longer crashes with a null dereference in `LayoutAnimationsProxy::updateLightNodeProps` (`SIGSEGV`, fault address `0xc8`, thread `mqt_v_js`, a few seconds after start; the QA app's checks did it every run). Reanimated's layout-animation proxy attaches to the surface when Reanimated loads, and the engine's mounting delegate has to sit behind it, which the engine does when the host tells it that Reanimated is loaded. The host told it at its own first animated node only, so until then the delegate in front of the proxy consumed every engine mutation, the proxy's tree lacked the nodes created meanwhile, and the next update of one of them crashed. The host now tells the engine in the same turn of JavaScript as the load, whoever makes it. A surface that is created after a late load still starts with the delegate in front (see "Lazy Reanimated" in `native/svelte-core/SPEC.md`).
- A `List` with `initialScrollIndex` scrolls to its row once the content the row is in has been laid out, as React Native's list does, and the row is the right one. With a `header`, when the list's own layout came before the header's (React Native's layout results can put an ancestor ahead of its descendant), the first scroll was sent without the header's height and the list opened above the row by that height (two rows early under an 80 dp header and 40 dp rows), and nothing sent it again. A list that has no rows at its first layout, because they load, never scrolled, and a scroll sent when the rows arrived would have gone out ahead of the commit that has them, to a scroll view with no content to move in, which Android clamps to 0. The scroll is now sent when the header's first layout, the list's own and the layout of the rows' content (at the size the rows ask for) are in, once; until then the rows mounted are the ones around the row, not the first rows of the list (a frame at the target showed none). Rows that arrive in chunks are scrolled to with the first: the list ends where the rows it has end when the row is not among them, as React Native's does (one scroll, to the end when the index is past the data). A `scrollToIndex` called before the first layout waits for the header's size too, and a scroll the app asks for itself is the last word over `initialScrollIndex`. An `initialScrollIndex` that is set after the list had its first rows without one scrolls nothing when the list grows (#120).
- A `List` whose whole content fits its viewport (or whose row is in the last page) with an `initialScrollIndex` shows all its rows. The jump asks the platform for an offset it cannot give: the scroll view stays where it is and sends no scroll event, and the list kept the offset it had asked for as its window, so the rows above it were unmounted and only the last ones were reported viewable. The window is now the offset the content allows: its padding along the axis, the header, the rows and the footer, and on iOS the `contentInset` after it, less the viewport, on either axis. A lower value than the platform's (a footer not laid out yet, a percentage padding, an inset iOS adds by itself) is put right by the scroll event that a jump that moves comes with.
- On Android, a `TextInput` (and an `<input>` or `<textarea>`) asks the keyboard for the same `inputType` as React Native's: a multiline field with `autoCorrect` on and the default `autoCapitalize` is a text field with `TYPE_TEXT_FLAG_CAP_SENTENCES`, `TYPE_TEXT_FLAG_AUTO_CORRECT` and `TYPE_TEXT_FLAG_MULTI_LINE`, and every other combination of `multiline`, `autoCorrect`, `autoCapitalize`, `keyboardType` (and `inputMode`) and `secureTextEntry` ends in the flags React Native's `ReactTextInputManager` leaves (the engine's differed in 314 of 384 combinations: it left `autoCorrect` and the capitalisation off a password and `multiline` off a number password, `autoCorrect` and `multiline` off a numeric or phone keyboard, and gave `visible-password` and `url` a text class React Native does not give them). A multiline field of a keyboard that is not text now takes several lines, as in React Native, and a multi-line password stays masked (making a view multi-line by hand removes the platform's masking, so it is set again). Three differences from React Native are kept on purpose: the type is recomputed from the props at every change, so a `keyboardType` that changes at runtime does not leave the old keyboard's variation bits behind, as React Native's staged bits do; a multiline password stays masked (React Native's `setInputType` makes a multiline view multi-line with `setSingleLine(false)`, which unmasks it); and a field with `secureTextEntry` is always masked, whatever the flags say. React Native's flags for `secureTextEntry` with `keyboardType="email-address"`, `"phone-pad"` or `"url"` (`0x40a1`, `0x13`, `0x80`) are no password type to Android, which leaves such a field unmasked (it also unmasks a field that was masked when only its keyboard type changes), where the engine has always masked it. The engine keeps React Native's flags for them and sets `PasswordTransformationMethod` itself after every change of the props, for every keyboard but `visible-password` (which wins over `secureTextEntry`), and takes it away when `secureTextEntry` goes (#141). Changing the input type also sends no change or selection event any more: each swap of the platform's input type sets the text again, which reported an empty-selection change to JavaScript and counted it as an edit.
- On Android, a predictive Back gesture that starts while a push is still sliding in takes the screen over from where it is drawn instead of snapping it. The preview used to set the screen's translation from its own progress: a `slide_from_left` screen half in jumped across half its width at the first step, a sheet by its whole offset, and a `slide_from_bottom` or modal screen never had its vertical offset written. The preview now starts where the screen is drawn and does not move it against the finger (a `slide_from_right` push or a sheet barely in keeps its offset and goes on from it; an offset behind the finger, a vertical one the preview does not move, and the scale of a cancelled gesture still springing back, leave as the gesture goes on). The screen below the push, which the cut had put in place at once, is drawn where it was and comes in place with the gesture, and, at a commit (often below progress 1), over the exit instead of jumping what was left; it is put in place when the cancel's spring ends or is cancelled, and a stale one is never carried to a later gesture (#121). A gesture from the right edge, or in a right-to-left layout, still moves the screen the way it did (a known gap, SPEC.md).
- On Android, a Back gesture, the system's predictive one and the app's own edge swipe, is for the screen it began on. A route that opened while the gesture was held (a push, a modal, a sheet that cannot be dismissed) was moved by the rest of it, dismissed by its commit (the Router removed it and kept the screen the gesture began on) and restored by a cancel (to Y = 0 for a sheet, not its rest), with that screen left displaced behind it. When the stack changes in front, the gesture is over: the screen it moved goes back to its rest (X = 0, a sheet's own offset in Y, whole), the layer it held is released, and what is left of the gesture (its steps, the system's commit or cancel, the release of the finger) applies to nothing, and is not taken for a back key that would dismiss what opened (#124).
- `KeyboardStickyView` without the engine's frames (iOS, and Android where the engine is not there) keeps the `transform` of its own style (#132): it replaced it with the keyboard's translation, so `style={{ transform: [{ scale: 0.95 }, { translateY: 12 }] }}` came through as `[{ translateY: -266 }]`. The keyboard's translation now comes first in the list, outside the view's own entries, so a scaled view is moved by the keyboard's whole height and not by a fraction of it.
- A `KeyboardAvoidingView` of `behavior="height"` in a window that changes size with the keyboard open (a split screen or window that grows from 350 to 600 dp, with a 140 dp keyboard) asks for the avoided height at once, 460 dp, as a view that fills the window (or reaches the bars at its bottom) is taken to fill it still (#134). It went to 210 dp, then to a request with no height at all, which lets the view extend under the keyboard until the next layout, before the 460 dp. A view that is not at the bottom of the window is measured at its natural height first, as it was.
- On Android, `scrollToEnd` of a `ScrollView` goes to the end of its scroll range, the padding at its edges included, as React Native's does (the content's height and the bottom padding, held inside the range): under a header whose room is the scroll view's `paddingTop` it stopped that much short of the end, and the same for `paddingLeft` and `paddingRight` in a horizontal one. It is also what lets `KeyboardChatScrollView` end a thread above the composer when a message is sent with the keyboard up.
- A `KeyboardAvoidingView` of `behavior="height"` that is disabled and enabled again with the keyboard still open no longer shrinks twice (#125): the overlap it adds back to a measured height is the one applied to the view, and while the view is disabled none is, so the natural layout measured then was added to the old overlap again (a 600 dp view with a 140 dp keyboard asked for 320 dp, and 460 dp only after the layout of that). It asks for 460 dp at once.
- A `KeyboardAvoidingView` of `behavior="height"` shrinks from the height it has when the keyboard opens, not from the first one it measured: a view resized while the keyboard was closed (a window or split screen that changed size, a layout that grew) got the old height less the keyboard's the next time it opened, then corrected itself when its own layout was measured (#117).
- On Android, a rounded `Image`, `ScrollView` or `Text` with an outset `boxShadow` keeps the shadow and the rounded clip: the view clipped itself to its outline, which cut the shadow, or, for a scroll view and a text, lost the clip of its content to the rounded padding box. They clip the content as React Native's views do (`overflow: hidden` on a text and a scroll view, an image always), and leave the shadow, which is drawn with the background, alone.
- On Android, an animated `borderRadius` of a box React Native's drawables draw moves the clip and the shadow of `elevation` with it; the view's outline was not asked for again.
- On Android, `setNativeProps` takes `boxShadow`, `borderStyle`, `transformOrigin`, the colour of each side (`borderTopColor` and the others; `borderLeftColor` and `borderRightColor` turn in a right-to-left layout as they do in a style), and `borderColor` colours every side, the sides that had a colour of their own included (it changed nothing once a border had sides). Colours, the shadow and the origin are converted as a style's are, so `"rgba(0,0,0,0.5)"`, `"0 4px 8px red"` and `"top left"` work, and a raw value in `style` cannot override the converted one.
- On Android, `setNativeProps` and an animated radius that makes React Native's drawables draw the box keep the view's clickable flag, hardware layer and offscreen alpha (they were dropped: a pressed row stopped being clickable for accessibility services), and the content container of a scroll view that has a `transform` and a `transformOrigin` pivots on its size once laid out, not on the 0 x 0 it has at mount.
- On Android, an animated `borderRadius` on a box the engine's drawable draws that makes React Native's draw it (a divider, or sides with widths or colours of their own, given round corners) builds the box again at once; it drew one border all the way round until the next commit.
- On Android, the border widths of a view are turned with its colours in a right-to-left layout (`borderLeftWidth` is drawn on the right, as React Native draws it: the width stayed on the left while the colour moved to the right), a scroll view's content sits at Yoga's origin (inside its border) plus the padding a large or translucent header gives it, and a text is drawn at the whole pixels of its padding, as React Native's are.
- On Android, the sides and corners of a box React Native's drawables draw follow the layout direction the view resolves once it is attached (they followed the app's configuration, which differs for a view that resolves another).
- On Android, a border whose sides have different widths (`borderBottomWidth: 1` alone, `borderTopWidth: 1` with `borderBottomWidth: 6`) draws each side with its own width. Every side took the widest one, so a view with only a bottom border was boxed in on all four sides.
- An `autocomplete` of one token is read whatever its case, as HTML reads it: `autocomplete="CURRENT-PASSWORD"` or `"OFF"` on an `<input>` (or a `TextInput`'s `autoComplete`) gives the same autofill hint as the lowercase value. It gave none, while a value of several words (`"SECTION-SIGNIN USERNAME"`) was already read so (#114).
- On Android, the default push and pop no longer render the two screens into full-screen hardware layers: the screens are drawn whole and the stack fades them by laying the surface they fade against over them, which looks the same. The first push of a session spent 20 to 40 ms of one frame building those layers on a Galaxy A16; its worst frame there is now 31 to 37 ms instead of 39 to 55 ms (28 to 37 ms instead of 42 to 50 ms for a screen with long lists), and later pushes' worst frames are 14 to 21 ms instead of 19 to 26 ms. About 20 ms of the first push's longest frame remains: the GPU driver's own first-time work for a second screen, which a layer warmed ahead does not avoid. A screen scaled by predictive back, a screen with a background that is not an opaque colour, and the other `animation` values keep their layers (#111).
- An `AnimatedView` whose style holds a Reanimated CSS key (`transitionProperty`, `transitionDuration`, `animationName`, ...) keeps the rest of its style again. Since 0.4.0-rc.11 the view kept only the CSS keys on a device and lost everything else in that style (background colour, size, padding, border, transform), so a pressable that scales with a CSS transition drew no background and collapsed: Reanimated 4.7 returns four entries from the function that splits the CSS keys from the style, where the library took the fifth. The tests ran on a stub with five, so they now check the stub against the vendored Reanimated.

## 0.4.0-rc.11 - 2026-11-23

### Changed

- **Expo SDK 58, React Native 0.88 and React 19.3.** The package targets `expo` 58.0.26, `expo-constants` 58.0.16, `react` 19.3.0 and `react-native` 0.88.1 (peer ranges `~58.0.26` and `~58.0.16`); SDK 57 and React Native 0.86 are no longer supported. An app on SDK 57 changes:
  - in `package.json`, the four versions above (`pnpm add expo@58.0.26 expo-constants@58.0.16 react@19.3.0 react-native@0.88.1`) and its other Expo modules (`pnpm exec expo install --fix`);
  - in `pnpm-workspace.yaml`, `overrides` `expo-modules-core: 58.1.0` and `"@react-native/metro-config": 0.88.1`, and the patch `expo-modules-core@58.1.0` in `patchedDependencies` in place of 57.0.23 (remove the old lines and `patches/expo-svelte/expo-modules-core@57.0.23.patch`, then `pnpm exec expo-svelte init` copies the new patch and adds the entry);
  - then `pnpm install` and `pnpm exec expo prebuild --clean`: SDK 58's templates differ from 57's in what the library patches. Android builds with compile SDK 37 (install Android SDK Platform 37 and Build-Tools 37.0.0), Android Gradle plugin 9.2.1, Gradle 9.4.1 and Kotlin 2.2; iOS starts React Native from a `SceneDelegate` (the scene-based life cycle iOS 27 requires), which the plugin now patches too.
  The Node ranges `expo-svelte doctor` accepts are the same (24.3 or newer, 22.17 or newer, 26 or newer): React Native 0.88.1 itself excludes Node 25 now, not only the tools a fresh install used to pick.
- The libraries the package carries are the versions of Expo SDK 58: react-native-reanimated 4.7.1, react-native-worklets 0.13.0, react-native-gesture-handler 3.3.0, react-native-svg 15.16.0 and, for an app that turns them on, expo-image 58.0.18, expo-video 58.0.14, expo-blur 58.0.6, expo-linear-gradient 58.0.4, react-native-webview 14.0.1, react-native-view-shot 6.1.1, react-native-maps 1.29.11, lottie-react-native 7.5.0 and @react-native-community/datetimepicker 9.2.1. react-native-mmkv is 4.3.2 (it asks for MMKV core 2.4.1: 2.4.0's two AARs share one namespace, which Android Gradle plugin 9 refuses; no change for an app's data or API). The others keep their versions, which accept React Native 0.88 (react-native-nitro-modules 0.35.10, react-native-quick-crypto 1.1.3, react-native-quick-base64 2.2.2, hermes-intl 0.1.2, expo-conic-gradient 0.2.1, react-native-video 6.19.3, rive-react-native 9.7.1, react-native-pdf 7.0.3, react-native-blob-util 0.24.9, react-native-fast-shadow 0.1.1, react-native-animateable-text 0.19.3). The library's patches to them are ported to these versions (gesture handler's gains a second one, which makes its podspec find the Worklets copy); the Worklets copy leaves out its new `plugin-oxc/` (prebuilt binaries of a Rust plugin nothing here loads); react-native-blob-util 0.24.9, which react-native-pdf reads its files with, gets a one-line patch of its own, because Android Gradle plugin 9 refuses the default Proguard file its build names. expo-video 58 takes `Image.resolveAssetSource` from the whole of `react-native`, which would bundle React Native's index (its components, `Animated`, the virtualized lists) into every app that turns expo-video on: Metro resolves that one file to a module that imports `resolveAssetSource` from its own file, as expo-video 57 did (`LEAN_IMPORTS` in `metro.ts`). react-native-quick-base64 2.2.2's iOS module gets one too: it found the JavaScript runtime through `RCTCxxBridge`, which React Native 0.88 removed, and now asks the bridge it is given (the bridgeless `RCTBridgeProxy`) for it. react-native-nitro-modules 0.35.10 gets the `installJSIBindingsWithRuntime:callInvoker:` overload of Nitro 0.37: React Native 0.87 and later call only that one on iOS, so without it Nitro never installed, and `localStorage` (MMKV) and `crypto` (quick-crypto) failed and the app stopped at the first use.
- Gesture handler 3 (the main entry's gestures): `TouchEventType.TOUCHES_CANCELLED` is `TouchEventType.TOUCHES_CANCEL` (the value is the same), a `responder` whose `onResponderGrant` answers `true` no longer holds the native handlers back (RNGH 3 dropped `handleSetJSResponder`; a handler's `cancelsJSResponder` is the one direction left), and `hitSlop` reaches the native side in RNGH 3's form (a negative `width` or `height`, or `left`, `right` and `width` together, throws in development as RNGH says). The `Gesture.*` builders, `GestureDetector` and the callbacks are the same.
- The foreign view libraries' props that changed with their versions: `expo-image` takes `svgVariables` and `transition.skipOnCacheHit`; `expo-video` the Android `controllerAutoShow`; `expo-blur` clips to its container's radii (`borderRadii`); `react-native-view-shot` captures `webp` (`webm` is a deprecated alias) and checks its options as version 6 does (a bad number or boolean falls back to its default, with a warning); `lottie-react-native` takes `applyOpacityToLayersAndroid`; `react-native-maps` markers take `flat`; `react-native-webview` takes `removeIosKeyboardObserver` (iOS) and needs Android 7 (API 24).
- iOS navigation restoration (the root router's state after the system ended the process) is read from the scene: the plugin adds `stateRestorationActivity(for:)` and a `willConnectTo` override to the `SceneDelegate` of Expo's SDK 58 template, as UIKit calls no application delegate restoration callback in an app that has scenes. The `AppDelegate` callbacks stay for a project whose template has no scene delegate.
- A gesture callback that reads `$state` or a prop is still refused in development: Worklets 0.13's plugin writes a worklet's `__closure` as an array (names only in the function's own source), and the check reads the names from there.
- iOS push: a silent push still runs your JavaScript, `init` and the hooks with no screen. Expo SDK 58's template makes the screen from the scene, so the plugin starts the React host from `AppDelegate.swift` in a launch in the background instead of wrapping the template's `startReactNative` call (which the template no longer has); the scene makes the first screen when the user opens the app, as before. A launch in the background is one with no connected scene a main-queue turn after `didFinishLaunching`: under scenes the state is `background` there for every launch.
- The Android engine and the plugin follow React Native 0.88 and SDK 58: the `tintColor` of an image is React Native's `std::optional` (an unset tint is no tint), the accessibility role `tabbar` is known, and `expo/config-plugins` is imported without an extension (Expo 58's `exports` map has no `./config-plugins.js`).
- React Native 0.88's types for the modal's event handlers (`onRequestClose`, `onShow`, `onDismiss`, `onOrientationChange`) return `void | Promise<void>`: an arrow function that returns a value (`onRequestClose={() => (open = false)}`) no longer type-checks, so the example and the guide use a block (`() => { open = false; }`). The handler's behaviour is the same.
- The Expo template of SDK 58 builds a release with R8 (`android.enableMinifyInReleaseBuilds=true`) and Android Gradle plugin 9, whose keep rules are strict: the library's `consumer-rules.pro` now keeps what its native code and reflection reach (the engine's `MountingManager.onTransaction` that C++ calls, which an R8 release stripped, leaving the first screen empty with `NoSuchMethodError`; the event dispatcher's batch-listener field; Room's constructor for WorkManager, which react-native-maps brings).
- Svelte is the registry's `svelte` 5.59.1. Custom renderers, which the package needed a build of an open pull request for (sveltejs/svelte#18042, served by pkg.pr.new), were merged and released in Svelte 5.59.0, so the package's peer dependency is now `svelte` 5.59.1 exactly and nothing is vendored or fetched from a preview server. An app changes its `svelte` dependency from `https://pkg.pr.new/svelte@216f258…` (or a `file:` tarball) to `5.59.1`: run `pnpm exec expo-svelte init` again, which sets it and installs, or `pnpm add svelte@5.59.1`. A `svelte` before 5.59.0 (the pull-request build included: it has a `./renderer` export, with other method names) makes `expo-svelte doctor` and the Metro, transformer and Vite entries fail with that fix; any other version fails the doctor's peer check. Svelte's compiler still refuses `transition:`, `in:`, `out:` and `animate:` on a custom renderer, so the Metro transformer still removes the refusal as it loads the compiler, and the app has no patch of Svelte to declare. The Svelte of the merged API names the renderer's methods `createText`, `getNodeType` and `getText` (the pull request's were `createTextNode`, `nodeType` and `getNodeValue`), which `expo-svelte/renderer` follows.
- SvelteKit is 3.4.0 (was 3.1.1), exact: the peer dependency, and the patch that lets its route scanner leave the `+mobile.svelte` files alone is now `@sveltejs__kit@3.4.0.patch`. To update an app, run `pnpm exec expo-svelte init` again: it pins `@sveltejs/kit` to 3.4.0, copies the new patch into `patches/expo-svelte/` and declares it, and warns about the old entry; delete the `@sveltejs/kit@3.1.1` line from `patchedDependencies` in `pnpm-workspace.yaml` and `patches/expo-svelte/@sveltejs__kit@3.1.1.patch`, then `pnpm install`. `$app/paths`' `resolve` follows 3.4.0: it throws for an absolute or protocol-relative URL (`resolve("https://example.com/a")`), as it does on the web, and a route id with no parameter, or with only an escape (`/a[x+2f]b`), needs none; a search or a hash after the id is left as it is.
- Tailwind is 4.3.5 (was 4.3.3) and Vite `^8.3.8` (was `^8.1.4`), as peer dependencies: `pnpm add -D tailwindcss@4.3.5 vite@^8.3.8` in an app that has them. Tailwind 4.3.5 writes the selector of `group-hover:` and the other `group-*` and `peer-*` classes with the class last (`:is(:where(.group):hover .group-hover\:p-2)`), so the build reports the ones it leaves out under their own name, not under `group` or `peer`.
- The package's npm page links the repository, the guide (now at <https://expo-svelte.alfayez.dev>; the old address redirects) and the issues.

### Fixed

- On Android, a pop that plays during the first 70 ms of a push (the screen below still fading out) no longer blanks the screen below. It was taken to nothing and faded back in only after 35 % of the way back, so for about 70 ms the screen showed nothing but its background; it now comes back to whole from where the push had faded it.
- On Android a `TextInput` (and an `<input>` or `<textarea>`, which are one) sends `onContentSizeChange` and `onScroll` as React Native's does. `onContentSizeChange` gets `event.nativeEvent.contentSize` (`{ width, height }`, in dp) when the field first lays out and whenever an edit or a layout changes it, single-line or multiline, so a composer that grows with its text takes its height from the callback on both platforms. `onScroll` gets `contentOffset` and `layoutMeasurement` when the text scrolls inside the field (the caret scrolls into view, the user drags). Neither is sent unless the field has the handler. Before, the Android engine sent neither, and `onLayout` was the only way to follow the size (#89).
- A remote form's `submit()` that the server accepts after the form was reset no longer resets it again: a draft typed after the reset (an editor closed and opened again while the older request was out) stays. A submission accepted with no reset in between starts the form again, as before (#103).
- `Keyboard.dismiss()` closes the keyboard of a focused `TextInput` (and of an `<input>` or `<textarea>`), on both platforms. React Native's dismiss blurs the input its own `TextInput` records as focused, and the package's `TextInput` recorded nothing, so the call did nothing, and neither did Back on a `Modal` while the keyboard was up (it closes the keyboard first). The input now records itself when it takes focus, as React Native's does, the command reaches its view through its handle, and a focused input that goes away (a sheet closed while typing) closes the keyboard as it goes, not once its view has left the window (#110).
- On Android, `insets.keyboardHeight` and `insets.keyboardVisible` (and so `KeyboardAvoidingView`) change as the keyboard starts to open or close, not once it has finished: the content moved up only after the keyboard had slid over it, and stayed up while it slid away (#109).

## 0.4.0-rc.10 - 2026-11-22

### Changed

- The package is `expo-svelte`, published on npm: `pnpm add expo-svelte@next` (a release candidate is on the `next` tag). Unscoped `svelte-native` is NativeScript's Svelte integration, and the name "Svelte Native" was that project's. Everything named after the package follows it, so an app on `@alfayez/svelte-native` changes:
  - in `package.json`, the dependency (`pnpm remove @alfayez/svelte-native && pnpm add expo-svelte@next`), `"main": ".expo-svelte/entry.ts"`, and the scripts: `expo-svelte dev`, `android`, `ios`, `doctor`;
  - every import, `@alfayez/svelte-native` and its subpaths, to `expo-svelte` (`expo-svelte/core`, `expo-svelte/app`, …);
  - in `metro.config.js`, `withSvelteNative` from `@alfayez/svelte-native/metro` to `withExpoSvelte` from `expo-svelte/metro`, and in `vite.config.ts`, `svelteNative()` from `@alfayez/svelte-native/vite` to `expoSvelte()` from `expo-svelte/vite`;
  - in `app.json`, the plugin `"@alfayez/svelte-native"` to `"expo-svelte"` (its options are the same; the manifest's `extra.svelteNative` is `extra.expoSvelte`);
  - the generated folder `.svelte-native/` to `.expo-svelte/` (delete the old one, and ignore the new one in `.gitignore`), and the environment variables `SVELTE_NATIVE_*` to `EXPO_SVELTE_*`.
  Then prebuild again. The native module and pod names (`SvelteCore`) and the app identifiers stay; the native views' Swift and Kotlin classes named after the package are renamed with it.
- On Android a push with the default animation moves as Android's own transition between two screens does (the new screen 96 dp in from the right over 450 ms, the screen below 96 dp left) and fades through, as Material's transitions do: the screen below fades out over the first 35 % of the movement (about 70 ms) and the new one fades in over the rest, so the two screens' content never shows at once; back is the reverse. It slid in across the full width over 250 ms with nothing moving or darkening below it, so two screens of the same colour showed no edge and their texts looked mixed while it slid. React Navigation's native stack plays Android's activity transition, where the new screen fades in over the old one for 83 ms; that is `animation="android_activity"` here. iOS keeps UIKit's push. The back gesture and the edge swipe move the screen as before; when they complete, the screen leaves from where they took it, the screen below staying where the gesture showed it.
- `animation` takes every value of React Navigation's native stack: `slide_from_left`, `fade_from_bottom`, `simple_push` and `flip` are new, with `android_activity`. On Android `fade`, `slide_from_right`, `slide_from_left`, `slide_from_bottom` and `fade_from_bottom` play react-native-screens' own animations between the two screens (a 150 ms crossfade; the whole width over 400 ms, the screen below pushed out; the whole height over 400 ms; 8 % up while fading in); `slide_from_right` moved the new screen alone over 250 ms and `fade` faded it in alone, `slide_from_bottom` rose over 250 ms. `flip` and `simple_push` are the default on Android, as in React Navigation. A screen the back gesture or the edge swipe ends slides off to the right across the width, unless its animation is the default or `android_activity` (it moves on and fades out); a `fade` screen faded out in place and a `slide_from_bottom` one fell. A page's own `<Screen animation>` now plays on the push that brings it in: the router makes a pushed screen once its page has loaded (a moment in a bundled app), so the page's options are part of the commit that brings the screen in. The first time a route was pushed, its screen came in with the `Stack`'s options and the page's arrived afterwards (its title and header updated, its animation came too late), on both platforms; with a `loading` snippet that is still so, since the screen comes at once to show it. On iOS a push stays UIKit's whatever the value (React Navigation animates `fade`, `slide_from_bottom` and `fade_from_bottom` there; not yet here), and `flip` flips a full-screen modal.
- A screen is opaque. One without a background of its own (from its style or class; `backgroundColor: undefined` is none) takes the one of the stack or screen it is in, so a tab's screens, a nested stack's and a page whose `<Screen style>` has no background look as the rest of their stack does, and one inside nothing that has a background gets the system's, in the app's light or dark mode: white or black on iOS (the elevated dark grey for a modal or a sheet in the dark mode), Material 3's surface on Android. React Native leaves a screen transparent, so a pushed screen showed the one below it through itself while it slid in, in every stack that no `<Stack style>` reached (a tab's stack, a nested stack). A transparent modal stays transparent, and so do the screens inside one or inside a `<Modal transparent>`. A `<Stack>` or `<Screen>` `style` or `class` with a background wins as before; an app that drew something behind its screens on purpose gives them `backgroundColor: 'transparent'`.
- A `Text` or a `TextInput` left without a colour by its style, its class and the text style of the HTML elements around it (which only the elements an HTML file is made of pass on) has the system's text colour in the app's light or dark mode: black or white on iOS, Material 3's on-surface on Android. React Native draws it black in both modes, so it vanished on a dark background. `color: undefined` after a colour leaves none, so `style={{ color: error ? 'red' : undefined }}` gets the system's colour when there is no error. A nested `Text` still takes its parent's colour. On Android an input's placeholder with no colour of its own is a light grey in the dark mode (it was 40 % black in both). An app in the dark mode that put text with no colour on a light surface of its own (a `bg-white` card with no `dark:` variant) colours that text.
- Android follows the app's `userInterfaceStyle`, as iOS does: the config plugin writes it into the manifest and svelte-core sets the night mode when the application starts, and the engine's header, tab bar, toolbar, system bars' icons and blur draw in it (they followed the system's mode, so an app kept light by `expo-system-ui` had a dark header in the system's dark mode). Expo leaves `userInterfaceStyle` to `expo-system-ui` on Android, so an app without that package followed the system's mode there while iOS kept Expo's default, `light`. An app with no `userInterfaceStyle` is now light on both; set `"automatic"` to follow the system. An app that lists `expo-system-ui` keeps that package's way. Prebuild again to get it.
- `expo-svelte init` writes `"userInterfaceStyle": "automatic"` in the `app.json` it creates, so the light and dark colours of the theme it writes show on both platforms. An existing `app.json` keeps its mode.
- `expo-svelte android`, `ios` and `dev` run Expo with its TypeScript setup off (`EXPO_NO_TYPESCRIPT_SETUP=1`). The first run of a new app no longer stops to ask whether to install `@types/react`, which the setup asks for and building or running a Svelte app doesn't need. Expo prints one line saying it skipped the setup. Setting `EXPO_NO_TYPESCRIPT_SETUP=0` in the environment gives Expo's setup back.

### Fixed

- A rest route matches zero segments, as in SvelteKit: `files/[...path]` opens `/files` (with `path` `""`) as well as `/files/a/b`, and `a/[...rest]/z` opens `/a/z`. Before, the base path matched no route (#80).
- When several routes match a URL, the native router opens the one SvelteKit opens: SvelteKit's route sort, segment by segment, across every navigator. `/files/report` opens `files/[id]` and not `files/[...path]`, and `/settings/account/edit` opens `settings/[area]/[action]` and not `[section]/account/edit`. Before, the route with more static segments won, then the first file (#82).
- `goto(href, { replace: true })` (and `replaceState`) to a page in tabs or a stack that isn't open yet replaces the screen on top. A sheet opened by a link and replaced by a tab route is no longer left under the tabs for Back to show again (#88).
- A link that arrives and opens a screen while the platform is still answering for the launch link wins over it: the launch link no longer resets the app and takes the newer screen away (#85).
- A static route whose name isn't ASCII (`src/routes/café`, `src/routes/العربية`) opens from its URL written either way, `/café` or `/caf%C3%A9`, and from a link: routes are matched against the decoded pathname, as SvelteKit matches them. Before, `goto` threw `No native screen` and `openURL` returned false (#94).
- A route whose load fails after Back took its screen away no longer replaces the screen the user went back to with its error: the screen that is leaving shows nothing. A route still on the stack that fails throws where it renders, as before (#92).
- Enter in an input of a `<form>` presses the form's default button (its first submit button), as a browser does: the button's `onclick` runs, it is `event.submitter`, and a disabled one stops the submission. Before, Enter submitted the form directly, even with the Send button disabled, and named the input as the submitter. A form with no submit button is submitted by Enter only when the input is its one single-line field (#79).
- A `<dialog>` hears `onclose` when it comes in a spread (`<dialog {...rest}>`), as it does when written on the element (#81).
- An input's `autocomplete` goes over the hint its `type` gives (`type="password" autocomplete="new-password"`, `type="email" autocomplete="off"`), under a native `autoComplete` the element sets itself. As in React Native's `TextInput`, `autoComplete` becomes `textContentType` on iOS, where the views have no `autoComplete`, and React Native's Android autofill name on Android, where the engine now applies it as the field's autofill hint (it applied none). A value with section or address words (`shipping email`) is read for its token, and one with no hint on the platform (`on`) is left out, so it doesn't turn autofill off (#86).
- `inputmode` and `enterkeyhint` (and `TextInput`'s `inputMode` and `enterKeyHint`) are the keyboard and the return key, as in React Native's `TextInput`; the native views have only those names, so the props were dropped. `inputmode="none"` opens no keyboard, also with `autofocus` or `focus()`: the Android engine applies `showSoftInputOnFocus` now (#87).
- `readonly` on an `<input>` or `<textarea>`, written on the element or in a spread, and `TextInput`'s `readOnly` make the field not editable, and unlocking it makes it editable again: both were dropped, so a read-only field could be edited (#95).
- `TextInput`'s `selection` places the caret on Android, at mount and when it changes, as on iOS: the prop was dropped there. The `setTextAndSelection` command works on Android too (#90).
- A `TextInput` or `Switch` with a raw `onChange` still runs `onChangeText` or `onValueChange` and updates `bind:value`, after `onChange`, as React Native does. Before, `onChange` took both away, and a controlled field sent a stale event count (#91).
- A `List` whose `rowHeights` reads state (a row that expands) or is given a new function moves the rows below the one that changed, and `scrollToIndex` scrolls to where they are now. The rows kept the old offsets and overlapped until the items array changed (#93).
- A checkbox of a remote form's group (`fields.topics.as("checkbox", "work")`), or a radio, keeps the choice made on it when it goes off screen while others of its field stay (a row of a `List` that scrolled away): it is sent, and checking or unchecking the others leaves it checked. Before, the next submission dropped it. A default of a box that is gone is still not sent, as for every input that is gone (#96).
- `navigator.clipboard.write()` with HTML only writes the HTML's text with every character reference decoded, as HTML reads them (`Caf&#233; &copy; 2026` is `Café © 2026`; named references from the spec's whole table, numeric ones in decimal and hex). Only six were decoded (#97).
- A literal `style="direction: rtl"` on an HTML element builds, as React Native's `direction` (`ltr` or `rtl`), as the same style given as an expression does: the class and style converter had no `direction` (#98).

### Docs

- Getting Started no longer says Svelte transitions are unsupported: they play on HTML elements, with the limits the animation guide lists (#78).
- The speculative navigation example in Routing navigates when a screen reader or a keyboard activates the button, which calls `onPress` with no `onPressIn`, and forgets a handle once it is used (#84).
- The TextInput page says that Android doesn't send `onContentSizeChange` or `onScroll` yet (#89).

## 0.4.0-rc.9 - 2026-11-18

### Added

- The optional native view libraries are vendored and turned on in the config plugin's new `libraries` option, one by one: `expo-image` 57.0.5, `expo-blur` 57.0.3, `expo-linear-gradient` 57.0.2, `expo-conic-gradient` 0.2.1, `expo-video` 57.0.5, `react-native-video` 6.19.3, `lottie-react-native` 7.3.8, `rive-react-native` 9.7.1, `@react-native-community/datetimepicker` 9.1.0, `react-native-pdf` 7.0.3 (with `react-native-blob-util` 0.24.9, which it turns on), `react-native-webview` 13.16.1, `react-native-maps` 1.27.2, `react-native-view-shot` 5.1.0, `react-native-fast-shadow` 0.1.1 and `react-native-animateable-text` 0.19.3 (VENDORING.md, "Optional libraries"). A library is `true` or the options of its own config plugin (`"react-native-maps": { androidGoogleMapsApiKey }`), which the plugin runs from the copy. A listed library is linked on Android and iOS and bundled by Metro; an unlisted one is none of that: no native code in the build (on iOS not even compiled, so an app without react-native-maps has no CoreLocation reference for App Store Connect to ask a purpose string for), Metro resolves its name to a stub that says how to turn it on, and its components throw the same. React Native's libraries are `--link` arguments of `android-autolinking` and `ios-autolinking` (an original that autolinking finds of a library that is off is taken out), Expo's modules are search paths of Expo's own autolinker (`expoAutolinking.searchPaths` after a `--`, because Expo's command reads the paths after its `--exclude` options as names to exclude, and `use_expo_modules!(searchPaths:)`), and the Metro stubs and the manifest's `extra.svelteNative.libraries` come from the same option. `svelte-native doctor` lists the libraries that are on and refuses an app that lists one in its `package.json` (or its plugin in `plugins`).
- `createVideoPlayer` from `@alfayez/svelte-native/foreign`: `expo-video`'s own function, typed from the copy, for the `player` of `VideoView` (the package is not installed, so `expo-video/build/VideoPlayer` cannot be imported where a type checker looks).
- Push notifications, straight from the app's server to Firebase Cloud Messaging (Android) and the Apple Push Notification service (iOS) with the app's own credentials: no relay and no push service of Expo's (PUSH.md, and the guide's "Push notifications" page, which also sets up React Native Firebase and `expo-notifications` for apps that want those). Push is part of the library, with nothing to install: the config plugin's `capabilities.push` turns it on for the platforms it names (the Google services file, the notification icon, color and channel, the `aps-environment` entitlement and the `remote-notification` background mode), and only then does Firebase Messaging (26.0.2, Android) join the app's build; iOS goes to APNs without the Firebase SDK. An app with push off has none of Firebase and bundles none of push's JavaScript. The plugin refuses a server secret in the app (a service account key, a private key, a `.p8`), and refuses `expo-notifications` or `@react-native-firebase/messaging` beside it: an app has one push library.

On the device the library installs `fetch`, `Headers`, `Request`, `Response`, `Blob`, `File`, `FileReader` and `FormData` in place of Expo's and React Native's, and `URL.createObjectURL` and `URL.revokeObjectURL`; each global is a getter that loads its implementation on the first read, so the start-up loads none of it, and an app binary without the native module keeps Expo's `fetch`. A response's bytes stay native until the code reads them: `arrayBuffer()` and `bytes()` hand JavaScript one native buffer (no base64, no copy through a JavaScript array), `blob()` keeps them native, and `body` is a `ReadableStream` that reads them in 64 KiB chunks as they arrive (the transfer pauses while more than 1 MiB is unread). A `Blob` is native bytes too: joining, `slice`, uploading one and a multipart body built from them copy nothing through JavaScript, and `URL.createObjectURL(blob)` gives a `file://` URL an image, a video or a WebView loads. `fetch` takes http(s), `data:`, `file://` and (Android) `content://` URLs; `redirect` is `follow` (up to 20), `error` or `manual` (the redirect response itself, as Node's `fetch` gives it); `credentials: "omit"` sends no cookie and keeps none; an `AbortSignal` stops the request or the body (and `AbortSignal.timeout` and `AbortSignal.any` exist); `text()` decodes UTF-8 as the standard says (a byte order mark dropped, an invalid sequence U+FFFD). `FormData` extends React Native's, so `XMLHttpRequest` and axios still send it, and `xhr.send(blob)` sends one of the library's Blobs (as a file the library writes and deletes when the request ends); a caller's `Content-Type: multipart/form-data` without the body's boundary gets it, as React Native's and Expo's `fetch` do. A handle is an object of its own kind, so a `$state` array holds the handle itself, not a proxy of it.
- A view inside a text starts a new text under it, as in React Native: a `Text` in a `View` in a `Text` is a text, not a span of the outer one.
- Edits of the lowering that start at the same place apply the longer one first; `<View class:on={x} {...rest} />` (the directive first, a spread after it) was written wrongly. A multi-line `class:` directive no longer moves the lines below it.
- `bind:this` on a lowered `<View>`, `<Text>`, `<ScrollView>`, ... is a `ref` now. It was left as `bind:this` on a host tag, which Svelte's custom renderer refuses ("`bind:` is not compatible with `customRenderer`"), so a component with one did not build. The variable gets the host handle (`measure`, `scrollTo`, ...) and `null` when the element is destroyed.
- The class resolver (`resolveClasses`, `ClassResolver`) takes a third argument, `defer`, which leaves a font-relative line height or letter spacing as a `fontRelative` key for the host to make (the lowered HTML elements use it). Nothing else changes for components.
- `dist/node/transformer.cjs` and `dist/node/lower.js` include the HTML lowering and the converter of `css/`, to convert a `style="..."` string: each is about 90 kB larger (31 kB to 121 kB, and 9 kB to 99 kB). They are what Metro and the Svelte preprocessor run in Node when a file is built; the JavaScript of an app does not hold them (`apps/example/test/bundle.test.ts` checks that no module of the lowering or the converter is in the bundle). The list of style keys that the development warning of `style:` checks names against is a module of its own, loaded only when `__DEV__` is true, so a release bundle leaves it out.
- **Breaking:** expo-blur's component is now `ExpoBlurView` (the name `BlurView` is the library's own blur above); its props and `BlurTargetView` are unchanged. Rename the import and the tag where you use expo-blur's.
- On Android a message of the main looper applies every mounting transaction that is queued, and the ones queued while it applies (within 50 ms of work), where it applied one and left the looper free for a frame between two, as React Native's mount item dispatcher does; and the host asks the engine (`holdMounts`, `releaseMounts`) to apply the commits of an `animate:` or a transition that measures together. Before, a frame could be drawn between the commit of a flip's new order and the commit of its items' first frames: nearly every reorder showed the new order untransformed for a frame or two on a page with plain buttons. The first reorder after the app starts can still do it. A start-up's or an animation's commits that arrive faster than they apply are drawn a frame apart after 50 ms.
- The guide in `docs/` is reorganised in the shape of SvelteKit's, in sections: getting started, core concepts, a page for every component (what it is, an example, its props), native features, building and releasing, an appendix, and a reference for the command line, the configuration and every module. It is published at <https://svelte-native.alfayez.dev>. `svelte-native doctor` names the new path of "Creating a project".

### Fixed

- Android: a list that mounts rows while it scrolls (`List`, a windowed list) drops no more frames than before transitions. Since transitions the engine applied every commit that was waiting in one message of the main thread, so two commits that did not belong together were drawn in one frame; it applies one per message again, and only the commits the host holds together for an `animate:` or a transition (the layout read, then the first frames) are applied at once. On a Samsung A16 the lab's windowed list read 17 late frame intervals in twenty runs with the drain and 3 without it.

- A row of host tags (`<native-view nativeProps={{ style }}>`) costs less JavaScript to mount again: a `nativeProps` with no `ref` in it no longer goes through the wait for a screen that refs need, and an element that is not an HTML view builds its children without gathering lines. HTML elements had made 300 such rows 15 % slower to mount (130 ms to 148 ms of Svelte flush on a Samsung A16); on the PC's interpreter the same mount measures 9.0 ms before HTML elements, 10.4 ms with them, and 9.5 ms now.

- A single-line HTML `input` sends no line height, its own (`leading-*`) or inherited, so its text stays centred as on the web. On iOS a line height drew the text 2 pt low, and a text field view reused for another input kept it.

- Android: a `Text` nested in a `Text` with its own `onPress` (the inline link, `<Text>See <Text onPress={...}>this link</Text> here</Text>`) never got its presses: the engine sent every touch to the whole paragraph, so only an `onPress` on the outer `Text` worked. The touch now goes to the nested `Text` under the finger, as in React Native (`reactTagForTouch`): its `onPress`, `onPressIn`, `onPressOut`, `onLongPress` and `onPressChange` run, and the paragraph's does not, unless the nested `Text` has no handler; a press that moves far off the sentence is cancelled. A nested `Text` with `role="link"` is a link to accessibility services (a clickable span over its words, which a service lists and activates; the activation presses it). A touch on the `…` of a `numberOfLines` text is the paragraph's, not a hidden link's.
- Android: a `Text`, an `Image` or an `ActivityIndicator` with a press handler ran it twice per tap (the touch's press, then a second one from Android's click when the finger lifted). It runs once.
- A press whose node is unmounted while the finger is down no longer runs the node's handlers when the finger lifts, and a press whose end never arrives (native drops the touches of a deleted node) no longer leaves the next touch without a responder.

- A `Text`, `View` or `Pressable` whose `onPress` (or another press handler) is `undefined` (`onPress={enabled ? go : undefined}`) no longer keeps the press from the nearest ancestor that has a handler: Svelte compiled it to an event listener that stayed on the element and did nothing, and the host took the element for a pressable. The lowering now passes a press handler that is not a function written in place as the attribute `nativeOnPress` (and `nativeOnPressIn`, ...), which is the prop only while it is a function. An HTML element does the same for an `onclick` that may be `undefined` (a `div`, a `span`, a `p`; a button and a link press by themselves, so they are always pressable). A hand-written `native-*` tag keeps the old behaviour unless it uses these attributes.

The first three are changes in the native engine, so the native host has to be rebuilt.
- An app that installs the library from a tarball or git bundles again: Babel, which compiles the library's sources under `node_modules`, rejected the `declare` fields of `InlineStyle`; the five properties are typed by an interface merged with the class, and a test compiles every source file with `babel-preset-expo` as an app's Metro does.
- The guide's starter passes the doctor again: pnpm 12 does not apply a patch to the Svelte that `pkg.pr.new` serves, so the doctor failed with "svelte@5.56.7 is not applied". The Metro transformer no longer needs the patch: it removes the compiler's two refusals of the transition directives as it loads the compiler (`module.registerHooks`, Node 22.15 or newer). The package ships no patch of Svelte, `init` declares none and the doctor asks for none.
- `onintrostart`, `onintroend`, `onoutrostart` and `onoutroend` on an HTML element are no longer warned about ("never runs on a device"): Svelte's transitions send them and the handlers run.

- `@expo/metro-config` was required by the transformer without being declared: it resolved only under a hoisted install (see "Changed"). A test runs the transformer in a layout where it is only beside `expo`.
- `pressRetentionOffset`, which React Native's types accept on `Pressable`, was ignored by the host (it read only `pressRectOffset`, Pressability's name); it now widens the press region as in React Native.
- The `svelte-native` command line (`doctor`, `sync`, `dev`, …), `@example/svelte-native/metro` (`metro.config.cjs`), `/transformer` (Metro's workers), `/expo` (`@expo/config`'s plugin loader) and `/vite` did not load when the package was installed in an app's `node_modules`: Node refuses TypeScript from there (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`, Node 25 and 26), and Vite and `@expo/config` hand the file to Node. They worked in this repository only because the workspace link is not under `node_modules`. A test unpacks the packed package into a scratch `node_modules` and loads each with plain `node`.

### Added

- `openLaunchURL(router, accept?)` opens the link the app was launched with into the root router before its `<Router>` mounts and resolves with the link. A shell that chooses what to render by the launch link (the platform app's lab starts without its session) awaits it, so the navigator starts on the link's screen and the router's first screen is never rendered; the `<Router>` mounted afterwards does not read the link again, and the platform is asked once. `accept` refuses a link for the moment (it is left for the `<Router>`).
- SvelteKit remote functions. A `*.remote.ts` module is imported in native Svelte code as in the browser: Metro replaces it with the client stubs SvelteKit's Vite plugin would generate (same ids), and `query`, `query.batch`, `query.live`, `command`, `form` and `prerender` run on SvelteKit's own client files against the SvelteKit server named in the app config (`extra.svelteNative.remote`, written by the new `remote` option of the Expo plugin, or `configureRemote({ origin })`). Cookies are the platform's, requests carry the `Origin` SvelteKit's CSRF check wants, `query.live` streams through Expo's `fetch`, a `redirect()` goes through the router, and a build with no host throws at the first call. `form` is a native port: `fields.x.as(type)` returns the props of a `TextInput` or `Switch`, `submit()` is the submit button, a submission carries what the inputs show (defaults included) and a failed one is handled, not thrown (`form.error`). Numbers are read strictly, Arabic digits included, and `"1,000"` (a thousand or 1.000, depending on the reader) is not a number. A field none of whose inputs is on screen any more (a virtualized row, a closed modal) still posts what was typed or set. A submission always ends: `pending` goes back to 0 even when `handleError` or the data read throws. Peer dependencies: `@sveltejs/kit` 3.0.0-next.27 exactly, and `expo-constants`. New entries `@example/svelte-native/remote`, `/remote/runtime` and `/remote/globals`; a new dependency, `@babel/parser`. Hermes 0.17 has no `FinalizationRegistry`, which SvelteKit's query cache needs: the package supplies one, and a query object made in a component is released when the component is destroyed (its live stream closes, its cache entry is dropped) and made again if it is used afterwards. Nothing is installed on `globalThis`. See README, "Remote functions".

### Changed

- A navigation before the root `<Router>` has mounted drops the screens it replaces at once. They were kept until the native stack reported their exit, which a screen that was never shown cannot do, so the router's first screen stayed rendered (and the timeout warning fired) after the launch link replaced it. The same goes for a root `<Router>` that unmounts (a shell waiting for its session): the screens still leaving are dropped with it.
- The read of the launch link is bounded: the platform gets three seconds, after which the app starts as if it had no link, and an answer that comes later is opened if nothing has navigated since (never after, never twice). A read that failed is no longer remembered for ever (the next `openLaunchURL` asks again, unless the app has gone on meanwhile, when the link is stale and is dropped), and the `<Router>` reports a failed read instead of leaving an unhandled rejection.
- The Expo plugin's options take `remote: { origin, base?, appDir? }`; an `http:` origin also lets the Android and iOS builds use plain HTTP to it.
- The root router tells the remote runtime which screen is on top and how to follow a server redirect (`connectHost`).
- The windowed `List` mounts its overscan four frames after the rows that show, not one (the one-frame flush went ahead of the layout event of the visible rows on a phone with slow cores), and the wrapper of a row of a list whose rows have one size is described once per row. Once the animation layer is loaded only the nodes that can need it go through it, and a node the host has not built no longer reports its changes.
- Android boot (Samsung A16, 2 November 2026; SPEC "Boot on the phone, round 2"): the Expo plugin now generates `override fun attachBaseContext(base: Context)` into `MainApplication.kt`, which calls `BootBoost.preloadLibraries(base)` (SoLoader and the start's native libraries load on a thread of its own while the Application is set up). **A `MainApplication.kt` that already overrides `attachBaseContext` clashes with it**: `prebuild` now stops with a message unless the existing override calls `expo.modules.svelteengine.BootBoost.preloadLibraries(base)` itself (then the plugin adds nothing). `MainActivity.onCreate` gets two generated calls (`BootBoost.activityCreated()`, `ViewWarmup.begin(this)`).
- Android boot: `expo-blur`, `expo-conic-gradient`, `expo-image` and `expo-linear-gradient` are built when their first component is mounted (like `expo-video`), not with the host, so `requireNativeModule` on them builds the module on first use. The boot pin no longer asks the system whether the process is on screen: it is made in the app's main process (not in another process of the app), kept when the Activity says it exists, and dropped when no Activity came.
- A text under a live region tells it when its text changes (an engine text is a plain view); a role description is React Native's string ("Link", "Tab") instead of the engine's own lowercase one; a `button`, `imagebutton` or `togglebutton` role makes the node clickable.
- The Android host is the package's own engine (`native/svelte-engine`): Fabric's mounting is replaced by typed Kotlin views, so mounting 600 views costs about a fifth of React Native's on the Samsung A16 and the Reanimated frame path no longer builds Java maps. iOS keeps React Native's mounting.
- There is no React in the render path: the React host, `react-native-screens`, `react-native-safe-area-context` and the dev client are gone, and Metro maps `InitializeCore` to the package's own `init.ts`.
- `<View>`, `<Text>`, `<ScrollView>`, `<Image>`, `<ActivityIndicator>` and `<Pressable>` are lowered to host tags at compile time, so a row costs host nodes only.
- Boot on Android: route modules load on first use, the Expo module registry and the Reanimated and gesture hosts load lazily, view configs are static, start-up threads stay on the big cores until the first mount, and a baseline profile ships for the engine and updates modules.
- Frames on Android: pooled views, a text layout cache, views with partial alpha are no longer promoted to hardware layers, screens hidden with alpha instead of `INVISIBLE`, layout events delivered in the batch that mounted them, and a fixed native heap leak in animated views.
- Route tables are generated per bundle variant (`.svelte-native/routes.<variant>.ts`); Metro writes the table for the variant it bundles and refuses a bundle whose table belongs to another.
- The windowed `List` mounts the rows that fit first and its overscan a frame later, and fixed-height rows skip the layout report.
- `ref` callbacks follow React's contract on every element and component: the handle when the element is built, `null` when it is destroyed, and the old callback gets `null` before a replacement gets the handle.
- On iOS `Modal` mounts its native host only while it is shown, as React Native's does.
- A function-valued `ref` or attribute survives a spread on a lowered primitive.
- A popped iOS screen stays mounted until the stack reports its exit.
- Peer dependencies: `react-native-gesture-handler`, `react-native-reanimated` and `react-native-worklets` are required (a native rebuild); the libraries behind the wrappers are optional.
- The product (`APP_VARIANT=production`) contains no development lab: route discovery skips `__dev` directories and `export const lab = true` pages, Metro stubs the lab's modules, and a bundle whose table names the lab is refused.

### Fixed

- Android: events of `react-native-pdf`, `react-native-video`, `lottie-react-native` and `react-native-maps` that are not streams are no longer replaced in React Native's event queue. React Native's `Event.canCoalesce()` is `true` unless an event class says otherwise, and the queue then keeps only the last of two unread events of one name from one view while JavaScript is busy. `react-native-pdf` sends every message as one `topChange` event, so a document's `onLoadComplete` was overwritten by the `onPageChanged` the view posts 10 ms later: 28 of 182 `Pdf` row mounts on the emulator and 10 of 130 on the Samsung A16 raised no load event, and 0 of 39 do with the patch. The same is closed for the events of video (all but progress and bandwidth), Lottie (finish, loaded, failure) and maps (21 of the 26 event classes; the five streams keep coalescing). The patches are pnpm patches of this repository (`patches/react-native-pdf@7.0.3.patch`, `react-native-video@6.19.3.patch`, `react-native-maps@1.27.2.patch` and the existing `lottie-react-native@7.3.8.patch`, listed in `patchedDependencies`), so an app that is not this repository must carry them. The price is that JavaScript is told of every message of such an event, every `scaleChanged` of a PDF pinch included. `rive-react-native` needs no patch: its events leave through React Native's interop emitter, which never coalesces, and a test reads React Native's sources and fails when that changes. iOS cannot lose these events (it sends them with `dispatchEvent`, never through the queue's unique path).
- Android: the first screen of the app's stack no longer keeps what its header and sheet worked out while the screen was laid out detached. With a launch link opened before the `<Router>` mounts (`openLaunchURL`), an inline header title sat 1 px high, and a sheet link under a nested stack (`/__dev/tree/inbox/compose`) rested at its top detent over the whole pane, a root screen to look at, on some launches (a warm link, pushed onto a stack that has its size, was fine); any first screen of a cold start could hit it, not only a launch link's. A header lays out again when it attaches with a window inset it did not use (pushed screens too: every title sits at the status bar's inset, not a pixel above it), a sheet rests where its layout says whenever that moves, and a header inside a sheet keeps the padding its screen gave it. A layout does not move a sheet that is being dragged, is settling, leaving or animating, is in a transition of the stack, or is moved by a gesture of the stack (a predictive back swipe).
- iOS: the events of `react-native-video` and `rive-react-native` (load, ready, progress, play, pause, stop, error) reach JavaScript. They are legacy view managers, and React Native's interop gives such a view an event block only for an event prop that is `true`; the host's static view configs now list their events as attributes on iOS (`Kind.legacy`). Before, none of them was delivered there.
- iOS: `lottie-react-native` 7.3.8 is patched (`patches/lottie-react-native@7.3.8.patch`, through `patchedDependencies`): `onAnimationLoaded` and the failure event, which the view raised before it had an event emitter, are kept and sent when the emitter arrives, and a recycled view that gets the source it already shows says that its animation is loaded.
- iOS: the `tmpfile` captures of `react-native-view-shot` that a process left when it ended without exiting are deleted when the next process starts (the `svelte-capture-ios` module); React Native deleted them only when the next process captured something. The wrapper passes the library's own answer on: a plain path on iOS, sizes in points.
- `List`: `scrollToIndex` and `scrollToOffset` called before the scroll view is bound and has its first layout (a page that scrolls its list in the effect that runs as the list mounts) sent the command to no view and the list stayed at the top. The last such request is kept and sent when both are there. The two commands no longer subscribe the effect that calls them to the list's window, row sizes and header.
- iOS: a hidden `Modal` swallowed every touch on pushed screens.
- A scroll view's content container follows `contentContainerStyle` and `horizontal` after the first render.
