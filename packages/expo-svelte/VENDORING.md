# Vendoring third-party native dependencies

`expo-svelte` carries its third-party native dependencies itself: their published source is copied into `vendor/<name>/` of the package, and an app's `package.json` lists `expo-svelte` and nothing beside it. The rule: **vendor everything if possible, unless it is presented as an alternative** (push notifications: Firebase, `expo-notifications`). The pilot is `react-native-nitro-modules` 0.35.10 and `react-native-mmkv` 4.3.2 (MMKV is what `localStorage` is made of, Nitro is its runtime and quick-crypto's), which every app links; the crypto batch is `react-native-quick-crypto` 1.1.3, `react-native-quick-base64` 2.2.2 and `hermes-intl` 0.1.2 (what `crypto` and the `Intl` constructors Hermes lacks are made of), which every app links too; the optional native view libraries (expo-image, react-native-maps, ...) are vendored the same way and linked only for an app that turns them on ("Optional libraries" below); the UI batch is `react-native-gesture-handler` 3.3.0, `react-native-reanimated` 4.7.1, `react-native-worklets` 0.13.0 and `react-native-svg` 15.16.0, which every app links too ("The UI packages" below: they carry patches, a Babel plugin and codegen views); the rest follow this pattern (the list at the end).

## Where

- `vendor/<name>/` holds what the npm tarball publishes, unchanged: the JS the app needs (`src/`, `lib/`), `android/`, `ios/`, `cpp/`, Nitro's generated code, the podspec, `package.json` (the podspecs and the codegen read it) — plus `LICENSE` and `VENDOR.md` (upstream name and version, the tarball's integrity and sha256, what was left out, every local change, and the command that writes the directory again). `vendor` is in the package's `files`.
- `node scripts/vendor.ts <name>@<version> [--exclude <path>]... [--license-url <url>]` writes one: `npm pack`, unpack, check the tarball's integrity against npm's, replace `vendor/<name>/` as a whole. The output depends on nothing else (no date, no machine), so running it again with the same arguments gives the same bytes. A tarball without a `LICENSE` (npm omits one that is not in `files`: neither pilot package has one) gets the repository's, fetched at the tarball's own `gitHead`; its URL and sha256 are in `VENDOR.md`. `--exclude <path>` leaves out what the app never needs and the repository must not hold or run, and `VENDOR.md` lists it: the pilot leaves out the packages' own tests (`bun test` finds `*.test.*` files wherever they are, and MMKV's need `@testing-library/react-native`) and Nitro's `lib/tsconfig.build.tsbuildinfo` (the repository ignores `*.tsbuildinfo`). A path with `*` is a pattern over the package's files (`'lib/**/*.map'`: `*` stays in one directory, a directory part `**/` is any number of them; quote it, `VENDOR.md` does; a pattern that matches no file is refused). The UI batch leaves out the source maps of `lib/` (8 MB), gesture handler's and svg's `lib/commonjs` (Metro reads `src` through the `react-native` field, and nothing runs `main`), svg's `windows/` projects, the Gradle wrapper of svg and Reanimated (a jar and two scripts the app's Gradle never runs) and gesture handler's jest helpers.
- A local change is a patch file, `vendor-patches/<name>/*.patch` (`patch -p1`, applied in file name order), applied by the script after the unpack and listed under "Local changes" (by its path from the package's root and its sha256, so `VENDOR.md` names no machine). Nothing in `vendor/` is edited by hand. The pilot has none; the UI batch has five (gesture handler's one, Reanimated's three and Worklets' one: below), and four of the optional libraries have theirs (lottie-react-native, react-native-maps, react-native-pdf, react-native-video: events that must not coalesce, which were pnpm patches an app had to declare; react-native-pdf's second patch makes its Gradle find react-native from the app's directory, since the copy is not beside react-native in `node_modules` any more); react-native-blob-util's one line names the optimizing Proguard file, which Android Gradle plugin 9 (React Native 0.88) requires. `vendor-patches/` is in the package's `files`, and the doctor looks for the shape each patch leaves in the copy (`patchSpecs`, `vendored: true`).
- `.gitignore` re-includes `vendor/**/android/`, `ios/`, `build/` and `dist/` (the repository ignores all four everywhere else; an Expo module's JavaScript is in `build/`, react-native-maps' declarations in `dist/`) and ignores again what a native build writes (`android/build`, `ios/build`, `.cxx`, `.gradle`); ESLint and Biome skip `vendor/`; those native build outputs are not packed (`files` negates `vendor/**/android/build` and `ios/build`, not `build` at large).
- What the script leaves out (`--exclude`, listed in `VENDOR.md`): Expo's precompiled iOS frameworks (`prebuilds/`: 132 MB for expo-image, 9 MB for expo-video; Expo uses them only with `EXPO_USE_PRECOMPILED_MODULES=1`, an app that sets it builds these two from source), `*.tsbuildinfo`, a library's tests and the development files of its repository (view-shot's `example-expo`, `coverage`, `.claude`), and the `windows/` and `macos/` ports.

## JavaScript

- The library's own code imports a copy as `#vendor/<name>`, an entry of the package's `imports` map: `types` is the copy's declaration entry, `default` its source (`src/index.ts`, what Metro bundled from `node_modules` before: the `react-native` field). Metro, Vite, Bun, esbuild and TypeScript all read it, in the repository and installed alike. The map has an entry for each vendored package whose JavaScript the library imports (`react-native-mmkv`) and for the types of the other (`react-native-nitro-modules`, below).
- `withExpoSvelte` (Metro) resolves the bare names, and every path below them, to the copies **for every importer**: the app, a library that imports them (react-native-quick-crypto imports the Nitro runtime), the copies themselves. One copy of each, one module of each. A name an app stubs (`stubbedPackages`) is still stubbed first. A vendored package gets the `react-native` shim (`fabric/react-native-lite.ts`) exactly when its name is in `LITE_ORIGINS`, as the installed one did (`isLiteOrigin`).
- Types: `src/mmkv.ts` re-exports from `#vendor/react-native-mmkv`, so `dist/types` names it and an app's checker resolves it through the library's `imports` (`types` condition). The copy's declarations import `HybridObject` from `react-native-nitro-modules`, which the app does not install: `src/vendor-types.d.ts` declares that module as a re-export of `#vendor/react-native-nitro-modules`, and every declaration that names a vendored type carries a `/// <reference path>` to it (`publicAmbient` in `scripts/build-types.ts`). The UI batch has a file of its own, `src/vendor-types-ui.d.ts` (the same for `react-native-worklets`, `react-native-reanimated`, `react-native-svg` and `react-native-gesture-handler`, which Reanimated's and gesture handler's declarations import by name, and a library of the app may): loading it loads the declarations of all four (hundreds of files), so only `animation.ts` and `svg.ts` reference it and the primitives alone (`/core`) do not (`tests/package/type-budget.test.ts` keeps it so). Gesture handler's declarations are imported by deep path, `#vendor/react-native-gesture-handler/types/<path>` (an `imports` pattern with the `types` condition only: nothing runs it).
- Web: the web target of `expoSvelte()` already puts `.web.*` extensions first, so `#vendor/react-native-mmkv` builds with MMKV's web implementation and with no React Native and no Nitro (`tests/web-apis/web-mmkv.test.ts`).

## Native linking

React Native's autolinking links only the app's own dependencies, so the library adds its copies to the autolinking config **itself**, from `vendor/`, with the fields autolinking would print for the installed package (`src/vendored.ts`: the list, `vendoredDependency`, `linkVendored`).

- **Android**: `settings.gradle` already runs the config command through `expo-svelte android-autolinking <command...>`; that command now adds the entries (and the deferred-Nitro relinking, `deferredNitroPackages` and `NitroGate`, is applied after: the entries carry the same `packageImportPath` and `packageInstance` the installed packages had, which is what it matches).
- **iOS**: `expo-svelte ios-autolinking <command...>` does the same for the Podfile: `applyPodfileVendoredLinking` (`expo.ts`) puts one block before `config = use_native_modules!(config_command)` that finds the CLI from the app (`require.resolve('expo-svelte/package.json')`, as the template finds `expo`) and wraps `config_command`. Stripped and written again on every prebuild, like the excludes; it works under `EXPO_USE_COMMUNITY_AUTOLINKING=1` too.
- The entries are the reference captured from Expo's own `react-native-config` for the installed packages, with the directory of the copy (`tests/cli/fixtures/vendored-autolinking/`): `root` and `sourceDir`/`podspecPath`/`cmakeListsPath` in `vendor/<name>/`, `name` unchanged (**the Gradle project is `:<name>` and the pod is the podspec's own name**, so quick-crypto's `project(':react-native-nitro-modules')` and `s.dependency 'NitroModules'` find the copy).
- Nothing in either package computes a path from `node_modules`: Nitro's CMake and Gradle use prefab and project dependencies, the generated code is below the package, the podspecs use `__dir__`. iOS codegen finds the Nitro spec through the config's `root` (`ios/build/generated/autolinking/autolinking.json`, written from the command's output), which is why `package.json` with its `codegenConfig` stays in the copy.
- The UI batch the same way, with its own fields (`fixtures/vendored-autolinking/expo-sdk58-*.json` hold what Expo's `react-native-config` printed for each in `apps/example`; `componentDescriptors` and svg's `cmakeListsPath` are read from the copy's own `react-native.config.js` by a test): gesture handler's one (`RNGestureHandlerDetectorComponentDescriptor`, with its `android/CMakeLists.txt`), svg's 29 and its CMake file in the sources, `libraryName` from each `codegenConfig` (`rngesturehandler_codegen`, `rnreanimated`, `rnworklets`, `rnsvg`). The Gradle projects keep their names, which is what the packages look each other up by: Reanimated's `build.gradle.kts` needs `:react-native-worklets` and orders its native build after it, gesture handler's `build.gradle` adds its `reanimated/` and `svg/` source sets when `rootProject.subprojects` has `react-native-reanimated` or `react-native-svg` (and depends on them), svelte-core's `compileOnly project(':react-native-gesture-handler')`. The pods keep theirs: `RNGestureHandler`, `RNWorklets`, `RNReanimated` (which depends on `RNWorklets`) and `RNSVG`. Reanimated's Gradle task and its podspec's script run `scripts/validate-worklets-build.js`, which asked Node for `react-native-worklets/package.json` by name: a patch makes it read the copy beside it (`vendor-patches/react-native-reanimated/0002-...`).

## Optional libraries

Sixteen libraries are vendored for the apps that use them and cost the others nothing: `expo-image`, `expo-blur`, `expo-linear-gradient`, `expo-conic-gradient`, `expo-video` (Expo modules), `react-native-video`, `lottie-react-native`, `rive-react-native`, `@react-native-community/datetimepicker`, `react-native-pdf` with `react-native-blob-util`, `react-native-webview`, `react-native-maps`, `react-native-view-shot`, `react-native-fast-shadow` and `react-native-animateable-text` (React Native packages). They are `vendoredPackages` entries with an `optional` field (`src/optional-libraries.ts`: `kind`, the package's own config `plugin`, `requires`), and the app's plugin options say which it uses:

    ["expo-svelte", { libraries: { "expo-image": true, "react-native-maps": { androidGoogleMapsApiKey: "..." } } }]

A listed library is linked on Android and iOS, bundled by Metro, and its own config plugin (the copy's `app.plugin.js`) runs with the options given, as if the app had listed it in `plugins`. An unlisted one is none of that: its native code is not in the build (on iOS it is not even compiled: react-native-maps references CoreLocation, and App Store Connect would hold every app to a location purpose string if it were always linked), its name resolves to a stub in Metro, and its components throw how to turn it on. `libraries.ts` checks the option (`checkLibraries`: names, `true`/`false`/options, no options for a library without a plugin) and the plugin refuses what it cannot make sense of.

The decision is made twice from the one option, so a build and its bundle agree:

- **Prebuild** writes it into the generated files, which Gradle and CocoaPods run on every build: the React Native libraries are `--link <name>` arguments of `expo-svelte android-autolinking` (`settings.gradle`) and `ios-autolinking` (the Podfile block), and `linkVendored(config, platform, root, linked)` adds the entry of each named library to the config the command prints, **and takes out** any original that autolinking found of one that is not named (a copy installed for another package's sake: an app that carries a feature carries it from the library, and an app that does not carries none). The plugin also writes the names to `extra.expoSvelte.libraries` (the manifest `expo-constants` embeds), which the wrapper components read (`fabric/foreign-libraries.ts`) to say how to turn a library on where it is off.
- **Metro** reads the same option from the app's config as Expo reads it (`getConfig`: `appPluginOptions`, once for this and for the push client), and resolves the name of each library that is off, and every path below it, to a stub for every importer (`libraryStubSource`: `<name> is not in this app: turn it on with libraries: { "<name>": true } ...`); the ones that are on resolve to the copy, as the pilot's do. A config that cannot be read keeps every library, as it keeps the push client. `withExpoSvelte(config, { libraries })` names them when the config should not be read.

**Expo modules** (expo-image, expo-blur, expo-linear-gradient, expo-conic-gradient, expo-video) are not in React Native's autolinking config (they have an `expo-module.config.json`, not a `react-native.config.js`): Expo's own autolinker links them, and finds a package only through `node_modules` or a search path. The plugin gives it the **directory of each enabled copy** as a search path (a directory with a `package.json` is one module, so nothing else under `vendor/` is looked at): Android `expoAutolinking.searchPaths` in `settings.gradle`, found from the CLI's path (`<library>/vendor/<name>`), and iOS `use_expo_modules!(searchPaths: ...)` in the Podfile, found with `require.resolve` as the CLI is. The Expo modules that are off join Expo's `exclude`, so a copy installed for another package's sake is left out too. Expo's Gradle plugin builds the command as `... --exclude a --exclude b <searchPaths>`, and `--exclude` takes any number of values, so without a `--` in front the paths are read as names to leave out and nothing is found: the first Android search path is `"--"` (`tests/cli/library-linking.test.ts` runs Expo's own autolinker on it). Expo's Android modules build from the prebuilt AAR in `local-maven-repo/` (`expo-module.config.json`'s `publication`), which the copy keeps.

**Patched libraries and `settings.gradle`'s cache**: React Native keeps the config command's output until a lock file of the app changes, and `--link` arguments are not in any of them, so the block's lock files include `settings.gradle` itself.

**`androidOnDemandViewManagers`** names package classes (`com.rnmaps.maps.MapsPackage`) that Kotlin must find: the entries of a library that is off are dropped (`onDemandForLibraries`), so one config serves the builds that turn a library on and those that do not.

**`createVideoPlayer`** is exported by `expo-svelte/foreign`: the app cannot import `expo-video/build/VideoPlayer` where a type checker looks, since the package is not installed. It requires the module by name when called (the stub when `expo-video` is off) and is typed from the copy through the `#vendor/expo-video/*` import.

**The doctor** reports the libraries that are on (and why a library is on that the app did not list), refuses an app that lists an original, and checks the shape of each patch in the copy.

Not changed by any of this: the library's own foreign components (`/foreign`) mount the native views by name and import none of these packages, so nothing of an unused library is evaluated; JavaScript dependencies of the copies (`sf-symbols-typescript`, `crypto-js`, `base-64`, `nullthrows`, ...) are only reached by an app that imports a library's JavaScript itself, which none of the components do, and are not installed (an app that does add them to its own `package.json`).

The config plugins of the copies (react-native-maps, react-native-video) require `@expo/config-plugins` by that name, which the library does not declare: Node finds it where the app's `expo` put it, at the top of its `node_modules` (npm, Yarn, and pnpm's default hoisting). A pnpm install with `hoist=false` does not, and the prebuild then stops at "Cannot find module '@expo/config-plugins'" when one of those libraries is on. The date and time picker's plugin (since 9.2) and the plugins of expo-image and expo-video require `expo/config-plugins` instead, which the `expo` peer provides beside the library under every package manager.

## Collisions

An original must not be linked beside a copy.

- The config plugin stops the prebuild, `expo-svelte doctor` fails, and the autolinking commands refuse (exit 1, nothing on stdout) when **the app's `package.json`** lists a vendored name (`dependencies`, `devDependencies`, `optionalDependencies`): "`expo-svelte` includes react-native-mmkv 4.3.1; remove it from the app's dependencies (package.json), reinstall, and prebuild again." One list, `vendoredPackages` in `src/vendored.ts`, and one message (`collisionMessage`); a package added to the list is covered everywhere.
- The optional libraries are on the same list, and the refusal is the same whether or not the app turned the library on (its message adds how to turn it on, `libraries: { "<name>": true }`). The plugin also refuses an app that lists a library's own config plugin in `plugins`: the package is not installed, so Expo could not find it, and its options go under `libraries`.
- An original that autolinking finds **without** the app listing it is replaced, not refused: a package manager can install one as another package's dependency, Expo's autolinking finds it in `node_modules`, and refusing would refuse an app that did nothing wrong. The entry is replaced by the copy's under the same name, so it is linked once; the unused original in `node_modules` is inert (Metro never reaches it). The Nitro runtime pnpm installed for quick-crypto's peer is gone with quick-crypto's own vendoring (the lockfile has no `react-native-nitro-modules`); `react-native-quick-base64` is still installed, as a dependency of `@craftzdog/react-native-buffer`, which is the case this rule is for.

The UI packages are where this matters most, because other libraries depend on them. What an app that has such a library gets, by layer:

| What happens | Behaviour |
|---|---|
| The app lists `react-native-reanimated`, `-gesture-handler`, `-worklets` or `-svg` | Refused by the prebuild, `expo-svelte doctor` and the autolinking commands, with the one message: the library includes it at that version; remove it from the app's dependencies (package.json), reinstall, prebuild again; a library of the app that asks for it as a peer is served by the copy (`collisionMessage`). `expo-svelte init` prints the same for a project that lists one, and does not remove it. |
| A library of the app peer-depends on one (`@react-navigation/*`, `@gorhom/bottom-sheet`, Expo Router: gesture handler, Reanimated, Worklets) | **JavaScript**: Metro resolves the name, and every path below it, to the copy for every importer, so the library gets the copy's module, the same one the library itself uses (one `SharedValue` class, one set of worklet runtimes). **Types**: the library's declarations import the name; `vendor-types-ui.d.ts` answers to it (loaded with the main entry). **Native**: its autolinking entry (if the package manager installed an original, `auto-install-peers`) is replaced by the copy's under the same name, so the Gradle project `:react-native-reanimated`, the pod `RNReanimated` and the rest are the ones the library asked for. **Babel**: the Worklets plugin is the copy's whatever `node_modules` has. The package manager may warn about a peer that is not the app's (`pnpm peers check`); that is expected, and the copy is what runs, at its version (4.7.1 satisfies `react-native-reanimated >=3`, and not `^3`: such a library works as far as 4.x is compatible with it). |
| A package manager installs an original beside another library (pnpm did, for Expo Router's peers; with Expo SDK 58 it installs none, so the repository's `package.json` lists gesture handler, Reanimated and Worklets as development dependencies, at the versions of the copies: the tests that run the transformer or read their sources by name under Bun find them there; `apps/example` lists none) | Inert: Metro never reaches it, autolinking replaces it, and `babel-preset-expo`'s own lookup of `react-native-worklets/plugin` finds the copy's plugin, not the original's (`tests/compiler/worklets-plugin.test.ts` has an original whose plugin throws if it loads). The example and QA bundle tests check that no original is bundled. |

## The UI packages: gesture handler, Reanimated, Worklets, svg

Versions 3.3.0, 4.7.1, 0.13.0 and 15.16.0, as Expo SDK 58 pins them. Three have patches, which are `vendor-patches/<name>/*.patch` now, applied by `scripts/vendor.ts` (the three that pnpm used to apply, re-ported to these versions; `pnpm-workspace.yaml` and an app's `patchedDependencies` no longer name them, and `expo-svelte doctor` reads the copies instead, `PatchSpec.vendored`: the same shapes as before, in `vendor/`, one line each under "vendored packages"):

- gesture handler `0001`: iOS, the manager can be asked for the root gesture recognizer of a screen the library presents. `0002` (new with 3.x): `scripts/gesture_handler_utils.rb`, which its podspec runs to decide whether it links the Worklets pod (its native module reads the UI runtime through Worklets' stable API), looks for the Worklets copy beside it before asking Node for an installed one.
- Reanimated `0001`: Android, the engine's views are written natively and opacity/translate/scale skip React Native's prop path. `0002` (new): `scripts/validate-worklets-version.js`, which Reanimated's Gradle task and its podspec run, reads `package.json` of the Worklets copy beside it; by name, from `node_modules`, it found nothing. `0003` (new): `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` is on in `src/featureFlags/staticFlags.json` (Gradle and the podspec read that file, then the app's `package.json` `reanimated.staticFeatureFlags` over it), because the patched Android update is reached only through that flag: **an app sets nothing**, `expo-svelte init` no longer writes `reanimated` into its package.json, and an app's own value still wins (`ENABLE_SHARED_ELEMENT_TRANSITIONS: true` needs `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS: false` beside it, which Reanimated enforces). The Worklets flags (`worklets.staticFeatureFlags`) were never set and are not.
- Worklets `0001`: the UI runtime asks for a frame only while a callback waits.

**The Worklets Babel plugin.** `babel-preset-expo` adds `react-native-worklets/plugin` when `require.resolve` finds the package from the app's directory; no app has it, and one that does (pnpm installs an original for Expo Router's peers) has another version than the native code. The transformer makes that name resolve to `vendor/react-native-worklets/plugin/index.js` (`Module._resolveFilename`, installed when the transformer loads: `require.resolve` ends there on every Node the library supports, which a `module.registerHooks` resolve hook is not documented to reach), so the preset adds the copy's plugin, once, in the place it always puts it (an explicit `plugins` entry of the transformer would run before the preset's own plugins, and twice beside an original). The plugin's file is in the transformer's cache key. The wrapper is not installed under Bun (the repository's own tests run the transformer there, and a `require` of a relative file fails after it): a run there finds whatever `node_modules` has, the same version in this repository, and `tests/compiler/worklets-plugin.test.ts` runs the transformer in Node. A file of a vendored package is handled as a `node_modules` file by the transformer (TypeScript is left to Babel, as for an installed package), in the workspace and installed alike.

**Dependencies.** The JavaScript the copies import is found from where the library is, so the packages' own `dependencies` are the library's (same ranges): `@babel/plugin-transform-*` and `@babel/preset-typescript` (the Worklets plugin), `convert-source-map`, `semver` (Reanimated's and Worklets' build scripts), `react-native-is-edge-to-edge`, `hoist-non-react-statics`, `invariant`, `@egjs/hammerjs`, and svg's `css-select`, `css-tree` and `warn-once`. The Worklets plugin also requires `@babel/generator` and `@babel/traverse`, which its manifest does not list (`dependencies` of the library), and Metro's own `@babel/core` (an optional peer: the app has it). `tests/package/packaging.test.ts` reads each copy's manifest to keep this list complete.

**What is imported how.** The library's own source imports the main entries and types as `#vendor/<name>` (the `imports` map), and keeps the deep paths its JavaScript reaches (`react-native-reanimated/src/updateProps`, `react-native-svg/src/lib/extract/extractProps`, `react-native-gesture-handler/src/handlers/...`) by name: an `imports` target is an exact file, and Metro's alias resolves the names with file extensions. The tests' bundles do the same through esbuild's `alias` (`tests/support/paths.ts`: `vendoredAliases`), and stub by name (`#vendor/<name>` is the same stub).

**Left out of the copies**, see each `VENDOR.md`: source maps, `lib/commonjs` (svg; gesture handler 3 has none), `windows/` (svg), the Gradle wrapper (svg, Reanimated), gesture handler's `jest-utils` and `jestSetup.js`.

## Notes for the QA harness

The smoke app installs the production app's libraries as stand-ins (`apps/qa/qa/smoke-modules.json`, `package.json`). MMKV and Nitro are not on that list any more: their modules (`mmkv`, `nitro`) stay, still `shared`, with no `packages`; the smoke checks `require("react-native-mmkv")` and `require("react-native-nitro-modules")`, which Metro resolves to the copies. `libraryVendoredPackages` in `smoke-packages.cjs` names them (and the UI packages, which the smoke app never installed). quick-crypto and quick-base64 went the same way (modules `quick-crypto`, `quick-base64`, no `packages`), and the production app's `["react-native-quick-crypto", { sodiumEnabled: true }]` is the library plugin's `sodiumEnabled: true` in the smoke variant.

## Updating a copy

`vendor-updates/README.md` is the procedure an agent (or a person) follows to update a copy: pick the target by the package's policy, check the published tarball against the upstream source before it is copied, write the copy with the script, re-derive or drop the patches, update the library, prove it on both platforms, and report. `vendor-updates/<name>.md` is each package's strategy: what it is coupled to, its version policy, its patches, what the library relies on, what to look at in its source, what it downloads at build time, and what proves an update. A package added here gets its strategy file in the same change (`tests/package/vendor-updates.test.ts`).

## Adding a package

1. `node scripts/vendor.ts <name>@<version>` (with `--exclude` for what the app never needs: examples, docs, build outputs, tests, `prebuilds/`); commit `vendor/<name>/`.
2. Add it to `vendoredPackages` in `src/vendored.ts` (an optional library, in `src/optional-libraries.ts`, with `optional: { kind, plugin?, requires? }` and, for an Expo module, no `android` or `ios`): version, the Android `ReactPackage` import and instance (a test reads the copy's sources to keep them true), the iOS podspec file name. Add the entry's reference fixture under `tests/cli/fixtures/vendored-autolinking/` (capture Expo's `react-native-config` for the installed package first).
3. If the library imports it, an `imports` entry (`#vendor/<name>`) and the import; if its declarations import another vendored package, a `declare module` in `src/vendor-types.d.ts`.
4. Take it from `peerDependencies`, `peerDependenciesMeta`, `expo-svelte init`'s list, the doctor's `AUTOLINKED_PEERS`, and the `package.json` of `apps/*` and `examples/*`; `pnpm install`. Move its pnpm patch (`patches/<name>@<version>.patch`) into `vendor-patches/<name>/` so the copy carries it, keep its entry in `patchSpecs` with `vendored: true` (its shape check, which the doctor runs on the copy) and from `init`'s `patchedDependencies` and `pnpm-workspace.yaml`; its JavaScript `dependencies` become the library's.
5. `pnpm --dir packages/expo-svelte build`, and the checks in `AGENTS.md`.

## What the next batches must know

Measured on the installed packages (Expo SDK 58's `react-native-config` for each):

- **The entry has more fields than the pilot's two use, and the registry can say them** (`VendoredPackage.android`, tested against Expo's printed entries in `tests/cli/fixtures/vendored-autolinking/expo-sdk58-*.json`): `libraryName` is `codegenConfig.name`, else the `libraryName` of the `react { }` block of `android/build.gradle` (quick-crypto: `QuickCrypto`; Nitro has both and the codegen name wins); a view library lists its `componentDescriptors` (gesture handler: two, svg: 29); svg's codegen CMake file is `android/src/main/jni/CMakeLists.txt` (`cmakeListsPath`); hermes-intl is a pure C++ TurboModule (`cxxModule`: module name, CMake path, header name). Reanimated, worklets and gesture handler also have iOS `componentProvider`s in their codegen config, read from `package.json` by iOS codegen through `root`, which is why every copy keeps its `package.json`.
- **Crypto stack** (done: `react-native-quick-crypto` 1.1.3, `react-native-quick-base64` 2.2.2; hermes-intl with them): quick-crypto's Gradle project depends on `:react-native-nitro-modules`, its CMake on the prefab and its podspec on `NitroModules`; all three keep working against the copy because the entry keeps the name (the pod is the podspec's `s.name`). Its JavaScript `dependencies` (`@craftzdog/react-native-buffer`, `events`, `readable-stream`, `safe-buffer`, `string_decoder`, `util`) are pure JavaScript, so they are ordinary `dependencies` of the library, at the versions quick-crypto pins; the copy finds them in the directories above it (the package manager installs them beside the library). The Buffer package depends on `react-native-quick-base64`, so a package manager still installs the original beside the library: inert, replaced in the autolinking config and never reached by Metro. Its Expo plugin moved into the library's plugin as the `sodiumEnabled` option (Android: `sodiumEnabled=true` in `gradle.properties`; iOS: `ENV['SODIUM_ENABLED'] = '1'` in a marked block at the top of the Podfile; the podspec then downloads libsodium into the copy's `ios/libsodium-stable/`, which `.gitignore` and the package's `files` leave out). The plugin's other part, an iOS 16.4 deployment target for every pod, is not carried: the library's pod and ExpoModulesCore need 16.4 already. The copy leaves out the plugin (`app.plugin.js`, `src/expo-plugin`, `lib/typescript/expo-plugin`) and the built CommonJS and ES module copies of `src` (`lib/commonjs`, `lib/module`), which Metro's `react-native` field never reaches; `lib/typescript` stays. The library requires it as `#vendor/react-native-quick-crypto`, and `crypto` and `node:crypto` are still Metro aliases of the bare name, which reaches the same file. `deferredNitroPackages` names it (`packageImportPath` is kept: a test compares both lists).
