# react-native-nitro-modules

- **Current**: 0.35.10
- **Linked**: every app
- **Upstream**: https://github.com/mrousavy/nitro
- **Copy**: `vendor/react-native-nitro-modules/` (its `VENDOR.md` has the tarball's integrity, what was left out and the patches)

Follow `README.md` in this directory; this file is what is particular to this package.

## What the library uses it for

The runtime of the Nitro modules the library carries: react-native-mmkv (`localStorage`) and react-native-quick-crypto (`crypto`).

## Coupled with

react-native-mmkv and react-native-quick-crypto. Their native code is generated by Nitrogen for a Nitro version and calls the runtime's C++ API, so the three move together, to a runtime version both packages were generated for (each one's `nitrogen/generated` and its release notes say which).

## Version policy

Only with the group: the newest runtime that the newest mmkv and quick-crypto releases support. A runtime release alone is not taken.

## Local changes

- `vendor-patches/react-native-nitro-modules/0001-the-install-overload-of-react-native-0.87.patch` (iOS): React Native 0.87 and later call only `installJSIBindingsWithRuntime:callInvoker:`, and 0.35.10 has only the one-argument overload, so Nitro never installed (MMKV and quick-crypto failed at their first use). The patch adds the two-argument overload as Nitro 0.37 has it. Drop it with the update to a Nitro that has it (0.37 or later), which also needs MMKV and quick-crypto versions generated for that Nitro.

## What the library relies on

- `src/autolinking.ts`: the Android entry is wrapped in `NitroGate`, and the Nitro modules' native libraries load after the start (`deferNitroLibraries`, `DeferredNitroPackage`); it names `com.margelo.nitro.NitroModulesPackage`.
- The autolinking entry in `src/vendored.ts` (`NitroModulesPackage`, `NitroModules.podspec`).

## What to look at in its source

- The C++ headers under `cpp/` that generated code includes: a changed signature breaks mmkv and quick-crypto at compile time, which is the point of moving them together.
- How the Android package loads its library (`System.loadLibrary`): the start-up deferral depends on it.

## Native dependencies downloaded at build time

None of its own.

## Proof

- `tests/cli/vendored-autolinking.test.ts` and `tests/cli/library-linking.test.ts`.
- Android: a cold start of the example app logs the deferred load and `localStorage` and `crypto` work on the Web APIs screen (`?checks=<origin>`); iOS: the same screen.
