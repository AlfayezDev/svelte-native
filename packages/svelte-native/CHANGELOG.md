# Changelog

Notable changes to `@alfayez/svelte-native` (named `@rasheed/svelte-native` up to 0.4.0-rc.4), newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions are `0.x` while the package is private and its Svelte compiler is pinned to an unmerged pull request, so a minor version may break. Each line is what an app that uses the package gets.

## Unreleased

### Added

- The optional native view libraries are vendored and turned on in the config plugin's new `libraries` option, one by one: `expo-image` 57.0.5, `expo-blur` 57.0.3, `expo-linear-gradient` 57.0.2, `expo-conic-gradient` 0.2.1, `expo-video` 57.0.5, `react-native-video` 6.19.3, `lottie-react-native` 7.3.8, `rive-react-native` 9.7.1, `@react-native-community/datetimepicker` 9.1.0, `react-native-pdf` 7.0.3 (with `react-native-blob-util` 0.24.9, which it turns on), `react-native-webview` 13.16.1, `react-native-maps` 1.27.2, `react-native-view-shot` 5.1.0, `react-native-fast-shadow` 0.1.1 and `react-native-animateable-text` 0.19.3 (VENDORING.md, "Optional libraries"). A library is `true` or the options of its own config plugin (`"react-native-maps": { androidGoogleMapsApiKey }`), which the plugin runs from the copy. A listed library is linked on Android and iOS and bundled by Metro; an unlisted one is none of that: no native code in the build (on iOS not even compiled, so an app without react-native-maps has no CoreLocation reference for App Store Connect to ask a purpose string for), Metro resolves its name to a stub that says how to turn it on, and its components throw the same. React Native's libraries are `--link` arguments of `android-autolinking` and `ios-autolinking` (an original that autolinking finds of a library that is off is taken out), Expo's modules are search paths of Expo's own autolinker (`expoAutolinking.searchPaths` after a `--`, because Expo's command reads the paths after its `--exclude` options as names to exclude, and `use_expo_modules!(searchPaths:)`), and the Metro stubs and the manifest's `extra.svelteNative.libraries` come from the same option. `svelte-native doctor` lists the libraries that are on and refuses an app that lists one in its `package.json` (or its plugin in `plugins`).
- `createVideoPlayer` from `@alfayez/svelte-native/foreign`: `expo-video`'s own function, typed from the copy, for the `player` of `VideoView` (the package is not installed, so `expo-video/build/VideoPlayer` cannot be imported where a type checker looks).
- Push notifications, straight from the app's server to Firebase Cloud Messaging (Android) and the Apple Push Notification service (iOS) with the app's own credentials: no relay and no push service of Expo's (PUSH.md, and the guide's "Push notifications" page, which also sets up React Native Firebase and `expo-notifications` for apps that want those). Push is part of the library, with nothing to install: the config plugin's `capabilities.push` turns it on for the platforms it names (the Google services file, the notification icon, color and channel, the `aps-environment` entitlement and the `remote-notification` background mode), and only then does Firebase Messaging (26.0.2, Android) join the app's build; iOS goes to APNs without the Firebase SDK. An app with push off has none of Firebase and bundles none of push's JavaScript. The plugin refuses a server secret in the app (a service account key, a private key, a `.p8`), and refuses `expo-notifications` or `@react-native-firebase/messaging` beside it: an app has one push library.
- `push` from `@alfayez/svelte-native/push`: `permission` (reactive), `subscribe({ save })`, which asks for the permission, registers with the provider and calls `save` when the token is new or rotated, `unsubscribe()` and `on("message")`; and the `push` hooks of `src/hooks.mobile.ts`: `foreground` (how a message shows while the app is open), `background` (a data message, with no screen mounted: a process the system starts for one runs the hooks and shows its first screen only when the user opens the app, on iOS too) and `opened`. A tapped notification is a link: its `url` (a path of the app or a full link) opens through the router as any link does, from a cold start or with the app running, and `opened` returning `false` stops it.
- `createPush` from `@alfayez/svelte-native/push/server`, the sender for Node: `send(token, message)` to FCM's HTTP v1 API (an OAuth token from the service account key, cached) or to APNs over HTTP/2 (an ES256 token from the `.p8`, the sandbox or production host by the token's environment), with a result whose `reason` says what to do (`gone`: delete the token; `rate-limited` and `unavailable`: retry later; the others: a bug), and `close()`. Node's `crypto` and `http2` only. The queue, the retries, the tokens' storage and fan-out are the app's, and the guide says how.
- The command line for push: `svelte-native doctor` has a push section (the package and its version, a second push library, the Google services file and its package, the iOS entitlement and background mode after a prebuild); `svelte-native doctor --server` checks a server's `FCM_SERVICE_ACCOUNT` and `APNS_KEY`, `APNS_KEY_ID` and `APNS_TEAM_ID` and asks each provider once whether it accepts them; and `svelte-native push send` sends one message to one token with them. No line prints a key or a token.

### Changed

- The view libraries (`expo-image`, `expo-blur`, `expo-linear-gradient`, `expo-conic-gradient`, `expo-video`, `react-native-video`, `lottie-react-native`, `rive-react-native`, `@react-native-community/datetimepicker`, `react-native-pdf`, `react-native-blob-util`, `react-native-webview`, `react-native-maps`, `react-native-view-shot`, `react-native-fast-shadow`, `react-native-animateable-text`) are no longer optional peers. Remove them from the app's `package.json` (the prebuild and the doctor refuse an app that lists one) and list the ones it uses under `libraries` in the plugin's options; the options of their own plugins (`["react-native-maps", { androidGoogleMapsApiKey }]` in `plugins`) move there too. The pnpm patches of `lottie-react-native`, `react-native-maps`, `react-native-pdf` and `react-native-video` are in the copies now (`vendor-patches/`): remove their `patchedDependencies` entries and `patches/svelte-native/` files; `svelte-native init` no longer copies them. react-native-pdf's copy also finds react-native from the app's directory, since it is no longer beside it in `node_modules`.
- The library carries its third-party native dependencies itself, starting with `react-native-nitro-modules` 0.35.10 and `react-native-mmkv` 4.3.1 (VENDORING.md): their published source is copied into `vendor/` of the package, so an app's `package.json` lists the library and not them. Neither is a peer dependency any more, `svelte-native init` does not install them, and an app that still lists either is refused: the Expo plugin stops the prebuild, `svelte-native doctor` fails, and the autolinking commands refuse it at build time (the library links its copy, and the app's own would be linked beside it). Remove both from the app's dependencies, install again and prebuild again: the Android and iOS builds link the copies from the library's directory (`svelte-native android-autolinking` and the new `svelte-native ios-autolinking`, which the plugin writes into `settings.gradle` and the Podfile), and Metro resolves the names `react-native-mmkv` and `react-native-nitro-modules` to the same copies for every importer, react-native-quick-crypto included. The Gradle project and the pod keep their names, so quick-crypto links against the copy.
- `navigator.geolocation` runs on the library's own native code, `SvelteLocation` in svelte-core: Android's `LocationManager` (its fused provider on Android 12 and later, the GPS or the network otherwise; no Google library, so phones without Google services have it too) and iOS's CoreLocation, without CoreMotion. `capabilities.location` turns it on with nothing to install: the prebuild adds the location permissions (Android) and the usage text (iOS), and compiles the iOS code into the app only then (`svelteNative.location` in `ios/Podfile.properties.json`, a compile condition of the SvelteCore pod), so an app without location has no location API in its binary for App Store Connect to ask about. expo-location is no longer a dependency: an app may still install it for background location, which the capability does not do; its `background` and `motion` options are refused now, with a message that says so. Watch ids count from 1, a value the platform doesn't know is left out (read as `null`), and an Android watch whose provider is switched off reports `POSITION_UNAVAILABLE` and goes on. Turning the capability off and prebuilding again takes away the permissions, the flags and the compiled code; the iOS usage text stays.
- Push's iOS code is compiled into the app only when `capabilities.push` names iOS (`svelteNative.push`, the same way), so an app without push has no remote-notification API in its binary.
- The library's native code is one module, `native/svelte-core`: one Android Gradle project, `:svelte-core` (the engine's Kotlin and C++, the update store, the blur view, fetch and Blob, the clipboard; each keeps its Kotlin package), and one iOS pod, `SvelteCore` (a folder per area under `ios/`: fetch, clipboard, insets, navigation, updates, blur, the capture sweep, and the Objective-C++ screens). They were eight directories, four Gradle projects and seven pods. The Expo modules, their names and what JavaScript reads from them are unchanged. An app needs a new native build (`expo prebuild`, `pod install`); an app whose own Gradle files name `:svelte-engine`, `:svelte-updates` or `:svelte-blur` (a local module that compiles against the engine) names `:svelte-core` instead.
- Android: the native libraries of react-native-mmkv and react-native-quick-crypto load after the start instead of during it (7 ms of a cold start on a Galaxy A16: each package loaded its library on the main thread while the host was built, though nothing uses either library at the start). `settings.gradle` (the Expo plugin writes it) runs React Native's autolinking config command through `svelte-native android-autolinking`, which links a stand-in for each of the two packages and a gate around Nitro's: the first use of a Nitro module from JavaScript loads what is not loaded yet, and otherwise both load in the background a second after the first screen. An app that links one of these packages its own way (`react-native.config.js`), or builds with `EXPO_USE_COMMUNITY_AUTOLINKING=1`, keeps the old start. Needs a new native build (`expo prebuild`).

### Fixed

- `localStorage` and `sessionStorage`: a symbol property is an own property to reflection too (`Object.hasOwn`, `Object.getOwnPropertySymbols`, its descriptor), and a non-configurable one no longer makes `Object.keys(storage)` and `JSON.stringify(storage)` throw a proxy-invariant `TypeError` (#62). The members now come from a prototype of the storage's own, as a browser's come from `Storage.prototype`, and `Object.freeze(storage)` throws, as in a browser, instead of leaving an object whose keys cannot be listed.
- `navigator.geolocation`: `maximumAge` answers only with a position taken as the request asks, with or without `enableHighAccuracy`, as the web's acquisition steps compare it; a Balanced position no longer answers a high-accuracy request (#69). The system's last known position, taken no one knows how, answers only a request without `enableHighAccuracy`. A watch's positions are kept with its accuracy.

## 0.4.0-rc.8 - 2026-11-15

### Added

- The library's own `fetch`, on a native module of its own (`SvelteFetch`, in the new `native/svelte-core`: URLSession on iOS, React Native's OkHttp client on Android, so cookies and the app's interceptors are shared with React Native's networking). On the device the library installs `fetch`, `Headers`, `Request`, `Response`, `Blob`, `File`, `FileReader` and `FormData` in place of Expo's and React Native's, and `URL.createObjectURL` and `URL.revokeObjectURL`; each global is a getter that loads its implementation on the first read, so the start-up loads none of it, and an app binary without the native module keeps Expo's `fetch`. A response's bytes stay native until the code reads them: `arrayBuffer()` and `bytes()` hand JavaScript one native buffer (no base64, no copy through a JavaScript array), `blob()` keeps them native, and `body` is a `ReadableStream` that reads them in 64 KiB chunks as they arrive (the transfer pauses while more than 1 MiB is unread). A `Blob` is native bytes too: joining, `slice`, uploading one and a multipart body built from them copy nothing through JavaScript, and `URL.createObjectURL(blob)` gives a `file://` URL an image, a video or a WebView loads. `fetch` takes http(s), `data:`, `file://` and (Android) `content://` URLs; `redirect` is `follow` (up to 20), `error` or `manual` (the redirect response itself, as Node's `fetch` gives it); `credentials: "omit"` sends no cookie and keeps none; an `AbortSignal` stops the request or the body (and `AbortSignal.timeout` and `AbortSignal.any` exist); `text()` decodes UTF-8 as the standard says (a byte order mark dropped, an invalid sequence U+FFFD). `FormData` extends React Native's, so `XMLHttpRequest` and axios still send it, and `xhr.send(blob)` sends one of the library's Blobs (as a file the library writes and deletes when the request ends); a caller's `Content-Type: multipart/form-data` without the body's boundary gets it, as React Native's and Expo's `fetch` do. A `FormData` value may be React Native's `{ uri, name, type }`, read natively as it is sent; `blob:` URLs of React Native's own Blobs still fetch. On Android a `blob()` past 16 MiB is kept in a cache file, and a body too large for memory rejects instead of crashing the app. Request bodies are sent whole: a `ReadableStream` body is read to its end first, and an abort meanwhile rejects at once and cancels the stream with the signal's reason. `mode`, `cache`, `referrer` and `integrity` are accepted and ignored. On iOS a repeated response header arrives joined with ", " (Set-Cookie too), `statusText` is the standard phrase for the status, and a POST body that has no type (bytes, or a Blob without one) goes out as `application/octet-stream`, because URLSession would otherwise label it `application/x-www-form-urlencoded`.
- The showcase's "Web APIs" screen: a docs video downloaded as a body stream with a progress bar, its SHA-256 from `crypto.subtle`, a picture from `response.blob()` through an object URL, `crypto.randomUUID()`, and a visit count in `localStorage`. Opened with `?checks=<origin>`, it runs device checks of `fetch`, `Blob`, `crypto`, `localStorage` and `navigator` against the library's test server (`tests/fetch/server.ts`) and logs each as `[web-apis] …`.
- `crypto` and `localStorage` on the device, the web's own with nothing to import. `crypto` is `getRandomValues`, `randomUUID` and `subtle` (the Web Crypto API) from react-native-quick-crypto, native code on OpenSSL; a library that imports `crypto` or `node:crypto` gets react-native-quick-crypto itself, with Node's API (Metro resolves it). `localStorage` is the web's `Storage` (`getItem`, `setItem`, `removeItem`, `clear`, `key`, `length`, keys as properties) on an MMKV instance, so it is synchronous and survives a restart; `sessionStorage` is the same in memory for the app's process. Nothing loads until the name is first read. `@alfayez/svelte-native/mmkv` has react-native-mmkv's `createMMKV` and types, and `localStorageMMKV()`, the instance behind `localStorage`. On a binary without the native libraries (an over-the-air update onto an older build) `crypto` and `localStorage` read as `undefined`, with one warning. Guide: Native features, "Web APIs".
- The guide's "Web APIs" page (Native features): `fetch`, `Blob`, `File`, `FormData`, `crypto` and storage on the device; its crypto and storage sections moved there from "Platform APIs".
- `src/hooks.mobile.ts` (or `.js`), the native app's counterpart of SvelteKit's `hooks.client.ts`. Its top level runs right after the library's start-up and before the app's layout and routes (the modules the file imports run just before it), the place for a crash reporter's set-up or a background task's `TaskManager.defineTask`. `init` runs once when the app's JavaScript starts, in a launch without a screen too; the first screen waits for the promise it returns (the splash screen stays up), and a surface the host stops meanwhile never starts. `handleError` and `transport` are the remote functions' (SvelteKit's client hook, and the `transport` of the universal hooks, which the file can re-export from `./hooks`); `configureRemote({ transport, handleError })` still replaces them, and an app that uses no remote function loads nothing of SvelteKit for them. A failed `init` (a throw or a rejection) is a fatal error in a release build; in development it is the error screen, and the screen's Reload or the next edit of the file runs `init` again (an edit saved while `init` is still in flight runs once it has failed). A hot update of the file applies its new exports and remounts the screens without running `init` again; the development server writes the generated `.svelte-native/hooks.ts` again when the file is added or removed, and removing it drops its hooks. A hot update that runs `init` (the file added to a running app, or fixed) keeps the screens and their navigation until it has finished, then remounts. The generated entry imports `./hooks` after `@alfayez/svelte-native/app`, so a Metro that keeps the entry rewrites one without it. `bootSummary()` has a `hooks` phase (the file's evaluation) and, for an `init` that returns a promise, a `hooks init` one. Guide: Core concepts, "Hooks".
- File fields in remote forms: `fields.x.as("file")` and `as("file multiple")` give `value`, `multiple` and `onValueChange` for a picker of the app's, which passes `File`s (the library's own on the device: `new File([await (await fetch(uri)).blob()], name, { type })` keeps the bytes native from the file to the request). The submission is the binary form SvelteKit's server parses, with each file as SvelteKit lays it out, so the server action gets an ordinary `File`. A form without files is sent as before. On a build without the library's fetch module (an over-the-air update onto an older build), a submission with a file fails (`form.error` is SvelteKit's default 500), and the `TypeError` the app's `handleError` gets names the build it needs. `validate()` of a form with files sends them, as SvelteKit's form does. `as("image")` still throws. `NativeFileProps` is the props' type (`@alfayez/svelte-native/remote`). Guide: Core concepts, "Loading data", "Forms".
- A remote form submission that fails on the fields' issues (the preflight's or the server's) focuses the first input with an issue, in the order the inputs were made, among those on screen whose host can take focus. Validating alone never moves the focus.
- `navigator` on the device: `navigator.clipboard` and `ClipboardItem` (the async Clipboard API over the system clipboard, through a new native module of the library's, `SvelteClipboard` in `native/svelte-core`: `readText`, `writeText`, and `read` and `write` of `text/plain` and `text/html`; another type is refused with `NotAllowedError`; iOS shows its paste prompt on a read, and Android reads as empty while the app has no focused window), `navigator.share` and `navigator.canShare` (the Web Share API on the system share sheet: a title, a text and an absolute URL, no files; a dismissed sheet is an `AbortError` on iOS, and Android does not report one), `navigator.vibrate` (a duration or a pattern, `0` or `[]` stops, a call replaces the pattern playing; iOS starts its one fixed vibration at each of the pattern's vibrations) and `navigator.language` and `navigator.languages` (a BCP 47 tag: Android's locale at start, Java's form `zh_CN_#Hans` turned into `zh-Hans-CN`; on iOS, where React Native reports none, the runtime's default locale). Each loads what it is made of on first use; the clipboard module is registered lazily (the expo-modules-core patch, so run `svelte-native init` again to update the app's copy) and, on a build without it, `navigator.clipboard` reads as `undefined` with one warning. The showcase's Web APIs screen copies a UUID and shares a link, and its device checks are 33 (a clipboard round trip, an HTML item, and the language, `canShare` and `vibrate`). Guide: Native features, "Web APIs", "navigator".
- Capabilities: web APIs that need a permission of the system are off until the app says why it uses them, in the config plugin's new `capabilities` option. The first is `location`: with expo-location installed, `capabilities: { location: "Shows the stores near you." }` gives expo-location's plugin that text (iOS's `NSLocationWhenInUseUsageDescription`), or `{ whenInUse, background }` for its background APIs too. The prebuild stops on a capability without its library, on expo-location installed without the capability (so Expo's generic "Allow $(PRODUCT_NAME) to access your location" never ships), on the capability while expo-location is left out of autolinking (the plugin's `autolinkingExclude` or `expo.autolinking.exclude`), and on the capability together with expo-location's own plugin entry; an app that lists only that entry, or leaves expo-location out of autolinking, needs no capability. Without `background` the Always texts and the background mode are left out; `motion` gives the motion text iOS needs with expo-location (its own otherwise, which `navigator.geolocation` never shows). `navigator.geolocation` is then the W3C Geolocation API over expo-location's native module: `getCurrentPosition`, `watchPosition` and `clearWatch` with `enableHighAccuracy` (the GPS; Balanced without it), `timeout` (counted from the permission; for a watch from when it runs, one error per silence) and `maximumAge` (the app's last position or the system's last known one, which `getCurrentPosition` waits for at most 100 ms and a watch looks up alongside its own, using it when it comes before the watch's first position; a lookup that never answers holds up neither a `timeout: 0` answer nor a current position nor a watch, and a timeout that expires during it starts no native request), every position of a watch (no distance filter, where Android's default skips moves under 50 to 100 m), callbacks always later and guarded (a throw is reported as uncaught), iOS's errors of a running watch, and `GeolocationPositionError` codes (`PERMISSION_DENIED`, `POSITION_UNAVAILABLE`, `TIMEOUT`); what the platform does not know (iOS's -1, Android's altitude of accuracy 0) reads as `null`, and the heading of a device that does not move as `NaN`. `navigator.permissions.query({ name: "geolocation" })` answers `granted`, `prompt` or `denied`, and its `PermissionStatus` follows the user's answer and the app's return from the settings (`change` events); other names are refused with a `TypeError`. `GeolocationPositionError`, `GeolocationPosition`, `GeolocationCoordinates` and `PermissionStatus` are globals. Nothing loads until `navigator.geolocation` or `navigator.permissions` is read; in a build without expo-location `navigator.geolocation` reads as `undefined`, with one warning that says how to turn it on, and the permission reads `denied`. expo-location (`~57.0.21`) is an optional peer. Guide: Native features, "Web APIs", "Geolocation".

### Changed

- react-native-quick-crypto 1.1.3, react-native-mmkv 4.3.1, react-native-nitro-modules 0.35.10 and react-native-quick-base64 2.2.2 are required peers: `svelte-native init` installs them and `svelte-native doctor` fails without them. They are native code, so an app needs a new build. A clean Android release build of the showcase (x86_64 and arm64-v8a) took about 105 s longer with them (react-native-quick-crypto's C++ the most of it), its APK grew about 12 MB per ABI (OpenSSL and quick-crypto's library), and the JavaScript bundle about 940 KB (the four libraries' JavaScript, of which nothing runs before `crypto` or `localStorage` is first read).
- Remote functions send their requests through the global `fetch` (the library's own, which streams a response body on both platforms; Expo's on a binary without the native module), not `expo/fetch`.
- On Android the `SvelteFetch` module is registered lazily and prewarmed off the JavaScript thread (the expo-modules-core patch), in the place of Expo's fetch module, which the app no longer loads.

### Fixed

- A `Text` (or `<p>`, `<span>` and the other text tags) with `numberOfLines` and no `ellipsizeMode` no longer draws past its lines on Android. React Native's Text sends `ellipsizeMode: "tail"` when none is given, and the library's did not: Fabric measured the paragraph with its own default, `clip`, and Android's text view drew it with `END`, so a text too long for its lines was laid out at its line count and painted on more, over what came below it. The library now sends `"tail"` too, as React Native does; an explicit `ellipsizeMode` stands.
- A navigation to the screen the user is on with another query or hash that names a `presentation` (a sheet or a modal of the same page) opens that presentation. Since 0.4.0-rc.6 it changed the shown screen's URL in place, as a navigation without one does.
- A `<Screen>` that replaces another inside the same page (an `{#if}` that switches between two of them) keeps its header and toolbar options. The old one's cleanup, which ran after the new one had registered, erased them.
- `KeyboardAvoidingView` with `behavior="height"` no longer computes a negative height when the keyboard covers more than the view.
- `matchMedia` and `MediaQuery` for the system settings (`prefers-reduced-motion`, `prefers-contrast`, `inverted-colors`, `prefers-reduced-transparency`): the system's answer to an earlier question no longer overwrites a newer change, a question that never settled no longer keeps a new listener from asking again, and a change that was already queued when the last listener went no longer reaches the next reader.
- `aria-*` attributes written as HTML literals reach the native side with their types: `aria-hidden="true"`, `aria-checked="false"` and the other states are booleans (they were the strings `"true"` and `"false"`, so `aria-hidden="true"` hid nothing), `aria-valuenow="3"` and the other values are numbers (`aria-valuetext` stays text), and `aria-labelledby` takes HTML's space-separated ids as well as commas. A `null` `aria-label`, `aria-live` or `aria-hidden` leaves the matching `accessibility*` prop as it was.
- A prepared navigation (`router.prepare`) of a router that has been disposed does nothing: `prepare` returns one whose `ready` is `false`, and `commit()` of one prepared before is a no-op.
- `reset()` of a remote form while its preflight or a validation is still running: their issues no longer come back after the reset, and a submission whose preflight was running when the form was reset is not sent.
- Headless tasks on Android, and with them background tasks through Expo's task service (expo-task-manager, expo-background-task): the task ran, and then the launch reported a fatal JavaScript error, `property 'startHeadlessTask' is undefined`. Android's `HeadlessJsTaskContext` calls `AppRegistry.startHeadlessTask`, and the library's `AppRegistry` (the one native code calls) had no headless tasks. It now has React Native's API: `registerHeadlessTask`, `registerCancellableHeadlessTask`, `startHeadlessTask` and `cancelHeadlessTask`, as React Native's, and more forgiving in what it does not define: a task that fails with an error other than `HeadlessJsTaskError` is finished at once instead of at the native timeout, a task provider that throws or a task that returns no promise is a failed task rather than an error thrown into native code, and a retry the native side refuses finishes the task. Metro resolves `react-native`'s `AppRegistry` (and `AppRegistryImpl`) to it, so a library that imports `AppRegistry` from `react-native` registers with the registry native code calls, and React Native's own, which imports React's `renderApplication`, no longer enters the bundle or takes `RN$AppRegistry` over (expo-task-manager imports it, and so does Sentry's SDK, which patches `AppRegistry.runApplication`: it now patches the registry native code calls). Its `registerConfig`, `registerSection`, `getRegistry`, `getSections` and `getSectionKeys` are not provided (nothing installed calls them).
- Android: an app reopened after it was left with Back (its Activity finished, the process kept) or opened by a link after that showed its screens blank under their headers: the insets the engine reported for the new window were measured before the window was laid out (the right inset was the whole width, the bottom one more than the height), and every `SafeAreaView` padded its content to nothing. Seen on rc.5 to rc.7 on an Android 15 emulator, every time. The engine no longer measures against a window that is not laid out (until then it takes the overlay to fill the window, so the first read of a cold start still has the system bars), and reports what changed after each layout of the window.

## 0.4.0-rc.7 - 2026-11-13

### Added

- Media queries work on the device. React Native has no `window.matchMedia`; the library now installs one when the app starts (a function that loads its implementation on the first call, so the start-up reads nothing from the system), so `MediaQuery` from `svelte/reactivity` and shared web code that calls `matchMedia` no longer throw `window.matchMedia is not a function`. `new MediaQuery('(min-width: 600px)').current` is reactive in a template, `$derived` or `$effect`; `window.matchMedia(query)` returns a `MediaQueryList` with `matches`, `media` (as a browser writes it), `onchange`, `addEventListener('change', listener, { once, signal })` (an abort removes the listener) and `removeEventListener`, the older `addListener` and `removeListener`, and `dispatchEvent`; a `change` event has `matches` and `media` and comes only when the answer flips, and a list listens to the system only while it has a listener. Understood: comma lists, `not`, `only`, `and`, `or`, parentheses, the media types (`all` and `screen` match, `print` and the rest do not), and the features `width` and `height` (`min-`, `max-`, the range syntax `(width >= 600px)` and `(400px <= width < 700px)`; `px`, `em` and `rem` as 16px, other absolute units, `vw`, `vh`, `vmin` and `vmax` of the window, a unitless `0`, negative lengths), `device-width`, `device-height` and `device-aspect-ratio` (the screen's), `orientation`, `aspect-ratio`, `resolution` and `-webkit-device-pixel-ratio` (the window's pixel ratio), `prefers-color-scheme` (the system's mode), `prefers-reduced-motion` (Reduce Motion), `prefers-contrast` (`more` with iOS's Increase Contrast or Android's high contrast text), `prefers-reduced-transparency` (iOS's Reduce Transparency), `inverted-colors` (the system's color inversion), `forced-colors` (`none`), `update` (`fast`), `scripting` (`enabled`), `color-gamut` (`srgb`), `hover` and `any-hover` (`none`), `pointer` and `any-pointer` (`coarse`), `display-mode` (`standalone`) and `color`. A feature the device does not have and a value it does not take are unknown, as in Media Queries 4: false alone, and `not` leaves them unknown, but `(foo: bar) or (min-width: 600px)` is what the width says and `and` with a false part is false. A query that does not parse is `not all` (false; the rest of a comma-separated list still decides), and `media` says `not all` for a query that can never be true; nothing throws. Guide: Core concepts, "SvelteKit modules", "Media queries".

They are what Metro and the Svelte preprocessor run in Node when a file is built; the JavaScript of an app does not hold them (`apps/example/test/bundle.test.ts` checks that no module of the lowering or the converter is in the bundle). The list of style keys that the development warning of `style:` checks names against is a module of its own, loaded only when `__DEV__` is true, so a release bundle leaves it out.
- **Breaking:** expo-blur's component is now `ExpoBlurView` (the name `BlurView` is the library's own blur above); its props and `BlurTargetView` are unchanged. Rename the import and the tag where you use expo-blur's.
- On Android a message of the main looper applies every mounting transaction that is queued, and the ones queued while it applies (within 50 ms of work), where it applied one and left the looper free for a frame between two, as React Native's mount item dispatcher does; and the host asks the engine (`holdMounts`, `releaseMounts`) to apply the commits of an `animate:` or a transition that measures together. Before, a frame could be drawn between the commit of a flip's new order and the commit of its items' first frames: nearly every reorder showed the new order untransformed for a frame or two on a page with plain buttons. The first reorder after the app starts can still do it. A start-up's or an animation's commits that arrive faster than they apply are drawn a frame apart after 50 ms.
- The guide in `docs/` is reorganised in the shape of SvelteKit's, in sections: getting started, core concepts, a page for every component (what it is, an example, its props), native features, building and releasing, an appendix, and a reference for the command line, the configuration and every module. It is published at <https://svelte-native.alfayez.dev>. `svelte-native doctor` names the new path of "Creating a project".

### Fixed

- Android: a list that mounts rows while it scrolls (`List`, a windowed list) drops no more frames than before transitions. Since transitions the engine applied every commit that was waiting in one message of the main thread, so two commits that did not belong together were drawn in one frame; it applies one per message again, and only the commits the host holds together for an `animate:` or a transition (the layout read, then the first frames) are applied at once. On a Samsung A16 the lab's windowed list read 17 late frame intervals in twenty runs with the drain and 3 without it.

- A row of host tags (`<native-view nativeProps={{ style }}>`) costs less JavaScript to mount again: a `nativeProps` with no `ref` in it no longer goes through the wait for a screen that refs need, and an element that is not an HTML view builds its children without gathering lines. HTML elements had made 300 such rows 15 % slower to mount (130 ms to 148 ms of Svelte flush on a Samsung A16); on the PC's interpreter the same mount measures 9.0 ms before HTML elements, 10.4 ms with them, and 9.5 ms now.

- A single-line HTML `input` sends no line height, its own (`leading-*`) or inherited, so its text stays centred as on the web. On iOS a line height drew the text 2 pt low, and a text field view reused for another input kept it.

- Android: a `Text` nested in a `Text` with its own `onPress` (the inline link, `<Text>See <Text onPress={...}>this link</Text> here</Text>`) never got its presses: the engine sent every touch to the whole paragraph, so only an `onPress` on the outer `Text` worked. The touch now goes to the nested `Text` under the finger, as in React Native (`reactTagForTouch`): its `onPress`, `onPressIn`, `onPressOut`, `onLongPress` and `onPressChange` run, and the paragraph's does not, unless the nested `Text` has no handler; a press that moves far off the sentence is cancelled. A nested `Text` with `role="link"` is a link to accessibility services (a clickable span over its words, which a service lists and activates; the activation presses it). A touch on the `…` of a `numberOfLines` text is the paragraph's, not a hidden link's.
- Android: a `Text`, an `Image` or an `ActivityIndicator` with a press handler ran it twice per tap (the touch's press, then a second one from Android's click when the finger lifted). It runs once.
- A press whose node is unmounted while the finger is down no longer runs the node's handlers when the finger lifts, and a press whose end never arrives (native drops the touches of a deleted node) no longer leaves the next touch without a responder.

- A `Text`, `View` or `Pressable` whose `onPress` (or another press handler) is `undefined` (`onPress={enabled ? go : undefined}`) no longer keeps the press from the nearest ancestor that has a handler: Svelte compiled it to an event listener that stayed on the element and did nothing, and the host took the element for a pressable. The lowering now passes a press handler that is not a function written in place as the attribute `nativeOnPress` (and `nativeOnPressIn`, ...), which is the prop only while it is a function. An HTML element does the same for an `onclick` that may be `undefined` (a `div`, a `span`, a `p`; a button and a link press by themselves, so they are always pressable). A hand-written `native-*` tag keeps the old behaviour unless it uses these attributes.

The first three are changes in the native engine, so the native host has to be rebuilt.
- An app that installs the library from a tarball or git bundles again: Babel, which compiles the library's sources under `node_modules`, rejected the `declare` fields of `InlineStyle`; the five properties are typed by an interface merged with the class, and a test compiles every source file with `babel-preset-expo` as an app's Metro does.
- The guide's starter passes the doctor again: pnpm 12 does not apply a patch to the Svelte that `pkg.pr.new` serves, so the doctor failed with "svelte@5.56.7 is not applied". The Metro transformer no longer needs the patch: it removes the compiler's two refusals of the transition directives as it loads the compiler (`module.registerHooks`, Node 22.15 or newer). The package ships no patch of Svelte, `init` declares none and the doctor asks for none.
- `onintrostart`, `onintroend`, `onoutrostart` and `onoutroend` on an HTML element are no longer warned about ("never runs on a device"): Svelte's transitions send them and the handlers run.

Which build measured each suite, and why a result is carried from an earlier build, is in [PLAN.md](PLAN.md), "Final build gates". The package is private and has not been published. The entries that were under "Unreleased" since the first cut of this version on 1 November (`48d746e54`) are folded in, and so are those since the record of 4 November (`68ae53455`): SvelteKit remote functions, the launch link read before the router mounts, Android event patches for four view libraries, and the Android header and sheet fix for a screen's first layout.

### Added

- `openLaunchURL(router, accept?)` opens the link the app was launched with into the root router before its `<Router>` mounts and resolves with the link. A shell that chooses what to render by the launch link (the platform app's lab starts without its session) awaits it, so the navigator starts on the link's screen and the router's first screen is never rendered; the `<Router>` mounted afterwards does not read the link again, and the platform is asked once. `accept` refuses a link for the moment (it is left for the `<Router>`).
- SvelteKit remote functions. A `*.remote.ts` module is imported in native Svelte code as in the browser: Metro replaces it with the client stubs SvelteKit's Vite plugin would generate (same ids), and `query`, `query.batch`, `query.live`, `command`, `form` and `prerender` run on SvelteKit's own client files against the SvelteKit server named in the app config (`extra.svelteNative.remote`, written by the new `remote` option of the Expo plugin, or `configureRemote({ origin })`). Cookies are the platform's, requests carry the `Origin` SvelteKit's CSRF check wants, `query.live` streams through Expo's `fetch`, a `redirect()` goes through the router, and a build with no host throws at the first call. `form` is a native port: `fields.x.as(type)` returns the props of a `TextInput` or `Switch`, `submit()` is the submit button, a submission carries what the inputs show (defaults included) and a failed one is handled, not thrown (`form.error`). Numbers are read strictly, Arabic digits included, and `"1,000"` (a thousand or 1.000, depending on the reader) is not a number. A field none of whose inputs is on screen any more (a virtualized row, a closed modal) still posts what was typed or set. A submission always ends: `pending` goes back to 0 even when `handleError` or the data read throws. Peer dependencies: `@sveltejs/kit` 3.0.0-next.27 exactly, and `expo-constants`. New entries `@rasheed/svelte-native/remote`, `/remote/runtime` and `/remote/globals`; a new dependency, `@babel/parser`. Hermes 0.17 has no `FinalizationRegistry`, which SvelteKit's query cache needs: the package supplies one, and a query object made in a component is released when the component is destroyed (its live stream closes, its cache entry is dropped) and made again if it is used afterwards. Nothing is installed on `globalThis`. See README, "Remote functions".
- A development lab page, `/__dev/remote`, with the lab's own checks, a form and a live clock (the form and the clock appear once the app has a host; the page calls no remote function before that); QA and smoke builds only.
- Android: a screen reader now gets `accessibilityState` (selected, disabled, checked including mixed, busy, expanded), `accessibilityValue` (a slider's range and text), `accessibilityHint`, `accessibilityActions` with `onAccessibilityAction` (`{ nativeEvent: { actionName } }`), `accessibilityLiveRegion`, `importantForAccessibility` and `role` from the engine's views, the way React Native's Android views publish them (same TalkBack announcements, same node info, React Native's own role strings in the device's language). The engine dropped all of them before.
- `aria-*` props (`aria-label`, `aria-checked`, `aria-selected`, `aria-disabled`, `aria-expanded`, `aria-busy`, `aria-hidden`, `aria-live`, `aria-labelledby`, `aria-valuemin|max|now|text`) work on both platforms: React Native resolves them in `View.js`, which a Svelte host has none of, so they were ignored on iOS and on the Android engine alike.
- Gestures: `@rasheed/svelte-native/gestures` runs react-native-gesture-handler 2.32 on Svelte views (`gesture={...}` on any primitive, `<GestureDetector>`, `use:gesture`), with worklet callbacks on the UI thread, relations across components and development-time checks of what a worklet captures.
- Native-view wrappers in `@rasheed/svelte-native/foreign` for twelve libraries (expo-image, expo-blur, expo-linear-gradient, react-native-video, @react-native-community/datetimepicker, lottie-react-native, react-native-pdf, react-native-view-shot, rive-react-native, expo-conic-gradient, react-native-fast-shadow, react-native-animateable-text), next to `WebView`, `MapView`/`Marker`, `VideoView` and the generic `ForeignView`; all are optional peer dependencies.
- `@rasheed/svelte-native/svg`: react-native-svg 15.15.4 as 36 Svelte components (every element and filter, `SvgXml`, `SvgUri`) with the library's own prop extraction, refs with `getBBox`/`getTotalLength`/`toDataURL`, and `animatedProps`.
- `animatedProps` next to `animatedStyle` on any element, for animated props that are not style.
- `@rasheed/svelte-native/native-modules`: `turboModule(name)` and `nativeModule(name)` reach a native module without React; a smoke app (`APP_VARIANT=smoke`, `io.rasheed.svelteqa.smoke`) loads 36 native modules of the production app and `native-qa smoke` fails when one stops loading.
- File-based navigators: a `+layout.mobile.svelte` with `export const navigator = "stack" | "tabs"` makes its directory a stack or a tab bar, `<Stack>` and `<Tabs>` render it, and `goto`, `back`, `reset` and deep links resolve over the whole tree.
- Native screens through `<Screen>`: header (title, subtitle, back, left/center/right slots, search, large-title collapse, translucent), sheets with detents and drag, form sheets, tab bars with icons and badges, per-screen system bar colors, `onAppear`/`onDisappear`; `useHeader()` and `useToolbar()` report the bars' heights.
- A native bottom toolbar (`<Screen toolbar={...}>`): `UIToolbar` on iOS, a Material bar on Android, with badges, spacers, a center snippet and a translucent mode.
- Navigation state survives an Android Activity recreation (font scale, locale) and a process kill, and the launch link is the stack's base. On iOS it survives a process the system ended while the app was in the background (the `SvelteNavigation` module and an `AppDelegate.swift` patch from the Expo plugin), not one the user swiped away.
- A screen popped by JavaScript stays mounted until the stack reports `topExited`, on both platforms, so the transition finishes before the screen is destroyed.
- Expo Updates compatible with `eas update`: `@rasheed/svelte-native/updates` (`checkForUpdateAsync`, `fetchUpdateAsync`, `reloadAsync`) with a native store and launcher; a launch is confirmed only after a healthy window (idle, 3 s, no fatal), a fatal rolls the update back at the next start, and one unconfirmed launch does not blacklist a good update (on iOS a failing update needs two unconfirmed launches).
- Virtualized `List`: fixed or measured row heights, `horizontal`, `initialScrollIndex`, `header`/`footer`/`empty`, `onEndReached`, `onViewableItemsChanged`, row wrapper recycling.
- `KeyboardAvoidingView`, an insets store (`insets`, safe area and keyboard) on both platforms, and `Modal` presented on an engine overlay layer on Android.
- Config plugin options `autolinkingExclude` (leave packages and local Expo modules out of both autolinkers) and `androidOnDemandViewManagers` (keep a package's view managers off the app start).
- New entries `core`, `init`, `fabric`, `foreign`, `svg`, `gestures`, `updates`, `native-modules`, `animation`, `routes`, `lower`, `expo` and `elements`; `bootSummary()` exposes the boot phases.

### Changed

- A navigation before the root `<Router>` has mounted drops the screens it replaces at once. They were kept until the native stack reported their exit, which a screen that was never shown cannot do, so the router's first screen stayed rendered (and the timeout warning fired) after the launch link replaced it. The same goes for a root `<Router>` that unmounts (a shell waiting for its session): the screens still leaving are dropped with it.
- The read of the launch link is bounded: the platform gets three seconds, after which the app starts as if it had no link, and an answer that comes later is opened if nothing has navigated since (never after, never twice). A read that failed is no longer remembered for ever (the next `openLaunchURL` asks again, unless the app has gone on meanwhile, when the link is stale and is dropped), and the `<Router>` reports a failed read instead of leaving an unhandled rejection.
- The Expo plugin's options take `remote: { origin, base?, appDir? }`; an `http:` origin also lets the Android and iOS builds use plain HTTP to it.
- The root router tells the remote runtime which screen is on top and how to follow a server redirect (`connectHost`).
- The windowed `List` mounts its overscan four frames after the rows that show, not one (the one-frame flush went ahead of the layout event of the visible rows on a phone with slow cores), and the wrapper of a row of a list whose rows have one size is described once per row. Once the animation layer is loaded only the nodes that can need it go through it, and a node the host has not built no longer reports its changes.
- Android boot (Samsung A16, 2 November 2026; SPEC "Boot on the phone, round 2"): the Expo plugin now generates `override fun attachBaseContext(base: Context)` into `MainApplication.kt`, which calls `BootBoost.preloadLibraries(base)` (SoLoader and the start's native libraries load on a thread of its own while the Application is set up). **A `MainApplication.kt` that already overrides `attachBaseContext` clashes with it**: `prebuild` now stops with a message unless the existing override calls `expo.modules.svelteengine.BootBoost.preloadLibraries(base)` itself (then the plugin adds nothing). `MainActivity.onCreate` gets two generated calls (`BootBoost.activityCreated()`, `ViewWarmup.begin(this)`).
- Android boot: `expo-blur`, `expo-conic-gradient`, `expo-image` and `expo-linear-gradient` are built when their first component is mounted (like `expo-video`), not with the host, so `requireNativeModule` on them builds the module on first use. The boot pin no longer asks the system whether the process is on screen: it is made in the app's main process (not in another process of the app), kept when the Activity says it exists, and dropped when no Activity came.
- A text under a live region tells it when its text changes (an engine text is a plain view); a role description is React Native's string ("Link", "Tab") instead of the engine's own lowercase one; a `button`, `imagebutton` or `togglebutton` role makes the node clickable.
- The Android host is the package's own engine (`native/svelte-engine`): Fabric's mounting is replaced by typed Kotlin views, so mounting 600 views costs about a fifth of React Native's on the Samsung A16 and the Reanimated frame path no longer builds Java maps. iOS keeps React Native's mounting.
- There is no React in the render path: the React host, `react-native-screens`, `react-native-safe-area-context` and the dev client are gone, and Metro maps `InitializeCore` to the package's own `init.ts`.
- `<View>`, `<Text>`, `<ScrollView>`, `<Image>`, `<ActivityIndicator>` and `<Pressable>` are lowered to host tags at compile time, so a row costs host nodes only.
- Boot on Android: route modules load on first use, the Expo module registry and the Reanimated and gesture hosts load lazily, view configs are static, start-up threads stay on the big cores until the first mount, and a baseline profile ships for the engine and updates modules.
- Frames on Android: pooled views, a text layout cache, views with partial alpha are no longer promoted to hardware layers, screens hidden with alpha instead of `INVISIBLE`, layout events delivered in the batch that mounted them, and a fixed native heap leak in animated views.
- Route tables are generated per bundle variant (`.svelte-native/routes.<variant>.ts`); Metro writes the table for the variant it bundles and refuses a bundle whose table belongs to another.
- The windowed `List` mounts the rows that fit first and its overscan a frame later, and fixed-height rows skip the layout report.
- `ref` callbacks follow React's contract on every element and component: the handle when the element is built, `null` when it is destroyed, and the old callback gets `null` before a replacement gets the handle.
- On iOS `Modal` mounts its native host only while it is shown, as React Native's does.
- A function-valued `ref` or attribute survives a spread on a lowered primitive.
- A popped iOS screen stays mounted until the stack reports its exit.
- Peer dependencies: `react-native-gesture-handler`, `react-native-reanimated` and `react-native-worklets` are required (a native rebuild); the libraries behind the wrappers are optional.
- The product (`APP_VARIANT=production`) contains no development lab: route discovery skips `__dev` directories and `export const lab = true` pages, Metro stubs the lab's modules, and a bundle whose table names the lab is refused.

### Fixed

- Android: events of `react-native-pdf`, `react-native-video`, `lottie-react-native` and `react-native-maps` that are not streams are no longer replaced in React Native's event queue. React Native's `Event.canCoalesce()` is `true` unless an event class says otherwise, and the queue then keeps only the last of two unread events of one name from one view while JavaScript is busy. `react-native-pdf` sends every message as one `topChange` event, so a document's `onLoadComplete` was overwritten by the `onPageChanged` the view posts 10 ms later: 28 of 182 `Pdf` row mounts on the emulator and 10 of 130 on the Samsung A16 raised no load event, and 0 of 39 do with the patch. The same is closed for the events of video (all but progress and bandwidth), Lottie (finish, loaded, failure) and maps (21 of the 26 event classes; the five streams keep coalescing). The patches are pnpm patches of this repository (`patches/react-native-pdf@7.0.3.patch`, `react-native-video@6.19.3.patch`, `react-native-maps@1.27.2.patch` and the existing `lottie-react-native@7.3.8.patch`, listed in `patchedDependencies`), so an app that is not this repository must carry them. The price is that JavaScript is told of every message of such an event, every `scaleChanged` of a PDF pinch included. `rive-react-native` needs no patch: its events leave through React Native's interop emitter, which never coalesces, and a test reads React Native's sources and fails when that changes. iOS cannot lose these events (it sends them with `dispatchEvent`, never through the queue's unique path).
- Android: the first screen of the app's stack no longer keeps what its header and sheet worked out while the screen was laid out detached. With a launch link opened before the `<Router>` mounts (`openLaunchURL`), an inline header title sat 1 px high, and a sheet link under a nested stack (`/__dev/tree/inbox/compose`) rested at its top detent over the whole pane, a root screen to look at, on some launches (a warm link, pushed onto a stack that has its size, was fine); any first screen of a cold start could hit it, not only a launch link's. A header lays out again when it attaches with a window inset it did not use (pushed screens too: every title sits at the status bar's inset, not a pixel above it), a sheet rests where its layout says whenever that moves, and a header inside a sheet keeps the padding its screen gave it. A layout does not move a sheet that is being dragged, is settling, leaving or animating, is in a transition of the stack, or is moved by a gesture of the stack (a predictive back swipe).
- iOS: the events of `react-native-video` and `rive-react-native` (load, ready, progress, play, pause, stop, error) reach JavaScript. They are legacy view managers, and React Native's interop gives such a view an event block only for an event prop that is `true`; the host's static view configs now list their events as attributes on iOS (`Kind.legacy`). Before, none of them was delivered there.
- iOS: `lottie-react-native` 7.3.8 is patched (`patches/lottie-react-native@7.3.8.patch`, through `patchedDependencies`): `onAnimationLoaded` and the failure event, which the view raised before it had an event emitter, are kept and sent when the emitter arrives, and a recycled view that gets the source it already shows says that its animation is loaded.
- iOS: the `tmpfile` captures of `react-native-view-shot` that a process left when it ended without exiting are deleted when the next process starts (the `svelte-capture-ios` module); React Native deleted them only when the next process captured something. The wrapper passes the library's own answer on: a plain path on iOS, sizes in points.
- `List`: `scrollToIndex` and `scrollToOffset` called before the scroll view is bound and has its first layout (a page that scrolls its list in the effect that runs as the list mounts) sent the command to no view and the list stayed at the top. The last such request is kept and sent when both are there. The two commands no longer subscribe the effect that calls them to the list's window, row sizes and header.
- iOS: a hidden `Modal` swallowed every touch on pushed screens.
- A scroll view's content container follows `contentContainerStyle` and `horizontal` after the first render.
