# Changelog

Notable changes to `@rasheed/svelte-native`, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions are `0.x` while the package is private and its Svelte compiler is pinned to an unmerged pull request, so a minor version may break. Each line is what an app that uses the package gets.

## Unreleased

## 0.3.0 - 2026-11-10

The first release of the standalone repository (`AlfayezDev/svelte-native`, extracted from the Rasheed monorepo on 9 November 2026 with its full history; D15). Apps install it from the tag: `pnpm add "git+ssh://git@github.com/AlfayezDev/svelte-native.git#v0.3.0&path:packages/svelte-native"`. Proven on `abb4263` on the three devices (PLAN.md, "Standalone release 0.3.0"): the OVH emulator and the Samsung A16 pass every gate on the Android build of that commit, outside the documented exceptions (D1, D9, D11 and the first touch of a process); the iPhone SE 3 passes on the iOS build of `4f36d4d`, whose iOS app code is the same as `abb4263`'s (the commits between change the Android engine, its tests and the QA harness only).

### Added

- `@rasheed/svelte-native/platform`: `Platform`, `Appearance`, `Dimensions`, `Linking`, `Keyboard`, `AppState`, `BackHandler`, `PixelRatio`, `Share`, `Vibration` and `Alert`, React Native's own JavaScript-only modules, typed (React Native's types; `Platform` narrowed to `"ios" | "android"`), for an app without React. An app no longer imports them by `react-native/Libraries/…` path or declares their types itself. Importing the entry loads none of them; each loads on its first property read.
- `plugins: ["@rasheed/svelte-native"]` works: the package has a root `app.plugin.js`, which Expo finds for a bare package name. `@rasheed/svelte-native/expo` is the same plugin and keeps working; `svelte-native doctor` accepts either.
- `svelte-native doctor` checks that `hermes-intl` is a dependency of the app's own `package.json` (React Native's autolinking links only those), that the installed `expo` has `src/winter` (the runtime the library's polyfills load for the standard `URL`), skips `@sveltejs/kit` and `vite` when they are not installed, and reports an `expo-modules-core` that is not the patch's version with the `overrides` fix (see "Changed").
- Types: `HostHandle` is exported from the main entry; `onPressChange`, `pressRectOffset`, `delayPressIn`, `delayPressOut` and `minPressDuration` are props of `Pressable`, `Text` and `View`, and `View` takes `onPress`, `onPressIn`, `onPressOut`, `onLongPress` (all documented, all implemented by the host, none typed); the `ref` handles of `ScrollView` and `TextInput` have `dispatchCommand`.
- The package is installable by an app outside this repository, as a pnpm git dependency of the private repository (`git+ssh://git@github.com/AlfayezDev/svelte-native.git#<tag>&path:packages/svelte-native`). It carries the library's six native modules, `native/svelte-engine`, `svelte-updates`, `svelte-screens-ios`, `svelte-navigation-ios`, `svelte-insets-ios` and `svelte-capture-ios`, and one `expo-module.config.json` at the package root that links them through Expo's autolinking (the Gradle projects keep their names, `:svelte-engine` and `:svelte-updates`; the five iOS pods are listed in `podspecPath`). A `files` list packs `src/`, `native/` (sources and build files; no tests, no `SPEC.md`), the config, `patches/` and the documents; `LICENSE` is in the package.
- `@rasheed/svelte-native/package.json` is an export, for tools that resolve the package's directory.
- `withSvelteNative` (Metro), the Metro transformer and the native target of `svelteNative()` (Vite) fail with instructions when the installed `svelte` is a stock release without the `./renderer` export (the registry's 5.56.7 has the same version as the custom-renderer build): install `https://pkg.pr.new/svelte@216f258068d93170a927ad4d27ee6864b0b305c5` or the repository's vendored tarball.
- `ExpoView` and `defineExpoView` in `@rasheed/svelte-native/foreign` mount the native view of any Expo module by name, with no wrapper written for the library: `const CameraView = defineExpoView<CameraNativeProps, CameraViewRef>("ExpoCamera")` once, `<CameraView facing="back" barcodeScannerEnabled={false} />` where it is shown. The view's props and events come from the native module, a shared object prop (an `expo-video` player) is given as its id, children mount inside the view, and `ref` gives the host handle with the functions the module defines for the view (`handle.takePicture(...)`), as Expo's React adapter does. A library whose React component converts props or events before the view (expo-camera's `flash`, and the `barcodeScannerEnabled` its React component always sends, which starts the camera on Android; expo-linear-gradient's colours) still needs that step in the app; the dedicated components stay for those. A module or view the build does not have now fails with a message that says to install the library and rebuild.

### Changed

- **The library compiles every component of the app in runes mode by default.** A component with no rune in it is runes too, where Svelte alone infers legacy mode from the file; legacy mode turned a top-level variable that the markup mutates into reactive state even when it is a `const`, which a worklet then captured (the showcase's animateable-text crash). A file opts out with `<svelte:options runes={false} />` (a component's own `<svelte:options>` wins over the compile option, in the pinned Svelte). The Metro transformer and the web target of the Vite plugin apply it (the web target too, so a component both targets import means the same on each); `.svelte.ts`/`.svelte.js` modules were always runes. Svelte libraries below `node_modules` keep Svelte's own default (runes inferred per file), because forcing runes on a third-party legacy component would break it; this library's own components are always runes, also from an app's `node_modules`. An app that is migrating legacy components sets `runes: false`: `withSvelteNative(config, { runes: false })` and `svelteNative({ runes: false })` (Metro's workers get it in `SVELTE_NATIVE_RUNES`, and the transformer's cache key follows it). The build-time check that refuses a worklet reading state stays; its message for a component outside runes mode now names the three ways a component gets there. The showcase's animateable-text screen no longer needs `<svelte:options runes />`. The repository's own components that Svelte inferred as legacy (48 with no rune in them: 13 in the apps, 2 in the package, 33 test fixtures) compile unchanged apart from the compiler's own legacy wrappers and the plain variable a legacy `let` no longer becomes state; none used legacy syntax (`export let`, `$:`, `$$props`, `<slot>`, `on:`).
- **`hermes-intl` is a required peer dependency** (`^0.1.2`; the library requires it and Metro fails without it). Install it as a dependency of the app and rebuild the native app: it carries a native module that React Native's autolinking links only from the app's own dependencies.
- **`@sveltejs/kit` and `vite` are optional peer dependencies.** Only remote functions and the web target of the Vite plugin use them. The Metro plugin, the transformer, the Expo plugin, the command line and the runtime load and bundle without them (a test bundles a minimal app with neither resolvable); a feature that needs SvelteKit fails with a message that names `@sveltejs/kit` (a `*.remote.ts` module in the transformer, the runtime's imports in Metro's resolver, `svelteNative({ target: "web" })`, which now returns a promise of its plugins that Vite settles). An app that uses them keeps installing SvelteKit and its patch as before.
- **The default variant is `app`, not `qa`.** An app that sets no `APP_VARIANT` gets `.svelte-native/routes.app.ts` (it was `routes.qa.ts`); `qa`, `smoke` and `production` are names an app chooses with `APP_VARIANT` and are unchanged, and `production` still leaves the development lab out. An app that relied on the default being `qa` sets `APP_VARIANT=qa` for the command line (the QA app does, in its scripts and harness) and passes `variant` to the plugins, which gained the option for it: the Expo plugin's `variant` and `svelteNative({ variant })` (Metro's `withSvelteNative` had it).
- The Metro transformer finds `@expo/metro-config/babel-transformer` through `expo` (a required peer; `@expo/metro-config` is `expo`'s dependency), so it no longer depends on a hoisted install: pnpm's default layout has it only beside `expo`. The type of Metro's config is taken from `expo/metro-config`, not from `@expo/metro`.
- `expo` asks for `expo-modules-core` by a range (`~57.0.23`), so a fresh install takes the newest version in it and the patch (for exactly 57.0.23) fails with `ERR_PNPM_UNUSED_PATCH`: an app pins it with `overrides:` (`expo-modules-core: 57.0.23`) in `pnpm-workspace.yaml` (README, "Install in an app"). The doctor reports it with that fix.
- `animatedProps` of `AnimatedView` is typed as the worklet (or list of worklets) the host takes, as `animatedStyle` is, not as Reanimated's `useAnimatedProps` object; `animatedStyle` also takes a list. The `ref` of `View` and `GestureDetector` is a `HostHandle | null`, not `unknown`; the `ref` of `TextInput` still types React Native's `clear()`, which the host handle does not implement (set the bound `value` to `""`).
- `svelte` is a peer dependency (`5.56.7`, the custom-renderer build of sveltejs/svelte#18042 at `216f258`), not a dependency by `file:`; the repository installs its vendored tarball as a development dependency. `esbuild` is pinned to `0.28.1` in the package's own manifest instead of the workspace catalog, which a dependent cannot resolve.
- The six native modules moved from the example app's `modules/` to `native/` in the package, and the engine's `SPEC.md` with them (`native/svelte-engine/SPEC.md`). An app that linked them as local modules (`modules/svelte-engine` and the others) removes them and depends on the package; `autolinkingExclude` entries that named one of the six no longer exist (the six are one package). The example app links them through its workspace dependency, like any app.
- The entries a Node process loads are built JavaScript in `dist/node/` (committed; `pnpm build` writes it, a test fails when it is stale): the `svelte-native` command line, `/metro`, `/transformer`, `/expo`, `/vite`, `/lower` and `/routes`. Their `exports` are `{ "types": "./src/….ts", "default": "./dist/node/…" }`; every other entry is still the TypeScript Metro compiles. The built files name the runtime files Metro compiles by path into `src/` of the package (`src/package-root.ts`), and the doctor finds `patches/` the same way.

### Documented

- `Text` keeps whitespace exactly as written, as React Native's does: a sentence split across source lines reaches the native text with its line break and indent (Svelte's compiler only trims the edges of an element's content and turns a whitespace-only gap between nodes into one space). No HTML-style collapsing is applied. The recommended pattern is one source line, or a string (`{"one long string"}`). In REFERENCE.md ("Text and whitespace") and the README ("Coming from Svelte on the web"); `tests/text-whitespace.test.ts` pins it, so a change is deliberate.

### Fixed

- After a change of the text size (or any other change that recreates the Activity) the top screen could be missing from the accessibility tree for as long as it was shown, with TalkBack and `uiautomator` seeing an empty window though the screen drew correctly (about one recreation in six on the OVH emulator, on builds before the extraction as well). The Android engine applied a transaction Fabric handed it on the main thread (the size the new surface measures) ahead of the transactions from the JavaScript thread still waiting for the main looper, so the layout of the new size named views that did not exist yet and was dropped, and Fabric did not send it again; the top screen kept a frame of 0 px by the window's height. The engine now applies transactions in the order Fabric pulled them (`native/svelte-engine/SPEC.md`, "Transaction order").
- A worklet that read Svelte state threw `Tried to synchronously call a Remote Function. Called "anonymous" on the UI Runtime` when its screen mounted on a release build, and the screen drew nothing (the showcase's animateable-text screen did). Svelte compiles a read of state into `$.get(count)`, so the worklet captures `$`, Svelte's runtime, which does not exist on the UI runtime. Outside runes mode a variable that the markup mutates is state even when it is a `const`: `const count = createSharedValue(0)` with `count.value = ...` in a handler. The Metro transformer now fails the build of a file in which a function marked `"worklet"` (an `animatedStyle` or `animatedProps` worklet, a `runOnUI` callback) reads state, names the variables and the fix (`<svelte:options runes />` for a component outside runes mode, a shared value for `$state` and `$derived`). The callbacks of a gesture chain are not judged at build time (`.runOnJS(true)` makes reading state right for them); their development check is unchanged. The showcase screen is a runes component.
- An app's `svelte-check` failed in the library's own source, from a workspace link and from `node_modules`, on `react-native/Libraries/Image/resolveAssetSource`, `…/BackHandler`, `…/Platform`, `…/Linking` and others, unless the app declared those modules itself. The library's public declaration files and the source files that import them now reference `src/fabric/react-native-internals.d.ts`, whose declarations are React Native's own types; an app declares nothing. A test type-checks an app that has the packed package in `node_modules`, and another reads the import graph of every entry.
- The library's own `.svelte.ts` modules (`router.svelte.ts`, `insets.svelte.ts`) did not compile in an app that installs the package: the transformer left TypeScript in files under `node_modules` for Babel, but Svelte's module compiler runs first and reads JavaScript, so Metro stopped with `js_parse_error`. Types are stripped from a `.svelte.ts` file wherever it is. A test transforms them at the path an install puts them at, and another bundles an app that imports them.
- `@expo/metro-config` was required by the transformer without being declared: it resolved only under a hoisted install (see "Changed"). A test runs the transformer in a layout where it is only beside `expo`.
- `pressRetentionOffset`, which React Native's types accept on `Pressable`, was ignored by the host (it read only `pressRectOffset`, Pressability's name); it now widens the press region as in React Native.
- The `svelte-native` command line (`doctor`, `sync`, `dev`, …), `@rasheed/svelte-native/metro` (`metro.config.cjs`), `/transformer` (Metro's workers), `/expo` (`@expo/config`'s plugin loader) and `/vite` did not load when the package was installed in an app's `node_modules`: Node refuses TypeScript from there (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`, Node 25 and 26), and Vite and `@expo/config` hand the file to Node. They worked in this repository only because the workspace link is not under `node_modules`. A test unpacks the packed package into a scratch `node_modules` and loads each with plain `node`.

## 0.2.0 - 2026-11-08

Built from `1c7e2ea9f`, the final build: `feat/svelte-native-next` after the merge of `feat/svelte-native-launchfix`, on top of `c8faf5e97`. It is the last commit that changed app code (the foreign lab, in the QA bundle only); the harness commits `709bb4141` and `9c87e3bc7` before it and `35c332168`, `daa779196` and `1961920bc` after it change only the QA harness and `qa/gates.json`. Which build measured each suite, and why a result is carried from an earlier build, is in [PLAN.md](PLAN.md), "Final build gates". The package is private and has not been published. The entries that were under "Unreleased" since the first cut of this version on 1 November (`48d746e54`) are folded in, and so are those since the record of 4 November (`68ae53455`): SvelteKit remote functions, the launch link read before the router mounts, Android event patches for four view libraries, and the Android header and sheet fix for a screen's first layout.

### Added

- `openLaunchURL(router, accept?)` opens the link the app was launched with into the root router before its `<Router>` mounts and resolves with the link. A shell that chooses what to render by the launch link (the platform app's lab starts without its session) awaits it, so the navigator starts on the link's screen and the router's first screen is never rendered; the `<Router>` mounted afterwards does not read the link again, and the platform is asked once. `accept` refuses a link for the moment (it is left for the `<Router>`).
- SvelteKit remote functions. A `*.remote.ts` module is imported in native Svelte code as in the browser: Metro replaces it with the client stubs SvelteKit's Vite plugin would generate (same ids), and `query`, `query.batch`, `query.live`, `command`, `form` and `prerender` run on SvelteKit's own client files against the SvelteKit server named in the app config (`extra.svelteNative.remote`, written by the new `remote` option of the Expo plugin, or `configureRemote({ origin })`). Cookies are the platform's, requests carry the `Origin` SvelteKit's CSRF check wants, `query.live` streams through Expo's `fetch`, a `redirect()` goes through the router, and a build with no host throws at the first call. `form` is a native port: `fields.x.as(type)` returns the props of a `TextInput` or `Switch`, `submit()` is the submit button, a submission carries what the inputs show (defaults included) and a failed one is handled, not thrown (`form.error`). Numbers are read strictly, Arabic digits included, and `"1,000"` (a thousand or 1.000, depending on the reader) is not a number. A field none of whose inputs is on screen any more (a virtualized row, a closed modal) still posts what was typed or set. A submission always ends: `pending` goes back to 0 even when `handleError` or the data read throws. Peer dependencies: `@sveltejs/kit` 3.0.0-next.27 exactly, and `expo-constants`. New entries `@rasheed/svelte-native/remote`, `/remote/runtime` and `/remote/globals`; a new dependency, `@babel/parser`. Hermes 0.17 has no `FinalizationRegistry`, which SvelteKit's query cache needs: the package supplies one, and a query object made in a component is released when the component is destroyed (its live stream closes, its cache entry is dropped) and made again if it is used afterwards. Nothing is installed on `globalThis`. See README, "Remote functions".
- A development lab page, `/__dev/remote`, with the lab's own checks, a form and a live clock (the form and the clock appear once the app has a host; the page calls no remote function before that); QA and smoke builds only.
- Android: a screen reader now gets `accessibilityState` (selected, disabled, checked including mixed, busy, expanded), `accessibilityValue` (a slider's range and text), `accessibilityHint`, `accessibilityActions` with `onAccessibilityAction` (`{ nativeEvent: { actionName } }`), `accessibilityLiveRegion`, `importantForAccessibility` and `role` from the engine's views, the way React Native's Android views publish them (same TalkBack announcements, same node info, React Native's own role strings in the device's language). The engine dropped all of them before.
- `aria-*` props (`aria-label`, `aria-checked`, `aria-selected`, `aria-disabled`, `aria-expanded`, `aria-busy`, `aria-hidden`, `aria-live`, `aria-labelledby`, `aria-valuemin|max|now|text`) work on both platforms: React Native resolves them in `View.js`, which a Svelte host has none of, so they were ignored on iOS and on the Android engine alike.
- Gestures: `@rasheed/svelte-native/gestures` runs react-native-gesture-handler 2.32 on Svelte views (`gesture={...}` on any primitive, `<GestureDetector>`, `use:gesture`), with worklet callbacks on the UI thread, relations across components and development-time checks of what a worklet captures.
- Native-view wrappers in `@rasheed/svelte-native/foreign` for twelve libraries (expo-image, expo-blur, expo-linear-gradient, react-native-video, @react-native-community/datetimepicker, lottie-react-native, react-native-pdf, react-native-view-shot, rive-react-native, expo-conic-gradient, react-native-fast-shadow, react-native-animateable-text), next to `WebView`, `MapView`/`Marker`, `VideoView` and the generic `ForeignView`; all are optional peer dependencies.
- `@rasheed/svelte-native/svg`: react-native-svg 15.15.4 as 36 Svelte components (every element and filter, `SvgXml`, `SvgUri`) with the library's own prop extraction, refs with `getBBox`/`getTotalLength`/`toDataURL`, and `animatedProps`.
- `animatedProps` next to `animatedStyle` on any element, for animated props that are not style.
- `@rasheed/svelte-native/native-modules`: `turboModule(name)` and `nativeModule(name)` reach a native module without React; a smoke app (`APP_VARIANT=smoke`, `io.rasheed.svelteqa.smoke`) loads 36 native modules of the production app and `native-qa smoke` fails when one stops loading.
- File-based navigators: a `+layout.mobile.svelte` with `export const navigator = "stack" | "tabs"` makes its directory a stack or a tab bar, `<Stack>` and `<Tabs>` render it, and `goto`, `back`, `reset` and deep links resolve over the whole tree.
- Native screens through `<Screen>`: header (title, subtitle, back, left/center/right slots, search, large-title collapse, translucent), sheets with detents and drag, form sheets, tab bars with icons and badges, per-screen system bar colors, `onAppear`/`onDisappear`; `useHeader()` and `useToolbar()` report the bars' heights.
- A native bottom toolbar (`<Screen toolbar={...}>`): `UIToolbar` on iOS, a Material bar on Android, with badges, spacers, a center snippet and a translucent mode.
- Navigation state survives an Android Activity recreation (font scale, locale) and a process kill, and the launch link is the stack's base. On iOS it survives a process the system ended while the app was in the background (the `SvelteNavigation` module and an `AppDelegate.swift` patch from the Expo plugin), not one the user swiped away.
- A screen popped by JavaScript stays mounted until the stack reports `topExited`, on both platforms, so the transition finishes before the screen is destroyed.
- Expo Updates compatible with `eas update`: `@rasheed/svelte-native/updates` (`checkForUpdateAsync`, `fetchUpdateAsync`, `reloadAsync`) with a native store and launcher; a launch is confirmed only after a healthy window (idle, 3 s, no fatal), a fatal rolls the update back at the next start, and one unconfirmed launch does not blacklist a good update (on iOS a failing update needs two unconfirmed launches).
- Virtualized `List`: fixed or measured row heights, `horizontal`, `initialScrollIndex`, `header`/`footer`/`empty`, `onEndReached`, `onViewableItemsChanged`, row wrapper recycling.
- `KeyboardAvoidingView`, an insets store (`insets`, safe area and keyboard) on both platforms, and `Modal` presented on an engine overlay layer on Android.
- Config plugin options `autolinkingExclude` (leave packages and local Expo modules out of both autolinkers) and `androidOnDemandViewManagers` (keep a package's view managers off the app start).
- New entries `core`, `init`, `fabric`, `foreign`, `svg`, `gestures`, `updates`, `native-modules`, `animation`, `routes`, `lower`, `expo` and `elements`; `bootSummary()` exposes the boot phases.

### Changed

- A navigation before the root `<Router>` has mounted drops the screens it replaces at once. They were kept until the native stack reported their exit, which a screen that was never shown cannot do, so the router's first screen stayed rendered (and the timeout warning fired) after the launch link replaced it. The same goes for a root `<Router>` that unmounts (a shell waiting for its session): the screens still leaving are dropped with it.
- The read of the launch link is bounded: the platform gets three seconds, after which the app starts as if it had no link, and an answer that comes later is opened if nothing has navigated since (never after, never twice). A read that failed is no longer remembered for ever (the next `openLaunchURL` asks again, unless the app has gone on meanwhile, when the link is stale and is dropped), and the `<Router>` reports a failed read instead of leaving an unhandled rejection.
- The Expo plugin's options take `remote: { origin, base?, appDir? }`; an `http:` origin also lets the Android and iOS builds use plain HTTP to it.
- The root router tells the remote runtime which screen is on top and how to follow a server redirect (`connectHost`).
- The windowed `List` mounts its overscan four frames after the rows that show, not one (the one-frame flush went ahead of the layout event of the visible rows on a phone with slow cores), and the wrapper of a row of a list whose rows have one size is described once per row. Once the animation layer is loaded only the nodes that can need it go through it, and a node the host has not built no longer reports its changes.
- Android boot (Samsung A16, 2 November 2026; SPEC "Boot on the phone, round 2"): the Expo plugin now generates `override fun attachBaseContext(base: Context)` into `MainApplication.kt`, which calls `BootBoost.preloadLibraries(base)` (SoLoader and the start's native libraries load on a thread of its own while the Application is set up). **A `MainApplication.kt` that already overrides `attachBaseContext` clashes with it**: `prebuild` now stops with a message unless the existing override calls `expo.modules.svelteengine.BootBoost.preloadLibraries(base)` itself (then the plugin adds nothing). `MainActivity.onCreate` gets two generated calls (`BootBoost.activityCreated()`, `ViewWarmup.begin(this)`).
- Android boot: `expo-blur`, `expo-conic-gradient`, `expo-image` and `expo-linear-gradient` are built when their first component is mounted (like `expo-video`), not with the host, so `requireNativeModule` on them builds the module on first use. The boot pin no longer asks the system whether the process is on screen: it is made in the app's main process (not in another process of the app), kept when the Activity says it exists, and dropped when no Activity came.
- A text under a live region tells it when its text changes (an engine text is a plain view); a role description is React Native's string ("Link", "Tab") instead of the engine's own lowercase one; a `button`, `imagebutton` or `togglebutton` role makes the node clickable.
- The Android host is the package's own engine (`native/svelte-engine`): Fabric's mounting is replaced by typed Kotlin views, so mounting 600 views costs about a fifth of React Native's on the Samsung A16 and the Reanimated frame path no longer builds Java maps. iOS keeps React Native's mounting.
- There is no React in the render path: the React host, `react-native-screens`, `react-native-safe-area-context` and the dev client are gone, and Metro maps `InitializeCore` to the package's own `init.ts`.
- `<View>`, `<Text>`, `<ScrollView>`, `<Image>`, `<ActivityIndicator>` and `<Pressable>` are lowered to host tags at compile time, so a row costs host nodes only.
- Boot on Android: route modules load on first use, the Expo module registry and the Reanimated and gesture hosts load lazily, view configs are static, start-up threads stay on the big cores until the first mount, and a baseline profile ships for the engine and updates modules.
- Frames on Android: pooled views, a text layout cache, views with partial alpha are no longer promoted to hardware layers, screens hidden with alpha instead of `INVISIBLE`, layout events delivered in the batch that mounted them, and a fixed native heap leak in animated views.
- Route tables are generated per bundle variant (`.svelte-native/routes.<variant>.ts`); Metro writes the table for the variant it bundles and refuses a bundle whose table belongs to another.
- The windowed `List` mounts the rows that fit first and its overscan a frame later, and fixed-height rows skip the layout report.
- `ref` callbacks follow React's contract on every element and component: the handle when the element is built, `null` when it is destroyed, and the old callback gets `null` before a replacement gets the handle.
- On iOS `Modal` mounts its native host only while it is shown, as React Native's does.
- A function-valued `ref` or attribute survives a spread on a lowered primitive.
- A popped iOS screen stays mounted until the stack reports its exit.
- Peer dependencies: `react-native-gesture-handler`, `react-native-reanimated` and `react-native-worklets` are required (a native rebuild); the libraries behind the wrappers are optional.
- The product (`APP_VARIANT=production`) contains no development lab: route discovery skips `__dev` directories and `export const lab = true` pages, Metro stubs the lab's modules, and a bundle whose table names the lab is refused.

### Removed

- The `@rasheed/svelte-native/host` export and the React entry (`SVELTE_NATIVE_FABRIC`, `androidHeadless`, the dev client).
- The Android `Dialog` behind `Modal`.

### Fixed

- Android: events of `react-native-pdf`, `react-native-video`, `lottie-react-native` and `react-native-maps` that are not streams are no longer replaced in React Native's event queue. React Native's `Event.canCoalesce()` is `true` unless an event class says otherwise, and the queue then keeps only the last of two unread events of one name from one view while JavaScript is busy. `react-native-pdf` sends every message as one `topChange` event, so a document's `onLoadComplete` was overwritten by the `onPageChanged` the view posts 10 ms later: 28 of 182 `Pdf` row mounts on the emulator and 10 of 130 on the Samsung A16 raised no load event, and 0 of 39 do with the patch. The same is closed for the events of video (all but progress and bandwidth), Lottie (finish, loaded, failure) and maps (21 of the 26 event classes; the five streams keep coalescing). The patches are pnpm patches of this repository (`patches/react-native-pdf@7.0.3.patch`, `react-native-video@6.19.3.patch`, `react-native-maps@1.27.2.patch` and the existing `lottie-react-native@7.3.8.patch`, listed in `patchedDependencies`), so an app that is not this repository must carry them. The price is that JavaScript is told of every message of such an event, every `scaleChanged` of a PDF pinch included. `rive-react-native` needs no patch: its events leave through React Native's interop emitter, which never coalesces, and a test reads React Native's sources and fails when that changes. iOS cannot lose these events (it sends them with `dispatchEvent`, never through the queue's unique path).
- Android: the first screen of the app's stack no longer keeps what its header and sheet worked out while the screen was laid out detached. With a launch link opened before the `<Router>` mounts (`openLaunchURL`), an inline header title sat 1 px high, and a sheet link under a nested stack (`/__dev/tree/inbox/compose`) rested at its top detent over the whole pane, a root screen to look at, on some launches (a warm link, pushed onto a stack that has its size, was fine); any first screen of a cold start could hit it, not only a launch link's. A header lays out again when it attaches with a window inset it did not use (pushed screens too: every title sits at the status bar's inset, not a pixel above it), a sheet rests where its layout says whenever that moves, and a header inside a sheet keeps the padding its screen gave it. A layout does not move a sheet that is being dragged, is settling, leaving or animating, is in a transition of the stack, or is moved by a gesture of the stack (a predictive back swipe).
- iOS: the events of `react-native-video` and `rive-react-native` (load, ready, progress, play, pause, stop, error) reach JavaScript. They are legacy view managers, and React Native's interop gives such a view an event block only for an event prop that is `true`; the host's static view configs now list their events as attributes on iOS (`Kind.legacy`). Before, none of them was delivered there.
- iOS: `lottie-react-native` 7.3.8 is patched (`patches/lottie-react-native@7.3.8.patch`, through `patchedDependencies`): `onAnimationLoaded` and the failure event, which the view raised before it had an event emitter, are kept and sent when the emitter arrives, and a recycled view that gets the source it already shows says that its animation is loaded.
- iOS: the `tmpfile` captures of `react-native-view-shot` that a process left when it ended without exiting are deleted when the next process starts (the `svelte-capture-ios` module); React Native deleted them only when the next process captured something. The wrapper passes the library's own answer on: a plain path on iOS, sizes in points.
- `List`: `scrollToIndex` and `scrollToOffset` called before the scroll view is bound and has its first layout (a page that scrolls its list in the effect that runs as the list mounts) sent the command to no view and the list stayed at the top. The last such request is kept and sent when both are there. The two commands no longer subscribe the effect that calls them to the list's window, row sizes and header.
- iOS: a hidden `Modal` swallowed every touch on pushed screens.
- A scroll view's content container follows `contentContainerStyle` and `horizontal` after the first render.
