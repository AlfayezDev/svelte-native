# Svelte Native: unified engine plan

Written 25 October 2026 from the day's measurements on a Samsung SM-A165F (Android 16, 90 Hz) and an iPhone SE 3 (iOS 26, 60 Hz). Evidence and traces live in `.rasheed/native-qa/2026-10-25/`.

## Goal

One package, `@rasheed/svelte-native`, that runs Svelte components as native apps through one purpose-built path: compiled Svelte → one host → Fabric's shadow tree and Yoga → our own typed mounting layer → platform views. No React, no React Native JavaScript layer, no generic ViewManager or module registries at runtime. The build and release pipeline stays Expo: `expo prebuild`, config plugins, autolinking, the React Native Gradle plugin and Pods, EAS Build and Submit.

## Why: where the time goes today

| Cost, 300-row list, Samsung, warm | Today | Platform floor | Verdict |
|---|---|---|---|
| Svelte component instances (`View`/`Text` as components) | 45 ms | 0 | ours, compile away |
| Svelte runtime per row (each block, elements, text effects) | 32–37 ms | ≈ React's reconciler, 30 ms | parity already |
| JSI crossing, payload builder, host bookkeeping | ~10 ms | ~3 ms | small |
| Fabric C++: shadow nodes, Yoga, commit | 30 ms | same for any engine | keep |
| Android mount layer: createView, text state, layout, insert | 145–200 ms (+40–80 draw) | 42–67 ms with plain `FrameLayout` + `TextView` | 3–4× tax, replace |
| Reanimated Android per-frame prop path | 69 µs per view per frame | 1–2 µs direct setter | 30× tax, replace |
| Boot to display | ~700 ms | platform ≈ 200 ms | RN + Expo + Hermes init ≈ 420 ms, JS eval 260–275 ms |
| Bundle (spike, plain JS) | 2.07 MB | — | Reanimated + worklets 828 KB, RN JS 565, Svelte 205, React 8, ours 30 |

The React Native Android mount tax, traced: props cross JNI as `ReadableMap`, wrapped in `ReactStylesDiffMap`, a `ViewState` registry entry, ViewManager lookup by name, `createViewInstance` to an `AppCompatTextView`, `setId`, `addEventEmitters`, every prop dispatched by string through a generated delegate; text rebuilt as a Spannable from a MapBuffer (45 ms per 300); layout applied per view as a separate instruction (21 ms per 600). Boot: `ReactInstance.initialize` 208 ms (Hermes libraries 46, TurboModule and eager Expo module registry 75, Fabric 45), native library loads ~130 ms, sync `getViewManagerConfig` calls from react-native-screens at import, EmojiCompat init 22 ms from AppCompat.

iOS is different: React Native's iOS mounting is typed Objective-C++ with no JNI or string dispatch (React list mount 21 ms). It is kept for v1.

## Architecture

| Layer | Decision |
|---|---|
| Hermes, JSI, Fabric C++ (ShadowTree, Scheduler, Yoga, text measurement, event emitters) | keep, linked as prefab (`ReactAndroid::reactnative`, `ReactAndroid::jsi`, `fbjni`), the way Reanimated links |
| Build pipeline: Expo CLI, prebuild, config plugins, autolinking, RN Gradle plugin, CocoaPods, EAS | keep; our native code is an autolinked module, our host classes are installed by our config plugin (`withMainApplication`, `withMainActivity`, `withAppDelegate`) |
| Android host (`ReactHost` + `ReactInstance`) | fork into our package: `ReactInstance` is `internal` and constructs `FabricUIManager` non-injectably; ours initializes Hermes and Fabric with our `SchedulerDelegate` and a short TurboModule list |
| Android mounting (`FabricUIManager`, `MountItemDispatcher`, `SurfaceMountingManager`, ViewManagers) | replace: C++ `SchedulerDelegate` consumes shadow-view mutations, passes typed `ViewProps` to Kotlin setters, plain `View`/`TextView`, text set directly, layout in the same pass |
| JavaScript: React, RN JS layer, InitializeCore, LogBox, Fast Refresh | drop; our init, our host, Metro HMR remounts the root |
| Svelte primitives | compiled to tags; components only where behaviour lives (`TextInput`, `Switch`, `Modal`, `Pressable`) |
| Animation | keep `react-native-worklets` runtime; our UI-thread driver writes view setters directly; CSS keyframe and transition engine ported from Reanimated's C++ (MIT) onto our mounting layer; layout animations in our mounting delegate |
| Navigation, safe area, keyboard | ported, not shimmed: own stack container, `WindowInsets` store, keyboard insets. No ViewManager compatibility layer, because that layer is the tax |
| Modules (secure store, file system, image picker, localization, crypto, font, splash) | v1 keeps `expo-modules-core` for these (~50–80 ms boot); v2 ports them to direct JSI functions |
| Lists | own virtualized list; row recycling becomes possible because we own the views |
| Over-the-air updates | fork `expo-updates` (MIT) into `engine/updates/`, keep the EAS Update protocol (manifest, assets, rollback, `eas update` publishing unchanged), strip the React Native host hooks and dev-launcher integration, bind the launch asset path to our host's bundle loader. Hermes bytecode bundles are the same format, so published updates need no change |
| iOS mounting | keep React Native's (`RCTMountingManager`, component views) for v1; own host only where needed |

Package layout: `compiler/`, `host/` (JS), `engine/android/` (Kotlin + C++), `engine/ios/`, `animation/`, `navigation/`, `list/`, `init/` (JS boot), `cli/`, `expo/` (config plugin). All contact with React Native internals confined to `engine/`.

## Phases

Each phase ends with a number measured by the lab (`/__dev` runner, `tools/measure.py`, Perfetto) on both phones, recorded in the QA folder. The app stays runnable on the React host through the entry switch until phase 7.

### Phase 0: Android mounting spike (1–2 weeks) — DONE 25 Oct 2026, same day

Result (same APK, Perfetto traced): Samsung React Native mounting 172 ms avg per 600 views (frames 330–529 ms) vs engine 32 ms avg, 45–52 typical (frames ≤ 39 ms), plain-widget floor 42–67; emulator 111 → 25 ms. Render pixel-equivalent, scroll and touch work. Evidence in `.rasheed/native-qa/2026-10-25/README.md` ("Phase 0 result").

- Local Expo module `apps/platform/modules/svelte-engine` (Kotlin + CMake), forked `ReactHost`/`ReactInstance`, C++ `SchedulerDelegate`, Kotlin mounting for `RCTView`, `RCTText`/`RCTRawText`, `RCTScrollView`.
- Touch delivery through Fabric's C++ touch event emitter from our views.
- Acceptance: the Fabric spike page renders and scrolls 300 rows; UI-thread mount ≤ 70 ms (floor 42–67, React Native 145–200); touch counter works; no React loaded.
- Stop rule: if the mount does not land under 80 ms, the thesis is wrong at this layer and the plan falls back to the 3-week "unified on top of React Native" variant.

### Phase 1: element API and compiler (2 weeks) — DONE 25 Oct 2026 (same evening)

Result: `src/lower.ts` lowers package primitives to host tags at compile time (`style`→`nativeStyle`, valueless attributes stay `true`); hosts take React Native props as attributes. Emulator, engine on: component rows 68–71 ms JavaScript, equal to raw tags (125–134 before). React-host app renders unchanged.

- Preprocessor lowers `<View style={x} onLayout={y}>` to `<native-view style={x} onLayout={y}>`; per-attribute host diff; no `nativeProps` object, no rest-props proxy.
- Event names from static tables; `createNode` keeps RawProps (shadow-node cost is C++); own JSI host object deferred.
- Acceptance: 300-row mount, JavaScript side ≤ 80 ms with `<View>`/`<Text>` source (today 130 ms as components, 75–80 raw).

### Phase 2: core views and behaviour (3 weeks) — FIRST PASS 25 Oct 2026

Done: engine TextInput/Switch/ActivityIndicator/Image/Modal, multi-touch, z-order, momentum scroll + state updates, commands/setNativeProps/measure, accessibility exposure, responder + Pressability port (JavaScript host). Verified on the emulator through a driven check. Open: hitSlop in native hit-testing, `contentOffset` prop, paging, KeyboardAvoidingView, styled-span text parity, `measure` via the binding for engine tags, iOS counterparts.

- Responder system and a port of React Native's `Pressability` (plain class; swap `UIManager.measure` for the binding's `measure`).
- `TextInput` (own `EditText` + state protocol), `Switch`, `Image` (own `ImageView` + loader), `Modal` (Dialog), `ScrollView` commands and content container, `KeyboardAvoidingView`, `measure`/`dispatchCommand` handle API, accessibility props.
- Acceptance: 28/28 functional checks on the engine host, Android.

### Phase 3: animation (2–3 weeks)

- Shared values and worklets on the kept runtime; UI-thread driver with direct setters for transform, opacity, colours; layout props through Yoga re-layout; CSS keyframes and transitions; entering/exiting/layout animations; scroll handler worklets.
- Acceptance: churn-animated p95 ≤ React twin (today 21 vs 29 ms); 48 CSS tiles UI animation stage ≤ 1 ms; per-view per-frame cost ≤ 5 µs; max frame ≤ 20 ms with rounded tiles (today 55 ms spikes).

### Phase 4: boot and bundle (1–2 weeks)

- Own JavaScript init replacing InitializeCore (error handling, fetch/WebSocket/Blob, event emitter, AppRegistry callable); deep imports only; TurboModule list trimmed; no AppCompat, no EmojiCompat; no sync view-manager constant calls.
- Over-the-air updates: `expo-updates` forked and refactored onto our host (protocol client, asset store, launch path, rollback); `eas update` publishes as before. Not installed today, so this is additive.
- Acceptance: warm display ≤ 400 ms (today ~700); `Running "main"` ≤ 250 ms after process start; bundle ≤ 0.6 MB plain JS for the spike (today 2.07); an update published with `eas update` launches on the next start.

### Phase 5: navigation, insets, lists (3 weeks)

- Own stack container with transitions on the animation driver, predictive back; insets store; keyboard insets; virtualized list `<List items rowHeight>` with fixed heights first, measured later; row recycling.
- Acceptance: navigation-8 and modal-8 parity; 300-row list to pixels < 120 ms with ~20 mounted rows; churn-60s and soak-120s clean.

### Phase 6: iOS (3–4 weeks)

- Same JavaScript; React Native iOS mounting kept; own host via `withAppDelegate` where needed; `UINavigationController` for the stack; insets and keyboard ports.
- Acceptance: all parity scenarios on the iPhone; list mount ≤ 30 ms (React 21); signed build through the Mac recipe, then EAS Build.

### Phase 7: cutover (2 weeks) — DONE 25 Oct 2026, late evening (validated on emulator, Samsung and iPhone)

- Deleted: `src/host.tsx`, `src/react-components.ts`, `src/registry.ts`, `src/host-kind.ts`, `src/animated-host.ts`; the React entry and the `SVELTE_NATIVE_FABRIC` switch (`build.ts`); Metro's second mode (`metro.ts`: lite shim, renderer stubs and the InitializeCore → `init.ts` mapping are unconditional); the dev client (`cli dev` runs `expo start`); the `androidHeadless` option (the Android build is always headless); the React branches in SafeAreaView, KeyboardAvoidingView, insets, List, Router; the renderer's subscriber machinery; the lab's React twins and parity scenario; app deps `expo-dev-client`, `react-native-safe-area-context`, `react-native-screens` (still present as transitive deps of `expo-router` through `@expo/cli`; excluded from autolinking on both platforms via `expo.autolinking.exclude` in the app's package.json and the generated settings.gradle).
- Kept: `react` (React Native's peer; `useColorScheme` imports it), the engine lab switch `--ez svelteEngine false`, the spike roots (`SVELTE_NATIVE_ROOT`), reanimated patch part (a).
- Acceptance: lab 28/28 on emulator, Samsung and iPhone with the cutover build; boot, bundle and APK size compared with the React host baseline (morning: display 622 ms best-of-three, bundle 3.45 MB, APK 37.7 MB).

Total: 17–20 weeks. Phase 5's list work can start after phase 1 on the React host.

## Risks

- Fabric C++ internals (`ShadowTree`, `Scheduler`, `TextLayoutManager`, event emitters) are not public API. Pinned React Native 0.86.3; upgrade once per quarter; the touch points are confined to `engine/`. Same class of risk Reanimated carries.
- Responder semantics: ScrollView versus press, `keyboardShouldPersistTaps`, nested Text press. Copy React Native's logic, test on both phones.
- Android `TextInput` state synchronization races. Copy React Native's protocol.
- Text: simple strings go straight to `TextView`; nested styled spans still need an attributed-string path. Build both, measure each.
- Expo modules core kept in v1 costs ~50–80 ms boot; porting the seven modules is phase 4's stretch goal.
- Dev experience: no Fast Refresh or LogBox; Metro HMR remounts the root, errors go to the native red box and console. Svelte-level HMR later.
- The phone is shared and swaps under memory pressure; every acceptance number is best-of-three warm launches with the screen awake.

## Open decisions

1. Expo modules core in v1 (my pick: keep) versus port now.
2. Reanimated: keep the package for its JavaScript API and C++ CSS registries, or keep only `react-native-worklets` and port the CSS engine as source (my pick: port; the package's Android glue is the tax).
3. Navigation container: own `ViewGroup` stack (my pick) versus Fragments.
4. `Pressable` API: `pressed` as a snippet parameter (my pick) versus function-style props.
5. Virtualized list API: `<List items rowHeight>{#snippet row(item)}` with fixed heights first (my pick).
