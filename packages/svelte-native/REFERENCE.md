# @alfayez/svelte-native reference

The detail behind the [README](README.md): routing, primitives, the renderer and host, the loaders, the dev loop and each wrapped library. The README is the way in. The native engine (Android mounting, screens, foreign views, updates, gestures) is specified in [native/svelte-engine/SPEC.md](native/svelte-engine/SPEC.md); the measured state of the program is in [PLAN.md](PLAN.md); what changed per version is in [CHANGELOG.md](CHANGELOG.md).

## Authoring

```svelte
<script lang="ts">
  import { View, Text, TextInput, Pressable, useRouter } from "@alfayez/svelte-native";
  let name = $state("");
  const router = useRouter();
</script>

<View style={{ padding: 24, gap: 16 }}>
  <TextInput bind:value={name} accessibilityLabel="Name" />
  <Text>Hello {name}</Text>
  <Pressable onPress={() => router.goto("/account")} accessibilityRole="button">
    <Text>Account</Text>
  </Pressable>
</View>
```

- `src/routes/**/+mobile.svelte` defines native pages alongside browser `+page.svelte` files. Route groups, named parameters, optional parameters and rest parameters are supported. Static routes precede parameter routes. Parameter matchers are not implemented.
- `+layout.mobile.svelte` wraps the content of every screen below it (pages and navigator screens alike), outermost first; layouts receive `params`, `url` and a `children` snippet. The root layout is the app shell: it wraps the root navigator, receives it as `children`, and runs inside the router's context (`useRouter("root")`). A layout can also be a navigator (next section).
- A page can export `const presentation = "modal"` from its module script. `useRouter()` is the nearest navigator's router: `goto`, `back`, `replaceBase`, `openURL`, `current` (the deepest shown entry) and `entries`/`screens` (its own stack). Screen transitions and Android Back go through the host's navigation container (`src/fabric/navigation.ts`). Cold/warm deep links are matched against the route tree; unmatched URLs are ignored. The link the app was launched with is opened with `reset` (a direct load has no history: its screen is the base of the stack, with no back arrow); links that arrive later are plain `goto`s. A shell that chooses what to render by the launch link awaits `openLaunchURL(router, accept?)` (from the package; the root router; it resolves with the link) before it renders the navigator: the router has opened the link by then, so the navigator starts on the link's screen and never renders its first (`initial`) screen, and mounting the `<Router>` afterwards does not open the link again; `accept` can refuse a link for the moment (it is left for the `<Router>`). The platform is asked once, whoever asks, and gets three seconds: after that the app goes on as if it had no link, and an answer that comes later is still opened if nothing has navigated since (never after, never twice). A read that fails rejects and is asked again by the next call, unless the app has gone on in between (then the link is long stale and is dropped).
- `<Screen toolbar={{ items: [{ key: "reply", title: "Reply", icon: replyAsset }, { key: "gap", spacer: true }, { key: "archive", title: "Archive", icon: archiveSnippet, badge: 2 }], onPress: (key) => … }}>` adds a native toolbar at the bottom of the screen (`UIToolbar` on iOS, a Material bottom bar on Android), in flow below the content unless `translucent`. An item takes `key`, `title`, `icon` (an asset, drawn as a tinted template image, or a snippet), `badge` (text, a number, or `true` for a dot), `disabled`, `accessibilityLabel`, `testID`; `{ key, spacer: true }` is flexible space. `toolbar.hidden`, `translucent`, `tint` and `background` work as the header's, a `toolbarCenter` snippet puts custom content between the items, and nested `Screen`s merge their `toolbar` like their `header`. `useToolbar()` returns the toolbar's `{ height, inset }` (0 without one) to pad content under a translucent bar. Inside a `Tabs` pane the bar sits above the tab bar and takes no bottom inset of its own. Contract: `native/svelte-engine/SPEC.md`, "Toolbar".
- A `<Screen>` inside a page (or a layout) hands its options to the router's screen around it; inside a `<Modal>` or a tab pane it is the outermost one and draws its own header there; a `Screen` that no stack holds (a modal's content, the app shell) is rendered in a one-entry `native-stack` of its own, which iOS needs to draw the header. `inTabPane()` is true inside a pane, which ends at the tab bar and covers the bottom inset (a page pads that inset itself only outside a pane; `useHeader()` and `useToolbar()` give the header's and toolbar's heights).
- Primitives expose their React Native prop types and Svelte child snippets. `TextInput` and `Switch` support binding. `ScrollView` and `TextInput` accept a `ref` callback that receives the host handle (`scrollTo`, `focus`, `blur`, `measure`, `dispatchCommand`; `HostHandle` in `src/fabric/host.ts`). A `ref` follows React's rule for a callback ref: it gets the handle as soon as the element is on the screen (before `onMount` and the effects of the same flush; an element of a screen that is built off screen waits for its commit; what it asks of the handle before the view is on the screen waits for it) and `null` when the element is destroyed (the host finds that out after the flush in which the node left the tree; a node that is moved is not destroyed), and when the callback changes the old one gets `null` before the new one gets the handle. Components that make a richer handle of their own (`ViewShot`, `MapView`, `WebView`, `Video`, `LottieView`, `Pdf`, `Rive`, the svg elements) build their wrapper from the `ref` prop when it is set (`components/forward-ref.ts`), so the same holds for them. Use native style objects. HTML elements in the app's own files become native components (see "HTML element lowering"); a `<style>` block, DOM actions and SvelteKit browser navigation APIs do not become native controls.
- Lists: `<List items rowHeight={56} keyOf={(item) => item.id}>{#snippet row(item, index)}...{/snippet}</List>` mounts only the rows near the viewport (`overscan`, default 4 rows each side; 10 rows before the first layout) at absolute positions, so long lists cost a handful of native views instead of hundreds. With `rowHeight` every row has that fixed size and nothing is measured. Without it, rows start at `estimatedRowHeight` (default 48) and each row wrapper's `onLayout` fills a per-key height table; offsets are cached prefix sums rebuilt from the first changed index, the spacer is their sum, and a row whose measured size differs from the estimate shifts the rows after it on the next frame (batched, 16 ms). `rowHeights={(item, index) => number}` supplies sizes up front and skips measuring (edit items in place and the table is not rebuilt; pass a new array). `horizontal` flips the axis (`contentOffset.x`, `layout.width`, `left`, row-direction content; `rowHeight` is then the row width). Also: `initialScrollIndex`, `scrollToIndex(index, animated)` and `scrollToOffset(offset, animated)` on the bound list (a scroll asked for before the scroll view is bound and has its first layout is kept, the last one, and sent when both are there; the first window of ten rows is mounted before that layout and trimmed by it, so a row of that window can mount and unmount before the scroll brings it back), `keyExtractor` (alias of `keyOf`), `empty` snippet shown while `items` is empty, `onViewableItemsChanged({ viewableItems, changed })` (debounced 50 ms; `viewabilityConfig.itemVisiblePercentThreshold`, default 50), `header`/`footer` snippets, `onEndReached` with `onEndReachedThreshold` (fraction of the viewport, default 0.5) and the remaining `ScrollView` props. `recycle` keeps a pool of wrapper nodes (a full window for fixed rows, the high-water mark of the window otherwise) and re-targets them by index (slot = index modulo pool size) instead of mounting and unmounting rows: no host views are created while scrolling, but a row component's own state does not follow its item, so keep row state in `items`; late `onLayout` events after a retarget can mis-measure one row. `bind:this` exposes `scrollToIndex(index, animated)` and `scrollToOffset(offset, animated)`. `onRefresh`/`refreshing` are not provided: the host maps no refresh control. Native view recycling (reusing the native view across items) is not implemented.
- `<Native name="native-screen" attributes={{ ... }}>` renders a host tag chosen at runtime. The tags the host maps are `viewNames` in `src/fabric/host.ts`; an unmapped name throws when the host flushes. It is a `<svelte:element>`, and Svelte gives an `animate:` in the children that render with it to the wrong effect, so an `animate:flip` there does not play until its items are made again: write a tag you know as its own element (`<native-view>`), as the router does for its `native-stack`. The same holds for an app's own `<svelte:element>`: Svelte's runtime does this for any element it renders.
- Ordinary `.svelte.ts` modules, context, stores, runes and lifecycle hooks work. Shared validation/domain logic belongs in portable modules. SvelteKit server loads, form actions and remote functions still run on the server; native screens use explicit network boundaries.

### Runes mode

The library compiles every component of the app in runes mode, whatever the file looks like: a component with no `$state`, `$props` or other rune in it is runes too, where Svelte alone would infer legacy mode from it. Legacy mode turns a top-level variable that the markup mutates into reactive state, even a `const` (`const count = createSharedValue(0)` with `count.value = ...` in a handler), and a worklet that captures it captures Svelte's runtime, which the UI runtime does not have; the screen threw when it mounted. In runes mode state is what `$state` and `$derived` say it is. The build-time guard that refuses a worklet reading state stays (`assertWorkletsReadNoState`, `src/transformer.ts`).

| | compiled in runes mode? |
|---|---|
| a `.svelte` file of the app (and of a workspace package, which is linked from outside `node_modules`) | yes, unless the file has `<svelte:options runes={false} />`: a component's own `<svelte:options>` wins over the compile option (checked in the vendored Svelte, `compile` in `svelte/src/compiler/index.js`) |
| a `.svelte.ts` or `.svelte.js` module | always: `compileModule` has no `runes` option, a Svelte module is runes by definition |
| a `.svelte` file below a `node_modules` directory (a third-party Svelte library) | no: Svelte's own default, runes inferred per file. A library written in the legacy syntax (`export let`, `$:`, `$$props`, `<slot>`, `on:`) would not compile if runes were forced on it |
| this library's own components, wherever the package is installed (its path below an app's `node_modules` included) | yes, always; they are written in runes |

The rule is `runesOption` in `src/compile-options.ts`, which the Metro transformer, the web target of the Vite plugin and the package's tests share (`componentOptions` is the whole option set the transformer compiles a component with).

An app that is migrating legacy components turns the default off and moves its files over one at a time:

```js
// metro.config.cjs
module.exports = withSvelteNative(getDefaultConfig(__dirname), { runes: false });
```
```ts
// vite.config.ts
svelteNative({ target: mode === "native" ? "native" : "web", runes: false, kit: { /* … */ } })
```

With `runes: false` the library forces nothing and Svelte infers the mode of each file, as it does without this library; a file that wants runes mode asks with `<svelte:options runes />` (or by using a rune). `withSvelteNative` hands the option to Metro's workers in the environment (`SVELTE_NATIVE_RUNES=0`; the transformer's cache key includes it, so a changed option never reads a cached component), so a Metro started by the Vite plugin's native target gets the plugin's `runes` and an explicit `withSvelteNative(config, { runes })` in the app's `metro.config` wins over it. The web target of the Vite plugin passes SvelteKit a `dynamicCompileOptions` (SvelteKit forwards it to vite-plugin-svelte), which sets `runes: true` by the same rule; an app's own `kit.compilerOptions.runes` is kept for its own files, and the options its own `kit.dynamicCompileOptions` returns are applied over this one's.

The web target gets the default too, on purpose: a component under `src/lib` that a native page and a web page both import is compiled by Vite for the browser and by Metro for the device, and in two modes the same source would mean two things (a variable the markup mutates would be reactive in the browser and a plain variable on the device).

### Text and whitespace

`Text` keeps the whitespace it is given, exactly as React Native's `Text` does: nothing is collapsed, and no HTML-style rule applies (a browser collapses whitespace with CSS, and there is none here). A sentence split across source lines reaches the native text with its line break and the next line's indent:

```svelte
<Text>
  A sentence that is split
    across two source lines.
</Text>
<!-- draws "A sentence that is split⏎    across two source lines." -->
```

What Svelte's compiler does before the text gets there stays: it drops the whitespace at the edges of an element's content (the line breaks around the sentence above are not in the text), turns a whitespace-only gap between two nodes into one space, and turns the whitespace between a text and a nested element (`Before <Text>nested</Text>⏎  after.`) into one space. It leaves the inside of a text as written. Write a long sentence on one source line, or as a string:

```svelte
<Text>{"A long sentence, written as one string."}</Text>
<Text>{"A long sentence written "
  + "over two source lines."}</Text>
```

(`eslint-plugin-svelte`'s `svelte/no-useless-mustaches` flags a string literal in a mustache; turn it off for these.) `tests/text-whitespace.test.ts` pins this on the Fabric host, for the lowered `Text` and the component alike, so a change to it is a decision.

### File routing: layouts as navigators

The directory tree decides which stack or tab pane a page belongs to (contract: `native/svelte-engine/SPEC.md`, "Route tree: layouts as navigators"; code: `src/route-tree.ts`, `src/router.svelte.ts`, `src/build.ts`).

| file | role |
|---|---|
| `+mobile.svelte` | a page: one screen of the nearest navigator above it. `export const presentation` (a literal: `push`, `modal`, `transparentModal`, `sheet`, `formSheet`) is read at build time. Title, header, slots, search, sheet and system bars are set at run time with `<Screen>` inside the page. |
| `+layout.mobile.svelte` with `export const navigator = "stack" \| "tabs"` (a literal) | a navigator layout: its directory is one screen of the parent navigator, and the pages and navigators below it are its own. |
| `+layout.mobile.svelte` without it | a content layout around every screen below it. The root one is the app shell. |
| `+mobile.svelte` or `+layout.mobile.svelte` with `export const lab = true` (a literal), and everything under a `__dev` directory | the development lab: a route of every variant but the product (`APP_VARIANT=production`). Route discovery (`routeFiles`, so `svelte-native sync` and the prebuild plugin) does not read a `__dev` directory in the product, and leaves out a marked page, or a marked layout with its directory (not the root layout); the product's route tree, table and Metro graph never name them. |
| `(group)` | transparent for paths; a group directly under a tabs layout is flattened, its child directories become panes. |

```
src/routes/                                    the stand-in app's tree, tests/fixtures/stand-in-app (tests/app-tree.test.ts pins it)
  +layout.mobile.svelte                        app shell: receives the root navigator as `children`
  (public)/sign-in/+mobile.svelte              a root stack page (so are setup, projects, projects/new)
  (preferences)/preferences/+mobile.svelte     export const presentation = "modal": a root page, it covers the project's tab bar
  (project)/[slug]/
    +layout.mobile.svelte                      export const navigator = "tabs"; gets `panes` and `children`
    home/+mobile.svelte                        pane "home": a stack whose base is this page
    settings/+mobile.svelte                    pane "settings": base page, the sections
    settings/[section]/+mobile.svelte          pushed within the settings pane
  __dev/tree/                                  the route-tree lab: tabs with panes home and inbox
    inbox/+layout.mobile.svelte                export const navigator = "stack": the pane's stack options (optional)
    inbox/compose/+mobile.svelte               export const presentation = "sheet": a sheet of the inbox pane's stack
```

A tabs layout renders `<Tabs {items}>{@render children()}</Tabs>` with `items` keyed by the pane keys (in the bar's order); a stack layout renders `<Stack header={{ large: true }} animation="slide_from_right">{@render children()}</Stack>`, whose props are defaults under each screen's own `<Screen>` options (`loading` is the snippet shown while a route's modules load; `animation` is the default of push screens only, a modal or sheet keeps the platform's). A pane's stack layout is given the `params` and `url` of the tabs screen, and the pane shows the placeholder of the router around the tabs while the layout loads. Without `<Tabs>` or `<Stack>`, `{@render children()}` gets the defaults. `<Tabs>` outside a tabs layout stays what it was: `selected`, `onSelect` and a `content` snippet.

- Build errors name the file: a page next to a navigator layout, a pane without an index page, a page directly under a tabs layout, a tab bar inside a tab bar, a root layout that is a navigator, a navigator whose path is also another route's in its stack.
- `goto(href)` resolves over the whole tree and plans one operation per navigator on the way: tabs select the pane, the owning stack pushes, or pops to the entry when it already holds that href (Expo Router's `navigate`: the same screen is never stacked twice; another query is another href) (`replaceState` replaces its top, `reset` keeps the pane's index page and the target), and a stack above pops to the navigator's screen if it is on it (a modal over the tabs goes away) or pushes it (a deep link into tabs). `reset` is a new root for the whole chain: every stack above the owner resets to its screen (the root keeps only the tabs screen, the instance it had when it had one, so nothing remounts), every tabs node selects the pane, and the owner resets to the target; `goto("/acme", { reset: true })` from the platform app's workspace list leaves the root as `[tabs]`, so the first screen has no back arrow and Android back leaves the app. `replaceState` replaces the owner's top only. The same href as the shown entry does nothing.
- `prepare(href, navigation?)` (experimental) gets a `goto` ready while the finger is still down and returns `{ ready, commit(), discard() }`: the screen's modules load, and the screen is rendered off screen with Svelte's `fork()` (its effects wait, and nothing reaches the native stack, so Fabric is not asked for a node of it) so that `commit()`, when the finger lifts, only attaches it and runs its effects; `discard()` releases it. `commit()` does the navigation `goto` makes: when the screen was ready and the stacks have not changed since (no navigation, no screen that finished leaving: `navigations` and `stackWrites` in `router.svelte.ts`) it puts that screen on, and otherwise (the call came first and `ready` settles `false`, something changed in between, Svelte's async mode is off) the prepared screen is dropped and it is a plain `goto` from the stacks as they are. `discard()` takes effect a task later and a `commit()` before then wins (`Pressable` calls `onPressOut`, where a navigation is discarded, before `onPress` for a press of 130 ms or more); after that further calls do nothing and `ready` has settled `false`. The pages the screen renders are loaded first: the target page, its layouts and the base page of the pane a tabs navigator on the way shows (a fork renders a pane that was never selected, and a module that arrives after the fork would render outside it). A tree has one prepared navigation at a time (a newer `prepare` takes the screen of the one before, whose `commit()` is then a plain `goto`), only forward navigations (pushes and tab selections) are prepared, `prepare` reads the stacks untracked and so may be called from a handler, a timer or an effect, and every `prepare` ends in `commit()` or `discard()`: a fork that is neither is never released. It needs Svelte's async mode, which the library leaves off until the app asks: `withSvelteNative(config, { async: true })` in `metro.config.cjs` (and `svelteNative({ async: true })` in `vite.config.ts` for the web build) compiles every Svelte file the transformer sees, the app's, the library's own and a library's below `node_modules`, with Svelte's `experimental.async`. The setting reaches Metro's workers through the environment (`SVELTE_NATIVE_ASYNC`) and is part of the transformer's cache key. Svelte's flag is one switch for the whole process, turned on by the first module that imports `svelte/internal/flags/async`, and that import is all the option adds to a component without an `await` (the compiled output is otherwise identical, `tests/fork.test.ts`), so compiling some files with it and others without would change nothing at run time: the option is all or none, and a precompiled Svelte package that was built with `experimental.async` turns the mode on for an app that did not ask. The option also allows `await` in `$derived`, in the markup and at the top of a component. With it on, `tick()` waits for the next frame or a timer instead of a microtask, and in one update the components of different `{#if}`, `{#each}` and `{#key}` blocks run their `$effect.pre` and their teardown in another order (each component's own calls, and the tree, are the same: `tests/async-mode-parity.test.ts`). The screen is rendered by one JavaScript task of its own, so prepare when the thread is idle; Fabric still builds the screen's nodes in the flush that `commit()` causes. State a page's script acquires outside an effect (a subscription made while the component initialises) is not released by a `discard()`, because Svelte never runs the teardown of an effect that never ran: acquire in `$effect` or `onMount`. How to use it: [Routing, Preparing a screen](../../docs/20-core-concepts/10-routing.md#preparing-a-screen-experimental).
- `back()` pops the router's stack when it has more than one screen (a tabs router's is the selected pane's); at a pane's base it neither pops the pane nor switches tabs but lets the stack above pop; the root at one screen returns `false`. The Android key and links belong to the root router alone, which hands the key to the innermost active navigator: a pane under a covering modal is not active. The header's back arrow shows on the first screen of a nested stack navigator when its own screen has one below it (its first back pops it); a pane's base has none.
- Navigators below the root get their routers where their screens render: a pane's is named by its key, a nested navigator's by its node id, the root's by `"root"`. Each navigator screen owns its navigator's state, so two workspaces' tabs do not share stacks.
- Modals, sheets and form sheets belong to the stack of their page: one that must cover the tab bar lives outside the tabs directory.
- The navigation survives an Android Activity that is recreated (a font scale or locale change) and a process that was killed in the background: the root router's state (every stack, every tabs selection, the launch link already opened) is what a hot update keeps. The last surface to stop leaves it for the next one (in release builds too, unless the user is leaving the app), and the router writes it as JSON through the engine module after every change, which `MainActivity` keeps in the Activity's saved instance state and passes back as `initialProps.navigation` (the config plugin patches the generated Activity). A launch link that the restored state was opened with is not opened again; a different one resets. On iOS the `SvelteNavigation` module (`native/svelte-navigation-ios`) keeps the same JSON when the app enters the background and hands it over once at the next start, only if UIKit's own state restoration kept its state (the system deletes it when the user swipes the app away, as Android drops the state of a removed task) and the record is less than a day old; the config plugin patches the generated `AppDelegate.swift` to forward the callbacks Expo's delegate leaves out. The same `initialProps.navigation` path takes it from there. See `native/svelte-engine/SPEC.md`, "Navigation state across recreation and process death".

## Animation

The main entry (`@alfayez/svelte-native`) adapts Reanimated's animated view and shared values (`src/animation.ts`). The host runs `animatedStyle` worklets through Reanimated's mappers (`src/fabric/animation.ts`, `useAnimatedStyle` without the hook); the Svelte component owns the shared value's lifetime.

```svelte
<script lang="ts">
  import { AnimatedView, createSharedValue, withTiming } from "@alfayez/svelte-native";
  let expanded = $state(false);
  const progress = createSharedValue(0);
  const animatedStyle = () => {
    "worklet";
    return { transform: [{ translateX: progress.value * 120 }] };
  };
  $effect(() => { progress.value = withTiming(expanded ? 1 : 0); });
</script>

<AnimatedView {animatedStyle} style={{ width: 48, height: 48, backgroundColor: "blue" }} />
```

Capture plain shared-value handles in worklets. Read Svelte state on the JavaScript side and write the target into a shared value. A worklet cannot read a Svelte signal or proxy on the UI runtime, and the Metro transformer fails the build of a function marked `"worklet"` that does (it would throw "Tried to synchronously call a Remote Function" when the screen mounts). That includes a shared value in a component outside runes mode (a file that opts out with `<svelte:options runes={false} />`, an app that sets `runes: false`, or a Svelte library below `node_modules`): there a variable the markup mutates (`count.value = ...` in a handler) is state even when it is a `const`, so such a component with worklets starts with `<svelte:options runes />`. Components are runes by default ("Runes mode"). Call `createSharedValue` during component initialization; it cancels the current animation when the component is destroyed. Reanimated cancellation is asynchronous. `runOnUIAsync` and `runOnUISync` are available for explicit worklet calls.

Timing, spring, repeat, sequence and delay helpers retain Reanimated's APIs and reduced-motion behavior. `AnimatedView` also accepts Reanimated's CSS animation and transition style keys without a worklet, for example `style={{ animationName: { from: { opacity: 0.3 }, to: { opacity: 1 } }, animationDuration: "400ms", animationIterationCount: "infinite", animationDirection: "alternate" }}`; those run in C++ on the UI thread. On the Samsung, 48 such tiles cost 1.0 ms of UI-thread time per frame versus 2.3 ms for the same motion written as a `useAnimatedStyle` worklet, so prefer CSS keyframes for repeating or decorative motion on Android and keep worklets for values that follow state. This adapter does not expose every Reanimated component, gesture or layout-transition API.

The package's pnpm patch `patches/react-native-reanimated@4.5.1.patch` has two Android parts. (a) A direct path in Reanimated's `NativeProxy.synchronouslyUpdateUIProps`: when a frame update contains only `opacity` and a transform made of `translateX`, `translateY`, `scale`, `scaleX` or `scaleY` in pixels, it is written straight to the Android `View` instead of going through the view manager's prop diff and 4×4 matrix decomposition; rotations, skews, matrices, percentages, a transform origin or any other prop take Reanimated's regular path. (b) For engine views a C++ sink takes the frame's flat command buffers before any Java map is built and makes one JNI call per frame into the engine (`native/svelte-engine/SPEC.md`, "Animated write path"); (a) stays as the fallback. Review the patch when Reanimated changes. Expo's Babel preset configures the Worklets plugin automatically. Reanimated and Worklets require a native host rebuild when added or changed.

The development lab is a set of `/__dev` routes in the example app, present in development and in the QA builds (`io.example.svelteqa`, `io.example.svelteqa.smoke`) and absent from the production variant (`APP_VARIANT=production`: route discovery skips `__dev` directories and `export const lab = true` pages, and Metro stubs the lab's modules). `/__dev` covers state, derived values, effects and disposal, stores, reactive collections, context, bindable props, keyed children, await blocks, boundaries and the animation bridge; `/__dev/screens` and `/__dev/tree` the native screens and the route tree; `/__dev/foreign` the wrapped libraries (a section per library, one per row of the windowed `List`, all of them in a sheet); `/__dev/gestures` the gesture scenarios; `/__dev/smoke` the native module smoke test. Its checks only change local test state. The animation probe deliberately blocks JavaScript for one second.

The lab's **stress** panel is a scenario runner. Every scenario samples UI-runtime frame intervals with a monitor that lives on the UI runtime (`frames.ts`; nothing crosses threads per frame), calibrates the display's frame period first, and passes when at most 1% of intervals exceed 1.5 periods and none exceeds 4 periods (the production bar in `apps/qa/qa/gates.json` is stricter: 0.0 % dropped, none over 33 ms; see PLAN.md). Scenarios: `idle` calibration; `animation-48` (48 Reanimated tiles), `animation-48-square` (no rounded corners), `animation-48-translate` (one animated property) and `animation-48-css` (the same tiles on CSS keyframes) to attribute per-frame cost; `churn-static` and `churn-animated` (32 of 48 views replaced every 250 ms); `list-300` and `list-300-clipped` (mount, programmatic scroll and unmount of 300 rows) and `list-300-virtual` (the windowed `List`); `input-120` (controlled `bind:value` round trips) and `input-typing` (20 s of real keyboard input); `modal-8`; `navigation-8`, `header-8`, `sheet-8` and `tabs-8` (the native screens); `foreign-views`, `smoke` and the nine `gestures-*` scenarios; `churn-60s` (the cleanup verdict: every retired shared value must stop changing after destruction), `soak-120s` and `soak-mix` (heap before and after). Each result is logged as `[Svelte stress] {json}` for adb capture; `pnpm native-qa lab` reads them. These explicit stress controls ignore reduced motion. The screen keeps its device awake until it unmounts.

Where the program stands is in [PLAN.md](PLAN.md) ("Production plan status"); the measurements and traces behind it were kept in the monorepo this repository was extracted from (`.example/native-qa/2026-10-25/`) and are not part of it. Two facts from them matter when writing screens. On Android, repeated decorative motion should be a CSS keyframe or transition style on `AnimatedView` (run in C++ on the UI thread) and not a worklet: 48 such tiles cost 1.0 ms of UI-thread time per frame against 2.3 ms for the same motion as a `useAnimatedStyle` worklet, and the animated-churn scenario (32 animations started every 250 ms) stays above the frame bar on the A16 because of the worklet runtime. And an unvirtualized list of 300 rows still costs one long mount frame (about 70 ms on the Samsung A16, 26 Oct); `List` mounts the rows that fit first.

## SvelteKit modules

The imports of SvelteKit's `$app/*` resolve on the device to files of `src/kit/` (the table is `KIT_MODULES` in `src/kit/modules.ts`, `kitResolution` is what `withSvelteNative`'s `resolveRequest` calls, after the server-only refusals: `$app/server`, `$app/env/private`, `$env/*/private`). The names and signatures are SvelteKit 3's own: each export is declared `typeof Kit.name` against SvelteKit's `declare module` (`import type * as Kit from "$app/navigation"`), so `pnpm typecheck` fails when a signature drifts, and `tests/kit-device.test.ts` compares the exported names with the ones the installed SvelteKit declares. [SvelteKit modules](../../docs/20-core-concepts/60-sveltekit-modules.md) is the guide: what each returns and what is not there.

- **The root router.** `createRouter` with the scope `"root"` registers its router in `appRoot` (a `$state.raw` of `router.svelte.ts`, read by `rootRouter()`) and, when its component is destroyed, takes it out of `liveRoots` (a plain array, oldest first) and makes the newest one left the registration (a source read in a teardown answers with its value from before a write of the same batch, so a surface that starts before another one stops, in one turn, would otherwise be cleared by the stop; with two alive, the newer one's stop falls back to the older). That is how `goto` reaches the router from a timer or a module (`router.goto` plans from the root, whatever navigator it is called on), and how `page` follows it (an effect that reads `page` before the router exists runs again when it does). It is not `connectHost`'s `linkRouter`, which exists for the remote runtime and is set when the `<Router>` mounts. `page` is `rootRouter()?.current` (the deepest entry: through the top screen's tabs and stacks) with SvelteKit's neutral values for what a native screen has no counterpart of; a route's id is `/${route.id}` (the directory under `src/routes`, groups included, which is SvelteKit's). It is the app's top screen, not the reading component's: the screens below the top one stay mounted, so a screen that read its own data from `page` would see the top screen's. A screen uses its `params` and `url` props.
- **`goto`.** The body runs `untrack`ed (the router's `navigate` too, like `prepare`), as SvelteKit's does not track: an effect that navigates must not depend on the stacks it reads. `match` and `preloadCode` are untracked as well. A navigation to the visible screen's own page and path with another search or hash (`inPlace` in `createStore`) sets that entry's `url.search` and `url.hash` (a `SvelteURL`, so its readers update) and adds no screen, whether it replaces or not; a `reset` is not in place, and `prepare` does not prepare one (`commit()` is the `goto`). Relative URLs resolve against the screen on top, as the browser's do; another origin or scheme goes to `Linking.openURL`, as `useLink` does; `replace ?? replaceState ?? false` is the router's `replaceState`. SvelteKit's `reset` (scroll and focus) is not the router's `reset` (a new root, no history) and is ignored. `shallow` and `state` reject because there is no `page.state` to hold them. `preloadCode(id)` finds the route with that id in the tree and calls `router.preload`, which is `load` plus the wait (`loads` in `createStore`). `preloadData` is not mapped: a `load` function's result is what it returns, and a device has none. `router.prepare` is not `preloadData` either: it renders a screen off screen and has a handle to commit or discard, which a fire-and-forget preload has no way to hold.
- **`updated`.** The updates client keeps `pending` (set by every evaluation of the server's answer, a check's and a fetch's, so the check at launch counts) and `onPending(listener)`; `updated.current` reads it through `createSubscriber`, and `updated.check()` runs `checkForUpdateAsync`. `src/updates/instance.ts` is the client that `@alfayez/svelte-native/updates` and `updated` share; `state.ts` requires it on first use, so a screen that only reads `page` does not load it.
- **`mobile` on the web.** `src/web-env.ts` is a Vite plugin (`enforce: "pre"`) that `svelteNative()` adds in the web target. SvelteKit aliases `$app` to its `src/runtime/app` directory and Vite applies an alias before any plugin's `resolveId` sees the import, so the plugin matches both `$app/env` and `…/@sveltejs/kit/src/runtime/app/env` (and the same for `environment`), asks the rest of the chain what it resolves to (`this.resolve` with `skipSelf`), and answers with a virtual module, `\0svelte-native:mobile:<that file>`, that is `export * from "<that file>"; export const mobile = false;`. The import the virtual module makes is let through by its importer. `tests/web-mobile.test.ts` runs `vite dev` and the production build (client and server) of `tests/fixtures/web-mobile-app` and type-checks it. The type is `src/kit/modules.d.ts`, a script of `declare module` that merges with SvelteKit's; a program reaches it through the `/// <reference>` in `src/vite.ts` (the web's, through `vite.config.ts`) and in `src/router.svelte.ts` (the device's, through the router every screen's imports reach). SvelteKit 3 no longer declares `$app/environment`, and the declaration makes it `export * from "$app/env"`.
- **`svelte/motion` and `MediaQuery`.** Svelte builds `prefersReducedMotion` from `new MediaQuery(...)` as `svelte/motion` loads, and `MediaQuery` calls `window.matchMedia(...)` and listens with `svelte/events`' `on(q, "change", update)`. React Native has no `matchMedia`, so `polyfills.ts` installs one when it is absent (`/app` runs the polyfills before the Fabric host and so before any screen's code): a function that `require`s `match-media.ts` on its first call, so the boot loads and reads nothing of it (`tests/boot-graph.test.ts` fails when a static import reaches `match-media.ts` or `media-query.ts`; `tests/match-media.test.ts` counts the system reads). With it, `svelte/motion` is Svelte's own module: Metro has no rule for it (it used to resolve to `kit/motion.ts`, which stubbed `matchMedia` for the one call that loaded Svelte's and replaced `prefersReducedMotion` with a hand-made reader of `AccessibilityInfo`), and `tests/kit-motion.test.ts` runs Svelte's `prefersReducedMotion` through the polyfill. A module that loads `svelte/motion` before `polyfills.ts` has run throws `window.matchMedia is not a function` (the first test of that file); the generated entry imports `/app` first, so no screen or library does.
- **`window.matchMedia`.** `media-query.ts` is the evaluator, pure: `parseMediaQuery(text)` tokenizes once and gives `media` (a browser's serialisation: lower case, `(min-width: 600px)`, `(400px <= width < 700px)`, a query it rejects as `not all`), `sources` (which system sources its features read) and `matches(state)` for a `MediaState` (`width`, `height`, `screenWidth`, `screenHeight`, `scale`, `colorScheme`, `reducedMotion`, `highContrast`, `invertedColors`, `reducedTransparency`; a device gives it getters, so a query reads only the fields it needs, and `and` and `or` stop at the first part that decides). It is Media Queries 4's grammar: a list (comma is `or`), `not`, `only`, a media type (`all` and `screen` match), `and`, `or`, parentheses, `(feature)`, `(feature: value)`, `min-`/`max-`, and the range syntax. A condition is true, false or unknown (`Truth`: `null`), as in the specification. A parenthesis that starts with a name `FEATURES` (a `Map`, so `constructor` is not one) does not have, or has a value the feature does not take, a range shape with an unknown feature, and a function token (`foo(…)`, `not(…)`) are `<general-enclosed>`: unknown. `not` leaves unknown, `and` is false when any part is false and unknown when none is false and one is unknown, `or` is true when any part is true and unknown otherwise, and a query matches when it is true, so `(foo: bar) or (min-width: 1px)` is true and `not (foo)` false (`tests/media-query.test.ts`). What is not a condition (`()`, `(: 400px)`, an unbalanced parenthesis, `screen and`) makes the comma-separated query `not all`. `media` is `not all` for a query with an unknown condition and no feature the device knows that is not true (`context.known` and `context.unknown` of the parse; `matchMedia("(foo)").media === "not all"` is how pages detect a feature), and the text of the query otherwise (an unknown condition keeps its text, lower-cased and spaced). Values: lengths take `px`, `em`/`rem` (16px), the absolute units, `vw`/`vh`/`vmin`/`vmax` of the window (a `Value` is a function of the state, with the source it reads) and negative numbers; `color-gamut` has an `order` (a wider gamut matches the narrower names) and the device's is `srgb`. Nesting is limited to 32 levels so nothing throws. `match-media.ts` is the device: `MediaQueryList` (`matches` is read each time; `media`; `onchange` is an entry among the listeners, in order; `addEventListener("change")` with `once` and `signal` (an aborted signal adds nothing; an abort or the removal of the listener takes the other off), `handleEvent` objects and no duplicates; `addListener` and `removeListener`; `dispatchEvent`; an error in a listener goes to `setTimeout(() => { throw })` and does not stop the others) and `MediaQueryListEvent` (`matches`, `media`, `target`; Svelte's `on` reads `composedPath` and `target`). The system sources are shared: `Source` adds its native listener (`Dimensions`' `change`, `Appearance.addChangeListener`, `AccessibilityInfo`'s `reduceMotionChanged`, `darkerSystemColorsChanged` on iOS and `highTextContrastChanged` on Android) with its first list and removes it with its last, and a list holds its sources only while it has a listener, so `createSubscriber`'s teardown leaves nothing behind. A list fires `change` only when `matches` differs from the last event (or the value when the first listener came). The four accessibility settings (`prefers-reduced-motion`, `prefers-contrast`, `inverted-colors` with `isInvertColorsEnabled()`, `prefers-reduced-transparency` with `isReduceTransparencyEnabled()`, which Android answers `false`) are `Setting`s: false until `isReduceMotionEnabled()` (or `isDarkerSystemColorsEnabled()` / `isHighTextContrastEnabled()`) answers, asked when a list is made, when one starts to listen and when one is read with nobody listening (one question open at a time); an answer older than an event is dropped. The renderer's `addEventListener` and `removeEventListener` hand a target that is not a `NativeNode` (the `MediaQueryList` that `on(q, "change", …)` is given inside a component, where Svelte calls the renderer's) to the target's own methods; without that a component's `MediaQuery` throws on `node.listeners` (`tests/match-media-svelte.test.ts`).

## Web APIs

`fetch`, `Headers`, `Request`, `Response`, `Blob`, `File`, `FileReader` and `FormData` are the library's own on the device (`src/fetch/`), over the native module `SvelteFetch` in `native/svelte-core` (URLSession on iOS; on Android a private client derived from React Native's shared OkHttp client, with its own `JavaNetCookieJar` over `ForwardingCookieHandler`, so cookies are Android's `CookieManager`, as React Native's networking has them). `src/fetch/native.ts` is the contract both platforms implement: `NativeBlob` (immutable segments of memory or file ranges; `slice` and joins share them), `NativeRequest` (`start` resolves the head; one of `read`, `arrayBuffer`, `text`, `blob` takes the body; `cancel`; release by the garbage collector cancels), `blobFromURI`, `revokeObjectURL`, and the error codes. Bytes enter JavaScript only through an ArrayBuffer native code allocated. `polyfills.ts` installs the eight names as getters; the first read of any settles all of them through `fetch/install.ts`, which keeps what the runtime installed when the module is absent. `fetch/xhr.ts` wraps `XMLHttpRequest.prototype.send` on activation so React Native's XHR sends one of the library's Blobs as `{ uri }` and deletes the object-URL files it made at `loadend`. Host checks: `tests/fetch/` (the JavaScript layer over `fake-native.ts`, real HTTP against `tests/fetch/server.ts`), `native/svelte-core/android/src/test/run.sh` (the Kotlin classes against the same server, and a 64 MiB-heap JVM for large bodies). Device checks: the showcase's Web APIs screen with `?checks=<origin>`.

`crypto`, `localStorage` and `sessionStorage` are globals the device has because every app needs them, with the web's semantics on top of a native system. `polyfills.ts` defines each as an accessor (`defineLazyGlobal`, `lazy-global.ts`) unless the platform or a library has defined the name already: until the first read nothing loads, no Nitro module starts and no file is created (`tests/boot-graph.test.ts` fails when a static import reaches react-native-quick-crypto, react-native-mmkv or the Nitro runtime; `tests/web-apis.test.ts` counts what loads and when, against fakes of both libraries). The first read makes the value and replaces the accessor with it, an ordinary writable property, so a library that assigns its own `crypto` afterwards wins.

- **`crypto`** (`web-crypto.ts`) is `{ getRandomValues, randomUUID, subtle }` from react-native-quick-crypto 1.1.3: OpenSSL behind a Nitro module, the library's own Web Crypto implementation. Only `crypto` is defined. The library's `install()` (which also sets `Buffer`, `process` and the base64 globals) is not called. Evaluating the library does two things outside its exports, which the first read of `crypto` triggers and nothing here can avoid: it sets `process.nextTick` to `setImmediate` when there is none (for its asynchronous calls), and its Buffer imports react-native-quick-base64, which defines the globals `base64FromArrayBuffer` and `base64ToArrayBuffer` when it loads (seen on an emulator: `Buffer` stays undefined). A failure to load it throws with the fix (`svelte-native doctor`, then rebuild). Metro resolves `crypto` and `node:crypto` to react-native-quick-crypto (`NODE_CRYPTO` in `metro.ts`), from the app's `package.json` and through the rest of the resolver, so a library written for Node gets the Node API (`tests/metro-crypto.test.ts`). `LITE_ORIGINS` lists the four packages, so their import of `react-native` is the lite shim and the React Native index and the React layer behind it stay out of the bundle; the test reads the packages' sources and checks that the shim exports every name they import.
- **`localStorage`** (`web-storage.ts`, `local-storage.ts`) is a `Storage` over an MMKV instance with the id `svelte-native.local-storage` (react-native-mmkv 4.3.1). `createStorage(backend)` makes the object: `getItem`, `setItem`, `removeItem`, `clear`, `key` and `length`, keys and values passed through `String()`, a missing argument a `TypeError` (WebIDL's message), `key(n)` an unsigned long, and a `Proxy` for the named properties as a browser's storage has them: a key is a property (`storage.theme`, assignment, `delete`, `in`, `Object.keys`, `JSON.stringify`) unless its name is a member or comes from `Object.prototype`, which then stays the member; a write to any string name is an item (`storage.length = 5` stores the item "length"). Symbols are ordinary properties. Nothing reads `this`, so a detached method works. The MMKV instance is created, and the library required, when `localStorage` is first read (`typeof localStorage` included). On a binary without the native libraries (an over-the-air update onto an older build) the first read of `crypto` or `localStorage` is `undefined`, with one `console.warn`, and a later read tries again, so a feature probe takes its fallback instead of throwing. MMKV refuses an empty key, which a browser does not, so the empty key is stored as a NUL character and a key that starts with one gets another in front of it (`encodeKey`). Values written through `localStorageMMKV()` as numbers, booleans or bytes read as `null` from `getItem`. There are no `storage` events and no quota.
- **`sessionStorage`** is the same `Storage` over a `Map`: the app's process, as a tab's is a tab.
- **`@alfayez/svelte-native/mmkv`** (`mmkv.ts`) re-exports `createMMKV` and the types `MMKV`, `Configuration` and `Mode` from react-native-mmkv, and `localStorageMMKV()`, the instance behind `localStorage` (one instance, created on the first call). Importing the entry loads react-native-mmkv; the main entry and the primitives export none of it, so an app that does not use it does not load its types (`tests/exports.test.ts`, `tests/type-budget.test.ts`). On the web, the web target of `svelteNative()` puts React Native web's `.web.js` extensions in front of Vite's (`webExtensions` in `vite.ts`), so the entry builds with react-native-mmkv's web implementation (its data is in the browser's `localStorage`, under keys that start with the id) and without React Native or Nitro; without them Vite stops at React Native's Flow source (`tests/web-mmkv.test.ts` builds both ways). The four packages are required peers: `svelte-native init` installs them, `svelte-native doctor` checks the versions and that each is a dependency of the app itself (React Native's autolinking links only those).

## Foreign views

`@alfayez/svelte-native/foreign` mounts views other native libraries own inside the engine's tree (design and measurements in `native/svelte-engine/SPEC.md`, "Foreign views"). The components mount the native view by its Fabric name and port what the library's React code does before it; none imports the library or React.

```svelte
<script lang="ts">
  import { ExpoImage, BlurTargetView, ExpoBlurView, BlurView, LinearGradient, Video, LottieView, DateTimePicker, openDatePicker, WebView, MapView, Marker } from "@alfayez/svelte-native/foreign";
  import { Pdf, ViewShot, captureRef, Rive, ConicGradient, ShadowedView, shadowStyle, AnimateableText } from "@alfayez/svelte-native/foreign";
  import { ExpoView, defineExpoView } from "@alfayez/svelte-native/foreign";
</script>
```

The entry also holds the views of three libraries that the engine mounts through React Native's own mounting (SPEC "Foreign views"): `WebView` (react-native-webview: `source`, `onMessage`, `originWhitelist`, `onShouldStartLoadWithRequest` and the library's other events; `ref` gives `injectJavaScript`, `reload`, `postMessage` and the other commands), `MapView` and `Marker` (react-native-maps: children mount after `onMapReady`, `getCamera` goes through the library's module, and a Google Maps key is needed to draw tiles) and `VideoView` (expo-video: `player`, `surfaceType`), `ForeignView` for any other Fabric component by name and, for the views of Expo modules, `ExpoView` and `defineExpoView` (below). A touch inside a foreign view goes to the view, not to JavaScript; `pointerEvents="box-only"` keeps the touches of its frame for JavaScript.

**Any Expo view.** `ExpoView` mounts the native view of any Expo module by name, and `defineExpoView` makes a typed component of one. Both do what Expo's own React adapter (`NativeViewManagerAdapter` in `expo-modules-core`) does, without React: the view's props and events are the ones the native module reports (`expo.getViewConfig`), a shared object is given as its id, and the module's functions for the view are on the `ref` handle. Nothing of the library's JavaScript runs, so a library whose React component changes its props or events first (`expo-camera` maps `flash` to the native `flashMode`; `expo-linear-gradient` converts its colours) is mounted with the native names and values; its dedicated component, where there is one, does that step.

| | |
|---|---|
| `<ExpoView module view … />` | `module` is the native module's name (the first argument of `requireNativeViewManager`); `view` is the view's name when the module has several, and is left out for its only view. Every other prop goes to the view: the props the module declares and the `ViewProps` (`style`, accessibility, ...). A name the view does not declare is dropped, as for every foreign view. `module` and `view` are the component's, so a native prop of either name cannot be set. Another `module` or `view` is another native view. |
| props | A prop whose value is a shared object (an object with a numeric `__expo_shared_object_id__`, such as an `expo-video` player) is given as that id. Only a top-level prop is converted; a number, a string, a plain object and a function are as given. Nothing else is converted: Expo's native side reads colour strings itself. |
| events | An `on…` prop is the handler of the event of that name in the view's config (`onMountError` for `topMountError`), called with React Native's event object, `{ nativeEvent: payload }`, as it is for a React component of the view. |
| children | Mounted inside the native view by React Native, as for the other foreign views. |
| `ref` | Receives the host handle (`HostHandle`: `tag`, `measure`, `measureInWindow`, `dispatchCommand`, ...) with the functions the module defines for the view (`ViewPrototypes`), called as methods; their `this.nativeTag` is the handle's `tag`. `nativeTag` is also what lets the handle be passed to a module function that takes a view. A function of the view wins over a host method of the same name; a module that defines none gives the host handle alone. It is one object for the view's life (the host calls `ref` again only when the prop changes), and `ref` hears `null` when the view is unmounted. |
| `defineExpoView<Props, Methods>(module, view?)` | A component that is `ExpoView` with `module` and `view` fixed (a `module` or `view` prop is ignored). `Props` is the library's props type, with `children` as a `Snippet` and `ref` as a function of `ExpoViewHandle<Methods> \| null`, where `Methods` types the view's functions (an Expo library's own `…Ref` interface, where it has one); `style` and the handlers keep the library's types, which are the native ones when the library's React component converts them. Calling it reads nothing native, so it is safe at the top of a module; the view's props are as reactive as any component's. |
| errors | A module or view the build does not have throws when the view is mounted: `Expo module ExpoCamera has no view: the native module is not in this build, or it declares no such view. Install the library (npx expo install) and rebuild the native app.` (`has no view Name` when a view was named). |

`tests/foreign-expo-view.test.ts` runs the component against the fake Fabric binding with a made-up module; the module's view functions on a device are not yet run.

**Events on Android.** React Native's `Event.canCoalesce()` is `true` unless an event class overrides it, and `EventQueue::enqueueEvent` then replaces an unread event of the same name from the same view with the next one while JavaScript is busy. For a stream (a progress tick, a region per camera frame) that is what is wanted; for a message a handler must see once, it loses the event. The repository patches four libraries so that their non-stream events do not coalesce: `react-native-pdf@7.0.3` (its one `topChange` event: `onLoadComplete` was overwritten by the `onPageChanged` posted 10 ms later), `react-native-video@6.19.3` (a `coalescable` flag on `VideoCustomEvent`, true for `onVideoProgress` and `onVideoBandwidthUpdate` only), `lottie-react-native@7.3.8` (`onAnimationFinish`, `onAnimationLoaded`, failure; the same patch carries the iOS change) and `react-native-maps@1.27.2` (21 of the 26 event classes; the five streams keep coalescing). `rive-react-native` needs no patch: its events go through React Native's interop emitter, whose events have surface id -1 and are never coalesced. The price of a patch is that JavaScript is told of every message of such an event. The patches are `patchedDependencies` of this repository's `pnpm-workspace.yaml`, so an app outside it must carry them; `tests/foreign-libraries.test.ts` reads each installed package (and, for Rive, React Native's sources) and fails when a version no longer has the shape the decision was made for. The development lab has a busy-JavaScript check per library (`apps/qa/src/lib/native/dev/foreign-race.ts`, `runRace`) that holds the JavaScript thread while the native side raises two messages and fails on an unpatched copy for pdf, video and Lottie. iOS sends these events through `dispatchEvent`, never the queue's unique path, and cannot lose them. Mechanism with line numbers: `native/svelte-engine/SPEC.md`, "Foreign views", "Events on Android".

## Gestures

The main entry puts react-native-gesture-handler (RNGH 2.32, the version Expo SDK 57 pins) on Svelte views: its native recognisers and arbitration unchanged, its `Gesture.Pan()`/`Tap()`/`Pinch()`/`Rotation()`/`Fling()`/`LongPress()`/`Native()`/`Manual()` builders and `Race`/`Simultaneous`/`Exclusive` reused as they are, and the React `GestureDetector` replaced by a host module (`src/fabric/gestures.ts`, the way `animatedStyle` is handled). The app wraps nothing. Gestures need a native host rebuild (the package is autolinked); the lab and device acceptance are `native/svelte-engine/SPEC.md`, "Gestures (react-native-gesture-handler)".

```svelte
<script lang="ts">
  import { AnimatedView, Gesture, createSharedValue, withSpring } from "@alfayez/svelte-native";

  const x = createSharedValue(0); // first: it loads Reanimated, so the worklets below capture the real withSpring
  const pan = Gesture.Pan()
    .onUpdate((e) => { x.value = e.translationX; }) // UI thread: an inline callback of a Gesture.X().onY(...) chain is a worklet
    .onEnd(() => { x.value = withSpring(0); });
</script>

<AnimatedView gesture={pan} style={{ width: 96, height: 96 }} animatedStyle={() => { "worklet"; return { transform: [{ translateX: x.value }] }; }} />
```

- **Where.** `gesture={g}` on `View`, `Pressable`, `ScrollView`, `AnimatedView`, `Image`, `Text` and the `native-*` host tags; removing it (or `undefined`) detaches. `<GestureDetector gesture={g}>` is a `View` that carries it (one extra view, for React Native code and for children that do not forward attributes), and `use:gesture={g}` is the same attribute as an action on a host tag or a lowered primitive. The view keeps its own native view: `collapsable` is forced to `false` (`collapsable={true}` warns in development).
- **Threads.** A gesture whose callbacks are all worklets, without `.runOnJS(true)`, runs on the UI thread: Reanimated runs the callbacks (`WorkletEventHandler`, keyed by the view's tag) on the frame of the touch, so a busy JavaScript thread does not stall them. Any plain callback, or `.runOnJS(true)`, puts the whole gesture on the JavaScript thread (events through `RCTDeviceEventEmitter`), where callbacks read live Svelte state. Mixing is an error in development, as in RNGH. `GestureStateManager` (the second argument of `onTouches*`) works in worklet callbacks only. `runOnJS` and `scheduleOnRN` are exported from the entry and from `/animation`.
- **What a UI callback can capture.** SharedValues, numbers, strings, plain objects, other worklets and functions (called through `runOnJS`). **Not `$state`, `$derived` or `$props`**: Svelte compiles those reads into `$.get(signal)` and `$$props.x`, so the closure holds Svelte's namespace and the signal. Development builds check `__closure` of every UI callback when a gesture attaches or updates and throw naming the callback, the variable and the fix (copy it into a `createSharedValue`, or `.runOnJS(true)`). Release builds do not check. `import { Gesture as G }` or a callback held in a variable is not marked as a worklet by the Babel plugin; development warns that none of the callbacks are worklets.
- **Relations** (`simultaneousWithExternalGesture`, `requireExternalGestureToFail`, `blocksExternalGesture`, the compositions) work across components by handler tag: a gesture that mounts later sends the relations of the handlers that name it again. One gesture object drives one view; a second view that uses it throws RNGH's message (`Handler with tag N already exists. ...`).
- **Load order.** A worklet that captures `withSpring`, `runOnJS` and the like from `/animation` before Reanimated loads captures a stub; the first `Gesture` property read loads Reanimated and the builders, so a chain is safe, and a helper worklet above the first `Gesture` or `createSharedValue` call is not.
- Not supported: RNGH's components (`PanGestureHandler`, `Swipeable`, `ReanimatedSwipeable`, `DrawerLayout`, the buttons and touchables, `GestureHandlerRootView`), `Animated.event` with the native driver, `Gesture.ForceTouch`, the web, and `GestureStateManager` on the JS thread. A view that only carries a gesture is not an accessibility action: things that activate must be a `Pressable` or declare accessibility actions.

`bun test tests/gestures` covers it without a device: the native call sequences of RNGH's own detector for twelve gesture shapes (`tests/gestures/golden`, captured by `capture-golden.mjs`) against the host's, the JS receiver and the ported UI worklet against RNGH's `onGestureHandlerEvent` on the same event sequences, lifecycle (mount, update, reattach, detach, hot remount, 200-round churn), the guards, the real Babel transform on `.svelte` fixtures, the import graph and `svelte-check` on every builder method.

## Remote functions

The guide is [README](README.md#remote-functions); this is the map. SvelteKit's version is 3.1.1 (`peerDependencies`); every file named `kit/…` is `node_modules/@sveltejs/kit/src/…`.

### From a `*.remote.ts` to a call

1. Metro bundles `src/lib/x.remote.ts`. The transformer (`transformer.ts`, `sourceOf`) does not compile it: `remote/transform.ts` reads its exports and kinds (`@babel/parser`) and returns `import * as __remote from "@alfayez/svelte-native/remote/runtime"` plus `export const name = __remote.<kind>("<hash>/<name>")` for each export (`kit/exports/vite/plugins/remote.js`, the client branch of `transform`, builds the same module; reserved-word names are aliased as `create_exported_declarations` does). The hash is `hash(posix(relative(projectRoot, file)))` (`kit/utils/hash.js`, djb2, base 36). Anything the module imports (`$app/server`, the database) is never read.
2. `remote/runtime.ts` exports the six functions the stubs call. `query`, `query_batch`, `query_live`, `command` and `prerender` are SvelteKit's, wrapped in a `Proxy` that checks the environment and the host before each call (`RemoteConfigError`); `form` is `remote/form.svelte.ts`.
3. SvelteKit's files make requests with `fetch` and URLs like `${base}/${app_dir}/remote/${id}`. `fetch` there is `remote/globals.ts`'s: the path becomes `<origin><path>`, `credentials: "include"`, `Origin` on non-GET requests to the origin, the global `fetch`, read at each call: the library's own, or Expo's on a binary without `SvelteFetch` (or `configureRemote({ fetch })`).

### The native form

Instance: `method`, `fields`, `result`, `error`, `pending`, `submitted`, `submit()`, `reset()`, `preflight(schema)`, `validate({ all, preflightOnly })`, `enhance(callback)`, `for(key)`. Not present: `action`, `element`, the attachment symbol.

- `fields` nodes: `value()`, `set(value)`, `issues()`, `allIssues()`, `touched()`, `dirty()` are SvelteKit's `create_field_proxy`; `as(type, …)` is native (README table). Typing in an input marks the field dirty; leaving it marks it touched and, if it was edited, validated from then on; `set()` marks all three (as an attached form does).
- `as()` makes one *variant* per input (field, type and, for a radio or a list of boxes, option): its props, once, with a `ref` the host calls with the handle when the input is built and `null` when it is gone (the package's `ref` contract), the value it shows, and what it contributes to a submission. The props object is the same each call, so the host sees the same functions each render.
- A submission carries a copy of the fields at the moment `submit()` is called, made as a browser posts a form (`convert()`): what was set or typed, also for a field none of whose inputs is on screen any more (a virtualized `List` unmounts the rows that scrolled away, a closed `Modal` its inputs: that is not the user taking a value back); plus, where nothing was typed and an input is on screen, what the inputs on screen show (text: the string, `""` for none; number: the number, `undefined` for none; a checked box: `true`, an unchecked one is left out; a list of boxes: the checked ones in the order they were made, none checked is no field; radios: the chosen option, none is no field; select: the choice or its default, else the first option; hidden: the value). `.for(key)` adds `id: key`. The body is the binary form SvelteKit parses (`BINARY_FORM_CONTENT_TYPE`); a file field's `File`s are in it as SvelteKit lays them out (metadata in the header, bytes after it, the smallest first). A submit button's value is in the data only while it is the one pressed last (pressing another takes the previous one out, as `previous_submitter` does).
- `submit()` calls `assertReady()` (a missing host throws at the call), then with no `enhance`: `send` (preflight, request, issues and result from the response, `redirect` to `goto`, `refreshAll` unless `.updates(...)` or the server refreshed) and, if accepted, `reset()`. With `enhance(callback)`: preflight, then `callback(form)` where `form.submit()` sends the data taken when the submission began; no reset. `pending` covers the preflight and the request. Whatever fails (the data, the callback, the request) is handled and resolved `false`, and `pending` is undone once whatever happens: `handle_error(caught)` (the app's `handleError`; if that throws, it is logged and `form.error` is a plain 500), `form.error` is the `App.Error`, `result` and the issues are cleared (as `send`'s catch does), and `set_nearest_error_page` (a no-op: there is no page to replace).
- A submission that fails on issues (the preflight's or the server's) focuses the first input, in the order the inputs were made, that has an issue, is on screen and whose host handle has `focus()` (after a `tick()`, and not if `reset()` came meanwhile); validation alone never moves focus. `reset()` invalidates a preflight or validation in flight (`reset_id`, `validate_id`), so its issues do not come back; a request already sent is not cancelled, and its response still sets `result` and the issues. An input whose host is replaced keeps the newest host's handle (the renderer gives the new host its handle before it sweeps the old one's `null`). `validate()` of a form with files sends them (the validate-only body is the same binary form), as SvelteKit's does.
- A number is `parseLocalizedNumber(text)` (`remote/number.ts`): strict, in full, `NaN` for text that is not a number (and for the one shape that is a thousands mark and a decimal mark at once: one to three digits, a lone comma, three digits), `undefined` for none.

#### Where this differs from SvelteKit's client, on purpose

1. No `<form>`: no `action`, `element` or attachment; `enhance`'s instance has no `element`; the DOM events (`submit`, `input`, `focusout`, `reset`) are `submit()`, the props' handlers and `reset()`.
2. No file picker: `as("file")` and `as("file multiple")` give `value`, `multiple` and `onValueChange` for a picker of the app's, which passes `File`s (anything else throws a `TypeError`); `as("image")` throws.
3. `submit()` is the submit event, not the programmatic `instance.submit()` of an attached form (which skips `enhance` and the reset); there is no equivalent of the latter. `reset()` and `error` are additions.
4. A failed submission is resolved `false` and shown in `form.error`, not thrown; there is no error page, so `set_nearest_error_page` does nothing.
5. The values come from the props (`as`) and `set()`, not from a DOM mirror; what is submitted is computed from the inputs on screen as a browser's `FormData` would be (above), so a checkbox's `value()` is `false` while the post leaves the field out.
6. Numbers are read strictly and from Arabic digits (`number.ts`); a browser's number input cannot hold text that is not a number, a `TextInput` can, and it is `NaN`.
7. Issues are ordered by the order the fields were first rendered (SvelteKit's is the DOM's); DOM-only dev warnings (`warn_on_missing_issue_reads`, the `$` field name and `enctype` checks) are not ported.
8. A select has no option list of its own: `as("select", initial, options)` takes the starting choice; `radio`, `checkbox` and `select` props are for a `Switch` and a picker of your own, and `"submit"`'s props for a `Pressable`.
9. `form.for(key)` outside an effect is not remembered between calls (as in SvelteKit's, where the `$effect.pre` that remembers it also throws there).
10. The request goes through the transport of this package (README): the configured origin, `Origin` on non-GET requests, the platform's cookies, `redirect: "error"`, the global `fetch`; `x-sveltekit-pathname` is the router's URL (a native route, not a web route).
11. Outside the form: `refreshAll()` refetches queries and reconnects live ones (no `load` functions); `page.url` is the router's; `prerender` has no Cache API; no server-rendered payload exists to hydrate from; `navigator.onLine` is `true` and the page lifecycle events are the app's foreground and background; the query cache is released by the effect that made the object (Hermes 0.17 has no `FinalizationRegistry`), and an object used afterwards makes SvelteKit's again; a redirect to an address that is not `http:` or `https:` and not a route of the app is refused; `__SVELTEKIT_DEV__` is `false`.

### Environment

Nothing is installed on `globalThis`. `remote/environment.ts` holds stand-ins and `remote/globals.ts` hands them, with the engine's own where it has them, to SvelteKit's files as module-scoped names the transformer imports into them (`SHADOWS`): `btoa`/`atob` (the engine's own; Hermes 0.17 has them), `WeakRef` (the engine's own; one that holds strongly otherwise) and `FinalizationRegistry`. `assertEnvironment` names a missing `ReadableStream`, `TextEncoder`, `TextDecoder`, `AbortController`, `Headers`, `URL` or `URLSearchParams` (Expo SDK 57 installs them: `expo/src/winter` and the streams polyfill Expo's Metro adds).

Hermes 0.17 (React Native 0.86) has no `FinalizationRegistry`, which SvelteKit's query cache is built on (`kit/runtime/client/remote-functions/cache.svelte.js`: an entry is freed when its last query object is collected). `makeFinalizationRegistry(engine)` is the registry SvelteKit's files get. With no engine registry it keeps a `WeakRef` per target and a timer (`SWEEP_MS`, 3 s, only while something is registered, stopped while the app is in the background and run once when it comes back) calls the cleanup of the targets that were lost; with one it wraps it. Either way `unregister` works and `releaseNow(target)` runs a target's cleanup at once, once, and the engine's callback for that target then does nothing (so an entry is not released twice). `owned.svelte.ts` (`ownedQuery`, applied to what `query`, `query_batch` and `query_live` return) calls `releaseNow` from a `$effect.pre` teardown, so the effect that made a query object (a component, or an expression that runs again for another argument) frees its cache entry and closes its stream deterministically. The object it returns is a `Proxy` over SvelteKit's, so that an object used after its entry was freed makes SvelteKit's again from the same call (every string-named property and the async iterator re-acquire; the identifying symbols `updates()` reads do not) and is owned by the effect then running. A cleanup that throws is logged and does not stop the sweep.

## Renderer

Mounting is not free: Svelte's runtime (components, effects, host nodes) runs before the host builds the Fabric payload. Lowered `View`/`Text` rows cost about the JavaScript time of raw host tags (82–83 ms against 78 ms for 300 rows on the Samsung SM-A165F, 25 October 2026, against 125–134 ms before lowering). Keep unvirtualized lists short, paginate, or use `List`, whose first window mounts in 10 to 15 ms on the A16 and 5 to 6 ms on the iPhone SE 3 (PLAN.md).

A primitive that is not lowered (see "Primitive lowering") is one Svelte component (`View`, `Text`, …) that renders a literal host tag such as `<native-view>` with a `nativeProps` attribute, so a list row costs five host nodes (element, anchor, element, anchor, text) rather than the seventeen of a two-layer design; a lowered primitive is the host tag itself, with no component instance. `Host.svelte` (exported as `Native`) keeps the dynamic-tag form. The custom renderer keeps each host node's children in a doubly linked list, so Svelte's inserts, keyed moves, removals and sibling queries are O(1). Every change reaches the host through one invalidation sink (`setInvalidationSink`), which marks the node dirty and commits all dirty nodes in one Fabric transaction per root in a microtask, after the Svelte flush that produced them; a node rebuilds its immutable snapshot lazily when the host reads it. Event handlers reach the host as one stable dispatcher per event type, so native props keep their identity between flushes. `bun test` in this package covers these operations directly and through compiled Svelte components.

### Fabric host

`src/fabric` drives React Native's Fabric shadow tree directly from the Svelte renderer through the `nativeFabricUIManager` binding, with no React reconciler. `createFabricApp(App, props)` registers the `AppRegistry` runnable React Native's `runApplication` calls; `svelte-native sync` writes the entry that calls it, importing it from `@alfayez/svelte-native/app` (which runs `init.ts` and `polyfills.ts` first, in that order, and exports `createFabricApp`, `remountSurfaces`, `showError`, `fabricStats` and `flush`) (`SVELTE_NATIVE_ROOT=<path>` makes another component the root, for spikes). Mapped tags (`viewNames` in `src/fabric/host.ts`): `native-view`, `native-pressable`, `native-animated-view`, `native-keyboard`, `native-stack`, `native-screen` → `RCTView`; `native-safe-area` → `RCTView` on Android, `RCTSafeAreaView` on iOS; `native-text` → `RCTText`/`RCTVirtualText`; `native-scroll` → `RCTScrollView` with a `collapsable: false` content container; `native-input`, `native-switch`, `native-spinner`, `native-image` and `native-modal` → the platform's text input, switch, progress bar, image and modal views. On Android the transaction is mounted by the package's own engine (typed Kotlin views instead of React Native's Java mounting, `native/svelte-engine/SPEC.md`); on iOS React Native's mounting is kept. Views other libraries own are mounted by React Native inside the engine's tree ("Foreign views"). `bun test tests/fabric.test.ts` runs the host against a fake binding.

Press handling in the Fabric host: any node with `onPress`, `onPressIn`, `onPressOut`, `onLongPress` or `onPressChange` becomes a gesture responder (`src/fabric/responder.ts`) driven by a port of React Native's `Pressability` (`src/fabric/pressability.ts`), so `<Pressable>`, `<Text onPress>` and a `<View onPress>` behave as in React Native: the innermost enabled node takes the touch, a native scroll steals it through `topTouchCancel`, and `hitSlop`, `pressRectOffset`, `delayLongPress` (500 ms), `delayPressIn`, `delayPressOut`, `minPressDuration` (130 ms), `cancelable` and `disabled` apply. Handlers receive `{ nativeEvent, target, currentTarget }`; `onPressIn`/`onPressOut` pair with a delayed `onPressOut` exactly as React Native does, so a quick tap calls `onPress` before `onPressOut`. `onPressChange(pressed: boolean)` is a Svelte convenience: it is called with `true` when the press becomes active and `false` when it ends, so a component can keep `let pressed = $state(false)` and render a pressed state. Custom `onStartShouldSetResponder`, `onMoveShouldSetResponder` (and `...Capture` through `nativeProps`, because Svelte treats a `Capture` attribute suffix as an event option), `onResponderGrant/Move/Release/Terminate` and `onResponderTerminationRequest` attributes are honoured. `bun test tests/responder.test.ts` covers it.

### Primitive lowering

Metro's transformer runs `src/lower.ts` over every `.svelte` file before the Svelte compile. A file that imports `View`, `Text`, `ScrollView`, `Image`, `ActivityIndicator` or `Pressable` from `@alfayez/svelte-native` (or a subpath, with or without `as` aliases) has those tags rewritten to the host tags `native-view`, `native-text`, `native-scroll`, `native-image`, `native-spinner` and `native-pressable`, so a row costs host nodes only, with no component instance per primitive. Attributes, spreads, `ref`, `class`, `id` and children are carried over unchanged, except `bind:this`, which becomes `ref={__svelteNativeBind(set, get, keys)}` (`hostBind`, boxed with `hostValue` next to a spread; see "`ref` and `bind:this`" below): Svelte's custom renderer refuses `bind:` on a host tag, and what the host gives an element is the handle a `ref` takes (`measure`, `focus`, ...), not a DOM node. Self-closing tags become paired tags. Nothing else in the file changes, and the file keeps its number of lines, each construct on the line it was (columns shift on lines holding a lowered tag; no source map is produced). The line breaks of a source that the lowering moves go with it, and what it has to write twice (the setter and the getter of a `bind:this` target, the toggles of `class:` directives that a spread repeats, the style a `<View>`'s class is resolved against) is written on one line, so a copy adds none; a copy of an expression that has a comment (a `//` in a string is not one) or a template literal with a line break in it cannot be put on one line (`oneLine`), and then the lines below it move. A `<View>`'s style is copied only if it is a plain read (no call, which would run twice). The main entry's SVG elements named like primitives are `SvgText` and `SvgImage`, which are not primitives and are never lowered.

Left as components: `TextInput`, `SafeAreaView` (padding from the insets store), `Switch`, `Modal`, `AnimatedView`, `KeyboardAvoidingView`, `<svelte:component>`, local components that share a name, and any primitive tag using `let:`, a `bind:` other than `bind:this`, a `children` attribute, a snippet declared inside the tag, or (for `Pressable`) a `style` that is not an object literal or plain text. `transition:`, `in:`, `out:` and `animate:` on a lowered tag stay on the host tag, which plays them (see `fabric/transitions.ts`); a `use:` action other than `use:gesture` is passed through and reported with a warning. Files that do not mention the package are not parsed, and files that fail to parse are returned unchanged for the compiler to report. The same transform is exported as a Svelte preprocessor: `import { lower } from "@alfayez/svelte-native/lower"` and add it to `preprocess` for tooling such as svelte-check.

`style={…}` on a lowered tag is renamed to `nativeStyle={…}`: Svelte compiles a `style` attribute on any element to a string before the renderer sees it, so the host reads style objects from `nativeStyle` (hand-written `native-*` tags must use `nativeStyle` or `nativeProps` too). A press handler (`onPress`, `onPressIn`, `onPressOut`, `onLongPress`, `onPressChange`) that is not written as a function in place (`onPress={enabled ? go : undefined}`, `onPress={handler}`) is renamed to `nativeOnPress` and so on, for the same reason: Svelte would compile it to an event listener that stays on the element and does nothing while the value is `undefined`, and the element would keep the press from the nearest ancestor with a handler, which a `Text` or a `View` with no handler does not. As `nativeOnPress` it is the prop `onPress` while it is a function and none when it is not (a hand-written `native-*` tag takes the same attribute, or `nativeProps`). The lowering of an HTML element's `onclick` does the same (`onclick={enabled ? go : undefined}` on a `div` or a `span` is `nativeOnPress`; a button's and a link's `onPress` is a function that runs the handler when there is one).

### HTML element lowering

The same transform (`lowerPrimitives(content, { html: true })`, with the mapping in `src/lower-html.ts` and the table in `src/html-tags.ts`) lowers HTML elements, for the files the Metro transformer asks (`lowersHtml` in `src/compile-options.ts`: outside `node_modules` and outside this library's own `src`; a workspace package linked from outside `node_modules` counts as the app's). The web build never loads `lower.ts`, and the `lower` preprocessor leaves HTML alone, so a file is HTML wherever it is not compiled by Metro. A file is parsed only if it has a tag that is not a component, a host tag, a `script` or a `style` (`mayHaveHtml`). The guide's page is "HTML elements" (`docs/20-core-concepts/50-html-elements.md`); this is how it works.

- **Host tags.** `div section header footer main nav article aside ul ol li form label figure fieldset dl dd` are `native-view` (`native-pressable` with an `onclick`); `p span h1`–`h6` `strong b em i small code blockquote figcaption dt mark kbd time abbr s u del ins q cite sub sup var samp dfn data pre` are `native-text`; `hr` is a `native-view`; `button` and `a` are `native-pressable` (`native-text` for an `a` among text); `img` is `native-image`. They go through the paths a lowered `<View>` takes (`class` and `class:` as `nativeClass`, `style`, spreads, `use:` and the transition directives untouched), with `hostHtmlClass` for the class (it is not given the element's own style: the host knows the font size) and `hostWebSpread` (or `hostWebClickSpread` for a button and a link) for a spread. On the elements that are components (`input`, `textarea`, a checkbox, `dialog`) a `use:`, `in:`, `out:`, `transition:` or `animate:` directive, which Svelte refuses on a component, is taken out with a warning (`asComponent`). Components: `input` and `textarea` are `TextInput`, `input type="checkbox"` is `Switch`, `dialog` is `Modal`, imported as `SvelteNativeTextInput` and so on from `@alfayez/svelte-native/core` (a tag name has to start with a capital letter). Any other tag is a build error: an HTML element with no native equivalent (with a hint), a custom element, `<center>`.
- **Marker.** Every element made a host tag, and each `TextInput` and `Modal`, carries `nativeHtml` (`true`; `"inline"` for the text elements that flow in a line: `span`, `strong`, `b`, `em`, `code`, `a` among text, ...), which is hidden from props like `nativeClass`; a `<form>` also carries `nativeForm`. `nativeBase` is a style under `nativeClass` and `nativeStyle`: the name of the element for the ones with a default style, which the host works out (`baseStyle` in `fabric/host.ts`): `hairline` for an `hr`, bold, italic, underline, line-through, monospace, `mark`, and the headings and `small`, `sub`, `sup` as `fontScale`, a factor of the inherited font size.
- **Layout of the children.** A marked view lays its children out as CSS does (`fabric/html-flow.ts`, read in `childrenHost`): in a block container the bare text and the inline elements are one line (`buildRun`, below), and in a flex container each element is an item, with each run of bare text an anonymous item of its own (whitespace-only runs are nothing). A flex container is a view whose resolved style has `display: flex` or any of `flexDirection`, `flexWrap`, `gap`, `rowGap`, `columnGap`, `justifyContent`, `alignItems` and `alignContent`. The class compiler (and the converter of `style="..."`, and `style:display`) writes `display: flex` for `block`, `inline`, `inline-block` and `flow-root` too (React Native has no others, and `md:block` has to undo `hidden`), and so also writes the keyword that was used as `htmlDisplay`, a style key the native view ignores (like `fontRelative`): a `class="block"` view holds a line, a `class="flex"` view holds items, and `display: 'flex'` written by hand is its own keyword. An inline element whose own style sets `display` is in the line for `inline`, `inline-block`, `inline-flex` and `contents`; for `none` (`isHidden`) it is built as an item of its own without ending the run (a hidden text cannot be a span: a span takes no `display`; the line goes on around it, and the item is appended before the run's text, which does not matter for a box that is not drawn); for anything else (`<span class="block">`) it is an item of its own that ends the run. `htmlDisplay` is believed only when it is a keyword the native `display` can come from (`NATIVE_DISPLAY`), and a flex key (`gap`, ...) that a later item of a style array sets to `undefined` is not set. Development warns once per element when the keys of a flex container are on a marked text (`warnTextLayout`: a text does not lay its children out). The view remembers which of the two it was (`State.flex`), so a class that changes it builds its children again.
- **Text.** Text that is bare in a marked view (a `native-view`, `native-pressable` or `native-modal` with `nativeHtml`) is drawn by the host when it builds the view, whatever put it there (written in the element, `children`, a snippet, a block): `buildRun` takes a run of bare text and `"inline"` elements, drops the blanks at its ends and draws the rest in a `native-text` of its own (kept per run: an `implicitText` node with the view as its parent, so it takes the view's text style), whose first and last strings lose the whitespace at the edge of the line (`buildRun` builds the text again only when the run is not what it was made from: other members, a member that is not the Fabric node it was, or one with a change to build; a run's own props are compared every time, which costs a diff and a clone only if the inherited text style moved). A run of one element is that element. Text a marked view does not hold (a `View` of the package) is not drawn, and development warns once. The lowering still tells which runs hold text, only to make an `<a>` among them a press on the text. `pre` writes its text as a template literal expression (`{`...`}`), which Svelte does not trim or collapse, and the newline right after `<pre>` stays outside it so no line moves. `<br>` in text is `{"\n"}`. A view inside a text starts a new text under it (React Native's rule), so the `insideText` of the children of a node is only whether it is a text itself.
- **Events.** `onclick` and `on:click` are `onPress`. A button's and an `a`'s press goes through `hostClick`: the handler first, with an event whose `preventDefault` works, then the `onclick` of a spread (`onHtmlClick` listeners, what `hostWebClickSpread` makes of it), then what the press does by itself unless the default was prevented: a link's `useLink()` call with `hostHref(event)` (the `href` the element has: it stays an attribute, so one from a spread counts, and none is no link) and a submit button's `hostSubmit`, which reads the element's own `type` (`button` and `reset` do nothing). `hostSubmit` walks up the element tree from the press event's `currentTarget` to the nearest node with `nativeForm` and dispatches `submit` there, so the form needs no context and a field in another component finds it. `TextInput` with `nativeHtml` works the HTML attributes out when it renders (`html-input.ts`): `type` is the keyboard (under any native prop the element has), `disabled`, `readonly`, `maxlength`, `rows` and the rest are the native props, `oninput` is `onChangeText`, `onchange` is `onEndEditing`, `onkeydown`/`onkeyup` are `onKeyPress`, Enter in a single-line input is `hostSubmit` unless the key press of Enter was prevented, and a string `style` is read with the `style:` rules; the events have `hostInputEvent`'s fields (`target.value`, `.name`, `.id`, `.type`) and `hostKeyEvent`'s (`key`). The events of marked nodes have `currentTarget` and `target`. A web handler that cannot run (`onmouseover`, `onpaste`, ...: in lower case, or an `on:` directive, and not one the element gets) is a warning with file, line and column. Svelte's custom renderer refuses `on:`, so an `on:event={f}` that the element does not take itself is written `onevent={f}`, and one with a modifier (`on:click|preventDefault`) or without a function (`on:click`) is an error that says to write the attribute.
- **Style.** A static `style="..."` is converted at build time by `src/css/inline.ts`, with the class converter (`css/properties.ts`): a declaration it cannot express, or a `vw`/`vh`/`env()` value, is an error that names it; a string with `{...}` in it is an error. A unitless `line-height` and an `em` `letter-spacing` stay under a `fontRelative` key. `style:property={value}` directives become one `hostStyleProps({...})` call joined with the element's own style, and a `style={text}` whose value is text when the app runs is read by `styleText` in `mergeHostProps`; both use the small parser of `html-style.ts` (camel case, `px` and numbers are dp, `rem` is 16, `%`, colors and keywords pass, `!important` is dropped; a value it cannot use, a custom property and a name React Native does not know warn in development).
- **Text inheritance** is the host's (`src/fabric/text-inherit.ts`, `inheritTextStyle` in `fabric/host.ts`). A marked element's text keys (`color`, `fontSize`, `fontWeight`, `fontFamily`, `fontStyle`, `lineHeight`, `letterSpacing`, `textAlign`, `textTransform`, `textDecorationLine`/`Color`/`Style`, `fontVariant`), from its class, style and default style, are the text style of the marked elements above it with its own over it; a marked `native-text` that is not inside another, and a marked `native-input`, are built with the text style they inherit under their own. Nodes that are not marked (a `<View>`, a `<Text>`, a navigator) neither give nor stop it. Relative values wait: the class resolver is asked to `defer` them (`resolveClasses(className, style, true)`: a `fontRelative` key instead of dp), and the host makes them dp for the font size the element ends up with; a `fontScale` (a heading's 2em) is a factor of the inherited size. Decorations add up (`addDecorations`: a `<s>` in a `<u>` is `underline line-through`, and a `none` takes no line away, as in CSS). When a marked element's text style changes, the marked nodes below it are marked dirty (`markInheritors`, which also reaches the text a view draws itself) and rebuilt in the same flush; an unchanged style is the same object, so nothing below it is touched. A marked `native-pressable` with `disabled` is disabled for the screen reader too (`aria-disabled`), as React Native's `Pressable` makes it.
- **`ref` and `bind:this`.** `bind:this={target}` is `ref={hostBind(set, get, keys)}` (`bindThisText` in `lower-html.ts`, for the lowered primitives too): the variable gets the host handle, and `null` only if it still holds that handle when the element goes away; the computed keys of the target (`els[i]` has `[i]`) are read where the attribute is, so the `ref` is made again when one changes and the old target is written with the old keys, as Svelte's own `bind:this` follows its target. The host calls a `ref` when its element is in a screen, not when it builds the view (`setRefSink`, `earlyRef` in `fabric/host.ts`): at once when the renderer sets it on an element that is on a surface, and when the subtree it is in is linked into one when not (Svelte sets attributes while it builds a subtree and links the subtree after: `NativeNode.waiting` counts the refs a subtree is waiting to give, `giveRefs` in `renderer.ts`). `onMount` and effects find the handle, and a screen that is built off screen (a `fork()`, `router.prepare`) calls no ref until it is committed, or ever, if it is discarded. What a handle is asked before its view is on the screen (`focus()`, `measure`) waits and is done after the flush that puts it there. A handle is an object of its own kind, not a plain one, so a `$state` array does not wrap it in a proxy (the variable holds the very handle).
- **An element that becomes another component.** A Fabric node cannot change its component, and what an element is depends on where it is: a text is `RCTText` alone and `RCTVirtualText` as a span of a run (and a text input is another view when it turns multiline). When `build` finds the view name of an element that has a node changed, it makes the element again (`remake`): a new tag, no props kept, its children built into the new node, the old `ref` hears `null` and then the new handle (the handle's `tag` reads the element's current tag, so an old one reaches the new view), and the animation and gesture layers let go of the old tag (`detachAnimation`, `detachGesture`) and attach the element as new. An element whose node is made in a flush and that is given a `ref` there (a remade one, a foreign view) is `uncommitted` until the flush's `completeRoot`: what its `ref` callback asks of the handle (`measure`, `focus`) waits with the rest (`drainQueues`), since the platform does not have the view yet.
- **`<svelte:element>`, `<svelte:head>`.** `this={tag}` is `this={hostTag(tag)}` (`html-tags.ts` is the table; a literal is mapped when the file is built), and the element is marked, as `"inline"` when it is a text that flows (a literal is read when the file is built, a tag worked out when the app runs by `hostInline(tag)` when it can be read twice). `bind:this` is the handle (boxed: Svelte sends every attribute of a dynamic element through `set_attributes`, which drops a function), `onclick` and `on:click={f}` are `onPress` (a tap is a touch; a `click` listener hears only the accessibility services), and any other `on:event={f}` is `onevent={f}`, as for any element; a modifier is an error. Its `class`, `style` and web events are not adapted (a warning). `<svelte:head>` is taken out, with its lines kept; `<svelte:window>`, `<svelte:document>` and `<svelte:body>` are errors.
- **Errors and lines.** `lowerHtml` collects every problem and throws one error: an element with no native equivalent (with a hint), a tag that is not one, an input type that has none, `bind:` other than `this`, `value`, `checked`, `open`, `class:` on a component-made element, an interpolated string `style`, an unconvertible one, a `<br>` outside text. Only text is inserted, renamed and moved, and the newlines of what moves go with it (`moveOut`, `replace`), so a line number is where the source says; edits that start at the same place apply the longer one first. `tests/lower-html-compile.test.ts` lowers and compiles random files and expressions that span lines, and counts the lines.

`dist/node/transformer.cjs` bundles the converter of `css/` for this, so it is larger than before; the parts of `css/` that `lower-html.ts` imports (`properties.ts`, `values.ts`, `color.ts`, `parse.ts`, `table.ts`) are loaded by Node from the sources too (the transformer's tests run it so), so they avoid TypeScript syntax Node cannot strip (no parameter properties), and they are in the transformer's cache key (`cacheKeyFiles`, with a test that follows the imports of `lower.ts`).

## Integration

The platform's Vite configuration composes `svelteNative({target: mode === "native" ? "native" : "web", kit: ...})` (`runes: false` turns off the runes default for both targets, "Runes mode"). Web mode runs SvelteKit and excludes mobile entry files from dependency discovery. Native mode discovers routes and invokes Expo's Metro/Hermes export. The native graph rejects `.server.ts`, `src/lib/server`, private environment and ingest imports.

Metro uses `withSvelteNative(getDefaultConfig(__dirname))`. It compiles Svelte with the pinned custom renderer, in runes mode by default (`{ runes: false }` turns that off; "Runes mode"), and resolves every native `svelte/*` import to the same runtime. Add `"@alfayez/svelte-native"` (the package's `app.plugin.js`, which Expo finds for a bare package name; `"@alfayez/svelte-native/app.plugin"` is the same file) to the Expo config's plugins. React Native's Gradle cache does not track Svelte files or external workspace sources, so this plugin rebundles the JavaScript graph on every Android release build; native compilation stays incremental. Expo continues to provide module resolution, native code generation, assets and Hermes compilation. The Node-side entries (the CLI, `/metro`, `/transformer`, `/expo`, `/vite`, `/lower`) are built JavaScript in `dist/node/` (README, "Set up an app"; `pnpm build` after a change to the code they come from), so an app needs no TypeScript support in Node; in this repository `node packages/svelte-native/src/cli.ts` still runs the sources.

The plugin accepts `["@alfayez/svelte-native", { androidViewRecycling: true }]` to enable React Native's experimental Android view recycling (`enableViewRecycling` plus the `<View>`/`<Text>` opt-ins, or an object choosing `view`, `text`, `image`, `scrollView`). It writes a `ReactNativeFeatureFlags.dangerouslyForceOverride` block after `loadReactNative(this)` in the generated `MainApplication.kt`. This is React Native's recycling; the engine has its own view pool on Android (SPEC "Frames: recycling, text cache"). It is off by default: on 25 October 2026 it halved native view creation time on the Samsung (0.27 ms versus 0.5 ms per view) without improving frame times.

The plugin also takes `autolinkingExclude: string[]`: package names, or the names of the app's own local Expo modules under `modules/`, that both autolinkers leave out of the build. The library's six native modules are one package, `@alfayez/svelte-native` (`expo-module.config.json` at the package root lists their Gradle projects and pods), so they are never excluded one by one. It writes them into `settings.gradle` (Expo's `expoAutolinking.exclude`, and `--exclude` on the React Native config command, next to the headless excludes) and into the `Podfile` (`use_expo_modules!(exclude:)` and the same `--exclude` on `expo-modules-autolinking react-native-config`); an empty list restores the template. The platform app gives the product and the QA app the libraries of the native module smoke test, so only the smoke app (`APP_VARIANT=smoke`) links them, and the product (`APP_VARIANT=production`) adds its QA-only Expo modules (`svelte-qa-android`, `svelte-qa-ios`, `view-bench`: the touch injector, the iOS inspection module and the view bench), whose classes are then not compiled into the app at all; the smoke app excludes nothing, and every prebuild rewrites the list, so one directory can be prebuilt for one variant and then for another (`native/svelte-engine/SPEC.md`, "Native modules (smoke test)"). `withSvelteNative(config, { stubbedPackages, stubbedFiles, stubbedDirectories, variant })` in the Metro config resolves those packages (and every path inside them), the named source files and every file inside the named directories (however it is imported; the platform app's product stubs its development lab this way) to a stub that throws `<package> is not in this app (APP_VARIANT=…)` when used, so an app that does not link a library does not bundle its JavaScript either. The same call writes the route table of its `variant` (`.svelte-native/routes.<variant>.ts`, which exports `variant`, `lab` and `tree`; `syncRoutes`, on when the project has `src/routes`) when the config loads, and in development again whenever a route file changes, and resolves `./routes` (the generated entry's import) and `@alfayez/svelte-native/routes` (the app's read of `variant` and `lab`) to it. There is no table the variants share, so a sync or a bundle of one variant never changes what another's Metro serves; the stubs are a directory per variant for the same reason. `@alfayez/svelte-native/platform` exports `turboModule(name)` and `nativeModule(name)`, the lookups for a native module whose library's JavaScript needs React or reaches another module.

```sh
svelte-native sync
svelte-native dev --port 8081
svelte-native android --device
svelte-native ios --device
vite build --mode native
# Or export iOS bytecode without building its native host:
svelte-native build --platform ios
```

The app's hooks are `src/hooks.mobile.ts` (or `.js`; `hooksFile`). `syncRoutes` writes `.svelte-native/hooks.ts` (`syncHooks`), which imports the file and calls `registerHooks` (`app-hooks.ts`, exported by `/app`) with its exports, or `registerHooks({})` without one (so a removed file's hooks go); the entry imports it as `./hooks` between `/app` and the layout, whether or not the file exists, so adding or removing the file changes that module alone (a development Metro's `watchRoutes` also watches `src`, not recursively, for it) and an entry without the import is stale (`staleEntry`). `registerHooks` calls `init` the first time a registration has one (a throw or a rejection: `__DEV__` logs it and `launchSurface` mounts the error screen in place of the app until a registration or the screen's Reload, `retryInit`, runs `init` again; release reports it through `ErrorUtils.reportFatalError`); a registration while `init` is pending is queued and runs if that `init` fails. While the promise `init` returned is pending, `launchSurface` holds the surface (`stopApplication` drops a held one) and starts it when the promise settles, and `remountSurfaces` leaves the running screens as they are and remounts once it settles. A watcher that throws (a `transport` Kit's `init_transport` refuses) is rethrown after `init` has started. `remote/config.ts` reads `handleError` and `transport` through `watchHooks`, under what `configureRemote` set. Tests: `tests/hmr.test.ts` ("src/hooks.mobile.ts"), `tests/entry.test.ts`, `tests/metro-routes.test.ts`, `tests/remote-runtime.test.ts`.

Generated entries and exports live under ignored `.svelte-native/`. Android export produces `dist/android/index.hbc`, its composed source map and assets there. A native host must still be built with Expo/Gradle or Xcode. Release host builds use the same Metro transformer and generated entry. The native dev server reloads changed Svelte files; preserving component state across edits is not guaranteed.

### Variants

A build is one variant, named by `APP_VARIANT`; the generated route table is `.svelte-native/routes.<variant>.ts`, one per variant. An app that sets none is the variant `app` (`routes.app.ts`). The variant `production` leaves the development lab out (every other variant has it, `qa` and `smoke` included); an app with variants of its own sets `APP_VARIANT` in each build, and an app whose default is another name passes `variant` to the three integrations that write the table (`withSvelteNative`'s option, the Expo plugin's `variant` option and `svelteNative({ variant })`; the command line reads `APP_VARIANT` only), as the QA app does with `qa`.

### Node-side dependencies

What the Node-side code (the Metro integration, the transformer, the Expo plugin, the Vite plugin, the command line) needs, and what an app has to provide: `expo` (a required peer) for the config plugin and for `@expo/metro-config/babel-transformer`, which the transformer finds through `expo`'s own directory (`upstreamTransformerPath`; `@expo/metro-config` is `expo`'s dependency, so pnpm's default layout has it only there); `svelte` (the custom-renderer build), `esbuild`, `@babel/parser`, `@babel/types` and `@jridgewell/trace-mapping` (dependencies of the package). `@sveltejs/kit` is read only by remote functions (the transformer replaces a `*.remote.ts` module and the resolver finds SvelteKit's client runtime) and by the web target of the Vite plugin, which imports `@sveltejs/kit/vite` when it is asked for; `vite` is only the tool that runs the plugin. When either is missing the feature fails with a message that names `@sveltejs/kit`, and nothing else notices. The transformer strips TypeScript before Svelte's module compiler for a `.svelte.ts` file wherever it is, `node_modules` included (the library's own `router.svelte.ts` and `insets.svelte.ts` are two); the TypeScript of a package that Svelte does not compile is left to Babel.

### Route loading

Routes load lazily. The generated table (`.svelte-native/routes.<variant>.ts`, one per variant) exports `tree` (the route tree `buildTree` makes of `src/routes`): a `load()` per page that requires its `+mobile.svelte` and the content layouts above it, and a `layout()` per navigator layout. A navigation loads the routes it pushes right away; a screen that renders loads its own route (the first screen, a restored stack), so creating the router loads nothing. Until a route settles its screen is empty, or shows the `loading` snippet of the `<Stack>` around it (or the one passed as `<Router {router} {loading} />`). A failed load is rethrown where the screen renders (the nearest `<svelte:boundary>` draws it) and retried on the next navigation (for a navigator layout, one through any navigator of its chain, so a pane's layout is retried by the next navigation into the pane). `presentation` and `navigator` are read when the table is generated, so they must be literals in the module script (`export const presentation = "modal"`, `export const navigator = "tabs"`). Release bundles stay in one file (Expo's embed export does not split chunks); the loaders defer evaluation, which is what boot pays for.

### Animation API loading

The animation exports of the main entry and the Fabric host both load Reanimated and worklets on first use (≈ 90 ms of boot on a mid-range phone, including a second Hermes runtime): the host on the first node with `animatedStyle`, `entering`/`exiting`/`layout` or CSS animation keys, the module on its first call (`createSharedValue`, `withTiming`, `runOnUISync`, …). Until then the module's exports are loading stubs; after the load they are Reanimated's own functions (live bindings, re-assigned by the shared loader in `src/fabric/reanimated-load.ts`). One rule follows: a worklet that calls `withTiming`/`cancelAnimation` or reads `ReduceMotion`/`Easing` on the UI runtime must be created after some animation call ran on the JavaScript thread (creating the shared value it animates is enough); a worklet created before that captures a stub, which the UI runtime rejects as a remote function.

### Gesture API loading

The gesture host loads on the first node with a `gesture` attribute (the host `require`s `fabric/gestures.ts` there, after Reanimated); the gesture exports of the main entry (`src/gestures/index.ts`) load no builder and no Reanimated when they are imported, only on the first read of a `Gesture` property, so an app that never uses them pays for evaluating the module and nothing more at boot (`tests/gestures/isolation.test.ts` checks the import graph: nothing of the host is reached through an ES `import`). On Android the first attach calls `SvelteEngine.enableGestures()`, which installs RNGH's root helper on the engine's root view.

### Doctor

`svelte-native doctor` (`src/doctor/`) checks an app's setup. It runs in the app's directory, reads files and runs `pnpm --version`, and writes nothing (`cli.ts` dispatches it before the `.svelte-native/` sync every other command makes). The result of each check is `pass`, `fail`, `skip` (an optional library that is not installed) or `unknown` (printed `????`: it could not tell). The exit status is 1 when any check failed, 2 for an argument it does not know, 0 otherwise; `unknown` and `skip` never fail it. `--json` prints `{ ok, appRoot, checks: [{ group, status, message, details?, fix? }] }`.

| Check | Passes when | Fails or cannot tell |
|---|---|---|
| node | the Node version satisfies `requirements.node.app` (`src/doctor/requirements.ts`: `^22.17.0 \|\| ^24.3.0 \|\| >=26.0.0`, what a fresh install of an `sv create` project accepts; not Node 25), or `requirements.node.repository` (the root `engines.node`, `>=25.0.0`) for an app that is a member of this repository's workspace (`apps/qa`, `apps/example`): the running Node's, and on Bun that of `node --version` | fails outside it, with the Node to install; `unknown` when no `node` can be run |
| pnpm | `pnpm --version` run in the app satisfies `requirements.pnpm` (the root `packageManager`) | fails below it; `unknown` when pnpm cannot be run |
| svelte | the `svelte` the app resolves has a `./renderer` export whose file exists and a compiler that knows `customRenderer`, and its version satisfies the peer range when the range is a version range | fails for the stock Svelte, naming which of the two is missing |
| peer dependencies | each package of `peerDependencies` the app resolves satisfies its range (exact, `~`, `^`, comparators, `\|\|`); an optional peer that is not installed (a view library, `@sveltejs/kit`, `vite`) is skipped in one line; `hermes-intl`, `react-native-quick-crypto`, `react-native-mmkv`, `react-native-nitro-modules` and `react-native-quick-base64` are also dependencies of the app's own `package.json`, and the installed `expo` has `src/winter` (which `polyfills.ts` loads through `expo-runtime.ts`: a standard `URL` for the router) | fails for a version out of range or a required peer that is missing, for one of those five installed but not a dependency of the app (React Native's autolinking reads only the app's own dependencies, so the build would have no native module for it), and for an `expo` without `src/winter`; `unknown` for a range that is not a version range (`file:`, a URL) |
| patches | for each file of `patches/`: the installed package has exactly the patch's version and carries the patch | fails with what is missing, and a fix that depends on whether the app declares the patch |
| library | the app's `package.json` lists the package | fails if it does not |
| Metro | a `metro.config.*` mentions `withSvelteNative` outside a comment | fails with no Metro config; `unknown` when the config does not mention it (it may apply it from a file it imports) |
| Expo plugin | `app.json` lists `<package>/expo` or the bare `<package>` (its `app.plugin.js`) in `plugins` (as a name or the first item of a pair), or an `app.config.*` names one of them as a string outside a comment | fails if there is only an `app.json` without it, or no Expo config; `unknown` when an `app.config.*` does not name it (it may build its plugins in code) |

**A patch is applied when two things hold of the installed files, not when `patchedDependencies` names it.** The first is the shape the package's own tests pin (`src/doctor/shapes.ts`, one function per patched package, each taking the files of the installed package and returning what is missing): the Android events that must not coalesce override `canCoalesce()` to return false (and the video emitter's two streams, and the map's five, still do), the gesture handler's manager has `currentManager` and the registration the screens ask for, Reanimated has the sink and the engine hook, the worklets frame loop requests a frame only on demand, Expo's `ModuleRegistry` lists the lazy modules the patch defines, SvelteKit skips `+mobile` files. The second is the patch file itself (`src/doctor/hunks.ts`): every hunk's result, the context and the added lines, is in the installed file, so a package patched with an older copy of the patch, or half of it, fails even when the first holds. The tests call the same functions (`tests/foreign-libraries.test.ts`, `tests/expo-lazy-modules.test.ts`, `tests/rngh-patch.test.ts`, `tests/worklets-frame-loop.test.ts` on the repository's install, `tests/doctor.test.ts` on fake apps with patched and unpatched copies of the files), so the shape is written once.

The version a patch is for is the one in its file name, and pnpm applies it to that version only; the doctor fails a package of another version before it looks at the files. `expo-modules-core` is found through `expo` (it is `expo`'s dependency, not the app's), and because `expo` asks for it by a range (`~57.0.23`) a fresh install floats to the newest version in it: its fix is an `overrides:` entry (`expo-modules-core: 57.0.23`) in `pnpm-workspace.yaml`, not `pnpm add`. SvelteKit's patch is checked only when `@sveltejs/kit` is installed. To add a patch: add the file to `patches/`, the entry to `patchSpecs` in `src/doctor/patches.ts` with a function that returns the problems of the installed package, declare it in the repository's `pnpm-workspace.yaml` from `packages/svelte-native/patches/`, and add it to the table and the YAML block of the README's "Apply the patches"; `tests/doctor-repository.test.ts` fails until the file, the entry, the declaration and the lockfile's hash agree.

### Fabric entry dev loop

The entry has its own development loop; it does not use Fast Refresh (there is no React) or Expo's dev client (its launcher UI is React).

- Metro: `cd apps/qa && node ../../packages/svelte-native/src/cli.ts dev --port 8181` (the same as `svelte-native dev`; it writes the entry, then starts Metro).
- Host: a debug APK (`./gradlew assembleDebug -PreactNativeDevServerPort=8181` in `apps/qa/android`, so the debug host asks Metro on port 8181 and not 8081). The Expo plugin's Android build has no dev client. A debug build skips JS bundling and loads `.expo/.virtual-metro-entry` from Metro, which resolves to `.svelte-native/entry.ts`.
- Device: `adb reverse tcp:8181 tcp:8181`, then launch the app. A release APK cannot be pointed at Metro (its Hermes bytecode is embedded and release has no dev support), and a debug build that keeps `expo-dev-client` opens the React launcher instead of the app.
- Edit to screen: Metro pushes the changed module over its `/hot` socket (React Native's `HMRClient`, registered by `init.ts`; Fast Refresh must be on in the dev menu, which is its default). Metro re-runs the edited module and each importer up to the nearest `module.hot.accept()`. The generated entry accepts at the top (`if (__DEV__) module.hot?.accept(() => remountSurfaces())`), so every edit re-runs the entry, which re-registers the fresh root component, and `remountSurfaces()` unmounts every running surface and starts it again on the same root tag with the same initial props.
- Kept across an edit: the navigation state (every stack and every tabs selection: each root `createRouter` adopts what the previous router published on `globalThis.__svelteNativeHmrState`, nested along the entries and recorded by route id (restored by id, else by href), and drops what no longer exists; a hand-made router with a `scope` takes its own the first time it is created), native state (engine overlay, native modules, the JS heap outside re-run modules) and any module Metro did not re-run. Lost: component state, and state held by re-run modules. An edited `*.svelte.ts` store is re-run together with its importers, so its connections are not reused; close them in a `module.hot.dispose` handler if that matters.
- Errors: in development an uncaught fatal error, or a throw while mounting or flushing a surface, replaces the surface with a red `ErrorScreen` (message, first stack frames, a Reload button that remounts). The error is reported to the native exception manager as non-fatal so the process survives and the screen stays; `console.error` is also forwarded to `reportSoftException`, so it reaches logcat. Frames are unsymbolicated bundle positions. An error before the first surface exists (while the entry's modules load) has no surface to draw on; it is reported natively only. Release builds keep the fatal path.

Verified on an Android emulator (API 36) with this recipe: a save reaches the screen through `remountSurfaces()` about one second later, a `throw` at the top of a route's script shows the error screen with the process alive, and reverting the file restores the app. Three details the loop depends on: `svelte-native dev` writes the entry before Metro starts; `react-native/Libraries/Core/InitializeCore` resolves to this package's `init.ts`, because Expo's `src/winter` runtime (run before the entry) imports it; and `Expo.fx` registers a placeholder "main" component in development, which the `AppRegistry` accepts and ignores. Do not start Metro with `CI=1`: Expo then disables the file watcher and serves stale bundles. Package-file edits are hot too, since the repository root is watched. Not verified: the loop on iOS, and edit latency on a physical Android device (the emulator runs over an SSH forward).

## Type checking an app

An app's type checker (`tsc`, `svelte-check`, the Svelte language server) reads the package's declarations, not its source. Every public entry of the exports map has three conditions, in this order: `svelte-native-source` (the TypeScript or Svelte file: only this repository asks for it), `types` (the declaration, in `dist/types/`) and `default` (what runs: the source for Metro, a built file in `dist/node/` for the Node-side entries):

```json
"./metro": { "svelte-native-source": "./src/metro.ts", "types": "./dist/types/metro.d.ts", "default": "./dist/node/metro.cjs" }
```

Metro and Vite ask for `react-native`, `import`, `require`, `default` and the like, never `svelte-native-source` or `types`, so what they compile is unchanged. Before this, `types` named the sources, so an app's checker parsed and checked the library's implementation (`skipLibCheck` does not skip a `.ts` file). `/remote/runtime` and `/remote/globals` are not typed (Metro substitutes them; no app imports them).

**The `svelte-native-source` condition.** This repository's tsconfigs (`packages/svelte-native/tsconfig.json`, `apps/example/tsconfig.json` and `test/tsconfig.json`, `apps/qa/tsconfig.json` and `qa/tsconfig.json`) set `customConditions: ["svelte-native-source"]`; `tsc`, `svelte-check` and the editor read it from the tsconfig, so the apps and the package's own files are checked against `src/` and an edit needs no rebuild. No fixture that stands for an app outside the repository sets it (`tests/types.test.ts`). A new tsconfig that checks code importing `@alfayez/svelte-native` in this repository takes the same line. The name is not `source`: many React Native libraries (`react-native-builder-bob`'s output: `react-native-quick-base64`, `@react-native-firebase/*`) have a `source` condition of their own, and an app that took it would type-check their sources too (19 errors in the QA app, in files that are not this repository's).

**Module resolution.** The declarations resolve with `moduleResolution: "bundler"` (SvelteKit's default in `.svelte-kit/tsconfig.json`). The `.svelte` specifiers inside `dist/types/` stay (`Foo.svelte.d.ts` is what `./Foo.svelte` finds), and under `node16` and `nodenext` `./Foo.svelte` resolves to `Foo.d.svelte.ts` instead, so every component is untyped there. Every library built with `svelte-package` shares that limit; the guide's Configuration page tells an app to use `bundler`.

**How the declarations are built.** `pnpm --dir packages/svelte-native build` writes `dist/node/` (`scripts/build-node.ts`) and then `dist/types/` (`scripts/build-types.ts`), and both are committed: a git dependency is not built when an app installs it. `tsconfig.types.json` lists the entries (its `files`); svelte2tsx's `emitDts` (a development dependency: what `@sveltejs/package` uses) makes a `.d.ts` of each module they reach and a `.svelte.d.ts` of each component; the hand-written `.d.ts` files of `src/` (`elements.d.ts`, the ambient `declare module`s) are copied; relative specifiers end in `.js` (`.svelte` ones stay, `Foo.svelte.d.ts` is what `./Foo.svelte` finds); the `/// <reference path>` to `kit/modules.d.ts` (`mobile` in `$app/env`) is put back in the declarations of `/vite` and `/router`, since TypeScript drops it; what no declaration names is left out (the reference of `elements.d.ts` to React Native's internal modules goes with it: no declaration names them); and a declaration whose name differs from another's only in case is written under another name, since a case-insensitive file system (macOS, Windows: an app's checkout, an rsync to a Mac) holds one of the two (`renamedForCase`: `router.svelte.d.ts`, the router's module, is `router.svelte-module.d.ts` beside `Router.svelte.d.ts`, the component; the build fails on a pair it was not told about). A new public entry is a line in the exports map (`svelte-native-source`, `types`, `default`) and in `tsconfig.types.json`. `tests/types.test.ts` fails when `dist/types/` is not what the build writes, when an entry has no declaration, and when the primitives' declarations name Reanimated or react-native-svg. The build fails (it does not write a partial `dist/types/`) when TypeScript cannot write a declaration for an exported value: give the export an explicit type.

**Keeping them cheap.** A declaration that names another package's types makes every app's checker load that package, whatever the app imports: TypeScript loads every module a barrel names. The main entry re-exports the animation, gesture and SVG exports, so an app that imports only `View` and `Text` still loads Reanimated, Worklets, react-native-svg (Reanimated's own declarations import it) and the gesture handler, about 340 of the 600 files; the primitives alone (`/core`) load the gesture handler and React Native, not Reanimated or react-native-svg, because `AnimatedView`'s props type (which names Reanimated's) is in `AnimatedView.svelte` and not in `elements.d.ts`. Keep a type that names one of those packages out of the files the primitives import. `tests/type-budget.test.ts` runs `tsc --extendedDiagnostics` on three apps that resolve the `types` condition (`View` and `Text`; those and an animation, a gesture and an SVG component; the primitives from `/core`) and fails when the files or the instantiations grow past a budget set 15 % above what was measured; its header says how to find what grew (`tsc --explainFiles`) and how to re-measure (`KEEP_TYPE_BUDGET_FIXTURE=1`). A control run with the `svelte-native-source` condition checks that the sources are what it resolves then.

**React Native's internal modules.** The library imports some of React Native's modules by path (`react-native/Libraries/Utilities/Platform`, `…/BackHandler`, `…/Image/resolveAssetSource`, …) for which `react-native` ships no types, or none with a default export, and declares them in `src/fabric/react-native-internals.d.ts`. That file is a script of `declare module`s, which cannot be imported, so each source file that imports one of them carries a `/// <reference path>` to it (`init.ts`, `polyfills.ts`, `router.svelte.ts`, `remote/link.ts`, `elements.d.ts`): the declarations arrive with whichever entry the checker follows into the source, which is what this repository's apps do. An installed package's declarations name none of them (an import in a function body is not in a declaration). `tests/internals-types.test.ts` reads the import graph of every entry's source and fails when one reaches an import of an internal module without them; `tests/node-modules.test.ts` runs `svelte-check` on an app that has the packed package in `node_modules` (and a control file whose two mistakes must be, and are, the only errors).

Types that were wider than the host or narrower than what it does (found by checking what this document says against them): `onPressChange`, `pressRectOffset`, `delayPressIn`, `delayPressOut` and `minPressDuration` on `Pressable`, `Text` and `View`, and `onPress`, `onPressIn`, `onPressOut`, `onLongPress` on `View` (the host makes any node with a press handler a responder; React Native's `ViewProps` has none); `animatedProps` on `AnimatedView` is a worklet (or a list of them), as `animatedStyle` is, not Reanimated's `useAnimatedProps` object; the `ref` of `View` and `GestureDetector` is a `HostHandle` (exported from the main entry), and those of `ScrollView` and `TextInput` also have `dispatchCommand`. A `TextInput` ref is typed with React Native's `clear()`, but the host handle does not implement it (set the bound `value` to `""`). `pressRetentionOffset`, which React Native's types accept on `Pressable`, is now honoured (it is `pressRectOffset`).

## Experimental dependency

Native compilation depends on Svelte's [unmerged custom-renderer PR](https://github.com/sveltejs/svelte/pull/18042), pinned to commit `216f258068d93170a927ad4d27ee6864b0b305c5` (5.56.7). The package and the example app, the web target included, both depend on that build, vendored as `vendor/svelte-5.56.7-216f258.tgz`. The package also owns a small pnpm patch to SvelteKit 3.1.1 so its route scanner accepts mobile siblings. Both pins must be reviewed when updating Svelte or SvelteKit.

The pinned compiler currently requires boundary failure snippets to be declared outside `<svelte:boundary>` and passed with `{failed}`. Svelte DOM transitions, React widgets and Svelte DOM libraries are not adapted; a further native view needs an entry in the host's view-name table (`viewNames` in `src/fabric/host.ts`) or a wrapper in `@alfayez/svelte-native/foreign`. Android and iOS run on physical phones (Samsung SM-A165F, iPhone SE 3rd generation) and, for Android, on an emulator; tablets and foldables have not been exercised.

pnpm reports Svelte peer-range warnings for the compiler's URL dependency even though its package version is 5.56.7. The compiler/runtime pin is intentional; changing it requires native compilation and device checks.

`bun test tests/renderer.test.ts` exercises compiled reactive updates, keyed identity, conditional removal, event delivery and effect disposal. `pnpm typecheck` validates the public primitives and tooling.

The foundation port was first exercised on a physical Samsung SM-A165F (Android API 36), in the Example product app of the monorepo this repository was extracted from (its screens are not part of this repository), including a standalone release with Metro stopped: login validation, onboarding, profile and photo updates, email verification, device revocation, Arabic/English preferences, workspace creation/deletion, account deletion, session retention, deep links and startup retry. Browser login, onboarding, workspace creation and profile saving were also checked. Hermes exports contain bytecode version 98 and source maps with the original Svelte source contents.
