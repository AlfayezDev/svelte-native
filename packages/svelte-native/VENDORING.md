# Vendoring third-party native dependencies

`@alfayez/svelte-native` carries its third-party native dependencies itself: their published source is copied into `vendor/<name>/` of the package, and an app's `package.json` lists `@alfayez/svelte-native` and nothing beside it. The rule: **vendor everything if possible, unless it is presented as an alternative** (push notifications: Firebase, `expo-notifications`). The pilot is `react-native-nitro-modules` 0.35.10 and `react-native-mmkv` 4.3.1 (MMKV is what `localStorage` is made of, Nitro is its runtime and quick-crypto's), which every app links; the optional native view libraries (expo-image, react-native-maps, ...) are vendored the same way and linked only for an app that turns them on ("Optional libraries" below); the rest follow this pattern (the list at the end).

## Where

- `vendor/<name>/` holds what the npm tarball publishes, unchanged: the JS the app needs (`src/`, `lib/`), `android/`, `ios/`, `cpp/`, Nitro's generated code, the podspec, `package.json` (the podspecs and the codegen read it) — plus `LICENSE` and `VENDOR.md` (upstream name and version, the tarball's integrity and sha256, what was left out, every local change, and the command that writes the directory again). `vendor` is in the package's `files`.
- `node scripts/vendor.ts <name>@<version> [--exclude <path>]... [--license-url <url>]` writes one: `npm pack`, unpack, check the tarball's integrity against npm's, replace `vendor/<name>/` as a whole. The output depends on nothing else (no date, no machine), so running it again with the same arguments gives the same bytes. A tarball without a `LICENSE` (npm omits one that is not in `files`: neither pilot package has one) gets the repository's, fetched at the tarball's own `gitHead`; its URL and sha256 are in `VENDOR.md`. `--exclude <path>` leaves out what the app never needs and the repository must not hold or run, and `VENDOR.md` lists it: the pilot leaves out the packages' own tests (`bun test` finds `*.test.*` files wherever they are, and MMKV's need `@testing-library/react-native`) and Nitro's `lib/tsconfig.build.tsbuildinfo` (the repository ignores `*.tsbuildinfo`).
- A local change is a patch file, `vendor-patches/<name>/*.patch` (`patch -p1`, applied in file name order), applied by the script after the unpack and listed under "Local changes" (by its path from the package's root and its sha256, so `VENDOR.md` names no machine). Nothing in `vendor/` is edited by hand. The pilot has none; four of the optional libraries do (lottie-react-native, react-native-maps, react-native-pdf, react-native-video: events that must not coalesce, which were pnpm patches an app had to declare; react-native-pdf's second patch makes its Gradle find react-native from the app's directory, since the copy is not beside react-native in `node_modules` any more). `vendor-patches/` is in the package's `files`, and the doctor looks for the shape each patch leaves in the copy (`patchSpecs`, `vendored: true`).
- `.gitignore` re-includes `vendor/**/android/`, `ios/`, `build/` and `dist/` (the repository ignores all four everywhere else; an Expo module's JavaScript is in `build/`, react-native-maps' declarations in `dist/`) and ignores again what a native build writes (`android/build`, `ios/build`, `.cxx`, `.gradle`); ESLint and Biome skip `vendor/`; those native build outputs are not packed (`files` negates `vendor/**/android/build` and `ios/build`, not `build` at large).
- What the script leaves out (`--exclude`, listed in `VENDOR.md`): Expo's precompiled iOS frameworks (`prebuilds/`: 132 MB for expo-image, 9 MB for expo-video; Expo uses them only with `EXPO_USE_PRECOMPILED_MODULES=1`, an app that sets it builds these two from source), `*.tsbuildinfo`, a library's tests and the development files of its repository (view-shot's `example-expo`, `coverage`, `.claude`), and the `windows/` and `macos/` ports.

## JavaScript

- The library's own code imports a copy as `#vendor/<name>`, an entry of the package's `imports` map: `types` is the copy's declaration entry, `default` its source (`src/index.ts`, what Metro bundled from `node_modules` before: the `react-native` field). Metro, Vite, Bun, esbuild and TypeScript all read it, in the repository and installed alike. The map has an entry for each vendored package whose JavaScript the library imports (`react-native-mmkv`) and for the types of the other (`react-native-nitro-modules`, below).
- `withSvelteNative` (Metro) resolves the bare names, and every path below them, to the copies **for every importer**: the app, a library that imports them (react-native-quick-crypto imports the Nitro runtime), the copies themselves. One copy of each, one module of each. A name an app stubs (`stubbedPackages`) is still stubbed first. A vendored package gets the `react-native` shim (`fabric/react-native-lite.ts`) exactly when its name is in `LITE_ORIGINS`, as the installed one did (`isLiteOrigin`).
- Types: `src/mmkv.ts` re-exports from `#vendor/react-native-mmkv`, so `dist/types` names it and an app's checker resolves it through the library's `imports` (`types` condition). The copy's declarations import `HybridObject` from `react-native-nitro-modules`, which the app does not install: `src/vendor-types.d.ts` declares that module as a re-export of `#vendor/react-native-nitro-modules`, and every declaration that names a vendored type carries a `/// <reference path>` to it (`publicAmbient` in `scripts/build-types.ts`).
- Web: the web target of `svelteNative()` already puts `.web.*` extensions first, so `#vendor/react-native-mmkv` builds with MMKV's web implementation and with no React Native and no Nitro (`tests/web-apis/web-mmkv.test.ts`).

## Native linking

React Native's autolinking links only the app's own dependencies, so the library adds its copies to the autolinking config **itself**, from `vendor/`, with the fields autolinking would print for the installed package (`src/vendored.ts`: the list, `vendoredDependency`, `linkVendored`).

- **Android**: `settings.gradle` already runs the config command through `svelte-native android-autolinking <command...>`; that command now adds the entries (and the deferred-Nitro relinking, `deferredNitroPackages` and `NitroGate`, is applied after: the entries carry the same `packageImportPath` and `packageInstance` the installed packages had, which is what it matches).
- **iOS**: `svelte-native ios-autolinking <command...>` does the same for the Podfile: `applyPodfileVendoredLinking` (`expo.ts`) puts one block before `config = use_native_modules!(config_command)` that finds the CLI from the app (`require.resolve('@alfayez/svelte-native/package.json')`, as the template finds `expo`) and wraps `config_command`. Stripped and written again on every prebuild, like the excludes; it works under `EXPO_USE_COMMUNITY_AUTOLINKING=1` too.
- The entries are the reference captured from Expo's own `react-native-config` for the installed packages, with the directory of the copy (`tests/cli/fixtures/vendored-autolinking/`): `root` and `sourceDir`/`podspecPath`/`cmakeListsPath` in `vendor/<name>/`, `name` unchanged (**the Gradle project is `:<name>` and the pod is the podspec's own name**, so quick-crypto's `project(':react-native-nitro-modules')` and `s.dependency 'NitroModules'` find the copy).
- Nothing in either package computes a path from `node_modules`: Nitro's CMake and Gradle use prefab and project dependencies, the generated code is below the package, the podspecs use `__dir__`. iOS codegen finds the Nitro spec through the config's `root` (`ios/build/generated/autolinking/autolinking.json`, written from the command's output), which is why `package.json` with its `codegenConfig` stays in the copy.

## Optional libraries

Sixteen libraries are vendored for the apps that use them and cost the others nothing: `expo-image`, `expo-blur`, `expo-linear-gradient`, `expo-conic-gradient`, `expo-video` (Expo modules), `react-native-video`, `lottie-react-native`, `rive-react-native`, `@react-native-community/datetimepicker`, `react-native-pdf` with `react-native-blob-util`, `react-native-webview`, `react-native-maps`, `react-native-view-shot`, `react-native-fast-shadow` and `react-native-animateable-text` (React Native packages). They are `vendoredPackages` entries with an `optional` field (`src/optional-libraries.ts`: `kind`, the package's own config `plugin`, `requires`), and the app's plugin options say which it uses:

    ["@alfayez/svelte-native", { libraries: { "expo-image": true, "react-native-maps": { androidGoogleMapsApiKey: "..." } } }]

A listed library is linked on Android and iOS, bundled by Metro, and its own config plugin (the copy's `app.plugin.js`) runs with the options given, as if the app had listed it in `plugins`. An unlisted one is none of that: its native code is not in the build (on iOS it is not even compiled: react-native-maps references CoreLocation, and App Store Connect would hold every app to a location purpose string if it were always linked), its name resolves to a stub in Metro, and its components throw how to turn it on. `libraries.ts` checks the option (`checkLibraries`: names, `true`/`false`/options, no options for a library without a plugin) and the plugin refuses what it cannot make sense of.

The decision is made twice from the one option, so a build and its bundle agree:

- **Prebuild** writes it into the generated files, which Gradle and CocoaPods run on every build: the React Native libraries are `--link <name>` arguments of `svelte-native android-autolinking` (`settings.gradle`) and `ios-autolinking` (the Podfile block), and `linkVendored(config, platform, root, linked)` adds the entry of each named library to the config the command prints, **and takes out** any original that autolinking found of one that is not named (a copy installed for another package's sake: an app that carries a feature carries it from the library, and an app that does not carries none). The plugin also writes the names to `extra.svelteNative.libraries` (the manifest `expo-constants` embeds), which the wrapper components read (`fabric/foreign-libraries.ts`) to say how to turn a library on where it is off.
- **Metro** reads the same option from the app's config as Expo reads it (`getConfig`: `appPluginOptions`, once for this and for the push client), and resolves the name of each library that is off, and every path below it, to a stub for every importer (`libraryStubSource`: `<name> is not in this app: turn it on with libraries: { "<name>": true } ...`); the ones that are on resolve to the copy, as the pilot's do. A config that cannot be read keeps every library, as it keeps the push client. `withSvelteNative(config, { libraries })` names them when the config should not be read.

**Expo modules** (expo-image, expo-blur, expo-linear-gradient, expo-conic-gradient, expo-video) are not in React Native's autolinking config (they have an `expo-module.config.json`, not a `react-native.config.js`): Expo's own autolinker links them, and finds a package only through `node_modules` or a search path. The plugin gives it the **directory of each enabled copy** as a search path (a directory with a `package.json` is one module, so nothing else under `vendor/` is looked at): Android `expoAutolinking.searchPaths` in `settings.gradle`, found from the CLI's path (`<library>/vendor/<name>`), and iOS `use_expo_modules!(searchPaths: ...)` in the Podfile, found with `require.resolve` as the CLI is. The Expo modules that are off join Expo's `exclude`, so a copy installed for another package's sake is left out too. Expo's Gradle plugin builds the command as `... --exclude a --exclude b <searchPaths>`, and `--exclude` takes any number of values, so without a `--` in front the paths are read as names to leave out and nothing is found: the first Android search path is `"--"` (`tests/cli/library-linking.test.ts` runs Expo's own autolinker on it). Expo's Android modules build from the prebuilt AAR in `local-maven-repo/` (`expo-module.config.json`'s `publication`), which the copy keeps.

**Patched libraries and `settings.gradle`'s cache**: React Native keeps the config command's output until a lock file of the app changes, and `--link` arguments are not in any of them, so the block's lock files include `settings.gradle` itself.

**`androidOnDemandViewManagers`** names package classes (`com.rnmaps.maps.MapsPackage`) that Kotlin must find: the entries of a library that is off are dropped (`onDemandForLibraries`), so one config serves the builds that turn a library on and those that do not.

**`createVideoPlayer`** is exported by `@alfayez/svelte-native/foreign`: the app cannot import `expo-video/build/VideoPlayer` where a type checker looks, since the package is not installed. It requires the module by name when called (the stub when `expo-video` is off) and is typed from the copy through the `#vendor/expo-video/*` import.

**The doctor** reports the libraries that are on (and why a library is on that the app did not list), refuses an app that lists an original, and checks the shape of each patch in the copy.

Not changed by any of this: the library's own foreign components (`/foreign`) mount the native views by name and import none of these packages, so nothing of an unused library is evaluated; JavaScript dependencies of the copies (`sf-symbols-typescript`, `crypto-js`, `base-64`, `nullthrows`, ...) are only reached by an app that imports a library's JavaScript itself, which none of the components do, and are not installed (an app that does add them to its own `package.json`).

## Collisions

An original must not be linked beside a copy.

- The config plugin stops the prebuild, `svelte-native doctor` fails, and the autolinking commands refuse (exit 1, nothing on stdout) when **the app's `package.json`** lists a vendored name (`dependencies`, `devDependencies`, `optionalDependencies`): "`@alfayez/svelte-native` includes react-native-mmkv 4.3.1; remove it from the app's dependencies (package.json), reinstall, and prebuild again." One list, `vendoredPackages` in `src/vendored.ts`, and one message (`collisionMessage`); a package added to the list is covered everywhere.
- The optional libraries are on the same list, and the refusal is the same whether or not the app turned the library on (its message adds how to turn it on, `libraries: { "<name>": true }`). The plugin also refuses an app that lists a library's own config plugin in `plugins`: the package is not installed, so Expo could not find it, and its options go under `libraries`.
- An original that autolinking finds **without** the app listing it is replaced, not refused: pnpm installs react-native-quick-crypto's peer `react-native-nitro-modules` on its own (`auto-install-peers`), Expo's autolinking finds it in `node_modules`, and refusing would refuse every app that uses quick-crypto. The entry is replaced by the copy's under the same name, so it is linked once; the unused original in `node_modules` is inert (Metro never reaches it). It goes away when quick-crypto is vendored (the next batch).

## Notes for the QA harness

The smoke app installs the production app's libraries as stand-ins (`apps/qa/qa/smoke-modules.json`, `package.json`). MMKV and Nitro are not on that list any more: their modules (`mmkv`, `nitro`) stay, still `shared`, with no `packages`; the smoke checks `require("react-native-mmkv")` and `require("react-native-nitro-modules")`, which Metro resolves to the copies. `libraryVendoredPackages` in `smoke-packages.cjs` names them.

## Adding a package

1. `node scripts/vendor.ts <name>@<version>` (with `--exclude` for what the app never needs: examples, docs, build outputs, tests, `prebuilds/`); commit `vendor/<name>/`.
2. Add it to `vendoredPackages` in `src/vendored.ts` (an optional library, in `src/optional-libraries.ts`, with `optional: { kind, plugin?, requires? }` and, for an Expo module, no `android` or `ios`): version, the Android `ReactPackage` import and instance (a test reads the copy's sources to keep them true), the iOS podspec file name. Add the entry's reference fixture under `tests/cli/fixtures/vendored-autolinking/` (capture Expo's `react-native-config` for the installed package first).
3. If the library imports it, an `imports` entry (`#vendor/<name>`) and the import; if its declarations import another vendored package, a `declare module` in `src/vendor-types.d.ts`.
4. Take it from `peerDependencies`, `peerDependenciesMeta`, `svelte-native init`'s list, the doctor's `AUTOLINKED_PEERS`, and the `package.json` of `apps/*` and `examples/*`; `pnpm install`. Move its pnpm patch (`patches/<name>@<version>.patch`) into `vendor-patches/<name>/` so the copy carries it, and drop it from `patchSpecs` and from `init`'s `patchedDependencies`.
5. `pnpm --dir packages/svelte-native build`, and the checks in `AGENTS.md`.

## What the next batches must know

Measured on the installed packages (Expo SDK 57's `react-native-config` for each):

- **The entry has more fields than the pilot's two use, and the registry can say them** (`VendoredPackage.android`, tested against Expo's printed entries for the next packages in `tests/cli/fixtures/vendored-autolinking/expo-sdk57-android-next-batches.json`): `libraryName` is `codegenConfig.name`, else the `libraryName` of the `react { }` block of `android/build.gradle` (quick-crypto: `QuickCrypto`; Nitro has both and the codegen name wins); a view library lists its `componentDescriptors` (gesture handler: two, svg: 29); svg's codegen CMake file is `android/src/main/jni/CMakeLists.txt` (`cmakeListsPath`); hermes-intl is a pure C++ TurboModule (`cxxModule`: module name, CMake path, header name). Reanimated, worklets and gesture handler also have iOS `componentProvider`s in their codegen config, read from `package.json` by iOS codegen through `root`, which is why every copy keeps its `package.json`.
- **Crypto stack** (`react-native-quick-crypto` 1.1.3, `react-native-quick-base64` 2.2.2): quick-crypto's Gradle project depends on `:react-native-nitro-modules` and its CMake on the prefab, and its podspec on `NitroModules`; all three keep working against the copy because the entry keeps the name (the pod is the podspec's `s.name`). It has JavaScript `dependencies` of its own (`@craftzdog/react-native-buffer`, `events`, `readable-stream`, `safe-buffer`, `string_decoder`, `util`) that its copy must still resolve: library `dependencies` (the package manager installs them beside the library, in no app's package.json) or copies of their own (the Metro alias is by name, so a bare name works for either). Its Expo plugin (`app.plugin.js`: `sodiumEnabled`, written into the Gradle properties and the Podfile) has to move into this library's plugin, as an option. Vendoring it removes the Nitro runtime pnpm installs for it on its own. `deferredNitroPackages` already names it (`packageImportPath` is kept).
- **Gesture handler, Reanimated, worklets**: they carry pnpm patches (`patches/`), which become `vendor-patches/<name>/`; the doctor's `patchSpecs`/`shapes.ts` read the installed package and must read `vendor/` instead, and `init` stops declaring them in `patchedDependencies`. Two things need a decision first: `babel-preset-expo` adds `react-native-worklets/plugin` only when it can resolve the package from the app, so a vendored worklets needs the plugin added by the library's own transformer or Metro config; and Reanimated's Gradle task `validate-worklets-version.js` and its `compatibility.json` resolve worklets by name from node_modules, which a vendored pair does not have (patch the script's lookup in `vendor-patches/`).
- **react-native-svg, hermes-intl**: native and no alternative: vendor (svg: JavaScript entries through `#vendor/…`; hermes-intl: the polyfills import it by name, so the Metro alias covers it, and its `cxxModule` fields are in the registry now).
- **Optional view wrappers**: done, see "Optional libraries".
