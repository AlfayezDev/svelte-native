# Vendoring third-party native dependencies

`@alfayez/svelte-native` carries its third-party native dependencies itself: their published source is copied into `vendor/<name>/` of the package, and an app's `package.json` lists `@alfayez/svelte-native` and nothing beside it. The rule: **vendor everything if possible, unless it is presented as an alternative** (push notifications: Firebase, `expo-notifications`). The pilot is `react-native-nitro-modules` 0.35.10 and `react-native-mmkv` 4.3.1 (MMKV is what `localStorage` is made of, Nitro is its runtime and quick-crypto's); the UI batch is `react-native-gesture-handler` 2.32.0, `react-native-reanimated` 4.5.1, `react-native-worklets` 0.10.1 and `react-native-svg` 15.15.4 (below: they carry patches, a Babel plugin and codegen views); the rest follow this pattern (the list at the end).

## Where

- `vendor/<name>/` holds what the npm tarball publishes, unchanged: the JS the app needs (`src/`, `lib/`), `android/`, `ios/`, `cpp/`, Nitro's generated code, the podspec, `package.json` (the podspecs and the codegen read it) — plus `LICENSE` and `VENDOR.md` (upstream name and version, the tarball's integrity and sha256, what was left out, every local change, and the command that writes the directory again). `vendor` is in the package's `files`.
- `node scripts/vendor.ts <name>@<version> [--exclude <path>]... [--license-url <url>]` writes one: `npm pack`, unpack, check the tarball's integrity against npm's, replace `vendor/<name>/` as a whole. The output depends on nothing else (no date, no machine), so running it again with the same arguments gives the same bytes. A tarball without a `LICENSE` (npm omits one that is not in `files`: neither pilot package has one) gets the repository's, fetched at the tarball's own `gitHead`; its URL and sha256 are in `VENDOR.md`. `--exclude <path>` leaves out what the app never needs and the repository must not hold or run, and `VENDOR.md` lists it: the pilot leaves out the packages' own tests (`bun test` finds `*.test.*` files wherever they are, and MMKV's need `@testing-library/react-native`) and Nitro's `lib/tsconfig.build.tsbuildinfo` (the repository ignores `*.tsbuildinfo`). A path with `*` is a pattern over the package's files (`'lib/**/*.map'`: `*` stays in one directory, a directory part `**/` is any number of them; quote it, `VENDOR.md` does; a pattern that matches no file is refused). The UI batch leaves out the source maps of `lib/` (8 MB), gesture handler's and svg's `lib/commonjs` (Metro reads `src` through the `react-native` field, and nothing runs `main`), svg's `windows/` projects, the Gradle wrapper of svg and Reanimated (a jar and two scripts the app's Gradle never runs) and gesture handler's jest helpers.
- A local change is a patch file, `vendor-patches/<name>/*.patch` (`patch -p1`, applied in file name order by the script after the unpack, listed under "Local changes" of `VENDOR.md` by its place in the package and its sha256; one that does not apply stops the script and leaves the earlier copy as it was). Nothing in `vendor/` is edited by hand. `vendor-patches/` is not packed: the copies are what ships. The pilot has none; the UI batch has five (below).
- `.gitignore` re-includes `vendor/**/android/` and `ios/` (the repository ignores `ios/` and `android/` everywhere else); ESLint and Biome skip `vendor/`; `vendor/**/build` and the like are not packed.

## JavaScript

- The library's own code imports a copy as `#vendor/<name>`, an entry of the package's `imports` map: `types` is the copy's declaration entry, `default` its source (`src/index.ts`, what Metro bundled from `node_modules` before: the `react-native` field). Metro, Vite, Bun, esbuild and TypeScript all read it, in the repository and installed alike. The map has an entry for each vendored package whose JavaScript the library imports (`react-native-mmkv`) and for the types of the other (`react-native-nitro-modules`, below).
- `withSvelteNative` (Metro) resolves the bare names, and every path below them, to the copies **for every importer**: the app, a library that imports them (react-native-quick-crypto imports the Nitro runtime), the copies themselves. One copy of each, one module of each. A name an app stubs (`stubbedPackages`) is still stubbed first. A vendored package gets the `react-native` shim (`fabric/react-native-lite.ts`) exactly when its name is in `LITE_ORIGINS`, as the installed one did (`isLiteOrigin`).
- Types: `src/mmkv.ts` re-exports from `#vendor/react-native-mmkv`, so `dist/types` names it and an app's checker resolves it through the library's `imports` (`types` condition). The copy's declarations import `HybridObject` from `react-native-nitro-modules`, which the app does not install: `src/vendor-types.d.ts` declares that module as a re-export of `#vendor/react-native-nitro-modules`, and every declaration that names a vendored type carries a `/// <reference path>` to it (`publicAmbient` in `scripts/build-types.ts`). The UI batch has a file of its own, `src/vendor-types-ui.d.ts` (the same for `react-native-worklets`, `react-native-reanimated`, `react-native-svg` and `react-native-gesture-handler`, which Reanimated's and gesture handler's declarations import by name, and a library of the app may): loading it loads the declarations of all four (hundreds of files), so only `animation.ts` and `svg.ts` reference it and the primitives alone (`/core`) do not (`tests/package/type-budget.test.ts` keeps it so). Gesture handler's declarations are imported by deep path, `#vendor/react-native-gesture-handler/types/<path>` (an `imports` pattern with the `types` condition only: nothing runs it).
- Web: the web target of `svelteNative()` already puts `.web.*` extensions first, so `#vendor/react-native-mmkv` builds with MMKV's web implementation and with no React Native and no Nitro (`tests/web-apis/web-mmkv.test.ts`).

## Native linking

React Native's autolinking links only the app's own dependencies, so the library adds its copies to the autolinking config **itself**, from `vendor/`, with the fields autolinking would print for the installed package (`src/vendored.ts`: the list, `vendoredDependency`, `linkVendored`).

- **Android**: `settings.gradle` already runs the config command through `svelte-native android-autolinking <command...>`; that command now adds the entries (and the deferred-Nitro relinking, `deferredNitroPackages` and `NitroGate`, is applied after: the entries carry the same `packageImportPath` and `packageInstance` the installed packages had, which is what it matches).
- **iOS**: `svelte-native ios-autolinking <command...>` does the same for the Podfile: `applyPodfileVendoredLinking` (`expo.ts`) puts one block before `config = use_native_modules!(config_command)` that finds the CLI from the app (`require.resolve('@alfayez/svelte-native/package.json')`, as the template finds `expo`) and wraps `config_command`. Stripped and written again on every prebuild, like the excludes; it works under `EXPO_USE_COMMUNITY_AUTOLINKING=1` too.
- The entries are the reference captured from Expo's own `react-native-config` for the installed packages, with the directory of the copy (`tests/cli/fixtures/vendored-autolinking/`): `root` and `sourceDir`/`podspecPath`/`cmakeListsPath` in `vendor/<name>/`, `name` unchanged (**the Gradle project is `:<name>` and the pod is the podspec's own name**, so quick-crypto's `project(':react-native-nitro-modules')` and `s.dependency 'NitroModules'` find the copy).
- Nothing in either package computes a path from `node_modules`: Nitro's CMake and Gradle use prefab and project dependencies, the generated code is below the package, the podspecs use `__dir__`. iOS codegen finds the Nitro spec through the config's `root` (`ios/build/generated/autolinking/autolinking.json`, written from the command's output), which is why `package.json` with its `codegenConfig` stays in the copy.
- The UI batch the same way, with its own fields (`fixtures/vendored-autolinking/expo-sdk57-*.json` hold what Expo's `react-native-config` printed for each in `apps/example`; `componentDescriptors` and svg's `cmakeListsPath` are read from the copy's own `react-native.config.js` by a test): gesture handler's two component descriptors, svg's 29 and its CMake file in the sources, `libraryName` from each `codegenConfig` (`rngesturehandler_codegen`, `rnreanimated`, `rnworklets`, `rnsvg`). The Gradle projects keep their names, which is what the packages look each other up by: Reanimated's `build.gradle.kts` needs `:react-native-worklets` and orders its native build after it, gesture handler's `build.gradle` adds its `reanimated/` and `svg/` source sets when `rootProject.subprojects` has `react-native-reanimated` or `react-native-svg` (and depends on them), svelte-core's `compileOnly project(':react-native-gesture-handler')`. The pods keep theirs: `RNGestureHandler`, `RNWorklets`, `RNReanimated` (which depends on `RNWorklets`) and `RNSVG`. Reanimated's Gradle task and its podspec's script run `scripts/validate-worklets-build.js`, which asked Node for `react-native-worklets/package.json` by name: a patch makes it read the copy beside it (`vendor-patches/react-native-reanimated/0002-...`).

## Collisions

An original must not be linked beside a copy.

- The config plugin stops the prebuild, `svelte-native doctor` fails, and the autolinking commands refuse (exit 1, nothing on stdout) when **the app's `package.json`** lists a vendored name (`dependencies`, `devDependencies`, `optionalDependencies`): "`@alfayez/svelte-native` includes react-native-mmkv 4.3.1; remove it from the app's dependencies (package.json), reinstall, and prebuild again." One list, `vendoredPackages` in `src/vendored.ts`, and one message (`collisionMessage`); a package added to the list is covered everywhere.
- An original that autolinking finds **without** the app listing it is replaced, not refused: pnpm installs react-native-quick-crypto's peer `react-native-nitro-modules` on its own (`auto-install-peers`), Expo's autolinking finds it in `node_modules`, and refusing would refuse every app that uses quick-crypto. The entry is replaced by the copy's under the same name, so it is linked once; the unused original in `node_modules` is inert (Metro never reaches it). It goes away when quick-crypto is vendored (the next batch).

The UI packages are where this matters most, because other libraries depend on them. What an app that has such a library gets, by layer:

| What happens | Behaviour |
|---|---|
| The app lists `react-native-reanimated`, `-gesture-handler`, `-worklets` or `-svg` | Refused by the prebuild, `svelte-native doctor` and the autolinking commands, with the one message: the library includes it at that version; remove it from the app's dependencies (package.json), reinstall, prebuild again; a library of the app that asks for it as a peer is served by the copy (`collisionMessage`). `svelte-native init` prints the same for a project that lists one, and does not remove it. |
| A library of the app peer-depends on one (`@react-navigation/*`, `@gorhom/bottom-sheet`, Expo Router: gesture handler, Reanimated, Worklets) | **JavaScript**: Metro resolves the name, and every path below it, to the copy for every importer, so the library gets the copy's module, the same one the library itself uses (one `SharedValue` class, one set of worklet runtimes). **Types**: the library's declarations import the name; `vendor-types-ui.d.ts` answers to it (loaded with the main entry). **Native**: its autolinking entry (if the package manager installed an original, `auto-install-peers`) is replaced by the copy's under the same name, so the Gradle project `:react-native-reanimated`, the pod `RNReanimated` and the rest are the ones the library asked for. **Babel**: the Worklets plugin is the copy's whatever `node_modules` has. The package manager may warn about a peer that is not the app's (`pnpm peers check`); that is expected, and the copy is what runs, at its version (4.5.1 satisfies `react-native-reanimated >=3`, and not `^3`: such a library works as far as 4.x is compatible with it). |
| A package manager installs an original beside another library (pnpm does, for Expo Router's peers: this repository has gesture handler, Reanimated and Worklets in `node_modules` and `apps/example` lists none) | Inert: Metro never reaches it, autolinking replaces it, and `babel-preset-expo`'s own lookup of `react-native-worklets/plugin` finds the copy's plugin, not the original's (`tests/compiler/worklets-plugin.test.ts` has an original whose plugin throws if it loads). The example and QA bundle tests check that no original is bundled. |

## Tests

`tests/package/vendor-script.test.ts` (the script's layout against a fixture tarball, no network, with patterns and patches; the copies against their `VENDOR.md`, patches included), `tests/cli/vendored-autolinking.test.ts` (the entries against the reference, replacement, refusal, both commands, the plugin), `tests/cli/expo-headless.test.ts` (the Podfile block), `tests/compiler/metro/vendored.test.ts` (the aliases and the shim), `tests/package/vendored-types.test.ts` (an app with neither package type-checks `@alfayez/svelte-native/mmkv`), `tests/cli/doctor.test.ts`, `tests/package/packaging.test.ts` (the packed package holds the copies with their `LICENSE` and `VENDOR.md`, none is a peer, and the packages' own JavaScript dependencies are the library's), `tests/compiler/worklets-plugin.test.ts` (the real transformer, in Node: the plugin is the copy's, once, with or without an original in the app), `tests/upstream/*` (what the patches leave in the copies; the doctor's check of them is `tests/cli/doctor.test.ts`).

## The UI packages: gesture handler, Reanimated, Worklets, svg

Versions 2.32.0, 4.5.1, 0.10.1 and 15.15.4, as the peers were. Three have patches, which are `vendor-patches/<name>/*.patch` now, applied by `scripts/vendor.ts` (the three that pnpm used to apply are byte for byte what they were; `pnpm-workspace.yaml` and an app's `patchedDependencies` no longer name them, and `svelte-native doctor` reads the copies instead, `vendoredPatchSpecs`: the same shapes as before, in `vendor/`, one line each under "vendored packages"):

- gesture handler `0001`: iOS, the manager can be asked for the root gesture recognizer of a screen the library presents.
- Reanimated `0001`: Android, the engine's views are written natively and opacity/translate/scale skip React Native's prop path. `0002` (new): `scripts/validate-worklets-version.js`, which Reanimated's Gradle task and its podspec run, reads `package.json` of the Worklets copy beside it; by name, from `node_modules`, it found nothing. `0003` (new): `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` is on in `src/featureFlags/staticFlags.json` (Gradle and the podspec read that file, then the app's `package.json` `reanimated.staticFeatureFlags` over it), because the patched Android update is reached only through that flag: **an app sets nothing**, `svelte-native init` no longer writes `reanimated` into its package.json, and an app's own value still wins (`ENABLE_SHARED_ELEMENT_TRANSITIONS: true` needs `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS: false` beside it, which Reanimated enforces). The Worklets flags (`worklets.staticFeatureFlags`) were never set and are not.
- Worklets `0001`: the UI runtime asks for a frame only while a callback waits.

**The Worklets Babel plugin.** `babel-preset-expo` adds `react-native-worklets/plugin` when `require.resolve` finds the package from the app's directory; no app has it, and one that does (pnpm installs an original for Expo Router's peers) has another version than the native code. The transformer makes that name resolve to `vendor/react-native-worklets/plugin/index.js` (`Module._resolveFilename`, installed when the transformer loads: `require.resolve` ends there on every Node the library supports, which a `module.registerHooks` resolve hook is not documented to reach), so the preset adds the copy's plugin, once, in the place it always puts it (an explicit `plugins` entry of the transformer would run before the preset's own plugins, and twice beside an original). The plugin's file is in the transformer's cache key. The wrapper is not installed under Bun (the repository's own tests run the transformer there, and a `require` of a relative file fails after it): a run there finds whatever `node_modules` has, the same version in this repository, and `tests/compiler/worklets-plugin.test.ts` runs the transformer in Node. A file of a vendored package is handled as a `node_modules` file by the transformer (TypeScript is left to Babel, as for an installed package), in the workspace and installed alike.

**Dependencies.** The JavaScript the copies import is found from where the library is, so the packages' own `dependencies` are the library's (same ranges): `@babel/plugin-transform-*` and `@babel/preset-typescript` (the Worklets plugin), `convert-source-map`, `semver` (Reanimated's and Worklets' build scripts), `react-native-is-edge-to-edge`, `hoist-non-react-statics`, `invariant`, `@egjs/hammerjs`, and svg's `css-select`, `css-tree` and `warn-once`. The Worklets plugin also requires `@babel/generator` and `@babel/traverse`, which its manifest does not list (`dependencies` of the library), and Metro's own `@babel/core` (an optional peer: the app has it). `tests/package/packaging.test.ts` reads each copy's manifest to keep this list complete.

**What is imported how.** The library's own source imports the main entries and types as `#vendor/<name>` (the `imports` map), and keeps the deep paths its JavaScript reaches (`react-native-reanimated/src/updateProps`, `react-native-svg/src/lib/extract/extractProps`, `react-native-gesture-handler/src/handlers/...`) by name: an `imports` target is an exact file, and Metro's alias resolves the names with file extensions. The tests' bundles do the same through esbuild's `alias` (`tests/support/paths.ts`: `vendorAliases`), and stub by name (`#vendor/<name>` is the same stub).

**Left out of the copies**, see each `VENDOR.md`: source maps, `lib/commonjs` (gesture handler, svg), `windows/` (svg), the Gradle wrapper (svg, Reanimated), gesture handler's `jest-utils` and `jestSetup.js`.

## Notes for the QA harness

The smoke app installs the production app's libraries as stand-ins (`apps/qa/qa/smoke-modules.json`, `package.json`). MMKV and Nitro are not on that list any more: their modules (`mmkv`, `nitro`) stay, still `shared`, with no `packages`; the smoke checks `require("react-native-mmkv")` and `require("react-native-nitro-modules")`, which Metro resolves to the copies. `libraryVendoredPackages` in `smoke-packages.cjs` names them (and the UI packages, which the smoke app never installed).

## Adding a package

1. `node scripts/vendor.ts <name>@<version>` (with `--exclude` for what the app never needs: examples, docs, build outputs); commit `vendor/<name>/`.
2. Add it to `vendoredPackages` in `src/vendored.ts`: version, the Android `ReactPackage` import and instance (a test reads the copy's sources to keep them true), the iOS podspec file name. Add the entry's reference fixture under `tests/cli/fixtures/vendored-autolinking/` (capture Expo's `react-native-config` for the installed package first).
3. If the library imports it, an `imports` entry (`#vendor/<name>`) and the import; if its declarations import another vendored package, a `declare module` in `src/vendor-types.d.ts`.
4. Take it from `peerDependencies`, `peerDependenciesMeta`, `svelte-native init`'s list, the doctor's `AUTOLINKED_PEERS`, and the `package.json` of `apps/*` and `examples/*`; `pnpm install`. Move its pnpm patch (`patches/<name>@<version>.patch`) into `vendor-patches/<name>/` so the copy carries it, drop it from `patchSpecs` (its shape check is a `vendoredPatchSpecs` entry in `src/doctor/patches.ts`, which the doctor runs on the copy) and from `init`'s `patchedDependencies` and `pnpm-workspace.yaml`; its JavaScript `dependencies` become the library's.
5. `pnpm --dir packages/svelte-native build`, and the checks in `AGENTS.md`.

## What the next batches must know

Measured on the installed packages (Expo SDK 57's `react-native-config` for each):

- **The entry has more fields than the pilot's two use, and the registry can say them** (`VendoredPackage.android`, tested against Expo's printed entries for the next packages in `tests/cli/fixtures/vendored-autolinking/expo-sdk57-android-next-batches.json`): `libraryName` is `codegenConfig.name`, else the `libraryName` of the `react { }` block of `android/build.gradle` (quick-crypto: `QuickCrypto`; Nitro has both and the codegen name wins); a view library lists its `componentDescriptors` (gesture handler: two, svg: 29); svg's codegen CMake file is `android/src/main/jni/CMakeLists.txt` (`cmakeListsPath`); hermes-intl is a pure C++ TurboModule (`cxxModule`: module name, CMake path, header name). Reanimated, worklets and gesture handler also have iOS `componentProvider`s in their codegen config, read from `package.json` by iOS codegen through `root`, which is why every copy keeps its `package.json`.
- **Crypto stack** (`react-native-quick-crypto` 1.1.3, `react-native-quick-base64` 2.2.2): quick-crypto's Gradle project depends on `:react-native-nitro-modules` and its CMake on the prefab, and its podspec on `NitroModules`; all three keep working against the copy because the entry keeps the name (the pod is the podspec's `s.name`). It has JavaScript `dependencies` of its own (`@craftzdog/react-native-buffer`, `events`, `readable-stream`, `safe-buffer`, `string_decoder`, `util`) that its copy must still resolve: library `dependencies` (the package manager installs them beside the library, in no app's package.json) or copies of their own (the Metro alias is by name, so a bare name works for either). Its Expo plugin (`app.plugin.js`: `sodiumEnabled`, written into the Gradle properties and the Podfile) has to move into this library's plugin, as an option. Vendoring it removes the Nitro runtime pnpm installs for it on its own. `deferredNitroPackages` already names it (`packageImportPath` is kept).
- **hermes-intl**: native and no alternative: vendor (the polyfills import it by name, so the Metro alias covers it, and its `cxxModule` fields are in the registry now). The UI packages (gesture handler, Reanimated, Worklets, svg) are done, below.
- **Optional view wrappers** (lottie, maps, video, pdf, ...): link **only when the app enables them**. The mechanism extends directly: a registry entry gets a condition (an option or capability of the plugin), the plugin writes the enabled names into the blocks it already generates (`settings.gradle`: a `--link <name>` argument of `android-autolinking`; the Podfile block: the same for `ios-autolinking`), and `linkVendored` links only the packages that are on, the pilot's two being always on. `autolinkingExclude` already names packages an app leaves out; the same list can turn a vendored one off (the Expo plugin's auto-plugin history already skips an excluded package). Metro's alias costs nothing for an unused name; the bundle of an app that turned one off should stub it the way `stubbedPackages` does.
